# Constellation: переносимый пилот, обслуживание и откат

Этот runbook предназначен для участника разработки, который проверяет переход на
Constellation на отдельной копии, а не выполняет rollout настоящих проектов.
Пользовательские сценарии описаны в [гайде](https://forgeplan.dev/ru/docs/guides/constellation/),
контракты CLI/MCP — в [справочнике](https://forgeplan.dev/ru/docs/reference/constellation/).

## 1. Допуск по версии и сохранение исходного состояния

Документ относится к неопубликованной рабочей версии `0.39.0+constellation.s1.1`,
не к опубликованной `0.38.0`. `c852f40c` — прежняя база исследования и аудита,
а не точный source pin более позднего рабочего дерева с исправлениями совместимости.
Допуск выбранного бинарника требует его собственного source pin и SHA-256:
одна строка версии не переносит результаты между сборками.
Ограниченные CLI/MCP-наблюдения относятся к macOS/arm64; это не полная приёмка
RFC-015/S1-G, не S2–S4. Windows/NTFS, аварийные сценарии и все команды миграции
здесь не объявляются проверенными.

1. Выберите отдельно установленный бинарник этой сборки с `semantic-search`.
   Сохраните абсолютный путь, вывод `--version`, source revision и SHA-256.
   Одного номера версии недостаточно, чтобы различить локальные сборки.
   Не подменяйте рабочий бинарник в `PATH` до завершения пилота.
2. Зафиксируйте путь и версию прежнего рабочего бинарника. Остановите его MCP,
   watch, git-sync и прочие процессы записи перед копированием данных.
3. Сделайте полную резервную копию `.forgeplan/` **вне workspace**, включая
   Markdown, конфигурацию, индекс, поколения и локальные служебные данные.
   Отдельно сохраните MCP config клиента и пользовательский реестр
   `~/.forgeplan/constellations.yaml`, если собираетесь менять его.
   Экспорт старым бинарником полезен дополнительно, но не заменяет полную копию.
4. Ограничьте доступ к backup: config может содержать ключи, журналы — частный
   текст. Не коммитьте эти данные. Сохраните контрольные суммы и убедитесь,
   что архив читается, прежде чем разрешать миграцию.

Markdown в `.forgeplan/<kind>/` — canonical source of truth, LanceDB —
производный индекс. Legacy и Constellation layout не взаимозаменяемы.
Не восстанавливайте индекс удалением всего `.forgeplan/`.

## 2. Изолированный sandbox и один writer

Для нового учебного workspace выберите пустой каталог **вне** любого существующего
workspace. Обнаружение `.forgeplan/` идёт вверх по родительским каталогам; ответ
`Already initialized at ...` может относиться к родителю. Экспортируйте пустой
`FORGEPLAN_WORKSPACE`, чтобы `.env` не восстановил чужую привязку, и проверьте путь до `new` или `update`.

Пример для POSIX shell, где `FPL` — выбранный абсолютный путь бинарника:

```bash
set -eu
export FORGEPLAN_WORKSPACE=""
SANDBOX=$(mktemp -d "${TMPDIR:-/tmp}/forgeplan-pilot.XXXXXX")
cd "$SANDBOX"
git init --quiet
"$FPL" --version
"$FPL" init -y
if [ ! -f .forgeplan/config.yaml ]; then
  printf '%s\n' 'Refusing artifact writes: no local workspace. Choose TMPDIR outside existing workspaces.' >&2
  exit 1
fi
```

Не продолжайте, если показан не sandbox. Для испытания существующего проекта
работайте с отдельной копией и её backup. Не переносите опубликованный индекс
простым изменением пути: его идентичность связана с workspace. Не запускайте
старый и новый писатели на одном индексе. На время явного `index`/`embed` остановите
фоновый writer; затем оставьте один выбранный maintenance-процесс.

Если клон уже содержит tracked `.forgeplan/`, `init -y` может завершиться раньше,
не создав config. Если config есть, используйте `reindex`. Если его нет, после
полного backup допустим осознанный `init --force -y`: тела артефактов сохраняются,
но активный config заменяется defaults. Custom edits, включая `embedding`,
остаются **только в backup** до ручного переноса. Это не обычный recovery индекса.

## 3. Модель и явная публикация семантики

Для офлайн-инференса нужен полный совместимый BGE-M3 snapshot, а не только
`tokenizer.json`: в нём должны быть пригодные `onnx/model.onnx`,
`onnx/model.onnx_data`, `tokenizer.json`, `tokenizer_config.json`, `config.json`
и `special_tokens_map.json`. Наличие имени файла само по себе не доказывает,
что production loader сможет загрузить snapshot.

Приоритет кэша: `FORGEPLAN_MODEL_CACHE` → `~/.forgeplan/models` → platform/legacy
fallback при отсутствии home. Переменная указывает на **корень кэша**, не на
каталог одного snapshot. `HF_HOME` не переопределяет tract cache. Не удаляйте
старый кэш автоматически.

Для подготовки только модели с разрешённой сетью используйте `forgeplan setup --skip-alias --skip-hooks`, без установки псевдонима и hooks.
Только при создании нового workspace можно явно запросить скачивание через
`forgeplan init -y --with-model`; `init-model` не существует, `--model` у init нет.
Для уже инициализированного workspace init может завершиться до скачивания.
Перед офлайн-проверкой задайте выбранный корень кэша и `HF_HUB_OFFLINE=1`.
Если snapshot отсутствует, семантическая часть пилота BLOCKED, а не «пропущена».

Создайте учебный документ через `new note`, сохраните возвращённые ID и путь,
заполните тело через `update <ID> --body @file`. Включите преамбулу, одинаковые
заголовки, длинную секцию, Unicode, хвостовые пробелы и уникальный маркер в конце.
Далее из корня sandbox:

```bash
"$FPL" index --deadline-secs 300
"$FPL" index --list
"$FPL" embed
"$FPL" list
```

Если нужен автоматический режим, сначала включите `embedding` из раздела 4,
затем выполните этот `index`. После изменения конфигурации не начинайте
`embed` от прежней публикации: `CURRENT` связан с прежним `config_digest`,
и admission откажет с `profile_incompatible`. Публикацию новой конфигурации
делает штатный `index`, а не загрузка модели.

`embed` не имеет `--json` или `--model`. Обычный `index` не дренирует очередь
без `--embed-profile`; раздельные `index`, затем `embed` делают шаги явными.
Раскладка `s1-token-layout-v2` сохраняет body-absolute UTF-8 диапазоны;
длинная секция имеет несколько токеновых окон, а не одну строку на заголовок.
Переход со старой раскладки требует новой индексации и embedding.

## 4. MCP и автоматическое обслуживание

Сначала сохраните прежний MCP config, затем подключите выбранный бинарник явно.
Путь в конфигурации должен быть абсолютным. Пример запуска full-профиля:

```bash
FORGEPLAN_WORKSPACE="$SANDBOX" "$FPL" serve --profile full --auto-index --workspace "$SANDBOX"
```

Это stdio MCP server: клиент выполняет `initialize` и последующие tool calls;
команда не является shell-проверкой успешного чтения. Перезапустите старую сессию
клиента, чтобы она действительно использовала новый процесс.

`--workspace` задаёт серверный default. На старте full-сервера цель обслуживания:
`FORGEPLAN_WORKSPACE` → server default → cwd. Поэтому пример явно связывает
переменную с sandbox; для внешнего MCP-клиента задайте её в его `env`, а не
полагайтесь на окружение другой shell. Для отключения привязки задайте пустую
строку явно: одного `unset` недостаточно из-за загрузки `.env` CLI. Отдельный запрос выбирает workspace
по цепочке request `workspace` → `FORGEPLAN_WORKSPACE` → server default → cwd.
Запрос не перемещает фоновый хост; источники реестра не получают писателя автоматически.

Для автоматического embedding нужны **все** условия:

- сборка с `semantic-search`;
- активная конфигурация обслуживаемого workspace:

  ```yaml
  embedding:
    model: bge-m3
    chunk_size: 2000
  ```

- полный совместимый snapshot в кэше, доступный процессу сервера;
- работающий maintenance host, например full server с `--auto-index`.

Без `config.embedding` фон пропускает очередь. Наличие кэша и разовый ручной
`embed` не сохраняют эту настройку. `init --force` сбрасывает её вместе с остальным
активным config. Read-профиль `constellation-read` writer не запускает.

Сам config не запускает службу. Для следующих `CLI update` держите выбранный
full-сервер подключённым. Если правка сделана до запуска сервера, его начальный
полный проход должен подхватить строки без векторов даже при пустой очереди.
На полностью готовом индексе модельный worker не создаётся; разрешение профиля
всё ещё читает контрольные суммы файлов кэша.

`full` — профиль по умолчанию с записью, 76 зарегистрированных tools.
`constellation-read` — отдельный необязательный профиль с 9 handle-based read tools;
он не заменяет авторинг, не пишет данные и не дренирует очередь.

### Границы проверки совместимости

Дополнение документации от **2026-10-24** заменяет прежнюю оговорку об отказе CLI
`validate` на migrated layout. В ограниченном прогоне совместимости на source pin
`76a9b3f65a1e72fef0d1e745a983b1b5c711d3aaefcc51f6b833d0acd43613b5`
прошли 25 прежних наборов аргументов CLI — 25/25 на legacy и 25/25 на managed
Constellation layout. CLI `validate` работает на обоих layout; full MCP
`forgeplan_validate` также успешно проверен. Имена команд, tools, параметры и
существующие имена skills не меняются.

Это не проверка поведения всех 73 прежних full handlers: их схемы и annotations
сохранены, ещё 3 tools добавлены, всего 76 регистраций. Эти наблюдения нельзя
приписывать ни старой базе `c852f40c`, ни каждому последующему рабочему снимку.
[Ранняя запись прогресса в #538](https://github.com/ForgePlan/forgeplan/issues/538#issuecomment-6383528766)
содержит свои ограничения и не является финальной приёмкой. Проверка нового
бинарника должна иметь отдельный результат; общий acceptance
[#538](https://github.com/ForgePlan/forgeplan/issues/538) остаётся открытым.
Default-build проверки не доказывают semantic search или автоэмбеддинг.
Эта правка документации не выдаёт release/admission PASS, не активирует артефакты
и не закрывает G1/G2/G3 или #542.

#### Ограничение очереди и сохранение закреплённых версий: R9

Снимок
`04b901d433517f6dfad0b8f86233bb0735e826021e4e0f97e8958e0521daa7e8`
устраняет два дефекта, обнаруженные при подготовке большого реального корпуса.
Предел 64 теперь действует до подготовки текста и записи `pending`, а не
только на вектор входов, возвращаемый вычислителю.

У managed writer-таблиц удаляется настройка `lance.auto_cleanup.interval`:
возрастная очистка Lance не знает, какие версии закрепляют наши поколения.
Значение `0` не отключает очистку — оно разрешает её на каждом commit.
Сам restore пропускает очистку, после него политика применяется заново.
Каждый дополнительный commit берёт отдельный `WorkspaceLock` для явно
переданного канонического workspace. Read-only открытия политику не меняют;
замок не удерживается при загрузке модели и вычислении векторов.

Версии не удаляются автоматически; это сохраняет pins, но история занимает
место. Не применяйте возрастную очистку к этим таблицам без учёта закреплённых
поколений. Canonical Markdown и модель этой правкой не меняются.

На самом R9 прошли четыре адресных теста: сохранение исходного pin и его данных
после restore и следующей записи, recovery без изменения источника, восстановление
оборванной admission и обработка нескольких порций без tokenizer cache.
Предыдущие 71 тест относятся к промежуточному R8 и не прибавляются к R9.
Независимое Sol-ревью R9 не нашло оставшихся существенных замечаний; это не
формальный release PASS. Свежие semantic-бинарники без `test-helpers` находятся
в `.local/constellation-verification/compatibility-20261025/quality-r9-retention-sole/production-semantic/`.

Первоначальная подготовка завершена на том же R9 стандартным `release`:
449 документов и 6048 разделов, публичный semantic consumer подтвердил
6497/6497 пригодных строк. Бинарники этого прогона находятся в соседнем
`quality-r9-retention-sole/release-semantic/`, не в dev-сборке выше.

После каждой правки публичный CLI semantic consumer подтвердил 6498/6498
пригодных строк и pending=0, правильный source digest и неизменный профиль.
Разница с первоначальными 6497 — дополнительный раздел контрольной заметки.
Отдельно сохранена проверка восстановления старой CLI-записи R9 новым
сервером R11; она не выдаётся за запись той же сборкой.

У MCP сохранён прежний ответ `coverage/results/total` и поля
`id_canonical`/`id_display`/`semantic_score`; CLI-поля `persisted` и
`eligible_rows` нельзя требовать от этого ответа. Готовность опубликованных
привязок MCP-пробы дополнительно подтверждена строгим CLI semantic reader.
Поле `semantic_state` в manifest source entries само по себе не использовалось
как доказательство готовности векторов.

Результаты и SHA-256 36 исходных receipts записаны в
[EVID-204](../../.forgeplan/evidence/EVID-204-r11-automatic-bge-m3-cli-and-mcp-pilot-verification-ba7e7b0a.md).
Набор бинарников:
`.local/constellation-verification/compatibility-20261025/quality-r11-auto-backlog-sole/release-semantic/`.
Изменялась только собственная NOTE-057 в копии; оригинальные проекты,
конфиги и глобальный PATH не переключались. После проверок MCP-процессы
закрыты, поэтому для новых правок клиент должен снова запустить full host.

Финальная диагностика данных от 2026-10-28: `health=needs_attention`,

Прежний `healthy` относится только к измерению R6. Coverage, provider,
G1/G2/G3, #542 и подключение конфликтующих источников остаются отдельными
ограничениями; EVID-204 и RFC-018 остаются draft.




MCP-клиент должен запускать выбранный новый бинарник, а не уже работающий
сервер прежней версии. Ошибка `Table 'artifacts' was not found` при открытии
мигрированного workspace не требует создавать старую таблицу или стирать данные:
проверьте путь запуска и перезапустите MCP-подключение с проверенным бинарником.
Разрешение менять конфигурацию настоящих проектов этим примером не выдаётся.

При сравнении импорта/восстановления отличайте исходные данные от производного
кэша. Дата без времени в исходнике остаётся датой: не добавляйте вымышленное
время суток. Пересозданные legacy cache timestamps и R_eff могут отличаться;
такое различие воспроизводится и в контрольной `0.38.0`, а не требует возврата
устаревшего кэшированного score. В старом CLI `0.38.0` restore после
deprecate/supersede уже не имел receipts — не создавайте их задним числом.
MCP restore в `0.38.0` сбрасывал status, но сохранял историю deprecation;
её наличие не означает неудачное восстановление.

## 5. Проверки и критерии остановки

Это перечень действий оператора, не transcript выполненных команд и не новый
отчёт о тестах. Сохраняйте команды, версии, исходные байты, ответы и ошибки.

| Проверка | Что сравнить |
|---|---|
| `get <ID> --json` | CLI `body` равен всему исходному Markdown, включая frontmatter; не сравнивайте его с prose body pinned row |
| `search <маркер> --keyword --json` | Вернулся нужный документ и правильный источник |
| `search "<смысл хвостовой секции>" --semantic --json` | `semantic_available`, `eligible_rows`, `expected_rows`, `semantic_scope`, релевантность результата; полное покрытие не доказывает качество ranking |
| Остановка writer, правка sandbox-источника, свежее чтение | Новая редакция доступна как `persisted: false`; чтение не публикует новое поколение |
| `reindex`, затем `embed`, свежий процесс MCP | Новая редакция опубликована; обычное get/search и pinned get согласованы с их разными body-контрактами |
| Правка при работающем настроенном maintenance | Очередь дренируется без ручного embed; сохраните failed/stale и semantic coverage, не только exit code |
| Повреждённый или недоступный canonical source, затем `index`, `reindex` или `migrate` | Явный отказ, без сообщения об успехе и без замены `CURRENT.json` неполным поколением; прежние опубликованные строки остаются доступны pinned reader |

Принудительный semantic search без опубликованного профиля или eligible vectors
может вернуть ошибку. Это не доказательство отсутствия совпадений и не обещанный
keyword fallback. До embedding состояния `pending`/`unavailable` не означают
потерю Markdown; `failed` требует разбора ошибки, а не сокрытия результата.

Неполный захват источников — не успешная миграция схемы. Сначала восстановите
доступность или корректность исходника, сохранив его повреждённую копию для
разбора. Не обходите отказ удалением workspace или переключением на legacy.

Для исправления этой границы на source pin
`1a5fbbffe8cb3e43d0879f59508938b3e4bd476f16e9785aac6a0af177b5eac0`
прошли прямая core-регрессия и 9 CLI maintenance cases, включая неизменность
`CURRENT.json` после отказа. Это результаты тестовой сборки, не новой
production-сборки: её выпуск и semantic/auto-embed прогон остановлены из-за
недостатка места на диске. Статус и условия продолжения — в
[#538](https://github.com/ForgePlan/forgeplan/issues/538#issuecomment-6389212590).
Эта остановка относится только к названной исторической сборке; завершённая
проверка R11 с реальной моделью приведена в разделе 4 выше.

Full MCP `forgeplan_constellation_get` принимает `key`, возвращает вложенный
`artifact` с prose `body` и `source_digest`. Read-profile `constellation_get`
принимает `id` и scope/snapshot handle. При `snapshot_expired` откройте новый
scope, не выдавайте обновлённые данные за прежний snapshot.

Для federation регистрируйте `.forgeplan/`, не весь исходный код. Дублирующиеся
ID разрешайте квалификатором; проверяйте `partial`, `failures`, `truncated` и
источник. Не скрывайте required-source сбои постоянным `--allow-partial`.
Квалификаторы graph/impact поддержаны в реализации, но полная runtime-приёмка
этих ветвей здесь не заявляется. ContextPack оценивает units через chars/4:
это не строгий token cap модели или полного JSON.

Остановите пилот при потере байтов, неправильном источнике, скрытом отказе,
необъяснённом неполном покрытии или named refusal нужной операции. Для оценки
качества заранее выберите реальные задачи и ожидаемые документы; не заменяйте
их удобными синтетическими запросами.

## 6. Recovery индекса и откат

При обычном отставании производного индекса сохраните canonical Markdown и
конфигурацию, остановите конкурирующих writers и запустите подходящий бинарник
из правильного workspace: `forgeplan reindex` (на migrated layout передаёт работу
Constellation) либо явный `forgeplan index`, затем `forgeplan embed`, если нужна
семантика. Проверяйте ожидаемые документы и диагностику, не только exit code.
Не применяйте `rm -rf .forgeplan` и не используйте `init --force` как index reset.

Не рассчитывайте на первую миграцию legacy через `git-sync`
([#540](https://github.com/ForgePlan/forgeplan/issues/540)). При legacy `reindex`
учитывайте ошибки неконвенциональных имён файлов
([#495](https://github.com/ForgePlan/forgeplan/issues/495)).

Для отката:

1. Остановите новый writer и клиентов. Сохраните **текущее** `.forgeplan/`, MCP
   config и журналы отдельно: новые canonical изменения нельзя потерять при
   возврате к старому backup.
2. Сравните новые Markdown/config с исходной копией и сохраните дельту. Не
   распаковывайте старый архив вслепую поверх новых данных.
3. Верните согласованный набор: прежний полный workspace с подходящим индексом,
   прежний бинарник и MCP config. Одной замены бинарника недостаточно.
4. Если нужно сохранить новые canonical изменения, перенесите их штатным
   процессом выбранной версии и пересоберите **совместимый с ней** индекс.
   Проверьте list/get/search до возобновления записи.

Отключение дополнительного read-сервера не откатывает миграцию full writer.
Сохраните оба состояния до завершения разбора. Этот runbook не выполняет rollout
и не подтверждает миграцию каких-либо настоящих проектов.
