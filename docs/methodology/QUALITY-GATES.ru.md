# Quality Gates — Verification Gate + Adversarial Review

Руководство по проверкам качества решений в Forgeplan. Объединяет Verification Gate (Quint-code), Adversarial Review (BMAD), 13-Step PRD Validation (BMAD) и R_eff Quality Scoring (Quint-code/FPF).

## 0. Машинные проверки — не независимые ревьюеры

Здесь различаются **CLI/MCP 0.38.0**, **опубликованный маркетплейс** (`forgeplan-workflow` 1.23.1 / `fpl-skills` 1.75.1) и ограниченная политика core-ревью этого репозитория в §2. Последняя не меняет установленные/публичные копии молча. Источники закреплены ниже; черновики разработки — не поведение релиза.

| Проверка | Что действительно устанавливает | Кто действует дальше |
|----------|---------------------------------|----------------------|
| `forgeplan validate <ID> --json` | Правила типа/глубины, MUST-ошибки и SHOULD/COULD-находки | Автор исправляет структуру/содержимое |
| `forgeplan review <ID>` | Валидация и проверки активации PRD/Epic/Spec/RFC/ADR: ≥100 байт тела после trim, нет обнаруженной заглушки, есть связь с доказательствами | Оркестратор проверяет остальные инженерные требования/ревью |
| `/gate-check <ID>` | Пороги опубликованного скилла перед реализацией; не чтение кода и не активация | Оркестратор не начинает Build при FAIL |
| Независимый ревьюер / guardian | Подкреплённый доказательствами вердикт в указанном объёме, не структурная оценка | Исполнитель устраняет находки; оркестратор активирует после всей требуемой цепочки |
| `forgeplan activate <ID>` | Защищённый переход статуса; настраиваемая проверка происхождения доказательств о коде | Не запускает тесты реализации и не делегирует ревью |

В 0.38 **нет подкоманды `forgeplan gate`**. MCP `forgeplan_guard` проверяет **переходы фазы сессии**, а не независимое ревью. `phase` артефакта рекомендательная. Claims — сигналы координации, не блокировки доступа/исполнения; успешный claim/dispatch — не PASS.

### Минимум опубликованного `/gate-check`

Скилл читает записанную глубину, сверяет с `calibrate` без молчаливой смены и накладывает `.forgeplan/quality-gates.yaml` **по ключам** на поставляемые значения:

| Режим / уровень | Опубликованные MUST-проверки |
|-----------------|-----------------------------|
| Pre-build, Tactical/Standard | Ноль ошибок валидации (цикл пропускает отдельный Tactical gate) |
| Pre-build, Deep | Предыдущее + ≥1 связанный EVID с ≥3 секциями `### Hypothesis` |
| Pre-build, Critical policy | Предыдущее + active ADR со связью `informs` |
| Post-build, Deep | Ноль ошибок валидации + рост числа доказательств после pre-build |
| Post-build, Critical policy | Предыдущее + active ADR со связью informs |

Пороги R_eff, formality, granularity, reliability и числа доказательств — **SHOULD**, не опубликованные блокирующие числовые пороги. Проект может переопределить их; назовите настоящий источник. `gaps` и `blindspots` — советы по всей области, не число ошибок одного артефакта. Без исходного числа доказательств рост не подтверждён, а не пройден. Post-build не имеет секций Tactical/Standard; неизвестное имя loop-gate даёт отказ, не молчаливый PASS.

Скилл не активирует и не заменяет guardian. `--force` требует `--reason` и создаёт одну связанную Note с пропущенными проверками; цикл использует обход только по настойчивому запросу пользователя. Это не CLI `activate --force`, который обходит runtime-проверки и не доказывает независимое одобрение. Опубликованный цикл требует ADI и независимое ревью/guardian на **Standard+**, хотя концептуальная таблица §5 начинает часть проверок с Deep.

### Ограничения релиза, которые нельзя скрывать

- Ядро разбирает `critical` как Deep; отдельного Critical-конвейера роутера нет. Critical-пороги маркетплейса — контракт оркестрации, не ещё один режим валидации ядра.
- MUST валидатора — минимум. В 0.38 RFC Options/Implementation Phases — SHOULD; Epic требует Vision/Outcomes/Children/Phases/Progress; Spec допускает структурный **или поведенческий** контракт. Наличие/измеримость NFR и Requirement без Scenario проверяются как SHOULD. См. [практическую таблицу](FORGEPLAN-GUIDE.ru.md#правила-по-depth).
- Runtime-проверка связи с доказательствами — не полный аудит происхождения/независимости. Указывайте реальные результаты, объём доказательств и `weakest_link`; положительное число само по себе не означает готовность.

Источники: [проверки активации 0.38](https://github.com/ForgePlan/forgeplan/blob/d56466b10ddf788c62a6e8acffd0e0f578d0c1d1/crates/forgeplan-core/src/lifecycle/mod.rs#L139-L220), [проверка происхождения CLI](https://github.com/ForgePlan/forgeplan/blob/d56466b10ddf788c62a6e8acffd0e0f578d0c1d1/crates/forgeplan-cli/src/commands/activate.rs#L29-L61), [опубликованный gate-check](https://github.com/ForgePlan/marketplace/blob/b4e8a1b9bfaa4c9c44e6f8dc1039e09fa1b193f7/plugins/fpl-skills/skills/gate-check/SKILL.md#L114-L176), [YAML порогов](https://github.com/ForgePlan/marketplace/blob/b4e8a1b9bfaa4c9c44e6f8dc1039e09fa1b193f7/plugins/fpl-skills/templates/quality-gates.yaml#L116-L188).

## 1. Verification Gate (5 пунктов)

До принятия решения (ADR/RFC) примените пункты, требуемые выбранным процессом/глубиной (§5). Это вопросы для ревьюера, не пять проверок, автоматически выполняемых CLI.

### 1.1. Deductive consequences — Дедуктивные следствия

> Что должно быть истинным, если решение верно?

Если решение X правильное, то обязательно должны выполняться условия Y, Z, W. Проверь каждое. Если хотя бы одно не выполняется — решение под вопросом.

**Пример**: Если мы решили использовать LanceDB, то должно быть верно:
- LanceDB поддерживает наши типы данных (structured + vectors)
- Производительность на 10K артефактов приемлема (<100ms запрос)
- Есть стабильный Rust SDK

### 1.2. Strongest counter-argument — Сильнейший контраргумент

> Настоящий (не strawman) контраргумент против решения.

Сформулируй самый сильный аргумент ПРОТИВ выбранного варианта. Strawman (заведомо слабый аргумент) не считается — нужен реальный risk.

**Пример**: "LanceDB — молодой проект, API может сломаться между версиями. SQLite стабилен 20+ лет."

### 1.3. Self-evidence check — Проверка самодостаточности evidence

> Независимы ли источники доказательств и относятся ли они к утверждению?

Одна сессия может дать реальный тест в целевом контексте; несколько сессий — повторять одно неподтверждённое заявление. Оценивайте контекст и независимость отдельно. CLI 0.38 читает объявленные CL/source tier, а не подсчитывает сессии с автоматическим назначением CL1.

**Штраф**: объявленный CL1 вычитает 0.4 из оценки вердикта; обоснуйте выбор уровня контекста.

### 1.4. Tail failure scenarios — Маловероятные катастрофические сценарии

> Сценарии с вероятностью <10% каждый, но катастрофическими последствиями.

Перечисли 2-3 сценария "что если всё пойдёт не так". Оцени: можем ли мы их пережить? Есть ли rollback plan?

**Пример**:
- Гипотетическое прекращение поддержки хранилища → проверить актуальный формат экспорта и выполнить пробную миграцию
- BGE-M3 недоступна у поставщика → сохранить необходимые файлы/кеш модели. Модель ~2.1 GB загружается отдельно, **не встроена в бинарь**. Для автономной работы файлы должны уже быть доступны.

### 1.5. WLNK challenge — Проверка слабого звена

> Действительно ли это самое слабое звено, или есть скрытое?

R_eff = min(evidence_scores). Убедись, что ты определил НАСТОЯЩЕЕ слабое звено. Часто реальный risk скрыт за тем, что кажется очевидным.

**Вопрос**: "Я считаю, что слабое звено — производительность. Но может быть, реальная проблема — developer experience или миграция существующих данных?"

## 2. Adversarial Review Protocol

Протокол ревью, применяется на уровнях Deep и Critical. Управляется core-политикой [ADR-027 — Финитное evidence-обоснованное независимое ревью без квоты на дефекты](../../.forgeplan/adrs/ADR-027-finite-evidence-backed-independent-review-without-a-defect-quota.md); план cutover и приёмка — в [RFC-014 — Core review policy, bounded documentation cutover](../../.forgeplan/rfcs/RFC-014-core-review-policy-bounded-documentation-cutover.md). Этот раздел — **единственный нормативный core-протокол**; короткие определения и инструкции в других местах ссылаются сюда.

> **Граница применимости (core-политика, без авто-распространения).** Раздел управляет owning Forgeplan core / source-документами. Опубликованный бинарь, установленные копии плагинов, публичные website-поверхности и исторические артефакты (session snapshots, `docs/vnext/**` audits, инстанцированные тела шаблонов) сохраняют прежний текст до тех пор, пока эти поверхности не будут обновлены независимо. Это изменение не правит Rust validator, CLI/MCP runtime и шаблон, встроенный в опубликованный бинарь, и не является автоматическим распространением downstream.

### Основные правила

1. **Ноль реальных дефектов — не auto-PASS и не auto-FAIL.** Сам по себе ноль не доказывает ни тщательности, ни поверхностности. Ревьюер **MUST** активно искать контрпримеры и противоречия, прежде чем принять нулевой исход. Нулевой вердикт допустим только когда выполнены все условия §D1 для текущего полного candidate.
2. **Обязательный активный поиск контрпримеров.** Ревьюер читает артефакт, смежные документы, prior art и негативные сценарии, специфичные для цели. Пассивный поиск подтверждений ревью не считается.
3. **Обязательная структурированная отчётность.** Каждый finding несёт severity (`Critical`, `HIGH`, `MEDIUM`, `LOW`, `Warning`, `Pass`), точное местоположение (раздел / строка / диапазон), последствие и текущее состояние (`open`, `fixed`, `authorized-justified-acceptance`, `blocked-external`).
4. **Неразрешённые `HIGH` или `Critical` блокируют ревью** (`BLOCKER`). Артефакт не переходит к следующему gate, пока такие findings остаются `open`.
5. **`Warning` / `MEDIUM` / `LOW` не стираются zero-defect оговоркой.** За ними сохраняется путь «исправить или получить owner-authorized justification». Ревьюер никогда не принимает риск за владельца.
6. **Ревьюер никогда не выдумывает и не дублирует findings.** Re-spawn только ради ненулевого счётчика запрещён; повтор ревью только из-за нуля запрещён.
7. **Generator ≠ verifier.** Авторский разбор, ручная отметка владельца и успешная structural validation не являются независимым verdict.

### D1. Bounded zero-defect PASS — семь условий

Независимый ревьюер **MAY** завершить проверку вердиктом **PASS с нулём реальных дефектов** только когда выполнены все перечисленные ниже условия на текущем, полном candidate.

1. **Независимость.** Generator и verifier различаются. В отчёте названы автор, ревьюер, роли, назначенные модель / effort и пределы независимо подтверждаемой идентичности. Авторский разбор, ручная отметка владельца и успешная structural validation не являются независимым verdict.
2. **Текущая версия.** Названы owning workspace, точный объект, объём, критерии и исключения. Для артефакта: закреплены canonical slug, полный body SHA-256, status / depth и значимые связи. Для дерева: baseline commit плюс digest фактического candidate-содержимого, включая dirty файлы. Один `HEAD` без содержимого рабочей копии недостаточен. Ревьюер лично перепроверяет актуальность этих данных на момент verdict.
3. **Покрытие.** Каждому обязательному критерию сопоставлены проверка, результат и ссылка на доказательство, либо документирована неприменимость. Непроверенный обязательный критерий не превращается в N/A ради PASS. Зафиксированы сильнейший контраргумент, существенные границы и негативные случаи, а не только happy path.
4. **Достаточность доказательств.** Указаны происхождение, сохраняемая выдержка / результат и digest (или стабильная ссылка) на материал. Для исполняемых действий — реальные команды, среда, наблюдённые результаты / exit codes, объём выполнения; ненулевое выполнение отличается от «ничего не запустилось». Чужой отчёт помечен как чужой; догадка помечена как inference. Observed, inferred, skipped, unavailable не смешиваются. Hash подтверждает идентичность цитируемого содержимого, а не его корректность.
5. **Находки и ограничения.** Все реальные находки остаются в отчёте с severity, ссылкой на строку / раздел, последствием и текущим состоянием. Неразрешённые `Critical` / `HIGH` означают **BLOCKER**. `Warning` / `MEDIUM` / `LOW` сохраняют путь «исправить или owner-authorized justification»; ревьюер не принимает риск за владельца. Значимые неустранённые сомнения в покрытии или доказательствах превращают нулевой счётчик в BLOCKER или CONCERNS, а не в PASS.
6. **Сохранённые gates.** Получены все требуемые reviewer count и раунды, validation / ADI / Verification Gate / R_eff и профильные проверки в своей области. Требования guardian, security, runtime, consent и activation выполнены там, где они применимы к заявленному gate. Отчёт не выдаёт частичный результат за весь конвейер.
7. **Конечный отчёт.** Ревьюер явно называет, что именно прошло, что не проверено, какие внешние условия остаются и почему этого достаточно ровно для заявленного объёма. Фраза «всё хорошо» без пунктов 1–6 не является законченным ревью.

### D2. Re-review и конечность

Новый независимый review необходим, если релевантно изменились проверенная версия, критерии или доказательства; исправлены реальные находки; существенная проверка была пропущена; доказательства отсутствуют или недостаточны. Ревьюер перепроверяет исправление и возможные новые дефекты. Нерелевантная редакционная правка требует записи причины сохранения применимости прежнего verdict, а не молчаливого использования.

Обязательные **Critical ≥ 2 раунда** сохраняются даже при нулевом исходе первого раунда. Назначенные число и специализации reviewer сохраняются: в частности **2+ audit-агента** и `security-expert` + `code-reviewer` / `reviewer` при действующем триггере `CLAUDE.md` (≥5 commits OR new public API). Этот протокол удаляет из того блока только квотную фразу «Each MUST find ≥3 issues; Zero findings → re-spawn», не её trigger и не роли. Для Deep новое число reviewer не вводится вместо ранее применимого. При реальной проблеме число повторов определяется закрытием проблемы и действующими gates, а не искусственным пределом. Повтор ревью только ради ненулевого счётчика запрещён.

### D3. Строго ограниченный PASS

Design-only PASS относится к полноте проекта решения, когда runtime явно исключён из его критериев; он **не** означает runtime / implementation / publication / activation PASS. Если runtime включён в критерии, его пропуск запрещает такой PASS. Отсутствующий producer или accepted contract не становится ни выдуманным дефектом, ни полученным доказательством; внешнюю зависимость можно оставить закрывающему implementation gate, но весь gate нельзя объявить пройденным. Это изменение применяется только к core-политике и source-документам; опубликованный бинарь, установленные копии и исторические артефакты сохраняют прежний текст до независимого обновления.

### D4. Owner-approved quota-only precedence и граница истории

Выбор владельца зафиксирован сейчас. Этот **draft** не объявляет себя уже действующим правилом и не позволяет автору самому закрыть P1. После реального ограниченного применения и независимой проверки, с lifecycle действиями оркестратора, этот owning core ADR и текущие `docs/methodology/QUALITY-GATES.md` §2 / RU §2 имеют приоритет **только в вопросе квоты на дефекты** над старыми quota-фразами и историческими/template копиями. До этого узкие полномочия владельца по рассмотрению поправки поддерживают рассмотрение этой поправки только пока она на рассмотрении; никаких автоматических полномочий source / activation / runtime. Все остальные действующие gates — validation / ADI / Verification Gate / R_eff / security / runtime / consent / activation, число и роли reviewer, раунды Critical, BMAD 13-step, профильные требования — сохраняют прежнюю силу. Устаревшие quota-фразы в installed / website / Marketplace / session snapshots не переписываются массово.

### Процесс

```
1. Автор готовит артефакт (PRD, RFC, ADR, Spec).
2. Ревьюер перезакрепляет canonical slug, полный body SHA-256,
   status / depth, значимые outbound-связи и (для дерева) digest
   рабочей копии.
3. Ревьюер активно ищет контрпримеры и противоречия, а не подтверждения.
4. Ревьюер составляет список findings: severity, местоположение, последствие, состояние.
5. Вердикт по D1.7 и D2:
   - все применимые критерии покрыты И доказательства достаточны И требуемые раунды сделаны И сохранённые gates удовлетворены -> PASS
     (сохранённые неблокирующие Warning / MEDIUM / LOW findings исправлены или покрыты owner-authorized justification; необязательные nondefect-наблюдения не блокируют; ноль реальных дефектов допустим, но сам по себе не необходим и не достаточен; ревьюер не принимает риск владельца)
   - любой неразрешённый Critical / HIGH -> BLOCKER
   - любая отсутствующая обязательная проверка / доказательство / сохранённый gate -> CONCERNS или BLOCKER по влиянию, никогда PASS
   - иначе -> CONCERNS
6. Автор обрабатывает каждый finding:
   - Critical / HIGH -> исправляет
   - Warning / MEDIUM / LOW -> исправляет или фиксирует owner-authorized justification
   - Pass -> на своё усмотрение
7. Независимый re-review исправлений (обязателен для Critical, ≥ 2 раунда всего).
```

### Классификация серьёзности

| Severity | Описание | Действие |
|----------|----------|----------|
| **Critical / HIGH** | Блокирует реализацию или фундаментальный дефект | Обязательно исправить до продолжения; неразрешённое = BLOCKER |
| **MEDIUM / Warning** | Существенная проблема, неполнота, неясность | Исправить или зафиксировать owner-authorized justification |
| **LOW** | Локальная проблема, ясность, стилистика | Исправить или обосновать |
| **Pass** | Замечание, улучшение, стилистика | На усмотрение автора |

### Для уровня Critical — несколько раундов

На уровне Critical проводится минимум 2 независимых раунда Adversarial Review. Второй раунд фокусируется на:
- Перезакреплении текущей версии и доказательств после изменений первого раунда.
- Проверке, что находки первого раунда действительно исправлены (а не молча понижены).
- Поиске проблем, возникших из-за исправлений.
- Межсекционной согласованности.

Ноль находок в первом раунде не отменяет второго.

## 3. BMAD 13-Step PRD Validation

Полная валидация PRD по 13 шагам из BMAD-METHOD. Применяется на уровнях Deep и Critical.

Это **процедура ревью**, не обещание, что `validate` или `review` выполняет все тринадцать содержательных проверок. Бинарь реализует отдельные правила с фиксированной серьёзностью; доменное суждение, полноту и отчёт обеспечивает автор/ревьюер. В 0.38 наличие/измеримость NFR и несвязанные требования дают предупреждения; прохождение MUST не делает неизмеренные требования проверенными фактами.

| Шаг | Название | Что проверяет |
|-----|----------|---------------|
| 1 | **Discovery & Confirmation** | Тип документа определён корректно, задача ясна |
| 2 | **Format Detection & Structure** | Структура соответствует шаблону, все секции на месте |
| 3 | **Information Density** | Нет filler/fluff, каждое предложение несёт смысл |
| 4 | **Product Brief Coverage** | Product brief полностью покрыт: проблема, аудитория, цели |
| 5 | **Measurability** | FR и NFR тестируемы и измеримы (числа, метрики) |
| 6 | **Traceability** | Цепочка: Summary -> Criteria -> User Journeys -> FRs прослеживается |
| 7 | **Implementation Leakage** | Нет имён фреймворков, библиотек, технологий в требованиях |
| 8 | **Domain Compliance** | Учтены доменные требования (healthcare, fintech, и т.д.) |
| 9 | **Project-Type Compliance** | Учтена специфика типа проекта (API, mobile, web, CLI) |
| 10 | **SMART Requirements** | Specific, Measurable, Attainable, Relevant, Traceable |
| 11 | **Holistic Quality Assessment** | Общая оценка 1-5 по качеству документа |
| 12 | **Completeness** | Нет template variables (`{{placeholder}}`), все секции заполнены |
| 13 | **Report Finalization** | Итоговый отчёт с рекомендациями и action items |

### Частичное применение (для уровня Standard)

На уровне Standard обязательны только 3 шага:
- **Шаг 3** (Information Density) — убрать воду
- **Шаг 5** (Measurability) — FR/NFR должны быть тестируемы
- **Шаг 7** (Implementation Leakage) — требования без привязки к реализации

## 4. R_eff Quality Scoring

Система оценки качества решений из Quint-code. Основной принцип: **доверие к решению = его слабейшее звено**.

### Формула

```
R_eff = min(own_evidence_scores, eligible_recursive_dependency_scores)
```

**НИКОГДА среднее (average).** Одно слабое доказательство обрушивает весь score.

**Какая эвиденция участвует**: min идёт только по *текущей* эвиденции артефакта. Пакеты с терминальным статусом (`superseded`/`deprecated`) исключаются — вытесненный пакет остаётся в графе как история, но больше не говорит о текущей надёжности (ADR-020, зеркало dependency-пропуска ADR-002). Draft-эвиденция считается (это штатное состояние свежего измерения до активации). **Свежий активный** `refutes` по-прежнему обнуляет score; путь восстановления — честное вытеснение: слинковать пакет ре-верификации и `supersede <старый> --by <новый>`.

### Расчёт evidence score

```
fresh_evidence_score = max(0, verdict_score - CL_penalty - type_penalty)
```

CLI использует рекурсивный расчёт: `type_penalty` равен 0 для `test`/`measurement`, 0.1 для `benchmark`, 0.2 для `audit`. Истёкшее учитываемое доказательство получает 0.1 до вычитаний verdict/CL/type. Без учитываемых собственных доказательств собственная оценка решения — 0. Рекурсивный результат также берёт минимум с учитываемыми зависимостями после штрафа связи: `based_on`/`informs` вычитают 0.1, `refines` — 0. Draft/терминальные зависимости и зависимости Note/Memory пропускаются.

Плоская совместимая helper-функция `r_eff()` не вычитает штрафы типа и зависимостей; её формула — не пользовательский расчёт `forgeplan score`. Источники: [рекурсивный вызов CLI](https://github.com/ForgePlan/forgeplan/blob/d56466b10ddf788c62a6e8acffd0e0f578d0c1d1/crates/forgeplan-cli/src/commands/score.rs#L130-L142), [расчёт типа/истечения](https://github.com/ForgePlan/forgeplan/blob/d56466b10ddf788c62a6e8acffd0e0f578d0c1d1/crates/forgeplan-core/src/scoring/reff.rs#L232-L254) и [минимум зависимостей](https://github.com/ForgePlan/forgeplan/blob/d56466b10ddf788c62a6e8acffd0e0f578d0c1d1/crates/forgeplan-core/src/scoring/reff.rs#L424-L499).

### Verdict scores (оценка вердикта)

| Verdict | Score | Описание |
|---------|-------|----------|
| `supports` | 1.0 | Evidence подтверждает решение |
| `weakens` | 0.5 | Evidence ослабляет уверенность |
| `refutes` | 0.0 | Evidence опровергает решение |

### CL penalties (штрафы за уровень конгруэнтности)

| Congruence Level | Penalty | Описание |
|------------------|---------|----------|
| CL3 | 0.0 | Тот же контекст, внутренний тест |
| CL2 | 0.1 | Похожий контекст, related project |
| CL1 | 0.4 | Другой контекст, внешняя документация |
| CL0 | 0.9 | Противоположный контекст |

### Evidence Decay (устаревание)

Каждый evidence имеет поле `valid_until` (TTL). После истечения:
- Evidence НЕ удаляется
- Score становится **0.1** (stale, not absent)
- Это отличие от 0.0 — stale evidence лучше, чем полное отсутствие

Это реализованное правило истечения, не гарантия, что устаревшее доказательство содержательно лучше: оно применяется до verdict/CL, поэтому даже истёкший refutes получает 0.1. Без `valid_until` истечения нет. Перепроверьте утверждение, не продлевайте дату ради повышения числа.

### Пороги доверия

| R_eff | Статус | Действие |
|-------|--------|----------|
| >= 0.5 | Adequate | Решение можно принять |
| < 0.5 | Needs Review | Требуется дополнительный evidence или пересмотр |
| < 0.3 | AT RISK | Решение ненадёжно, необходима переоценка |

Это рекомендации по интерпретации, не порог активации CLI и не опубликованные MUST-пороги `/gate-check`. R_eff — не вероятность корректности и не замена доказательствам ревьюера.

### Пример расчёта

Решение: "Использовать LanceDB для хранения артефактов"

Учебные свежие доказательства с явными типами, без более слабой зависимости:
1. Бенчмарк на 10K записей (`benchmark`): supports (1.0), CL2 -> max(0, 1.0 - 0.1 - 0.1) = **0.8**
2. Наблюдения по документации SDK (`measurement`): supports (1.0), CL1 -> max(0, 1.0 - 0.4 - 0.0) = **0.6**
3. Ревью использования в production (`audit`): weakens (0.5), CL1 -> max(0, 0.5 - 0.4 - 0.2) = **0.0**

```
R_eff = min(0.8, 0.6, 0.0) = 0.0 — AT RISK
```

Слабое звено — отзывы о production использовании. Нужен дополнительный evidence (CL2+) или пересмотр.

## 5. Когда применять каждую проверку

| Уровень глубины | Verification Gate | Adversarial Review | 13-Step Validation | R_eff Scoring |
|-----------------|-------------------|--------------------|--------------------|---------------|
| **Tactical** | Нет | Нет | Нет | Нет |
| **Standard** | Да (3 из 5 пунктов) | Нет | Частично (шаги 3, 5, 7) | Опционально |
| **Deep** | Да (все 5 пунктов) | Да | Полные 13 шагов | Да |
| **Critical** | Да (все 5 пунктов) | Да, несколько раундов | Полные 13 шагов + domain | Да, обязательно |

### Какие пункты Verification Gate на уровне Standard

На уровне Standard обязательны минимум 3 из 5 пунктов. Рекомендуемые:
1. **Deductive consequences** — всегда полезно
2. **Strongest counter-argument** — защита от confirmation bias
3. **WLNK challenge** — определить реальное слабое звено

Пункты 3 (Self-evidence check) и 4 (Tail failure scenarios) опциональны на Standard, но рекомендуются при любых сомнениях.

Таблица — концептуальный профиль ревью. С опубликованным `/forge-cycle` соблюдайте дополнительные Standard+ требования ADI/ревьюера/guardian и фактический файл порогов проекта. Таблица не разрешает пропускать более строгую проверку установленного процесса.

## Примеры smoke-проверок

В одноразовой инициализированной области с реальными возвращёнными ID посмотрите `forgeplan validate PRD-001 --json`, `forgeplan score PRD-001 --json`, `forgeplan review PRD-001`. Нетронутый PRD не становится готовым из-за положительной метрики. В настроенной агентной среде `/gate-check PRD-001` должен назвать режим/глубину/источник порогов и отделить MUST-ошибки от советов по всей области. При обновлении документации эти примеры **не запускались**.
