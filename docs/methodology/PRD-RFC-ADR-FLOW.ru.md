# PRD → RFC → ADR Flow — Decision Tree

Контракт runtime: **Forgeplan 0.38.0**. Дерево ниже помогает выбрать документы; стрелки обозначают подготовку артефактов, а не автоматическое создание или смену статуса. RFC предлагает технический подход, ADR фиксирует значимое решение; если ни то ни другое не нужно, используйте Note.

## Полный Flow (по шагам)

### Path 1: Новая фича (Full Path)

1. Изучите проблему пользователя; `/research` доступен при установленном публичном плагине `fpl-skills`.
2. Выполните `forgeplan route "Описание задачи"` и оцените предложенную глубину и цепочку артефактов.
3. Создайте PRD через `forgeplan new prd "Название функции"` и заполните требования и ожидаемые результаты. CLI создаёт шаблон, а не проводит интервью и не реализует функцию.
4. Создайте SPEC, если нужен контракт. Core принимает структурные API/data-контракты **или** поведенческие требования со сценариями. Публичный `/spec-author` готовит и проверяет вторую форму для сценарной реализации.
5. Подготовьте RFC с проектом реализации и ADR со значимыми решениями в соответствии с глубиной и задачей.
6. Проверьте каждый артефакт через `forgeplan validate <ID> --ci`: устраните MUST и рассмотрите SHOULD. `forgeplan reason <ID>` требует настроенного LLM-провайдера и генерирует ADI-рассуждение, а не независимое подтверждение.
7. Получите независимое ревью до фиксации контракта. `/tdd` из публичного `agents-tdd` требует active PRD + active SPEC со сценариями; валидатор тестов проверяет RED до GREEN. Нельзя менять сценарии и зафиксированные тесты под написанный код.
8. Реализуйте и проверьте результат инструментами проекта. `/sprint`, `/build`, `/audit` — скиллы оркестрации маркетплейса, а не команды CLI core.
9. Запишите реальные результаты ревью/тестов в EVID, свяжите с целевым артефактом, рассчитайте score и примените команду жизненного цикла. EVID ревью спецификации может обосновать фиксацию контракта до кода; не выдавайте его за доказательство тестирования реализации.

### Path 2: Рефакторинг / Tech Debt (Quick Path)

Изучите текущее поведение и выберите глубину. Значимый выбор сохраните в ADR, план — в RFC при необходимости; не придумывайте пользовательский PRD ради внутренней работы. Зафиксируйте сохраняемое поведение контрактами и проверками.

### Path 3: Баг / Incident

Найдите первопричину, при необходимости заведите Problem или Note, исправьте и проверьте. ADR нужен, если исправление вводит решение, которое стоит сохранить, а не для каждого бага.

### Path 4: Roadmap / Большая инициатива

Создайте Epic для нескольких результатов; для каждой части создайте нужные PRD, SPEC, RFC и ADR. Явно задайте родителя и связи графа, отмечайте ход реализации чекбоксами.

## Когда что

| Потребность | Артефакт / публичная точка входа |
|-------------|--------------------------------|
| Проблема пользователя, результаты и требования продукта | `forgeplan new prd "Название"` |
| Проверяемый API/data- или поведенческий контракт | `forgeplan new spec "Название"`; `/spec-author` для сценариев |
| Техническое предложение | `forgeplan new rfc "Название"` |
| Решение и последствия | `forgeplan new adr "Название"` |
| Инициатива из нескольких артефактов | `forgeplan new epic "Название"` |
| Оркестрация исследования, реализации, ревью | Публичные `/research`, `/sprint`, `/build`, `/audit`, если установлены |

Slash-скиллам нужны соответствующие плагин и агентская среда. Установка одного CLI не устанавливает эти оркестраторы.

## Artifact Lifecycle

```
draft ──activate──→ active ──supersede──→ superseded
                      ├────deprecate──→ deprecated
                      └────mark stale─→ stale ──renew──→ active
                                          └─deprecate→ deprecated
```

`superseded` и `deprecated` терминальны в машине состояний. `reopen` создаёт новый draft из active/stale и выводит старый артефакт из обращения, а не оживляет терминальный. Рекомендательная метка `phase` (shape/validate/adi/code/test/audit/evidence/done) независима и допускает ручные переходы вне порядка. Ни `active`, ни фаза `done` не доказывают выпуск реализации.

`forgeplan stale` только сообщает об истёкших датах, а не сохраняет `status: stale`. Для уже сохранённого stale команда `renew` выполняет переход stale→active; истёкший active автоматически в это состояние не переходит.

Обычная активация проверяет MUST-валидацию и для PRD/Epic/SPEC/RFC/ADR — длину тела, наличие доказательств и заготовки. Используйте команды жизненного цикла; `update --status active|superseded|deprecated` не позволяет их обойти. `--force` явно обходит методологические гейты, но не подтверждает проверку.

## Правила связывания

| Связь | Пример CLI (существующие ID) |
|-------|-----------------------------|
| SPEC уточняет потребности продукта | `forgeplan link SPEC-001 PRD-001 --relation refines` |
| RFC опирается на требования | `forgeplan link RFC-042 PRD-001 --relation based_on` |
| ADR следует из проекта | `forgeplan link ADR-007 RFC-042 --relation based_on` |
| Evidence подтверждает артефакт | `forgeplan link EVID-001 PRD-001 --relation informs` |
| Замена выводит active-решение из обращения | `forgeplan supersede ADR-007 --by ADR-012` |

Публичные типы связей: `informs`, `based_on`, `supersedes`, `contradicts`, `refines`. Принадлежность Epic задаётся `parent_epic`, а не связью `belongs_to`, принимаемой `forgeplan link`. Таблица в теле не создаёт ребро графа.

## Depth Calibration (из Quint-code)

| Глубина | Цепочка, предлагаемая core route |
|---------|---------------------------------|
| Note / Tactical | Обязательной цепочки нет |
| Standard | PRD → RFC |
| Deep | PRD → SPEC → RFC → ADR |
| Critical | Допустимый алиас Deep; дополнительного Epic-гейта в core нет |

Это рекомендация маршрутизации, а не автоматическое создание цепочки. Epic и расширенная иерархия для стратегической работы — рекомендации методики. Реальные сигналы runtime и гейты описаны в [DEPTH-CALIBRATION.ru.md](DEPTH-CALIBRATION.ru.md).
