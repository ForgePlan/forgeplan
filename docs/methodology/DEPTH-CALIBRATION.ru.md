# Depth Calibration — когда какой уровень глубины

Руководство по выбору уровня глубины проработки решения. Основано на Quint-code depth calibration и адаптировано для Forgeplan.

## Обзор уровней

В Forgeplan **0.38.0** значения runtime `Mode`: `note`, `tactical`, `standard`, `deep`. Входное `critical` преобразуется в `deep`: стратегической работе могут понадобиться Epic и расширенная иерархия, но отдельного Critical-гейта в core нет.

| Уровень | Как выбирать | Цепочка core route |
|---------|--------------|--------------------|
| **Note** | Сохранить краткое наблюдение | Нет |
| **Tactical** | Очевидное, обратимое, ограниченное изменение | Нет; Note по желанию |
| **Standard** | Несколько подходов, умеренное влияние | PRD → RFC |
| **Deep** | Высокие ставки, безопасность, миграция, длительные последствия | PRD → SPEC → RFC → ADR |
| **Critical** | Стратегическая межкомандная инициатива | Алиас Deep; иерархия Epic — рекомендация методики |

Одна длительность не определяет глубину. Короткое изменение безопасности может требовать Deep.

## Дерево решений

```
Очевидно и обратимо?                         → Tactical
Несколько подходов, умеренные последствия?   → Standard
Безопасность / миграция / широкое влияние?   → Deep
Стратегическая инициатива из многих частей?  → Гейты Deep + Epic при необходимости
```

`forgeplan route "задача"` предлагает глубину и цепочку. `forgeplan calibrate` анализирует содержание существующих артефактов и сообщает рекомендуемое повышение; он не меняет depth и не создаёт недостающие артефакты.

## Триггеры автоматической эскалации

Ниже — **рекомендации calibrate**, не автоматические изменения и не гарантия обнаружения каждого риска:

| Сигнал в содержании | Предлагаемый минимум |
|---------------------|----------------------|
| Более 3 строк вида `- [` или `* [` | Standard |
| Более 10 таких строк | Deep |
| Заголовок Security/compliance/authentication либо “security considerations” | Deep |
| “breaking change”, `## Migration` либо “backwards compatibility” | Deep |
| Более 2 связей графа / более 5 | Standard / Deep |
| Непустой `parent_epic` | Standard |
| Более 4 заголовков `## ` / более 8 | Standard / Deep |
| Более 50 строк тела / более 200 | Standard / Deep |

Результат — максимум обнаруженных минимумов; без сигналов предлагается Tactical. Риски для данных пользователя, публичного API, обратимости и других команд оценивайте самостоятельно: это критерии решения, а не обещание, что калибратор понимает их смысл.

## Требования к артефактам по уровням

### Tactical

- У core route нет обязательной цепочки. Если всё же создаёте PRD, его базовые MUST-секции сохраняются.
- Product Brief (`templates/brief/_TEMPLATE.md`) — облегчённый шаблон подготовки, а не отдельный runtime-тип и не освобождение от валидации PRD.
- Для изменения без артефактов доказательство не является предварительным условием. При активации PRD/Epic/SPEC/RFC/ADR общий evidence-гейт сохраняется.
- `forgeplan new` не задаёт автоматический `valid_until` через 90 дней; срок нужно назначать осознанно.

### Standard

- Core route рекомендует PRD + RFC, но не создаёт и не проверяет всю цепочку при каждой активации.
- PRD добавляет целевую аудиторию MUST; плотность Problem (50 слов) и отсутствие названий технологий в FR/NFR — SHOULD.
- Инварианты и откат ADR — SHOULD; инварианты и откат RFC — COULD.
- Независимое ревью, обоснование альтернатив, измеримые результаты и подходящие доказательства остаются работой методики, а не core-правилом «3 из 5».

### Deep

- Core route рекомендует PRD + SPEC + RFC + ADR.
- PRD добавляет Timeline, Stakeholders, Acceptance Criteria, Risks и измеримые Success Metrics MUST; плотность Problem и отсутствие технологий реализации становятся MUST. Rollback и Dependencies — SHOULD.
- RFC добавляет Risks MUST. Инварианты и откат ADR становятся MUST.
- SPEC принимает структурные контракты или поведенческие требования/сценарии на любой глубине. Сценарный процесс маркетплейса фиксирует эталон до кода; core не требует превращать каждый SPEC в PRD.
- Полные доказательства, план отката и adversarial review — требования методики; core-валидация не запускает тесты и не подтверждает ревью.

### Critical

Применяйте проверки Deep. Объединяйте стратегические результаты в Epic, когда это полезно. Передача `critical` сама по себе не добавляет отдельного Epic-гейта, фиксированного числа evidence packs или 13-шагового ревью.

### Общие границы активации и срока действия

Для PRD/Epic/SPEC/RFC/ADR обычная активация проверяет MUST-валидацию, не менее 100 байт в теле после trim, наличие доказательства и обнаруженные заготовки. Универсального порога положительного R_eff и автоматического запуска ADI/тестов нет. Рассматривайте SHOULD даже при успешном выходе `validate --ci`. `--force` обходит методологические гейты, но не машину состояний.

Назначайте `valid_until` по сроку полезности утверждения; валидатор не требует его у каждого Deep/Critical артефакта. Видимая дата в тексте не обязательно является индексируемой метаданной срока действия.

## Примеры

### Пример 1: Исправление опечатки в шаблоне — Tactical

**Ситуация**: В `templates/prd/_TEMPLATE.md` найдена опечатка в заголовке секции.

**Почему Tactical**: Очевидно что исправить, 1 файл, легко откатить, нулевой risk.

**Действие**: Исправить и закоммитить. Note не нужен.

### Пример 2: Добавить новый формат экспорта (JSON) — Standard

**Ситуация**: Пользователи просят экспорт артефактов в JSON помимо Markdown.

**Почему Standard**: Есть несколько подходов (serde_json vs. tera шаблоны, формат вложенности), фича на 2-3 дня, затрагивает модуль `artifact/writer`.

**Действие**: Создать Standard PRD с измеримыми требованиями к формату, затем RFC с описанием реализации. Отделить потребности продукта от выбора хранения и сериализации.

### Пример 3: Переход с SQLite на LanceDB — Deep

**Ситуация**: Решение о замене storage engine для поддержки vector search.

**Почему Deep**: Необратимо (миграция данных), затрагивает всю подсистему хранения, security implications (данные пользователей), срок реализации 1-2 недели.

**Действие**: PRD (зачем LanceDB) -> Spec (схема таблиц, API контракты) -> RFC (план миграции, этапы) -> ADR (почему LanceDB, а не Qdrant/Milvus/SQLite+расширения).

### Пример 4: Запуск Desktop App (Tauri) — Critical

**Ситуация**: Стратегическое решение о создании десктопного приложения параллельно с CLI.

**Почему Critical**: Стратегическая инициатива, множество подсистем (UI, IPC, state management), несколько "команд" (frontend/backend), roadmap-level решение на месяцы.

**Действие**: Epic (Desktop App v1.0) -> PRD[] (UI/UX, Data Sync, Settings) -> Spec[] (Tauri Commands API, React Components) -> RFC[] (архитектура IPC, state management) -> ADR[] (Tauri vs Electron, React vs Svelte, bundling strategy).
