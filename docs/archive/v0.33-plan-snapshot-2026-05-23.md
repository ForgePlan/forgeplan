## TL;DR (если читать только это)

В v0.32 мы выпустили большой набор новых возможностей и параллельно нашли **три серьёзных проблемы у живых пользователей**. v0.33 — это **«долечивание»**: закрываем эти три проблемы, плюс долг по безопасности, который копили несколько месяцев. Новых фич не планируется — фокус на «чтобы то, что есть, работало без сюрпризов».

**Главное для PM:**

- Один из пользователей пишет: *«работает медленно — если делать через MCP, агенты тормозят»*. Это **самая дорогая фигня для адопшна** и идёт первым приоритетом.
- Второй пользователь поймал баг про worktree: у него **сабагенты не видят файлы, которые сами же создали**. Workaround у него есть, но это блокирует масштабирование его пайплайна. Тоже первый приоритет.
- Третья проблема была найдена в момент релиза самим инструментом (хорошо что нашли, плохо что нашли): MCP сервер кэширует данные и не замечает что они устарели. В v0.32.1 быстрый фикс зашили, но осталось 4 мелких улучшения в эту же сторону.

Остальное — это **накопленный долг безопасности**: GitHub автоматический сканер пометил несколько слабых мест (низкого риска), которые мы запланировали закрыть, но в v0.32 не успели. Срочности нет — это уровень «по уму надо закрыть», а не «горит».

## Что мы выпустили в v0.32 (для контекста)

Это уже у пользователей в руках после `brew upgrade forgeplan`:

1. **Большой набор инструментов для онбординга в существующие проекты** — 6 новых типов артефактов (use case, glossary, hypothesis и др.) и 7 новых команд для AI-агентов. Это про работу с «brownfield» — кодом, который уже существует и в котором надо разобраться. Это была главная цель v0.32.
2. **3 улучшения процесса** — возможность исправлять опечатки в связях между артефактами, автоматическая активация доказательств, новый инструмент для обнаружения аномалий в данных.
3. **6 мелких улучшений** от обратной связи пользователей.
4. **Срочный патч v0.32.1**: фикс компиляции под Windows. Проблема не в коде, а в том, что три библиотеки случайно попали в блок «только для Unix». На macOS/Linux никто не заметил, а билд под Windows падал в момент публикации. Поправлено.

**Что важно:** v0.32 — крупный релиз с историей в нём. Это не «накопленный долг», это новая фича. Но в процессе её допила мы нашли проблемы, которые в v0.33 закроем.

## Что болит у пользователей прямо сейчас (источник v0.33 scope)

Эти три проблемы мы получили **за один день** — 2026-05-21, прямо в момент релиза v0.32. От реальных пользователей, не из теоретических аудитов. Это и есть главная причина почему v0.33 нужен.

### Проблема 1: «Медленно работает через MCP»

**Что пользователь видит:** запускаешь конвейер из 11 AI-агентов. Каждый из них делает простую операцию (создал PRD, привязал доказательство). По отдельности — секунда. Но в сумме всё ползёт. И самое обидное: если **обойти наш MCP сервер** и просто записать markdown-файл напрямую, а потом синхронизировать — **летает**. То есть наш сервер делает что-то лишнее.

**Что это для бизнеса:**
- Пользователь построил впечатляющий 11-агентный пайплайн на нашей методологии. Это **сильнейший use case** для маркетинга — «вот как с нами строят production AI workflows».
- Но пайплайн «работает» только на бумаге. В реальном времени — это боль.
- Если не починим — пользователи переходят на workaround, а workaround не использует наш UI/инструменты, и мы теряем телеметрию + контроль качества.

**Что планируем:**
- Сначала **профилирование** — измерить где именно медленно. Без замеров фиксить = гадать.
- Потом исправить 1-3 главных «горячих места».
- Цель: чтобы создание одного артефакта через сервер ощущалось как мгновенное.

**Сколько работы:** 2-4 рабочих дня. Зависит от того, что покажет профиль.

---

### Проблема 2: «Агент работает в одной папке, файлы создаются в другой»

**Что пользователь видит:** у него много git worktrees (это технически — копии репозитория на одном диске, для параллельной работы). Запускает AI-агента в одной такой папке. Агент через MCP создаёт артефакт. Артефакт **физически появляется не там**, где работает агент, а в исходном основном репозитории. Следующий агент (Guardian, проверяющий) приходит и **не находит файлы там, где они должны быть**. Решает что предыдущий агент схалтурил, отправляет переделывать. Получается loop.

**Что это для бизнеса:**
- Этот же пользователь запускает по **19 git worktrees параллельно** во время спринта. Это уже не «edge case» — это его обычный рабочий режим.
- Multi-worktree поддержка — **критична для команд**, где несколько фич идут параллельно.
- Пользователь сделал свой обходной путь (на уровне плагинов), и это работает, **но это не «правильный» путь**. По-хорошему наш MCP сервер должен сам понимать в какой папке его запустили.

**Что планируем:**
- Это **архитектурное решение, не простой баг**. Нужно выбрать одно из трёх:
  1. Добавить параметр «папка» в каждый вызов сервера
  2. Считывать переменную окружения при каждом запросе
  3. Сервер сам определяет через git, какая папка является «своей»
- Принять решение через нашу методологию (PRD → RFC → ADR), запрограммировать, написать тесты.

**Сколько работы:** 1-3 рабочих дня, включая решение какой из трёх вариантов выбрать. Это первая «фича» в v0.33, требующая дизайна.

---

### Проблема 3: «Сервер закэшировал старые данные и сломался»

**Что пользователь видит:** запустил сервер. Сделал работу. Потом обновил данные через CLI (другой канал). Возвращается к серверу — а он показывает «файл не найден», хотя файл вот же он. Сервер «застрял в прошлом».

**Что это для бизнеса:**
- Эта проблема **была найдена нами самими в момент релиза v0.32** (мы сами на неё попали — было ироничным подтверждением что баг реальный).
- Быстрый фикс уже выехал в v0.32.0 → v0.32.1. Сервер теперь сам обновляет кэш при ошибке.
- Но осталось 4 улучшения «по краям»:
  - Лимит количества повторных попыток (сейчас бесконечно)
  - Защита от перегрузки при многократных одновременных запросах
  - Более надёжный способ определения «когда именно случился сбой»
  - Тест, который воспроизводит проблему 1-в-1 (текущий тест — упрощённая модель)

**Что планируем:**
- Закрыть все 4 улучшения. Они мелкие, в сумме 6-10 часов работы.

**Сколько работы:** 1 день, низкий риск.

## Накопленный долг безопасности (нужно закрыть, но не горит)

Параллельно с пользовательской болью у нас лежат **8 пометок от аудита**, накопленных за последние месяцы. Все низкого/среднего риска, но **их пора закрыть** иначе они будут расти.

Самое важное в этой стопке:

- **CI помечает проблемы безопасности но не блокирует мердж** — это «театр безопасности». Если в код попадёт уязвимость, наш сканер её увидит, но всё равно даст смержить. Нужно либо реально блокировать, либо явно сказать «это advisory» и не делать вид что это gate. Фикс: 1 час.
- **Внешние GitHub Actions используют изменяемые версии (`@v2` вместо хеша)** — теоретически кто-то может перезаписать эту версию вредоносной. Низкий риск (нужно скомпрометировать действие у владельца), но best practice — пинить хеши. Фикс: 2 часа.
- **Windows-пути не санитизируются** — у нас есть код, который маскирует пути в логах (чтобы случайно не показать `/home/user/...`). Маскировка работает для Linux/macOS, для Windows — нет. Если кто-то запустит инструмент под Windows и случайно покажет лог в чате — там будут `C:\Users\...` пути. Низкий риск, но грязно.
- **Несколько мелких улучшений в качестве кода и тестах** — точечные фиксы по результатам аудита.

В сумме все 8 — **2 рабочих дня** работы по чёткому списку. Это «закрыть аудит и забыть».

## Что НЕ войдёт в v0.33 (явный scope cut)

Это важно проговорить, чтобы потом не было удивлений:

| Не делаем | Почему |
|---|---|
| Поддержка Windows как первоклассной платформы | Стратегически Unix-first. Windows работает через WSL. Можем вернуться в v0.34+. |
| Обновление до schemars 1.x | Это библиотека для описания API. Версия 1.0 ломает совместимость, нужна полная миграция кода. **2 рабочих дня изолированной работы — заслуживает своего sprint, не пихать сюда.** |
| Большой долг по архитектуре (`#296`, 6 пунктов) | «Хорошо бы переделать», но нет конкретного блокера. Откладываем до момента, когда что-то реально начнёт болеть. |
| Desktop приложение (Tauri) | Это **отдельный major release** на 2-4 недели. Не v0.33. |
| 8 черновиков PRD в backlog | Это в основном идеи прошлых месяцев. Без актуализации нельзя. По одному пересмотрим в v0.34+. |
| Расширения brownfield (Epic #287 продолжение) | Базовый Epic зашит в v0.32. Расширения — по запросу от пользователей. |

2. **PRD-001 ("RFC ADR Flow") висит черновиком с марта 2026** — самый старый stub. Либо доделать, либо deprecate. По-хорошему deprecate — его идея давно поглощена другими PRD.
3. **PRD-008 продублирован** — две версии одного PRD с разными названиями файлов. Случайно создали обе. Одну надо снести.
4. **3 проблемы помечены как «активные», но без доказательств** — наш health-check жалуется. Либо привязать evidence (если есть), либо явно перевести в другой статус.
5. **27 проблем «в работе» в backlog** — большинство старые. Нужна ревизия: что ещё актуально, что давно закрыто фактически но не помечено.
6. **Block 4 PRD-077** (FR-023..027 — какие-то задачи из предыдущего релиза) **молча провалился** через релиз v0.32. Не файлили нигде как issue, поэтому никто не заметил. Один из пунктов уже не нужен, остальные надо переоценить.

Эти 6 пунктов — не v0.33 scope, но «чистка» которая может занять полдня и сделает картину чище. Решать тебе — делать сразу или отдельной задачей.

## Риски, на которые PM стоит обратить внимание

1. **Профилирование MCP может показать что нужно переписать ~20% сервера**. Если так — это не v0.33 scope, это отдельный sprint. Лучше будет это понять рано и явно сказать «v0.33 — фикс симптома, v0.34 — переписывание движка». Иначе оценка будет ускользать.

2. **Worktree fix — архитектурное решение**. Три варианта, у каждого свои trade-offs. Если выбрать неправильный — придётся переделывать в v0.34. Стоит сделать ADI (наш собственный инструмент для оценки альтернатив) до выбора.

3. **GitHub Dependabot будет автоматически открывать новые PR с обновлением библиотек**. Часть из них будет «без проблем» (мерджим сразу), часть «ломает API» (откладываем как #318). Это **постоянный шум**, который надо обрабатывать. Не v0.33 issue, а ongoing.

4. **Один из пользователей уже сделал свой workaround** для Проблемы 2. После того как мы пофиксим, ему нужно будет **откатить свой workaround** и перейти на наш стандартный путь. Это коммуникационный момент: написать ему явно.
