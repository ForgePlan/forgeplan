### 1.1 Выброшенные BLOCKER'ы (4)

**B-DROP-1. PROTO-02 — схема EvidenceBundle не обеспечивает инвариант 5. Выброшен целиком.**
Сырьё: bundle с пустыми `base_sha`/`result_sha`, пустым `changed_paths`, пустым `delta_digest` и нулём criteria валидируется с **0 ошибок**; `criteria` без `minItems`, `commands` не в `required`, у SHA нет `pattern`/`minLength` — при том что `work-contract.schema.json:85-88` даёт `base_sha` `minLength: 7` (два документа расходятся в строгости).

Это не косметика — это ровно тот класс silent failure, о котором RED LINE #5.
Коррекция: добавить в §3/FPV-05 отдельный блокер «schema-level enforcement отсутствует», и в §7(a).7 — фикстуры negative-case (`base==result`, пустой delta, нулевые criteria) как AC для FPV-02.

## 3. Все ли 16 FPV оценены в §3

**Да, все шестнадцать (FPV-00…FPV-15) присутствуют.** Но три дефекта подачи:

- **Арифметика сводки вводит в заблуждение.** «0 READY, 11 NEEDS_FIX, 2 MERGE_WITH_OTHER, 2 DROP, 1 gate-issue (FPV-01) в NEEDS_FIX». Фактически NEEDS_FIX — **12** (00,01,02,03,04,05,06,07,08,10,11,14). Читатель не может сложить 11+2+2 до 16 без догадки, что FPV-01 — это «+1».
- **Вердикт вне объявленного словаря.** FPV-12 получает «MERGE_WITH_OTHER + SPLIT» — составной вердикт, которого нет в наборе; в сводке он посчитан как MERGE, а требование SPLIT (три хоста → три issue) теряется в подсчёте.
- **§3 противоречит §7(c).** §3 даёт FPV-13 вердикт **DROP**, а §7(c).18 ставит «FPV-11 / FPV-12 / **FPV-13** — до supersede ADR-009 … либо до сужения области», то есть трактует его как *заблокированный*, а не отброшенный. Одна и та же issue имеет два разных статуса в одном документе. То же мягче для FPV-15: §3 — DROP, §7(c).20 — «по умолчанию — DROP» (значит, не по умолчанию — не DROP).

## 5. Опасные, неверные или необратимые команды

**5.1 КРИТИЧНО — §6 шаг 4 уничтожает те самые +86 строк, которые спасает.**

```bash
git checkout -b docs/task-list-discipline origin/dev && \
git checkout docs/ddr-terminology-alignment -- CLAUDE.md && git add CLAUDE.md && git commit …
```

Проверено:
- `git diff --stat HEAD origin/dev -- CLAUDE.md` → **пусто** (закоммиченные версии идентичны);
- `git diff --stat -- CLAUDE.md` → `86 insertions` — правки существуют **только в рабочем дереве**.

Значит `git checkout docs/ddr-terminology-alignment -- CLAUDE.md` перезаписывает рабочее дерево закоммиченным блобом и **стирает все 86 строк**, после чего `git commit` либо ничего не коммитит, либо коммитит пустоту. Восстановления нет: изменение не в object store, не в стэше, не в reflog.
Правильная форма (изменение переносится само, потому что блоб на обеих ветках одинаков):

```bash
git fetch origin && git checkout -b docs/task-list-discipline origin/dev && git add CLAUDE.md && git commit -m "docs(claude): add Task List Discipline section"
```

**5.2 `create_github_issues.py` физически не может связать issue на установленном тулчейне — бриф этого не говорит.**
Проверено: `gh --version` → 2.83.2. Полный список флагов `gh issue edit` (FLAGS-блок) содержит `--add-assignee/--add-label/--add-project/--body/--body-file/--milestone/--remove-*/--title` и **не содержит `--parent` и `--add-blocked-by`**. `gh issue view --json` перечисляет доступные поля — `parent` и `blockedBy` **отсутствуют**.
Скрипт вызывает оба (`create_github_issues.py:163`, `:182`) с `check=False`, поэтому не падает, а печатает `WARN … native parent relation unavailable`. Итог: **16 публичных issue в трёх репозиториях создаются плоским списком без epic-родителя и без единого ребра зависимостей**, и это состояние нельзя доисправить тем же тулчейном. Бриф рекомендует не запускать скрипт по причинам арифметики бэклога (§7b.10) — верно по выводу, но по слабейшему из двух аргументов.

## 7. Вердикт §1: обоснован или это вкусовщина

### Обоснован. Проверено лично

| Утверждение §1 | Моя проверка |
|---|---|
| 148 EvidencePack, 0 с git-провенансом | `ls .forgeplan/evidence \| wc -l` = **148**; `grep -rl 'base_sha\|result_sha' .forgeplan/evidence/` = **0** |
| 0 упоминаний ADR в пакете | `grep -rnoE 'ADR-[0-9]{3}' docs/vnext/` = **0** |
| 1 упоминание `.forgeplan`, read-only | `grep -rn '\.forgeplan' docs/vnext/` = **1** |
| 25 `additionalProperties: false` (WC 10, EB 6, ER 5, VV 2, EM 2) | совпало до файла |
| ADR-001/003/009/011 — `status: active` | совпало |
| Ветка 12 позади origin/dev, 0 впереди | `12 0` |
| Противоречивый вердикт `forgeplan health` | воспроизведён: «Project looks healthy» и «Project is unhealthy» в одном выводе |

Это не вкусовщина. Каждое несущее число брифа проверяемо и верно.

### Аргумент за ОТКЛОНИТЬ, максимально сильный

1. **«Переработать» предполагает адресата.** Правку выполняет автор. Автора нет: MANIFEST не называет ни человека, ни генератор (§6.3). Инструкция «переработать» уходит в никуда — реально её выполнит тот же ForgePlan, то есть «переработка» = «написать заново», а это и есть отклонение с сохранением сырья.
2. **Два из трёх BLOCKER'ов не чинятся текстом.** Attestation-субстрат (Q5) и место хранения (Q3) требуют способностей, которых нет и которые пакет сам вынес в non-goals. Это не дефекты документа.
3. **Третий BLOCKER вообще не про vNext.** §2 прямо помечает B2 как «PRE-EXISTING CONTRADICTION — существует независимо от vNext». Использовать предсуществующее противоречие как основание не принимать vNext — категориальная ошибка: оно останется и после отмены программы. §1 при этом опирается именно на него («одно из них требует человека»).
4. **Экономика хуже, чем показано.** 13 из 15 исполнимых issue дублируют существующее (DUP-01); 14 из 16 не имеют ни одной заявки в корпусе из 77 PROB (PB-10). По собственному правилу проекта — `R_eff = min()`, слабейшее звено, никогда не среднее — программа, чьё слабейшее звено «неизвестно, кто это написал и против чего», получает 0, а не «нужна доработка».
5. **Субстрат сломан.** Строить слой верификации поверх графа, который молча теряет 21 артефакт и активный ADR (§6.1), — преждевременно вне зависимости от качества пакета.

### Устоял ли исходный вердикт

**Устоял как нижняя граница, но у него неверная единица измерения.**

Против ОТКЛОНИТЬ работает одно, зато решающее: 18 архитектурных документов никто другой не написал, они дёшевы в хранении и дороги в воспроизведении, и решение §5.1 (KEEP как аннекс) верно при **любом** вердикте. «Отклонить» несёт издержку (удалить/игнорировать) без выгоды против «сохранить и запереть исполнение». Кроме того, операционное содержание вердикта — это §7(c): семь issue заблокированы, две отброшены, две слиты, к отгрузке годен один слайс FPV-05. Это фактически отказ от 14/16 с carve-out'ом; ярлык мягче содержания, спор номинальный.

Настоящая претензия — не к слову, а к **единице вердикта**. Бриф выносит один вердикт «пакету». Доказательства поддерживают два разных вердикта двум отделимым половинам:

- **ПРИНЯТЬ С ПРАВКАМИ** — FPV-05 (#360, git-delta provenance gate) и корректностная часть FPV-06: разрыв измерен (0/148), репродьюсеры живые (#392 с цепочкой из 5 артефактов), зависимостей от Protocol v1/адаптеров/сервера нет. Это шипабельно сегодня обычным циклом.
- **ОТКЛОНИТЬ до появления спроса** — FPV-09…FPV-15: ноль заявок в 77 PROB, четыре необъявленных supersession, нулевые ссылки на возможности третьих сторон (ARCH-15, `grep 'http'` → 0 на 1171 строку). Им нужна не переработка текста, а demand-signal и верификация возможностей хостов.

Единый вердикт «ПЕРЕРАБОТАТЬ» одновременно недооценивает первую половину (она готова, а не «требует переработки») и переоценивает вторую (ей нужна не переработка, а основание существовать). Рекомендация: расщепить §1 на два вердикта по этим двум границам и добавить третий, предварительный: **починить субстрат** (реиндекс, дубли EVID-143/PRD-012, невидимые ADR-013/ADR-017) до любого MCP-шага из §5.2.
