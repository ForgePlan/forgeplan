## Problem

Тесты в `forgeplan-core::git::tests` падают недетерминированно при полном прогоне
`cargo test`, с сообщениями вида:

```
panicked at crates/forgeplan-core/src/git/mod.rs:939:69:
diff must succeed: Failed to run git (is git installed?): No such file or directory (os error 2)

panicked at crates/forgeplan-core/src/git/mod.rs:855:14:
called `Result::unwrap()` on an `Err` value: Os { code: 2, kind: NotFound, ... }
```

`git`, разумеется, установлен. Пропадает **`PATH`** — процесс на момент вызова не видит
переменную окружения, по которой ищется бинарь.

## Root cause

В крейте есть тесты, мутирующие process-global окружение (`PATH`, `HOME`) через
`std::env::set_var` / `remove_var`. В Rust 2024 эти функции `unsafe` именно потому, что запись
любой переменной гоняется с чтением **любой другой** из других потоков: внутри libc это общий
массив `environ`, и одновременные доступы не синхронизированы.

Cargo гоняет тесты одного бинаря параллельно. Пока один тест подменяет `PATH`, соседний
git-тест вызывает `Command::new("git")` и получает пустой или частично перезаписанный `PATH`.

Существующая митигация — пометки `#[serial_test::serial(env_path)]` / `serial(env_home)` —
неполна. Комментарий в `crates/forgeplan-core/Cargo.toml` (dev-dependencies, `serial_test`)
это честно фиксирует: локи внутрипроцессные, а полнота зависит от того, что **каждый**
мутатор помечен. Достаточно одного непомеченного, чтобы гонка вернулась.

## Измерено (2026-09-02, ветка fix/prob-088-semantic-search-distribution)

| Прогон | Падений в `git::tests` |
|---|---|
| `cargo test -p forgeplan-core --lib` (baseline, до правок) | 1 |
| тот же + 6 новых env-мутирующих тестов | **3** |
| тот же + те же тесты, переписанные без мутации env | 1 |
| `cargo test -p forgeplan-core --lib git::` (изолированно) | 0 из этих трёх |

Падает каждый раз **разный** тест из семьи `git::tests` — признак гонки, а не сломанной
логики. Изолированный прогон только `git::` эти тесты проходит.

Побочно: при изолированном прогоне всплыл другой отказ —
`git::tests::artifact_filenames_in_origin_dev_returns_filenames_from_real_fixture`, зависящий
от состояния `origin/dev` в рабочей копии. Это другой класс (тест привязан к реальному
состоянию репозитория, а не к гонке) и требует отдельного разбора.

## Почему это важно

- **CI краснеет случайно.** Падение не воспроизводится прицельно, и «перезапустить прогон»
  становится нормальной реакцией — ровно та привычка, которая потом пропускает настоящую
  регрессию.
- **Любая новая работа с env наказывается.** Разработчик, добавивший обычный тест на
  env-переменную, ломает чужие тесты в другом модуле. Связь неочевидна: сообщение говорит
  «is git installed?».

## Направления решения (не реализовано)

1. **Убрать мутацию env из тестов** — вынести чтение env в тонкую обёртку, а логику
   тестировать через инъекцию параметров. Так сделано в `embed::resolve_cache_dir_from` /
   `compose_first_run_notice` в этой же ветке: девять тестов, ноль обращений к окружению.
   Самый надёжный вариант — гонки нет, а не «упорядочена».
2. **Единая serial-группа на все env-мутаторы** — дешевле, но хрупко: полнота держится на
   дисциплине, а нарушение проявляется в чужом модуле.
3. **Не полагаться на `PATH` в git-хелперах** — резолвить `git` один раз при старте.
   Не отменяет гонку, но снимает самый частый её симптом.

Рекомендация — (1) как правило для нового кода, (3) как точечная защита существующего.
