## What was measured

Может ли `tract` (движок инференса на чистом Rust) заменить ONNX Runtime под BGE-M3 —
проверено запуском на настоящей модели, а не рассуждением о совместимости.

Три вопроса по возрастанию цены отказа, каждый следующий имеет смысл только при «да» на
предыдущий:

1. **Покрытие операторов** — разберёт ли tract граф BGE-M3 вообще. BGE-M3 это полный
   XLM-RoBERTa; отсутствие одного оператора закрывает вариант целиком.
2. **Совпадение чисел** — даёт ли tract тот же вектор. Это главный риск: расхождение здесь
   не ломает сборку и не бросает ошибку, а тихо портит поиск. Дефект такого рода не виден
   до тех пор, пока кто-то не заметит, что результаты выдачи бессмысленны.
3. **Скорость** — во сколько раз медленнее.

Зачем вообще: ADR-022 зафиксировал отказ от `semantic-search` в дистрибутивных бинарях,
потому что ONNX Runtime вшивается на этапе сборки и prebuilt не совпадает со средой сборки
на 4 таргетах из 5 (EVID-158). Движок на чистом Rust снимает весь этот класс по построению —
он компилируется там же, где компилируется наш бинарь. Раздел ADR-022 «что должно стать
правдой для пересмотра», пункт 2, называет именно этот сценарий.

## How

Пробник `tract-probe` (`tract-onnx 0.23.6` + `tokenizers 0.23`) на **тех же файлах модели**,
которые уже лежат в продакшн-кэше — `~/Library/Caches/forgeplan/models/models--BAAI--bge-m3/`.
Сравнение шло против настоящего пути (`forgeplan_core::embed::Embedder`), а не против
отдельно скачанной копии, чтобы исключить расхождение входных данных.

Платформа замера: macOS, Apple Silicon, release-профиль, 2026-09-02.

## Result

**Q1 — покрытие операторов: ДА.**

```
== Q1: parse the ONNX graph ==
  OK — graph parsed in 7.102479542s
== Q2: optimise into a runnable plan ==
  OK — optimised in 839.879042ms
```

Граф разобран и оптимизирован без единой недостающей операции. Формат с внешними весами
(`model.onnx` 708 KB + `model.onnx_data` 2.1 GB) прочитан корректно. Выходы:
`[1, 420, 1024]` (last_hidden_state) и `[1, 1024]`.

**Q2 — совпадение чисел: ДА, идентичны.**

Сырой выход tract оказался ровно в 26.2362 раза больше выхода fastembed — постоянный
множитель по всем компонентам, то есть тот же вектор до L2-нормализации (fastembed делит
на длину, пробник — нет):

```
  -2.0212407 / -0.077039994 = 26.236252
  -1.4779578 / -0.056332670 = 26.236246
  -1.4093826 / -0.053719170 = 26.236120
   0.5849239 /  0.022294640 = 26.236076
   0.3540369 /  0.013494262 = 26.236108
   0.6966203 /  0.026551815 = 26.236261
```

После деления на этот множитель максимальное расхождение — **1.6e-07**, то есть предел
точности float32:

```
  tract=-0.077040147  fastembed=-0.077039994  diff=1.53e-07
  tract=-0.056332769  fastembed=-0.056332670  diff=9.92e-08
  ...
  макс. расхождение: 1.63e-07
```

Главный риск варианта — тихо неверные эмбеддинги — **снят измерением**, а не рассуждением.

**Q3 — скорость: вдвое хуже.**

Замер на реальной длине артефакта (420 токенов от `chunk_size: 2000`), с прогревом,
среднее из трёх прогонов, один и тот же текст на обоих путях:

| Движок | На артефакт |
|---|---|
| ONNX Runtime (fastembed, текущий) | 611 мс |
| tract | 1227 мс |

Отношение **2.01x**.

## What this establishes

1. **Вариант технически открыт.** Оба риска, из-за которых он выглядел спекулятивным —
   покрытие операторов и корректность чисел — проверены и закрыты.
2. **Замедление бьёт по редкой операции.** 400 артефактов индексируются вместо ~4 минут
   около ~8. Поисковый запрос кодирует одну короткую строку, там разница между
   десятками миллисекунд и незаметна человеку. Цена платится там, где её почти не видно.
3. **Пулинг для BGE-M3 — `Cls`** (`fastembed/src/text_embedding/impl.rs:173`), то есть
   «взять первый токен» плюс L2-нормализация. Самая простая из возможных схем — значит
   переписывание постобработки не является тонким местом, каким выглядело до проверки.
4. **Класс проблем из EVID-158 снимается по построению.** Rust-зависимость компилируется
   везде, где компилируется наш бинарь; понятия «prebuilt не подошёл к среде сборки» для
   неё не существует.

## Limits of this evidence

- **Замерена одна платформа** — macOS/Apple Silicon. Утверждение «соберётся на всех пяти»
  следует из природы Rust-зависимости, но фактом сборки на остальных четырёх пока не
  подтверждено. Это проверяется в самой работе, не здесь.
- **Замерен один текст** одной длины (420 токенов). Отношение 2.01x не проверялось на
  коротких запросах и на других длинах; профиль замедления может отличаться.
- **Сравнивался один срез вектора** (6 из 1024 компонент). Постоянство множителя по всем
  шести — сильный признак совпадения целиком, но полная сверка 1024 компонент на выборке
  текстов — часть реализации, а не этого замера.
- **Пробник не воспроизводит постобработку.** Он даёт сырой выход модели; совпадение
  установлено с точностью до нормализации. Что нормализация даст ровно тот же результат —
  ожидаемо (деление на длину), но не измерено.
- Ничего не говорит о размере бинаря с вкомпилированным tract и о времени сборки.
