## Context

Ни один опубликованный бинарь ForgePlan никогда не содержал векторного поиска — ни brew, ни
`install.sh`, ни GitHub Releases, ни один из пяти таргетов, с момента введения cargo-dist.
Причина оказалась однострочной: `dist-workspace.toml` не объявлял ключ `features`, а
`semantic-search` не входит в default-набор ни одного крейта workspace (PROB-088).

Дефект прожил месяцы незамеченным по двум причинам. Fallback на keyword-поиск работает
корректно и молча. А документация не просто умалчивала — она **утверждала обратное**:
`getting-started/configuration.md:141` в обеих локалях писал, что фича «included in official
release binaries». Именно это расхождение и привело к репорту.

Прежде чем закрывать дефект, требовалось ответить на вопрос, который нигде не был записан:
**можно ли вообще включить эту фичу в дистрибутив.** Никакого ADR на эту тему не
существовало — прогреплены `.forgeplan/adrs/`, `docs/`, `CHANGELOG.md`. Вопрос
воспроизводился заново при каждом столкновении.

Ответ нельзя было получить рассуждением. `fastembed 5.17.3 → ort 2.0.0-rc.12 → ort-sys`
использует профиль `download-binaries`: сборка каждого таргета тянет prebuilt ONNX Runtime
из сети. Будет ли он существовать и слинкуется ли — свойство внешних артефактов, а не нашего
кода. При этом цена ошибки максимальна: cargo-dist роняет **весь** релизный workflow при
падении любого одного таргета (v0.32.0: сломался `x86_64-pc-windows-msvc`, и macOS с Linux
не опубликовались вовсе).

Штатной возможности проверить не было: `release.yml` на PR выполняет только `dist plan`, а
реальная сборка происходит лишь при push версионного тега — то есть в момент настоящего
релиза. Проверка выполнена через `pr-run-mode = "upload"` (документированная возможность
cargo-dist, upstream помечает её как временную) в PR #455.

Результат измерения — **EVID-158**: прошёл один таргет из пяти.

| Таргет | Итог | Причина |
|---|---|---|
| `aarch64-apple-darwin` | PASS | — |
| `x86_64-apple-darwin` | FAIL | prebuilt ONNX Runtime для этого таргета в ort rc.12 не публикуется вовсе |
| `x86_64-unknown-linux-gnu` | FAIL | `undefined symbol: __isoc23_strtol/strtoll/strtoull` |
| `aarch64-unknown-linux-gnu` | FAIL | то же |
| `x86_64-pc-windows-msvc` | FAIL | `LNK1120: 66 unresolved externals` из `libort_sys` |

Три разные причины, а не один починяемый дефект: отсутствующий артефакт upstream (C1);
prebuilt требует glibc ≥ 2.38, тогда как dist линкует Linux в контейнере со старым glibc
**намеренно**, ради совместимости с широким кругом дистрибутивов (C2); prebuilt собран
против иного варианта MSVC CRT (C3).

## Decision

**`semantic-search` не включается в дистрибутивные бинари.** Ключ `features` в
`dist-workspace.toml` остаётся отсутствующим — намеренно, с комментарием, фиксирующим
измерение и запрещающим бездумное возвращение ключа.

Вместо этого контракт объявляется явно и в тех местах, где его читают:

- README (раздел Install), страницы установки и конфигурации сайта в EN и RU называют состав
  фич дистрибутива, реальный размер модели (2.1 GB) и дают рабочую команду
  `cargo install --git … --features semantic-search`.
- Ложное утверждение «included in official release binaries» снято в обеих локалях.
- `Fix:`-хинт `forgeplan embed` заменён на команду, исполнимую без чекаута репозитория
  (`cargo install --git`, а не `cargo build`) — требование hint-контракта PRD-071,
  закреплено негативным тестом.
- `RELEASE-PROTOCOL` (EN + RU) получил проверку опубликованного артефакта по маркеру
  линковки: наличие `libc++` ⟺ ONNX влинкован. Зелёная сборка состав фич не доказывает —
  именно поэтому дефект и прожил так долго.

Сопутствующее решение: **модель кэшируется один раз на машину**, а не на проект
(`embed::resolve_cache_dir` — `FORGEPLAN_MODEL_CACHE` → платформенный user-cache →
фоллбэк), и о загрузке в 2.1 GB пользователь предупреждается **до** её начала. Это
относится к тем, кто соберёт с фичей, и закрывает PROB-089.

## Options considered

**(a) Включить `semantic-search` в основной дистрибутив.** Отвергнут — **измерением**, а не
опасением. Четыре таргета из пяти не собираются, а поскольку dist роняет весь workflow при
любом одном отказе, ключ не ухудшает релиз, а делает его невозможным. Это был предпочтительный
вариант по продуктовому требованию («поставил и пользуйся»), и он закрыт фактами.

**(b) Отдельный артефакт `forgeplan-semantic` для таргетов, где сборка проходит.** Отложен, не
отвергнут. Технически возможен: `aarch64-apple-darwin` собирается. Но покрывает один таргет из
пяти, требует второго канала дистрибуции с собственным протоколом релиза и оставляет
пользователей Linux, Windows и Intel-Mac ровно там же, где они сейчас. Цена постоянная,
выигрыш частичный. Пересмотреть, если появится prebuilt-покрытие для большего числа таргетов.

**(c) Сменить основание — собирать ONNX Runtime из исходников либо взять другой backend**
(`ort/load-dynamic`, `alternative-backend`/`ort-tract`; оба пути предложены самим сообщением
сборки). Не рассматривался как часть этого решения и **не измерялся**. Это смена архитектуры
зависимости с собственными последствиями — время сборки, размер, вопрос о том, где брать
runtime на машине пользователя. Требует собственного ADR и собственного измерения.

**(d) Оставить как есть и промолчать.** Отвергнут. Это статус-кво, который и породил
PROB-088: фича отсутствует, документация утверждает обратное, пользователь узнаёт правду из
отказа команды. Graceful degradation без объявленного контракта читается как баг, а не как
решение.

## Consequences

**Положительные**

- Релизная публикация не ломается. Ключ, который её сломал бы, снят до попадания в
  релизную ветку — именно ради этого измерение делалось до, а не после тега.
- Вопрос «почему в brew нет векторного поиска» получает письменный ответ с данными.
  Следующий столкнувшийся читает ADR, а не выясняет заново.
- Пользователь узнаёт состав фич **до** установки и получает исполнимую команду.
- Кто соберёт с фичей — качает модель один раз на машину, с предупреждением о размере;
  раньше это была копия 2.1 GB на каждый проект (измерено 4.2 GB на двух).

**Отрицательные и принимаемые**

- Продуктовая цель «поставил `fpl` — векторный поиск работает» **не достигнута**. Для неё
  нужна сборка из исходников, что отсекает пользователей без Rust-тулчейна. Это прямое
  следствие измерения, а не выбор из удобства.
- Мы зависим от prebuilt-покрытия upstream, на которое не влияем. `ort` — release candidate.
- Один канал дистрибуции с общим составом фич означает, что Apple Silicon не получает
  фичу, хотя технически мог бы. Плата за единообразие.

**Что должно стать правдой для пересмотра**

Решение не бессрочное. Возвращаться к нему, когда наступит любое из:

1. `ort` публикует prebuilt для всех пяти таргетов (снимает C1), а Linux-сборки перестают
   требовать glibc новее контейнерного (снимает C2).
2. Появляется backend без prebuilt-зависимости, приемлемый по времени сборки и размеру
   (закрывает C3 вместе с остальными) — тогда вариант (c) со своим ADR.
3. Спрос на векторный поиск у пользователей бинарной установки перевешивает стоимость
   второго канала — тогда вариант (b).

В любом случае перепроверять `pr-run-mode = "upload"` на всех пяти таргетах **до** тега.
Успешная сборка при этом всё ещё не доказывает наличие фичи — проверять маркер линковки.

## Rollback Plan

Решение отменяется добавлением `features = ["semantic-search"]` обратно в `[dist]`. Само по
себе это действие **опасно**: при текущем состоянии зависимостей оно не деградирует релиз,
а блокирует его целиком — четыре таргета из пяти не собираются (EVID-158).

Порядок безопасного отката, если условия пересмотра наступили:

1. Вернуть `pr-run-mode = "upload"` и `features` в отдельной ветке, **не** в релизной.
2. Прогнать PR, дождаться всех пяти `build-local-artifacts`. Зелёная сборка — необходимое,
   но не достаточное условие.
3. Скачать артефакт и проверить маркер линковки (`libc++` для macOS, `libstdc++` для Linux).
   Сборка может пройти, а фича не попасть — ровно так дефект и прожил месяцы.
4. Снять `pr-run-mode`, записать новый EVID, superseded этот ADR новым.

Откат документации отдельно не требуется: она описывает наблюдаемое поведение, и при
изменении состава фич правится тем же PR, что и конфиг.

Если фича включена ошибочно и релиз уже сломан — `git revert` коммита с `features` и
повторный тег; публикация не состоялась, значит откатывать в дистрибуции нечего.
