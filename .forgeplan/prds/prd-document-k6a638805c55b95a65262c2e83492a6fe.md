# Инженерные решения, связанные с версиями кода, контрактами и доказательствами

## Problem

При изменении системы из трёх и более репозиториев или замене легаси разработчику нужно понять: какие инженерные обязательства затронуты, какие потребители и варианты поведения важны, какие проверки действительно выполнены и что осталось неизвестным. Карта импортов, имя тестового файла, рассказ исполнителя о проверке и высокий R_eff по отдельности этого не показывают. Ревьюеру также нужен понятный разбор работы в незнакомом стеке, а не скрытое принятие риска автоматическим процессом.

Этот PRD уточняет полный продуктовый замысел NOTE-067 и пока не подтверждённую рынком постановку PROB-107. Сначала описана зрелая система, затем зависимости реализации. Запрос владельца определяет нужный объём, но не доказывает спрос других пользователей. Все продуктовые эксперименты ниже — NOT_RUN. Документ не объявляет реализацию, преимущество на рынке, корректность исполнения или готовность миграции.

## Goals

- G1: Объяснять изменение по цепочке PRD/ADR/SPEC → сценарий → код и поведение → межрепозиторный контракт → реальные проверки → явное решение о приёмке.
- G2: Построить собственное аналитическое ядро на Rust с переиспользованием подходящих парсеров, языковых анализаторов и результатов исполнения. Не ограничивать продукт адаптером и не обещать понимание любой программы.
- G3: Поддержать исследование легаси, независимую проверку паритета, контролируемое переключение и восстановление после новых записей без потери ошибок, состояния и внешних эффектов.
- G4: Давать человеку и агенту одни и те же привязанные к версии факты: ограниченный контекст, фактическую документацию, CLI/MCP, список/дифф/2D/3D, Web/Tauri и разрешённый автономный отчёт.
- G5: Сохранять канонические источники, права доступа, происхождение, совместимость и восстановление в локальной работе, федерации и необязательном командном развёртывании.
- G6: Измерять полноту решённой задачи, качество ревью и полную стоимость относительно альтернатив. Делить поставку по зависимостям, не удаляя зрелые возможности.

## Non-Goals / Out of scope

- В этой поставке документа нет изменений исходников/тестов/конфигурации, реализации, runtime-экспериментов, записей в трекер, активации или подтверждения спроса.
- Не обещаем восстановить все бизнес-правила, понять произвольный динамический код или доказать универсальную эквивалентность. Неизвестное остаётся видимым.
- Core не становится трекером, планировщиком агентов, менеджером процессов/worktree или новым верхнеуровневым оркестратором. Не создаём обязательный Git-хостинг, собственный компилятор или движок покрытия ради самого факта владения.
- Нет автоматического принятия EPIC-009, Protocol v1 и 16 задач FPV; нет конкурирующего нового EPIC, массовой замены решений или создания 16 PRD авансом.
- Этот PRD не выбирает обязательные SQLite, ATTACH, RRF, WASM, SSE, универсальную ActionBus, фиксированные четыре агентные роли или собственный формат ради формата.
- Балл, цвет, подпись, зелёный job, dry-run и пустой граф не дают скрытого разрешения на приёмку. Не обещаем универсальные задержки, долю рынка или скидку на токены.

Глубокое поведение, широкая языковая поддержка, расширения по запросу, документация, автономные отчёты, 3D, Tauri, командная работа и опциональный Hub остаются В ОБЪЁМЕ зрелого продукта. Зависимость от позднего этапа не означает отказ.

Сегменты за пределами потребности владельца — гипотезы, не опрошенные персоны.

## Foundation contracts

Это продуктовые инварианты для будущих SPEC/RFC, не выбранная схема или список crates.

### FC-1 — Единая привязка результата

Каждый результат несёт source identity, canonical subject identity, точную revision/content digest (включая dirty inputs), configuration/features/target, analyzer/producer/tool version, policy version, evidence references и provenance. Хранение, федерация, query, context, документы, UI и offline export сохраняют эту привязку. Намеренная подмена revision/config/producer/policy остаётся rejected либо incomplete по всей цепочке. Отдельно правильные слои о разных субъектах не дают общий PASS. Повторение общей проверки не считается независимым подтверждением.

### FC-2 — Типизированные факты и идентичность

Сущности: source, revision/config, file, symbol, endpoint/schema/event/package/FFI, artifact/scenario, test/run, evidence, policy, finding. Imports, references/type references, calls, implements, reads/writes, publishes/consumes, declares и verified-by имеют разный смысл. Статическое test uses не равно executed-by. Сохраняются call sites/spans, метод получения и resolved/heuristic/ambiguous/unknown/stale. Причины unknown различают неподдержанный язык/config, parse/read error, denied/missing source и динамику. Rename/move/overload требуют явного свидетельства преемственности: имя, строка или хеш не разрешают молча слить сущности. Удалённые субъекты сохраняют историю/ссылки/tombstones для drift.

### FC-3 — Классы хранения и восстановление

Версионируемые авторские артефакты и принятые code links/policies/exceptions каноничны. ADR-026 Class A contracts/bundles/verdicts — tracked, schema-validated, digest-linked, append-only через canonical operations. Class B raw receipts/journal локальны; promotion сохраняет нужный extract и digest receipt. Class C CI/deployment/tracker state остаётся внешней истиной с digest/временем наблюдения; frozen extract не создаёт вторую mutable authority. Производные graph/search/vector проекции пересобираются только из объявленных источников. Для каждого durable класса нужны authority, identity/history, expiry, retention и recovery; не всякая БД disposable. Сохранённые/редактированные по правам отчёты и canonical extracts должны позволять последующую проверку в заявленной области.

Новое поколение строится и проверяется до атомарной публикации; читатель удерживает согласованный snapshot; при неудаче остаётся пригодное предыдущее поколение; параллельные изменения не теряются. Crash durability проверяется отдельно от атомарной видимости. Версия схемы не заменяет publication protocol. Нельзя удалять открытую БД или каноническую историю ради rebuild. SQLite/FTS/vector stores, представление графа и ATTACH — альтернативы HYP-006 до измерений/решения. Identity/generation/search/snapshot/DTO сохраняются либо меняются рассмотренным решением, не побочным эффектом смены backend.

Технические кандидаты исходного F-01, а не выбранная архитектура: rusqlite/WAL, FTS5 с rust-stemmers, BLOB-векторы с SIMD либо sqlite-vec. FR-01 требует сравнить результат и стоимость этих вариантов с сохранением Lance; ни один механизм не получает предпочтение до решения по HYP-006.

### FC-4 — Пять уровней анализа

A: синтаксис/ERROR-области reusable parser. B: configuration-aware definitions/references/reexports/aliases/generics/macros/generated inputs compiler/LSP/SCIP в поддержанной области. C: ограниченные control/data/effects/transactions/errors/network/queues/async models. D: наблюдаемые тесты/coverage/traces/differential execution. E: утверждённые требования/сценарии/причины от артефактов и людей. Уровни дополняют, не подменяют друг друга. Rust/TS/JS/Python — опорные профили глубины и corpus, не запрет зрелой поддержки других языков. Capability profile явно задаёт конструкции/config, доставку, версии и доверие. Tree-sitter сам не даёт глубокую семантику; Rust не гарантирует точность/размер.

### FC-5 — Уровни тестовых доказательств

Отдельно показываем L1 объявление в исходнике; L2 обнаружение runner в config; L3 удостоверенное реальное исполнение/исход; L4 покрытие строк/регионов/ветвей; L5 силу assertions/mutation analysis; L6 проверенный SPEC-сценарий/эффекты/область паритета. Ребро test→symbol — кандидат, не L3–L6. Косвенный сценарный тест допустим; aggregate coverage не является test→region attribution. Stable test identities, raw results и failed/skipped/not-run/no-record/partial/stale сохраняются. Ноль исполненных или отсутствие required checks не даёт PASS. Эквивалентность выжившего mutant разбирается, не объявляется провалом автоматически. Переиспользуем cargo-llvm-cov/cargo-mutants и языковые инструменты.

Evidence связывает subject/config, команду, разрешённого report producer, runner/tool versions, run/attempt, время, exits/counts, исходные отчёты и digests. Хеш не удостоверяет автора или честное исполнение. Доверенная оболочка вокруг attacker-authored JUnit не делает исполнение доверенным. Contradictory exit/count/report, substituted output, replay, stale run и ослабление политики остаются rejected/incomplete. Удостоверенное исполнение необходимо, но недостаточно для паритета. R_eff — оценка цепочки evidence в своей модели, не вероятность корректности и не deploy authority.

### FC-6 — Запросы, бюджет, представления

Запрос объявляет scope/revision, edge kinds/direction, depth/budget/authority. Impact объясняет включение узла, путь, span/status и причину отсечения; зависимость не означает гарантированную поломку. SCC — группы сильной связности для циклов, не бизнес-границы. Bug/API/onboarding имеют разные маршруты чтения. Обязательные ограничения сохраняются целиком; недостаточный бюджет даёт явную неполноту/omissions/continuation, не молчаливую потерю ADR. Один версионируемый query result питает human/machine/agent/UI/offline output; renderer не повышает verdict и не создаёт approval. Наблюдаемая документация отделена от intended требований и сохраняет ручные пояснения.

## Constraints

### Technical

- Собственное Rust Core — допустимая зрелая цель; reusable tools — источники/сравнение. Нет adapter-only cap и переписывания compiler/coverage engine ради владения.
- ADR-025/026/003 и qualified addressing сохраняются; backend/portable identity/read maintenance/transport/schema решаются зависимым архитектурным циклом.
- Semantic support ограничена capability/config; read/parse/denied/unsupported никогда не empty-success.
- Общая семантика Web/Tauri/offline не означает одинаковые permissions/packaging. Существующие map/lazy3D contracts сохраняются до reviewed amendment.
- Артефакты создаются canonical CLI; этот PRD draft. Никакой legacy-table recreation/import или постороннего CLI repair.

### Business

- Полная цель перед этапами — правило владельца. Deadline/budget/market-share targets не заданы, остаются TBD; не предполагаем отсутствие ресурсов.
- Польза/спрос/превосходство — HYP-001/008, не ship claims. Optional Hub/language/deployment options получают условия/владельцев, а не удаляются как преждевременные.

### Regulatory and trust

- Только разрешённые очищенные данные. До исполнения/экспорта определить access, signer/runner/report producer, policy-change authority, exception expiry и retention.
- Нет автоматического принятия FPV, захвата protected claims или отката current main contracts; в этой поставке нет tracker/assignment/owner/due-date writes.

## Evaluation gate E0

E0 обязателен до confirmatory runs. Ответственны product owner и независимый от реализации/producer verifier. До допуска у каждого эксперимента должен быть назначенный ответственный. Пока роль TBD — эксперимент BLOCKED, не разрешён молча.

1. Определить decision/unit/task/config/segment matrix и полные denominators: независимо ожидаемые positives/negatives, missing facts, unknown, failures, refused/abandoned runs, attrition.
2. Закрепить три arm с одинаковыми information/access/training/models/task limits: A — без ForgePlan, обычные search/LSP/manual review; B — текущий ForgePlan плюс эквивалентные pinned external tools; C — собственная integrated vertical. UI-study отдельно выделяет interface effect; storage сравнивает keep-Lance improvements/storage-only SQLite/alternatives. Baselines не подменяются друг другом.
3. Измерить baseline. На его основе и решении заинтересованного владельца выбрать smallest useful change и maximum full adoption/operating cost, записать обоснование. Non-tradeable safety ceilings вывести из последствий отказа и protected policy. Token/cost gain не компенсирует critical missing consumer/behavior, wrong approval, leak или canonical loss.
4. Выбрать sample/horizon для нужной точности, detectable useful effect либо явно bounded corpus/transition coverage, включая sustained arrivals/load. Числа/corpus сейчас TBD; без них confirmation блокируется, а не оценивается задним числом.
5. Отделить exploratory calibration. До просмотра confirmatory outputs закрепить independent corpus/oracle, exact sources/revisions/dirty digests/config/tool/model/producer/policy, normalization/tolerances, severity/metrics/exclusions/stopping/threshold rationale/verifier approval. Изменение создаёт новую protocol version и новое решение.
6. Считать onboarding/training/setup help/integration, cold build/refresh/storage/query/operation, provider input/output/cache reads/writes/retries, human review, migration/parallel operation/recovery/maintenance за обоснованный горизонт. Публиковать distributions и scenario/segment cells, не лучший пример или aggregate со скрытой критичной регрессией.
7. Supports — только scoped claim, выполнивший все safety/coverage/useful-effect/cost критерии. Refutes — заранее заданная falsification. Иначе INCONCLUSIVE: сохранять failures/unknown, не promote и не включать acceptance-dependent использование. Повтор — только по новому обоснованному protocol, не переименование calibration или удаление плохих ячеек.
8. Task usefulness ≠ UI usefulness ≠ adoption; authenticity ≠ parity; backend preference не доказывает и не блокирует всю аналитику. Общие participants/runs/common-envelope checks коррелированы, раскрываются и не считаются независимыми.

## Acceptance Criteria

Следующие SMART-критерии привязаны к этапам и заранее закрепляемому измерительному протоколу.

Это проверяемые условия к конкретному выходу этапа, не выполненные результаты. Численные performance/usefulness thresholds фиксируются в E0 ДО named confirmatory cycle. Без protocol соответствующий AC BLOCKED, не PASS.

1. **AC-1 — Изменение контракта трёх репозиториев.** К P5 exit, до federated acceptance, пройти E0 producer/consumer rollout matrix минимум в трёх реальных разрешённых репозиториях. Учесть независимый bounded consumer oracle. Required-field/default/old-message break и unchanged-schema semantic break не должны PASS; harmless structural edit отличается от поломки. Wrong version/config, missing/denied source, mixed generation остаются incomplete/rejected. Измерить missed necessary changes/false alerts/review decisions/time/full cost каждого arm по frozen rules. Evidence: pinned contracts, compatibility/required-check reports, raw failures, independent verdict. NOT_RUN.
2. **AC-2 — Реальный legacy parity и post-write recovery.** К P6 exit, до cutover authorization, проверить один реальный компонент по pre-replacement independent frozen/held-out oracle и state/effect ledger. Normal/boundary/error/output/serialization/idempotency, injected regressions, approved divergences и nondeterminism controls обязательны; material mismatch не переименовывается в parity. Выполнить разрешённые new-version writes/in-flight effects и recovery/compensation; проверить old-reader compatibility/duplicate prevention, назвать irreversible point. Измерить bounded behavioral completeness/full migration/recovery cost по E0. Evidence: old/new/harness receipts, independent parity/recovery verdict. NOT_RUN.
3. **AC-3 — Незнакомая задача агента.** К P3 usable-vertical evaluation, до productivity claims, выполнить три equal-access arm на независимо оценённых незнакомых задачах. Negative cells: mandatory ADR truncation, SCC/cycles, wrong direction, missing expected fact, stale docs, normative/manual overwrite. Сравнить complete correct solution/missed changes/false alerts/review time/full provider/index/help costs по scenario rules; меньше tokens само по себе не доказательство. NOT_RUN.
4. **AC-4 — Доверие и required checks.** К P4 exit, до execution-based acceptance, все preregistered zero/skipped/partial/missing/stale/replay/substituted/contradictory report и unauthorized policy/required-tests/workflow weakening остаются non-passing. Включить trusted wrapper с attacker-authored JUnit без исполнения. Независимо восстановить producer/subject/config/run/policy binding, показать L1–L6 отдельно. Authentic execution не даёт AC-2 автоматически. NOT_RUN.
5. **AC-5 — Durable foundation и поэтапная единая привязка.** К P1 exit, до migration/publication, проинвентаризировать и проверить все утверждённые durable/local/external classes через failed publish/crash/schema/live-reader/restore matrix. Identity/content/history/link/exception-expiry восстановимы; mixed generation не current. На фактически поставленных foundation interfaces пройти цепочку canonical record/ссылка на внешний источник → построение и публикация projection generation → captured foundation read → foundation snapshot/export с проверкой FC-1 и инъекциями подмен source/subject, revision/dirty digest, config, producer, policy и evidence references; rejected/incomplete остаются таковыми. Это P1 proof EP-1, не проверка ещё не поставленных федерации, task queries, отчётов или UI. Полная FC-1 сохраняется: при вводе каждого consuming surface его владелец обязан выполнить реальные integrated positive/mismatch cases по EP-2…EP-7 до выхода соответствующего этапа, включая CLI/MCP, документы, federation/CI, Web/Tauri и offline export. P1 contract fixtures/prototypes не закрывают последующую integration acceptance. Backend preference требует отдельного full-horizon сравнения. NOT_RUN.
6. **AC-6 — Зрелые рабочие поверхности.** К P7 exit, до заявления operational readiness каждой поверхности, выполнить preregistered reviewer/developer tasks в CLI/MCP, list/diff/2D/3D и Web/Tauri с одинаковой captured subject/status semantics и существенной информацией, editor navigation, role/agent handoff, keyboard/text и authorized standalone offline report. Для ревьюера незнакомого стека первая подача простыми словами объясняет поведение/предпосылки/последствия, не требуя сначала открыть код; actual characterization/test evidence даёт привязанные к source/revision применимые input/output/error/effect examples, иначе явно unavailable, без выдумывания. Отдельно измеряются понимание и правильность решения, отдельно скорость, accessibility и backlog visibility; подробности доступны по запросу, фиксированные widgets/число примеров не требуются. Sustained-arrival triage соблюдает E0 visibility/escalation horizon без скрытых старых critical items; denied export/unknown independence не становятся permission. EP-7 доказывает FC-1 на реальных UI/desktop/agent/offline и optional Hub/extension consuming paths: прежние foundation fixtures не заменяют эту проверку. Optional Hub/on-demand extensions проходят свои deployment/access/compatibility/recovery scenarios до opt-in. UI benefit и repeat-use adoption — отдельные решения. NOT_RUN.
