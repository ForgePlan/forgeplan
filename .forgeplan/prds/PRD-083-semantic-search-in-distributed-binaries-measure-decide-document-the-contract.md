> [#451](https://github.com/ForgePlan/forgeplan/issues/451) / PROB-088 и PROB-089.

## Problem

Два связанных дефекта, вскрытых один за другим.

**PROB-088** — релизные бинари (Homebrew, `install.sh`, GitHub Releases, все пять таргетов)
собирались cargo-dist с default-features, а `semantic-search` не входит в default. Векторный
поиск BGE-M3 не был доступен ни в одной бинарной установке с момента введения cargo-dist.

**PROB-089** — когда фича всё-таки собрана, кэш модели ведёт себя плохо: пишется в CWD, то
есть дублируется на каждый проект (измерено 4.2 GB на двух проектах); корневой путь не покрыт
`.gitignore`, так что 2.1 GB весов висели untracked и один `git add -A` отправил бы их в
историю; а размер модели был указан в трёх местах тремя разными неверными числами (~150 MB,
~600 MB, при реальных 2.1 GB) и не сообщался пользователю вовсе.

Отягчающее обстоятельство: документация не просто молчала о составе фич — она **утверждала
обратное**. `website/.../getting-started/configuration.md:141` прямо говорил, что фича
«included in official release binaries». Пользователь, читавший документацию, имел все
основания ждать работающего векторного поиска.

Продуктовое требование, зафиксированное владельцем: пользователь ставит `fpl` и **сразу
пользуется** — модель докачивается при первом запуске с видимым прогрессом; если на каком-то
таргете это технически невозможно, пользователю говорят об этом внятно и дают рабочую команду.

Ограничение, из-за которого это не однострочная правка: цепочка
`fastembed → ort 2.0.0-rc.12 → ort-sys` использует профиль `download-binaries` (сборка тянет
ONNX Runtime из сети под конкретный таргет), а cargo-dist роняет **весь** релизный workflow,
если валится хоть один таргет. Прецедент: v0.32.0 упал на `x86_64-pc-windows-msvc` и утащил
публикацию macOS и Linux (`CHANGELOG.md:102`).

## Goals

- **G1.** Знать по измерению, а не по предположению, собирается ли `--features semantic-search`
  на всех пяти релизных таргетах и сколько весит итоговый бинарь.
- **G2.** Пользователь получает работающий векторный поиск из коробки — либо внятное
  объяснение с исполнимой командой, если на его платформе это невозможно.
- **G3.** Модель скачивается один раз на машину, а не на каждый проект, и никогда не попадает
  в git.
- **G4.** Размер загрузки назван честно и **до** её начала, из единственного источника правды.
- **G5.** Не подвергать риску публикацию релиза: изменение релизного конфига проверяется на
  всех пяти таргетах до попадания в `release/v*`.

## Non-Goals

- **NG1.** Не выбираем другой embedding-бэкенд и не мигрируем с `fastembed`/BGE-M3.
- **NG2.** Не вшиваем модель в бинарь. 2.1 GB весов остаются runtime-загрузкой.
- **NG3.** Не трогаем поведение fallback в `fpf search --semantic` — оно корректно.
- **NG4.** Не поднимаем `ort` с release-candidate до stable — вне нашего контроля.
- **NG5.** Не переносим автоматически существующие кэши пользователей. Перемещать гигабайты
  без спроса нельзя; вместо этого показываем команду.
- **NG6.** Не переопределяем `HF_HOME`. Общий HuggingFace-кэш — разумная системная конвенция.

## Target Users

- **Пользователь бинарной установки** (brew / `install.sh` / GitHub Releases) — основная
  аудитория. Ей нужен работающий векторный поиск либо честное предупреждение до установки.
- **Пользователь с несколькими проектами** — страдает от дублирования кэша сильнее всех:
  линейный рост 2.1 GB на проект.
- **Агент (LLM), читающий hint-протокол** — потребитель `Fix:`-строки; неисполнимая команда
  уводит его в тупик.
- **Мейнтейнер релиза** — рискует уронить публикацию всех таргетов разом.

## Functional Requirements

**Дистрибуция (PROB-088)**

- [x] **FR-001.** `features = ["semantic-search"]` добавлен в секцию `[dist]`
      `dist-workspace.toml`. Синтаксис сверен с официальной документацией cargo-dist
      (`book/src/reference/config.md`): ключ `features` существует и передаётся в cargo-сборку.
      `dist plan` на изменённом конфиге отработал без ошибок.
- [ ] **FR-002.** Доказать `dist build` на всех пяти таргетах: `aarch64-apple-darwin`,
      `x86_64-apple-darwin`, `aarch64-unknown-linux-gnu`, `x86_64-unknown-linux-gnu`,
      `x86_64-pc-windows-msvc`. Наличие фичи в артефакте проверяется маркером линковки
      (`libc++` присутствует ⇔ ONNX влинкован), а не фактом успешной сборки.
- [ ] **FR-003.** Оформить результат FR-002 как EvidencePack со `## Structured Fields`
      (`evidence_type: measurement`) и git-provenance.
- [ ] **FR-004.** Замерить размер релизного бинаря с фичей. Первое приближение из PROB-088:
      +19.8 MB (+41.8 %) на `aarch64-apple-darwin`, профили не сверялись.
- [ ] **FR-005.** ADR по составу фич дистрибуции — фиксирует принятое решение и причину
      отказа от альтернатив (второй артефакт `forgeplan-semantic`; оставить как есть).
      Нужен, потому что сейчас решения нет нигде, и вопрос воспроизводится заново.
- [ ] **FR-006.** Изменение релизного конфига мержится отдельным PR **до** релизной ветки,
      с зелёным прогоном всех пяти таргетов.

**Кэш модели (PROB-089)**

- [x] **FR-007.** `embed::resolve_cache_dir()` — `FORGEPLAN_MODEL_CACHE` → платформенный
      user-cache → фоллбэк. Передаётся в `InitOptions::with_cache_dir`. Один кэш на машину.
- [x] **FR-008.** Корневой `.gitignore` получил `.fastembed_cache/` (матч на любой глубине);
      тот же паттерн — в `GITIGNORE_CANONICAL_BODY` (шаблон для чужих проектов) и в
      `GITIGNORE_DRIFT_PATTERNS` (парная правка, которой требует комментарий в `init.rs`).
- [x] **FR-009.** Единственный источник размера — `embed::MODEL_DOWNLOAD_SIZE_HINT`.
      README и drift-детектор приведены к измеренным 2.1 GB.
- [x] **FR-010.** `embed::first_run_notice()` печатает модель, размер и целевой каталог до
      начала загрузки; молчит при наполненном кэше; обнаруживает старый локальный кэш и
      печатает команду переноса вместо повторной закачки.
- [x] **FR-011.** Ошибка инициализации эмбеддера оборачивается в сообщение про сеть, диск и
      `FORGEPLAN_MODEL_CACHE` вместо сырой ошибки fastembed.

**Хинты и документация**

- [x] **FR-012.** `Fix:`-хинт в `embed.rs` заменён на `cargo install --git … --features …`,
      исполнимый без чекаута. Аудит `fpf.rs:216` и `server.rs:6809` показал, что это
      fallback-warning без `Fix:`-строки — контракт PRD-071 они не нарушают, правки не
      требуют.
- [x] **FR-013.** Тест закрепляет контракт: в `Fix:`-строке, достижимой из бинарной
      установки, не должно быть `cargo build`.
- [x] **FR-014.** README: раздел Install получил подраздел о составе фич дистрибутива,
      реальном размере модели, расположении кэша и приоритете `HF_HOME`; таблица Cargo
      features исправлена.
- [x] **FR-015.** Сайт, `getting-started/configuration.md`: снято ложное утверждение
      «included in official release binaries»; исправлен неработающий совет диагностики
      (`forgeplan --version` не сообщает состав фич — проверять надо `forgeplan embed`).
- [ ] **FR-016.** Сайт, `getting-started/installation.md` — тот же контракт в разделе
      установки; RU-зеркало страниц.
- [ ] **FR-017.** `docs/operations/RELEASE-PROTOCOL` получает пункт сверки состава фич
      релизного бинаря перед каждым `release/v*` PR (дешёвый механизм — маркер линковки).

## Acceptance Criteria

- **FR-002 + FR-004**: для каждого из пяти таргетов есть измеренный результат сборки и размер
  бинаря — не оценка.
- **FR-003**: измерение зафиксировано EvidencePack'ом со структурными полями; без них парсер
  ставит CL0 и R_eff обнуляется.
- **FR-005**: ADR активен, ссылается на EVID, содержит рассмотренные альтернативы.
- **FR-007**: на машине с двумя проектами модель скачивается один раз; второй проект
  использует тот же кэш.
- **FR-008**: `git status` в свежем workspace после `forgeplan embed` не показывает кэш.
- **FR-010**: пользователь видит «~2.1 GB» до начала загрузки, а не после.
- **FR-012 + FR-013**: на свежеустановленном бинаре `forgeplan embed` печатает команду,
  исполнимую без чекаута; тест ловит регрессию.
- **FR-014 + FR-015 + FR-016**: ни одна страница документации не утверждает, что фича есть в
  релизных бинарях, пока это не станет правдой по FR-002.
- **PROB-088** и **PROB-089** переведены в терминальный статус со ссылкой на закрывающий EVID.
