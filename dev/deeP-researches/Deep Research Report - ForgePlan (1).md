# Архитектурный аудит и план реализации ForgeFarm

## Главный вывод

Самая сильная часть вашей идеи уже видна: **ForgePlan не надо превращать в оркестратор**. У ForgePlan уже есть ядро для артефактов и методологии: локальный `.forgeplan/` workspace, MCP-сервер, lifecycle `route → shape → build → evidence → activate`, `validate` и `health` как gate-механизмы, а также локальный semantic search на `fastembed`/BGE-M3 и LanceDB как встроенное хранилище индексов. Репозиторий ForgePlan сам dogfood’ит этот подход: артефакты живут в `.forgeplan/`, а ForgePlan позиционируется как framework для git-tracked артефактов, quality scoring и evidence-tracking. citeturn3view4turn3view5turn4search4turn16search3turn4search6

Отсюда следует ключевое архитектурное решение: **ForgeFarm должен стать execution/control plane над ForgePlan и Forgejo, а не их заменой**. Forgejo уже дает issue tracker, milestones, assignees, dependencies, Kanban projects, REST API с token auth и pagination, webhooks и Actions. В экосистеме ForgePlan уже есть направление на orchestration и UI: marketplace описывает `/smith` как master orchestrator, brownfield-pack как compositional ingestion layer, а `@forgeplan/web` — как browser viewer с time-travel, graph и health dashboard. Иначе говоря, у вас уже есть “что хранить” и “где отслеживать”; не хватает именно “как выполнять, планировать, параллелить, проверять и объяснять”. citeturn10view0turn6search2turn5search2turn5search6turn5search9turn19view0turn20search1

Практический вывод такой: **дефолтный happy path должен быть “один кодовый репозиторий + `.forgeplan/` внутри него + Forgejo Issues/Projects + ForgeFarm runtime рядом”**. Идея делать активный `.forgeplan` через git submodule как базовый режим выглядит более хрупкой, чем полезной: ForgePlan нативно стартует с `forgeplan init -y`, создавая `.forgeplan/` прямо внутри проекта, а сам workspace включает config и LanceDB storage; это сильный сигнал, что основной путь задуман как co-located repository model. Я бы оставил submodule только для редких случаев вроде shared portfolio-knowledge или published compositions, но не как основной режим ежедневной работы. Это уже архитектурный вывод, но он прямо следует из того, как ForgePlan сам устроен и документирован. citeturn3view0turn4search5turn3view4turn4search6

## Что в исходной идее недодумано

Самый главный недостающий элемент — **три разных слоя “истины” у вас пока смешаны в одно**. У вас одновременно фигурируют tasks как issues, артефакты как ForgePlan-файлы и “состояние выполнения агентами” как будто бы тоже должно жить на доске. Это плохая смесь. Артефакты ForgePlan — это структурированный decision trail, source-of-truth в git; Forgejo Issues и Projects — удобный внешний tracker и queue; а execution state долгоживущих агентных запусков должен жить в отдельном run-store ForgeFarm, потому что backlog/status на канбан-доске не выражают таких вещей, как checkpoint, retry class, merge blocker, verifier verdict, token burn, approval wait и replay point. ForgePlan сам различает structural validation, health debt и activation readiness; это уже намекает, что одного “столбца на доске” недостаточно даже для artifact lifecycle, не то что для multi-agent runtime. citeturn4search4turn16search3turn10view0turn6search1

Второй слабый участок — **канбан-статусы у вас пока слишком “человеческие”, а не “машинные”**. `backlog / doing / review / fail` удобно смотреть глазами, но такой набор статусов недостаточен для оркестратора. На уровне машины нужны как минимум: `ready`, `claimed`, `planned`, `blocked_by_dependency`, `executing`, `awaiting_verifier`, `awaiting_human`, `merge_conflict`, `policy_failed`, `retry_scheduled`, `done`. Forgejo Projects действительно дают Kanban board для organization of issues, но это не workflow engine. Значит, доска должна быть **проекцией состояния**, а не единственным носителем состояния. citeturn10view0turn6search1turn5search6

Третий недочет — **не определен контракт между planning и coding уровнями**. В ForgePlan экосистеме это уже partially решено методологически: `/smith` выбирает одну методологию и один dispatch path, а marketplace прямо подчеркивает “single-row rule” и анти-паттерн “methodology cocktails”. В row для BMAD есть fail-closed gate до начала code writes; в SPARC есть независимые проверки на spec stage, architecture stage и refine stage. То есть сама экосистема уже тяготеет к жесткому разделению: сначала спецификация и readiness, потом код, потом независимая проверка. В вашем описании это еще не зафиксировано как формальный контракт между L0/L1 и L2/L3. Без этого система неизбежно скатится в ранний code generation до стабилизации артефактов. citeturn20search1turn25search0

Четвертый пробел — **не описана модель конкуренции и изоляции**. Как только несколько агентов параллельно работают по разным задачам, вам нужны worktree isolation, ownership per slot, file-level locking policy, deterministic merge policy и отдельные scratch-области на каждый run/stage. Это особенно важно, потому что в Forgejo Actions jobs по умолчанию независимы, а значит “параллельность по умолчанию” — обычный сценарий. В ForgePlan ecosystem есть аналогичный образ мысли: brownfield-pack строится как composition существующих extractor-компонентов через mappings/playbooks, а не как shared mutable workspace; BMAD и другие методологии надстраивают fail-closed gates. Ваш текущий замысел про параллельность правильный, но ему не хватает технического контракта. citeturn5search6turn21search0turn25search0

Пятый недодуманный слой — **безопасность и trust boundaries**. Forgejo документация отдельно предупреждает, что `pull_request_target` выполняется в контексте target branch с write-capable token и доступом к secrets, поэтому взаимодействие с untrusted PR code опасно; для обычного `pull_request` write permissions у токена, наоборот, урезаны. Если ForgeFarm будет автоматически запускать код, собирать PR и делать merge, вам нужен четкий security split: untrusted code only in sandboxes/worktrees; merge — только через orchestrator with verified gates; workflow secrets — только в trusted branches/jobs. Иначе система будет удобной, но опасной. citeturn5search4turn5search5turn5search7

Шестой пробел — **память пока задумана слишком общо**. ForgePlan уже имеет локальный semantic search и derived LanceDB workspace, а marketplace документирует Hindsight как cross-session memory plugin; LangGraph хранит short-term memory через thread-scoped checkpoints; Mem0 специально разделяет память на слои, чтобы не смешивать текущее, сессионное и долгосрочное. Если просто “подрубить память”, получится слив всего подряд в один retrieval pool. Для вашей системы это нужно разрезать как минимум на operational state, episodic decisions, semantic retrieval и graph memory, иначе агент будет либо забывать важное, либо тащить мусор в контекст. citeturn3view5turn16search0turn14search12turn15search5turn15search17

## Продуктовая модель ForgeFarm

С продуктовой точки зрения ForgeFarm должен быть **не chatbot и не очередной task board**, а **control tower для AI-native delivery**. Это означает, что главная сущность для пользователя — не отдельный prompt, а **run**: кто взял задачу, на основании каких артефактов, какими агентами, через какие уровни, с какими проверками, почему задачу можно или нельзя merge’ить, сколько стоило выполнение и где оно застряло. Такой UI хорошо стыкуется с тем, куда уже смотрит ForgePlan ecosystem: `@forgeplan/web` описан как viewer с time-travel, artifact graph и health dashboard, а LangGraph frontend SDK стримит node outputs, token streams и subgraph discovery в реактивный UI, который можно naturally отображать как run inspector и lane cards. citeturn19view0turn21search0turn14search7turn14search20

На уровне продукта я бы разделил интерфейс на четыре поверхности. Первая — **Portfolio Board**, где пользователь видит эпики, задачи, blocked edges и прогресс по lane’ам. Вторая — **Run Inspector**, где в реальном времени видно, какой именно граф сейчас исполняется, какие subagents активны, какие tool calls были сделаны и где возник failure. Третья — **Artifact Explorer**, где живет time-travel/graph/health и откуда можно переходить в PRD, RFC, ADR, Evidence. Четвертая — **Operations View**, где видно throughput, retry rate, model pool utilization, latency, cost и policy failures. Это не произвольный набор: Mastra и VoltAgent обе подчеркивают observability как first-class runtime-слой, а LangSmith и OpenTelemetry дают понятную практику трассировки и анализа таких систем в production. citeturn22search2turn22search7turn23search0turn23search4turn29search6

Объектная модель ForgeFarm должна быть минимально двуслойной. **Issue** — это внешний task object в Forgejo. **Artifact** — это ForgePlan object в git. **Run** — это execution object в ForgeFarm. Между ними нужны жесткие ссылки: `Issue -> planned_by -> PRD/RFC/ADR`, `Run -> executes -> Issue`, `Run -> reads -> Artifact[]`, `Run -> produces -> branch/PR/evidence`, `VerifierRun -> assesses -> Run`. Тогда issue-board остается полезным для backlog management, но реальное агентное выполнение уже не размазывается по комментариям, labels и ad-hoc статусам. Forgejo умеет issues, assignees, milestones, dependencies и projects; ForgePlan умеет links, health, validation и evidence; ForgeFarm должен связать их, а не смешать. citeturn6search1turn10view0turn16search3turn4search4

Уровни `L0–L3` стоит закрепить формально, иначе они останутся только красивой метафорой. Я рекомендую такую модель. **L0** — scope and decision: route/decompose/PRD/RFC/ADR, сильные reasoning-модели, минимальная параллельность, обязательный generator≠verifier, human checkpoint на high-risk decisions. **L1** — planning and dependency control: task DAG, grouping, wave planning, skill/composition selection, capacity calculation, merge strategy. **L2** — implementation: code agents в изолированных worktrees, tool-rich execution, тесты, линтеры, code edits. **L3** — proof and closure: review, evidence, health/validate/activate gates, PR assembly, merge, retrospective memory writeback. Этот разрез очень хорошо ложится на ForgePlan lifecycle, marketplace master orchestration и технические возможности graph runtimes с subgraphs/interrupts/checkpoints. citeturn3view4turn20search1turn14search0turn14search15turn14search14

## Референсная архитектура ForgeFarm

В техническом смысле ForgeFarm лучше всего представить как шесть связных подсистем. **Ingress Layer** получает webhooks из Forgejo, при необходимости добирает данные через REST API, а также слушает ручные команды из UI. Forgejo официально поддерживает repository/org/system webhooks, token/bearer auth и paginated API; это делает его хорошим event source и system of record для задач. citeturn5search2turn6search2

**Artifact Gateway** должен работать только через нативный контракт ForgePlan: CLI и MCP, а не через прямые записи в derived storage. Это критично, потому что ForgePlan сам позиционирует markdown/project artifacts как authoritative trail, а LanceDB выступает derived storage/index inside workspace. Значит, ForgeFarm не должен “умничать” и писать в какие-то внутренние БД ForgePlan; он должен создавать и обновлять артефакты только через разрешенные artifact operations, а потом прогонять `validate`, `health`, `review` и `activate`-совместимые проверки. citeturn4search5turn4search6turn4search1turn4search4turn16search3

**Workflow Kernel** я бы делал на LangGraph.js. Причина не в хайпе, а в точном совпадении с вашей задачей: LangGraph — это низкоуровневый orchestration runtime для долгоживущих, stateful agent workflows; у него есть `StateGraph`, reducer-based shared state для fan-out/fan-in, subgraphs, streaming, interrupts для human-in-the-loop, time-travel и checkpoint backends для SQLite/Postgres/Mongo. Более того, frontend SDK умеет реактивно стримить node outputs и subgraphs в UI. Для real-time control tower это прямо в точку. citeturn14search0turn14search4turn14search15turn14search20turn14search14turn14search25turn14search1turn14search7

**Capacity and Queue Layer** поверх LangGraph я бы не пытался строить вручную на чистом event loop. Нужен отдельный конкурентный диспетчер для model pools, per-repo concurrency и rate limiting внешних API. Для этого из легких вариантов хорошо подходит BullMQ: у него есть flows, rate limiting, dedup/throttle и нормальная Redis-база для распределенной очереди. Если позже окажется, что вам нужны многосуточные бизнес-workflow’ы с сильной saga/compensation semantics между сервисами, тогда можно вынести outer shell в Temporal или Inngest; оба официально продают durable execution как first-class abstraction, но это уже следующий уровень сложности. Для v1 ForgeFarm, где LangGraph уже покрывает checkpoints/interrupts/time-travel, BullMQ обычно выгоднее по сложности-выхлопу. citeturn24search20turn24search2turn24search8turn24search3turn24search6turn24search4turn24search7

**Run Store** я бы делал на Postgres. Он должен хранить run metadata, state snapshots, issue-artifact-run links, queue claims, budgets, retry classes и human approvals. Для semantic retrieval туда же можно добавить `pgvector`, который позволяет хранить векторы и делать similarity search прямо в Postgres. Это особенно удобно, если вы хотите держать operational metadata, memory summaries и embeddings в одной транзакционной системе, а не плодить пять разных хранилищ на старте. citeturn28search0turn28search18

**Observability Layer** должен быть vendor-neutral снизу и opinionated сверху. Снизу — OpenTelemetry для traces/metrics/logs и GenAI semantic conventions; сверху — либо собственный UI, либо LangSmith/Mastra/VoltOps в зависимости от выбранного фреймворка. OpenTelemetry JS официально поддерживает traces и metrics в Node.js, а GenAI semantic conventions уже стандартизируют model calls, token counts и related AI telemetry. LangSmith хорошо встраивается в LangGraph/LangChain и дает observability плюс evaluation lifecycle. citeturn29search0turn29search1turn29search2turn29search5turn23search8turn23search0turn23search9

## Какие библиотеки и стеки я рекомендую

### Базовый стек для ядра

Если выбирать один стек под ForgeFarm v1, я бы выбрал **LangGraph.js + LangChain JS + BullMQ + Postgres/pgvector + OpenTelemetry + ForgePlan CLI/MCP + Forgejo API/webhooks**. LangGraph нужен как ядро orchestration state machine; LangChain JS — как библиотека для tool-using agents и model adapters; BullMQ — как capacity/rate-limiting layer; Postgres/pgvector — как run-store и basic semantic memory; ForgePlan — как artifact/methodology engine; Forgejo — как issue/project/PR surface. Эта сборка максимально согласована с вашей TypeScript-ориентацией и при этом не пытается заменить то, что ForgePlan уже делает хорошо. citeturn14search0turn15search8turn24search8turn24search2turn28search0turn4search5turn6search2turn5search2

Почему не “просто LangChain”? Потому что сами LangChain docs прямо разводят роли: `create_agent` подходит как configurable harness, **а для advanced needs, combining deterministic and agentic workflows, они рекомендуют LangGraph**. Ваш случай — именно advanced orchestration: уровни, очереди, fan-out/fan-in, verifier separation, interrupts, time travel, run replay, UI streaming. Простой agent harness здесь маловат. citeturn14search6turn15search4

### Где здесь место Deep Agents

**Deep Agents** я не ставил бы в центр системы, но охотно использовал бы внутри уровней `L1/L2` как **task-local worker abstraction**. Официальные docs подают Deep Agents как самый легкий путь к planning, filesystem context management, subagent spawning и long-term memory; отдельный `dcode` уже показывает, как этот SDK работает как coding agent с persistent memory, skills и approval controls. Это очень хорошо для “внутреннего работника” на конкретной задаче. Но как верхнеуровневый управляющий runtime для всего ForgeFarm Deep Agents слишком opinionated: вам нужен внешний state machine с board sync, policy gates, failure taxonomy и capacity-aware scheduling. Поэтому Deep Agents — да, но **как вложенный execution primitive, а не как мозг всей фермы**. Это вывод по архитектуре, но он хорошо согласуется с тем, как сам продукт позиционируется в документации. citeturn15search0turn15search12turn15search16

### Когда разумен Mastra

**Mastra** сегодня выглядит очень сильным кандидатом для команд, которым важен быстрый TypeScript DX и all-in-one слой: agents, workflows, networks, memory и observability в одной экосистеме. У него есть workflows с branching/parallel execution/resource suspension, networks для координации agents/workflows/tools, memory с semantic recall, working memory и observational memory, плюс неплохая observability story на traces/logs/metrics. Для внутреннего AI-продукта, где хочется быстро получить product-like experience, Mastra реально удобен. citeturn22search0turn13search6turn22search1turn22search14turn22search8turn22search2

Но для ForgeFarm я все равно не дал бы ему первенство над LangGraph.js. Причина простая: ForgeFarm нужен **не просто framework “для агентов и workflows”**, а язык для очень явного описания управляемого stateful orchestration. LangGraph в этом смысле ниже уровнем и ближе к “execution kernel”, что для вашего сценария полезнее. Mastra я вижу либо как быстрый прототип UI/control plane, либо как stack для отдельных product surfaces, но не как лучшее ядро для hard-mode orchestration. Это инженерный вывод, основанный на различии уровней абстракции в самих docs. citeturn13search0turn22search0turn14search0

### Когда разумен VoltAgent

**VoltAgent** интересен тем, что он тоже TypeScript-first, делает упор на multi-agent workflows, memory, pause/resume и observability через VoltOps. Для команды, которой нужна высокая разработческая скорость и сильный встроенный trace/debug UX, это приятный вариант. Но есть один важный нюанс: официальные docs прямо помечают Workflows API как preview. Для платформенного ядра, где вы хотите строить long-lived orchestration system с жесткими договорами совместимости, это заметный минус. citeturn22search10turn22search22turn13search5turn22search7

Мой практический вывод такой: VoltAgent хорош как **research/prototyping contender** или как stack для изолированных команд/сервисов, но **не как базовый execution kernel ForgeFarm v1**. Слишком высок риск, что вы завяжете архитектурное ядро на слой, который еще сам стабилизирует workflow semantics. Это не упрек библиотеке; просто у вас слишком “несущая” задача для preview-grade workflow core. citeturn22search22turn22search10

### Память и RAG

По памяти я бы делал **слоистую модель**, а не один “memory service”. Короткоживущая operational memory уже естественно живет у LangGraph в thread-scoped checkpoints. Проектная decision memory уже есть у ForgePlan через git-tracked artifacts, links, health и evidence. Cross-session working memory можно строить поверх Hindsight-подобного слоя из ForgePlan ecosystem или Mem0, который прямо предлагает layered memory model. Это три разных типа памяти, и их не надо склеивать в один индекс. citeturn14search12turn16search0turn15search5turn15search17

Для retrieval я бы начинал максимально прагматично. Сначала — **ForgePlan local semantic search** по артефактам и derived indices; затем — project-level semantic store на `pgvector` или Qdrant для summaries, code chunks и run retrospectives; уже потом — graph-enhanced retrieval. Здесь важно не перепрыгнуть через этапы. Microsoft GraphRAG — это модульный graph-based retrieval pipeline для извлечения структурированных knowledge graph данных из unstructured corpora; LightRAG — более легкий graph-enhanced RAG, который комбинирует graph и vector layers и уже поставляет API/WebUI и offline deployment docs. Это полезные системы, но они оправданы тогда, когда вам действительно нужно reasoning over relationships across many documents, а не просто “найти релевантный ADR или task note”. citeturn15search2turn15search6turn15search10turn15search3turn15search7turn15search11turn15search15

Мой практический выбор для ForgeFarm: **v1 — ForgePlan search + pgvector + episodic memory summaries; v2 — LightRAG для project corpus; GraphRAG — только если вы выходите на organization-wide knowledge graph questions**. Это позволит не перегрузить первую версию research-heavy инфраструктурой, сохранив понятный путь роста. citeturn3view5turn28search0turn15search5turn15search3turn15search2

## План реализации ForgeFarm

Сначала я бы сделал **foundation release**, где нет “магии”, зато есть все контракты. Нужны: Forgejo webhook ingestion, OAuth/token handling, issue templates и label taxonomy, явная state machine для runs, Postgres schema для `issues / artifacts / runs / worktrees / review_runs / approvals / budgets`, minimal UI board и minimal run inspector. На этом этапе нельзя писать код генераторами без жёсткого отделения tracker state от run state; иначе вы сразу попадете в проблему “status drift” между board и runtime. Forgejo уже дает все базовые primitives для tasks, projects, API и actions, а ForgePlan — для artifact lifecycle и CI gates. На foundation этапе задача не в интеллекте, а в **контракте системы**. citeturn6search1turn10view0turn6search2turn4search4turn16search3

Во втором этапе я бы делал **L0/L1 planning kernel**. Здесь появляется LangGraph state graph, decomposer, dependency planner, issue-to-artifact linker, route selector и approval interrupts. На этом же этапе нужно ввести policy: какие задачи имеют право стартовать без человека, а какие требуют явного approve/resume. LangGraph interrupts как раз рассчитаны на indefinite wait с сохранением state, а time-travel/checkpoints дадут воспроизводимость и replay при спорных решениях. citeturn14search14turn14search25turn14search20

Третий этап — **L2 implementation fabric**. Здесь появляются worktree manager, code agents, tool sandboxing, per-agent quotas, BullMQ queues, verifier agents и merge-preparation. На этом же этапе имеет смысл подключить LangChain/Deep Agents для task-local execution. Важно, чтобы каждый coding run имел парный verifier run и чтобы merge был доступен только после machine-readable ready verdict. Здесь же надо встроить ForgePlan lifecycle hooks: перед кодом — artifact readiness; после кода — evidence + validate/health. citeturn15search8turn15search0turn24search2turn24search20turn4search4turn16search3

Четвертый этап — **L3 proof, merge and learning**. Это review orchestration, evidence synthesis, PR body generation, merge policies, retrospective summarization и writeback в episodic memory. Если этого не сделать, у вас получится красивая autonomous coding farm без памяти о том, *почему* она приняла решение и *что* надо учитывать в следующем run. ForgePlan здесь особенно полезен, потому что его модель уже требует evidence и не дает “тихо протухать” решениям: `health` подсвечивает blind spots, stale, orphans и at risk artifacts. citeturn16search3turn4search2

Пятый этап — **observability and evals as product**, не как “доделка потом”. Здесь нужны OTel traces, cost metrics, per-level throughput, failure taxonomy dashboards, offline replay, golden tasks и judge/eval pipelines. LangSmith официально покрывает observability и evaluation lifecycle, а OpenTelemetry дает общий язык трассировки и GenAI telemetry. Для ForgeFarm это не nice-to-have: без этого вы не сможете управлять качеством оркестрации, а только смотреть на красивые анимации агентов. citeturn23search0turn23search9turn23search5turn29search6turn29search2

## Как встроить ваш полный marketplace-запрос про map-pack

Ваш запрос на **полный `forgeplan-map-pack`** по сути очень удачно подсвечивает, каким **должен быть весь ForgeFarm в миниатюре**. В нем уже есть правильные паттерны: orchestrator ничего не пишет сам; генератор отделен от верификатора; parallel scanners пишут в разные scratch targets; есть single writer `map-emitter`; есть deterministic guardian script отдельно от advisory LLM; есть fail-closed write gates; есть loop with max retries. Это практически идеальный вертикальный slice для ForgeFarm, потому что он проверяет сразу и orchestration, и isolation, и deterministic output, и policy gates. Кроме того, идея зеркалить brownfield-pack логична: официальный brownfield-pack в ecosytem сам построен как composition existing plugins/extractors через mapping YAMLs и playbook recipes вместо переизобретения extraction runtime. citeturn21search0turn25search0

Но в текущем описании map-pack я вижу несколько мест, которые обязательно надо допродумать перед реализацией. Во-первых, **ID стратегия `sha1(kind + ':' + path)[:12]` слишком хрупкая для rename/move сценариев**. Для карты это удобно на старте, но при рефакторинге пути будут меняться чаще, чем сущность узла. Я бы оставил path-based ID как initial deterministic seed для first emit, но ввел бы отдельную `lineage`/`supersedes` модель и `stable_node_key`, чтобы rename не выглядел как delete+create без истории. Иначе incremental append mode быстро начнет генерировать ложные “новые ноды”. Это уже инженерный вывод, но он прямо вытекает из ваших требований на append-only refresh и byte-identical reruns. 

Во-вторых, **вам нужна не просто atomic tmp-rename, а целая детерминизационная спецификация сериализации**. Для `map.json` должны быть зафиксированы: порядок массивов, порядок ключей, UTF-8 LF line endings, locale/timezone independence, normalization путей, сортировка по stable key, исключение run-specific metadata из финального файла. Иначе требование “re-run после +1 ноды — позиции байт-идентичны” не выдержит даже разных машин и сред выполнения. Это место почти всегда недооценивают, а для вашего acceptance оно несущeе.

В-третьих, **вам надо формализовать G1–G4 как machine-verifiable gates**, а не хранить их как идеи в голове. Я бы делал так. `G1`: snapshot locked — все scanners завершили работу, входные хэши и версии артефактов зафиксированы. `G2`: topology valid — node/zone extraction детерминирована, schema проходит, collision-free IDs. `G3`: trust-valid edges — high-trust graph edges подтверждены, grep-derived edges без `verified_by` дропнуты или помечены как concerns. `G4`: emitter/guardian finality — single writer создал candidate, deterministic guardian script дал PASS, flip в `confirmed` выполнен атомарно. Тогда loop и fail queue уже могут работать с понятной причиной отказа, а не с общим “map build failed”.

В-четвертых, **scratch contract надо ужесточить до per-run namespace**, а не просто `.work/.scan.code.json` и похожих имен. Я бы делал формат вроде `.work/runs/<runId>/scan/code.json`, `.work/runs/<runId>/scan/fpl.json`, `.work/runs/<runId>/scan/docs.json`, плюс отдельный `latest` symlink/index если нужно удобство. Иначе параллельные map-build runs начнут конфликтовать между собой, даже если внутри одного run сканеры уже разнесены по файлам. Ваше требование “параллельные сканеры пишут РАЗНЫЕ файлы” должно выполняться не только внутри одного orchestration cycle, но и между двумя concurrent cycles.

В-пятых, **append-only режим требует модели tombstones и supersession**, иначе “refresh --scope <zone>” не сможет корректно отражать удаленные/перемещенные сущности. Если вы хотите по-настоящему append-oriented evolution, то нужно либо хранить history log рядом с current view, либо иметь явные `status: active|superseded|deleted` записи с lineage pointers. Просто перегенерировать куски `map.json` недостаточно, если вы при этом обещаете историю и determinism.

Мой итог по map-pack такой: **это отличный первый flagship composition для ForgeFarm**, но его надо делать не как разовый “умный агент”, а как строго описанный pipeline в духе brownfield-pack: `schemas/`, `playbooks/`, `skills/`, `hooks/`, deterministic script guardians и один LangGraph/queue runtime, который лишь исполняет эту композицию. Тогда вы получите не только `map-build`, но и референсный шаблон для будущих ForgeFarm compositions — `spec-build`, `review-pack`, `evidence-pack`, `release-pack`. Это и есть правильный способ вырастить платформу, а не очередной набор prompt-скриптов. citeturn21search0turn25search0turn14search15turn14search20

## Итоговая рекомендация

Если свести все к одному решению, то я рекомендую строить ForgeFarm так: **ForgePlan остается ядром артефактов и методологии; Forgejo остается системой задач, досок, PR и событий; ForgeFarm становится отдельным TypeScript control plane, построенным вокруг LangGraph.js как orchestration kernel, BullMQ как capacity layer, Postgres/pgvector как run/memory store, OpenTelemetry как telemetry backbone и опционального LangSmith как eval/trace surface**. Память надо делать слоистой, а GraphRAG/LightRAG подключать только после того, как обычный semantic retrieval перестанет вытягивать product questions. citeturn3view4turn10view0turn14search0turn24search8turn28search0turn29search6turn23search0turn15search2turn15search3

Самая важная мысль: **не стройте “систему агентов”, стройте “систему контрактов вокруг агентов”**. В вашем контексте победит не тот стек, где агент красивее пишет код, а тот, где лучше определены source of truth, gates, run states, worktree ownership, verifier independence, observability и memory boundaries. У вас уже есть очень сильная база в ForgePlan ecosystem; теперь нужно не заменить ее, а дисциплинированно надстроить над ней execution plane, который умеет мыслить уровнями `L0–L3`, объяснять свои действия и воспроизводимо доводить задачу от issue до доказанного merge. citeturn20search1turn16search3turn14search23turn23search4turn29search5
