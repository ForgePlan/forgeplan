# ForgePlan × Референс A: проверка идей и рекомендуемое усиление

**Актуальный вывод после уточнения владельца:** проектировать полноценное аналитическое ядро ForgePlan на Rust, связывающее решения, код, поведение, межрепозиторные контракты и реальные проверки. Делить на этапы реализацию, а не заранее урезать целевой продукт до адаптера или пилота. Готовые анализаторы, библиотечные компоненты и пилоты помогают проверять эту архитектуру; не заменяют её. Технические механизмы остаются предложениями, не утверждённым RFC.

Это исследование, не утверждённый RFC и не разрешение на реализацию. Оно заменяет прежнюю версию аудита, в которой были фактические ошибки. Все 34 предложения сохранены в реестре ниже; исходная переписка — [dialog.txt](dialog.txt), тематический архив — [roadmap](forgeplan-research-roadmap.md).

## 2. Референс A оказался серьёзнее, чем его описывал диалог

### Реализация и объём

Это Python ≥3.11, Tree-sitter 0.25.2 с закреплёнными грамматиками, PyYAML; Python анализируется через `ast`, Pascal — отдельным разбором. В manifests нет обязательной графовой БД, embedding-модели или LLM SDK. В registry **10 языковых адаптеров**; Rails/Laravel/Flutter — не дополнительные языки. Признание расширения `.vue`/`.svelte` архитектурной эвристикой не равно полноценному анализатору этого языка.

Инвентаризация Git tree даёт **108 Python-файлов / 1 584 617 байт** основной реализации в непересекающихся группах `src/Референс A/*.py`, непосредственные `scripts/*.py`, `scripts/architecture/**/*.py`, `scripts/lang/**/*.py`. С отдельным HTTP-пакетом — 113 файлов / 1 608 745 байт; тесты, assets и benchmarks исключены. Это размер исходного текста, не LOC или оценка трудозатрат. Перенос Референс A — не перенос нескольких `.scm`-правил.

Источники: manifest (A-01), language registry (A-02), полный Git tree (A-03).

### Что действительно стоит взять

1. **Объяснимый impact.** Не просто список файлов, а путь зависимости, причина включения и «что читать первым». Отдельный запрос usages возвращает использования символа и координаты.
2. **Разные виды фактов.** Импорт, использование определения, эвристическая связь, архитектурное нарушение и вызов — не взаимозаменяемые рёбра.
3. **Явная политика поверх наблюдений.** Автоопределение слоёв предлагает гипотезу; конфигурация задаёт правило. `boundaries --strict` различает `pass / fail / incomplete / error`.
4. **Версия и происхождение результата.** `built-from`, digest, clean Git revision, версия извлекателя; для ForgePlan дополнительно нужен полный fingerprint настроек разрешения и проверяемого рабочего дерева.
5. **Актуальность с учётом гонок.** Изменения, пришедшие во время пересчёта, не должны пропасть при очистке dirty-state.
6. **Проверяемые пограничные случаи.** Реэкспорты, циклы alias, shadowing, Cargo renames, `#[path]`, glob imports, неизвестный тип receiver.

Источники: query contracts и impact (A-04), architecture strict (A-05), freshness (A-06), symbol tests (A-07).

### Что исправляет прежнее мнение о TypeScript

В текущем коде есть named/default/namespace imports, `export *`, `export { X as Y }`, `export * as ns`, цепочки реэкспортов и защита от циклов. Тест прямо различает symbol usage через barrel и module-level dependency: успешное разрешение определения не обязано добавлять прямое import-edge через промежуточный файл.

Следовательно, **«Референс A провалился на TS из-за barrels» не подтверждено**. Не подтверждено и обратное «TS разрешается полностью»: нелитеральные dynamic imports, условные package exports и type inference имеют ограничения. Тесты прочитаны, не выполнены. Источники: TS bindings (A-08), barrel assertions (A-07), dynamic import extraction (A-09).

Rust-поддержка включает Cargo roots/renames, `mod.rs`, inline modules, `pub use`, часть associated members и macro names. Это не rust-analyzer: распознавание макроса не является expansion, `cfg_attr` может давать несколько кандидатов, trait dispatch требует знания типов. Источники: Rust module layout (A-10), Definers limitations (A-11).

### Где нельзя доверять названию ребра

| Факт Референс A | Что установлено по реализации | Как использовать в ForgePlan |
|---|---|---|
| `imports` / `refs` | Локальная зависимость / ссылка; возможны candidate и type-only | Для навигации и списка кандидатов на проверку |
| `calls-api` | `implements`/`extends`/base type | Не выдавать за сетевой вызов или runtime trace |
| `data-flow :validation-module` | Импортируемый модуль содержит распознанный валидатор | Не утверждать, что данные действительно прошли валидацию |
| `http-calls` | Эвристика имён `*Client`/`*Remote` и другого репозитория | Только гипотеза межсервисной связи |
| `calls` | LSP call hierarchy либо специальное разрешение dispatch | Сохранять источник и ограничения метода получения |

Источники: edge construction (A-12), HTTP heuristic (A-13).

Unknown coverage неполна: некоторые неразрешённые импорты просто не становятся рёбрами; часть Rust diagnostics остаётся в логе. `pass` архитектурных проверок относится к охвату частей/файлов политики, не к полноте семантического разрешения. **Пустой граф нельзя трактовать как доказанную независимость.**

Обновление — hooks + stat-проверки + lazy refresh, не универсальный watcher. Hook не блокирует действие агента. Partial graph update ограничен Python/TS; Rust может требовать более широкого обновления. При сохранённых размере и mtime внешняя правка потенциально не обнаруживается stat-проверкой; это вывод по алгоритму, не воспроизведённый сбой. Parse cache при сборке отдельно использует content hash. Источники: freshness (A-06), partial update (A-14).

### Встраивать или использовать рядом

**Рекомендация:** сначала использовать Референс A рядом с LSP/ast-grep. Для машинной интеграции — ограниченный адаптер публичного JSON/CLI/MCP-контракта с закреплённой версией. Собственный Rust extractor оправдан, если измеренная точность, автономная поставка или требования к доказательствам не закрываются внешним инструментом.

Цена внешнего адаптера: Python runtime, второй индекс, совместимость формата и version pin. Цена собственного: разрешение языковых конструкций, инвалидация отрицательных ответов, миграции идентичности, конфигурации сборки и сопровождение grammars. Нельзя обещать то же качество, просто переписав обход Tree-sitter на Rust.

MIT допускает повторное использование кода, но при копировании существенных частей нужно сохранить copyright/permission notice; сторонние assets имеют отдельные notices. Установка hooks меняет настройки клиента, optional LSP запускает процесс в проекте. Эти действия требуют отдельной политики доверия; local-first не означает отсутствие побочных эффектов. В исследованном plugin executable pin отличается от HEAD plugin — фиксировать именно исполняемую ревизию. Источники: license (A-15), plugin manifest (A-16), LSP initialization (A-17).

## 3. Что на самом деле показывают бенчмарки

Отчёт Референс A impact benchmark (A-18) относится к **0.10.0**, build timing — к **0.2.3**, а прочитанный код — **0.16.0**. Задача: найти файловые зависимости на глубине два, не исправить баг или доказать совместимость поведения.

| Метрика из отчёта авторов | Результат | Ограничение |
|---|---|---|
| 100 impact-запросов | 100/100 по критерию, допускающему accepted extras; 90/100 при строгом равенстве | В 10 ответах суммарно 19 допустимых дополнительных файлов |
| 55 агентных вопросов | Полные ответы 55/55 с Референс A, 48/55 без него | Одна модель/настройка, по одному прогону на вопрос |
| Средние total tokens | 67 579 с Референс A против 98 800 без него | Парное среднее −32%; не универсальные −80–85% |
| Стоимость по отчёту | В среднем −38% | Цена зависит от модели, cache, повторов и качества ответа |
| Распределение экономии | Меньше токенов в 30 случаях, больше в 25 | Среднее скрывает проигравшие задачи |
| TS chrome-devtools / публичный репозиторий демо-карты | +13% / +26% токенов | Это расход, а не доказательство ошибок barrels |
| Rust agent-browser / compiler; Python FastAPI | −67% / −32%; +43% токенов | Язык сам по себе не определяет пользу |

Reference resolvers написаны отдельно от production extractor, но теми же авторами: независимость реализации не равна независимому исследованию. Выборка отбирает файлы с входящими зависимостями. Baseline частично перескорен после расширения reference; граф для агентных задач уже построен. Цифры «тысячи раз меньше контекста» сравнивают другие объекты, не итоговый счёт агента. Смешивать их нельзя.

Для ForgePlan нужен собственный парный эксперимент: одинаковая задача/модель/лимиты; текущий ForgePlan+tgrep/LSP против того же набора с Референс A, затем с новым мостом решение↔код. Измерять успешность задачи и пропущенные необходимые изменения, ложные тревоги, время ревью, tokens/cache/cost, время построения и обновления индекса. Повторять прогоны и публиковать разброс, а не лучший пример. Corpus pinning и небольшие fixtures предпочтительнее бесконтрольного копирования целых чужих репозиториев в Git.

## 4. Кейс Bun: подтверждён, но вывод из него другой

[Первичный отчёт Bun][bun] подтверждает перенос 535 496 строк Zig, 11 дней до merge, 6 778 commits и до 64 параллельных Claude. Автор раскрывает работу в Anthropic и использование pre-release модели. До merge заявлены 5,9 млрд uncached input, 72 млрд cached input reads, 690 млн output; оценка около $165 000 по API-ценам.

Доля cached input составляет около 92,4% от input, а не обещание скидки 92,4% на весь проект. Выходные токены, cache writes и ревью тоже стоят денег. Детерминированная выдача ForgePlan помогает только если клиент сохраняет весь подходящий префикс; один ответ MCP не управляет всей историей клиента. [OpenAI caching][cache] прямо требует совпадения префикса и задаёт условия по модели/длине/сроку жизни.

Что переносить:
- руководство механического переноса и проверку противоречий до массового кодирования;
- маленький пилот на трёх файлах;
- автор и ревьюеры в разных контекстах, проверку поведения, запрет «починить компиляцию заглушками»;
- разделение переноса и последующего идиоматического рефакторинга;
- изоляцию ресурсов, владение файлами, отдельные стадии compiler → linker → запуск → тесты → платформы.

Что не переносить как универсальную норму: ровно четыре роли для любой задачи, фиксированный множитель стоимости 4×, массовую работу в общем дереве и обещание безопасного all-at-once rewrite. Автор выбрал полную перепись в условиях Bun; Strangler Fig для чужого легаси — другое решение, не вывод из этого кейса.

Главная оговорка отчёта: **19 известных регрессий**, несмотря на прошедший существующий набор тестов. Например, побочный эффект внутри `debug_assert!` исчезал в release. Даже большой независимый от языка тестовый набор не покрывает всё; AST-граф и высокий R_eff тем более не доказывают паритет.

Все пути ниже относительно корня ForgePlan; line references относятся к прочитанному дереву.

Не все search-пути одинаковы: read-profile federation — lexical, forced CLI semantic имеет собственные ошибки, full MCP — свои semantic/fallback ветви. Смена ranking требует relevance-тестов, смена backend — сохранения этого контракта либо отдельного решения о его изменении.

Snapshot читает **локальные Git objects** без lazy fetch. Lockfile не содержит тела артефактов и не даёт CI удалённые исходники «бесплатно»: их надо заранее доставить. Live source identity зависит от canonical path; snapshot identity — от checkout path вместе с OID. Переносимый lock/bundle должен явно решить адресацию между машинами, а не просто сменить YAML на JSON.

Issue [#303][i303] закрыт с описанием per-call workspace resolver. Startup maintenance target и workspace запроса различаются; `current_dir()` как последний fallback не доказывает старый баг. [#305][i305] также закрыт. Предыдущая рекомендация «вылечить оба через SQLite» была необоснованной.

### Найденные проблемы существующего контракта

1. **Dispatch и параллельные владельцы.** Проверяется только выбранный bucket, хотя buckets относятся к разным агентам. Две задачи с одинаковым file set могут уйти разным агентам. Это уже открытый [#548][i548]; исходники `dispatch/mod.rs:443-480`, тест `580-611` признаёт случай и проверяет сериализацию на одном агенте. Нового runtime-прогона не было. Добавление AST не исправит алгоритм назначения.
2. **Drift и YAML.** `drift/mod.rs:57-89` использует body, а MCP советует добавить YAML `affected_files`. Создан [#577][i577] с четырьмя критериями проверки; не дубликат закрытого #293 про таблицы. Предложение: единый контракт извлечения, а не миграция СУБД. Пересмотреть при изменении extractor/ArtifactRecord.
3. **Snapshot persistence.** `snapshot.rs:83-101` обещает atomic write, но делает `fs::write` прямо в destination. Создан [#578][i578], отдельно атомарная видимость и crash durability. Это риск частичного файла по реализации, не воспроизведённая потеря данных; не относится автоматически к CURRENT publisher. Пересмотреть при изменении writer/контракта persistence.

Дополнительно drift использует Git history после `created_at`, не незакоммиченные изменения и не AST; ошибка основного Git probe даёт пустой список (`drift/mod.rs:98-127`). Пустой результат поэтому нельзя превращать в доказательство отсутствия изменений. Это ограничение следует включить в проектирование нового drift-контракта.

### Web — не пустое место

В локальном ForgePlanWeb `DependencyGraph.svelte` импортирует Force/Tree/Radial/Matrix/Lanes/Sankey/Sunburst/Idef0/ComposedMap. Это уже не исходные «пять видов». `ForceView.svelte:3-15,589` использует d3-force и SVG; `shared/api/poller.svelte.ts:4,21-24` задаёт default polling 10 секунд с возможностью override.

Перед выделением общего UI-пакета нужно инвентаризировать реальные зависимости и сценарии. SSE не является prerequisite codegraph; переход оправдан измеренной задержкой/нагрузкой. Десктоп даёт локальные файлы и editor links, но не превращает архитектурную эвристику в доказательство.

## 6. Опасные подмены в исходном дизайне

### Граф кандидатов — не доказательство поведения

- Tree-sitter строит устойчивое к ошибкам **синтаксическое дерево**, а не полную семантику типов и вызовов. Его runtime — C11; Rust bindings не делают сборку «без C toolchain». Источник: [Tree-sitter][treesitter].
- Связь test→function не доказывает, что тест исполнился и проверил нужный результат. Изменение сигнатуры не обязательно ломает контракт; неизменная сигнатура может менять поведение.
- Отсутствие входящих рёбер не разрешает удаление: возможны внешние потребители, reflection, routes, plugins. Большой fan-in — один сигнал риска; критичный leaf тоже может быть опасен.
- Количество FR не должно сравниваться с количеством `if`/branches. Нужно связать конкретные варианты поведения с проверками и явными решениями: сохранён / намеренно изменён / недостижим / неизвестен.
- SCC помогает увидеть циклы, но не выбирает границу транзакции, владельца данных и бизнес-смысл. Leaf-first — эвристика, не универсальный план миграции.
- Автоматически придуманные новой моделью fixtures не являются независимым эталоном старой системы. Нужны наблюдения старого поведения, контролируемые время/случайность/состояние и сравнение outputs, ошибок и побочных эффектов.
- BLAKE3 digest обнаруживает изменение байтов, но **не удостоверяет автора**. Подпись, доверенный signer и привязка к ревизии — отдельный контракт.

### SQLite: разумный кандидат, но отдельное решение

SQLite может уменьшить сложность поставки, но это гипотеза до измерения сборки/размера/поиска/восстановления. WAL допускает читателя со старым snapshot и только одного writer; он не исправляет автоматически lifetime handles. Источник: [SQLite isolation][sqlite-isolation].

`PRAGMA user_version` — версия схемы, не протокол публикации. Удалять открытый `.db` при обновлении — плохой контракт. Восстанавливаемую проекцию нужно строить отдельно и публиковать после проверки, учитывая открытых читателей и сбой. Review decisions, locked baselines, code links и принятые исключения должны иметь долговечный канонический источник вне сбрасываемого кэша.

Рефакторинг backend может сохранить identity/reconcile/federation/public DTO и заменить физическое хранение/versioned reads. Обе крайности неверны: «добавить SQLiteDriver и готово» и «обязательно переписать весь Constellation».

В SQL/Rust-эскизах диалога есть незакрытые контракты: embedding profile/dimension/normalization; хеш тела рядом с вектором; многократные call sites; symbol identity при rename/overload; связь артефактов; порядок FTS ranking. `ON DELETE CASCADE` для trace link способен уничтожить именно свидетельство удалённой реализации, которое должен показать drift. Dot product становится cosine лишь при нужной нормализации; `zip` не заменяет проверку размерностей. Эскизы не следует выдавать за готовую схему.

`ATTACH` имеет default limit **10** присоединённых БД, максимальный предел **125**, join — максимум 64 таблицы. Это не запрет федерации 100 репо, но и не «бесплатное» решение через один query. Источник: [SQLite limits][sqlite-limits].

### Частично сломанный код

Сохранять предыдущий хороший блок полезно только с явным `stale` и старой revision. Нельзя смешать старое и новое и назвать граф целиком текущим. Разбор частей должен учитывать изменения imports/exports/config, которые меняют разрешение в других файлах, включая прежние unresolved ответы. Ошибку чтения, неподдерживаемый язык и синтаксическую ошибку нельзя скрывать одним «нет зависимостей».

### Автономность и triage

Сильная идея пользователя — дать процессу продолжать независимую работу, а ему потом показать понятные места ревью. Это не разрешение автоматически принимать неизвестный риск.

Карточка должна отвечать: **что изменилось; кто может пострадать; что проверено на какой ревизии; что осталось неизвестным; какое решение требуется**. Топ-5 — порядок показа, не скрытие остальных блокеров. Продолжать можно независимые задачи в изоляции; merge/deploy/изменение схем данных требуют отдельного допуска. Высокий R_eff не должен прятать свежий drift под «туманом войны». Уровень экспертизы пользователя нельзя выводить только из Git blame.

## 8. Целевая система и первые проверочные сценарии

**Один из сквозных проверочных сценариев — [ПРЕДЛОЖЕНИЕ]:** в одном из трёх репозиториев меняется контракт API/события. ForgePlan показывает связанное решение, конкретные затронутые места потребителей, происхождение каждой связи, непройденные/устаревшие проверки и карточку решения для человека. Это проверка целевой системы, не ограничение всего продукта этим сценарием.

Пример: поле события `OrderCreated` стало обязательным. Недостаточно увидеть изменённый `pub fn`: нужно знать сериализуемую схему, версию producer/consumer, defaults и обработку старых сообщений. Граф импортов найдёт часть кандидатов; schema/contract test подтвердит или опровергнет совместимость.

Предлагаемый минимальный контракт факта: source identity + проверяемая revision/content digest + subject/span + вид связи + способ/версия получения + результат разрешения + ссылка на доказательство. Это не второй registry: использовать уже существующие Constellation identities. Для dirty tree одного HEAD недостаточно.

После уточнения владельца прежний порядок «сначала маленький адаптер, остальное только если понадобится» заменён проектированием от полной задачи. Цель включает собственное ядро анализа, тестовые доказательства, документацию, легаси, федерацию, CI/CD, 2D/3D, web/Tauri и командную эксплуатацию.

Подробные контракты, семь этапов и их проверочные условия сохранены в [дополнении к dialog.txt](dialog.txt), разделы 5–16; навигация — [часть VIII roadmap](forgeplan-research-roadmap.md#часть-viii-актуальное-направление-полноценная-система-реализуемая-поэтапно). Первый шаг — зафиксировать целевую модель и сквозные критерии, затем реализовывать проверяемые части. Storage-решение имеет собственную матрицу; смена LanceDB не является обязательным условием каждого пользовательского сценария.

Нужны как минимум три проверки пользы: межрепозиторное изменение контракта, перенос реального компонента легаси и работа агента с незнакомой задачей. Сравнивать пропущенные зависимости/сценарии, ложные тревоги, качество решения, время ревью и стоимость поддержания индекса; токены — дополнительная метрика. Пилот не доказывает всю целевую архитектуру, но проверяет конкретные риски.

Существующие дефекты #548/#577/#578 остаются входными рисками. Новые слои не должны усиливать ложное «конфликтов нет». Stale/unknown не превращаются в PASS, evidence соответствует проверяемой revision/configuration, пользователь видит основания решения.

**Позиционирование — [ПРЕДЛОЖЕНИЕ]:** «ForgePlan показывает, какие инженерные обещания затронуты изменением и чем подтверждено их сохранение». Это точнее, чем «математически доказывает соответствие PRD и кода». Отсутствие конкурентов не проверено; уникальность сочетания функций ещё нужно доказать пользовательским результатом.

Boundary result, job status, test evidence, coverage области анализа и `eligible` разделены; у тестов свои настройки. Hash/sidecar не удостоверяют честность недоверенного runner. Записанная команда не доказывает исполнение.

**Статус библиотек:** evidence (A-31), acceptance (A-32), controls (A-33) ещё не опубликованы отдельными пакетами. Часть evidence/required-tests уже в action; отдельные bundles, отчёты за период, acceptance report и control mappings остаются разработкой. Их нельзя ни объявлять готовыми, ни игнорировать как направление конкурента.

**Поправка позиционирования:** связывание кода с тестовыми записями и evidence уже присутствует у Референс A. Преимущество ForgePlan должно подтверждаться связностью PRD/ADR/SPEC, поведения, федерации и миграций, а не утверждением «этого нет ни у кого». Compliance-отчёт — технический материал для ревьюера, не автоматическая сертификация.

Полный набор выводов и предложений сохранён в дополнении к исходной переписке. Референс A build, action tests и независимые benchmarks в этой проверке **NOT_RUN**.
