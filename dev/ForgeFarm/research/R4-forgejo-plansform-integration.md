# Архитектурное исследование интеграции ForgePlan, Forgejo и оркестратора Forge Plansform

## Суть вывода

То, что вам показали, по сути является **git-native инженерным control plane**: задачи живут в issue tracker, артефакты решений и требований версионируются в Git, оркестратор читает это как источник истины, раздает работу нескольким агентам, прогоняет ее через CI и показывает весь поток на доске в реальном времени. В вашем случае эта идея хорошо ложится на связку **Forgejo как system of record для репозиториев, issues, PR, Actions, webhooks и API** и **ForgePlan как system of record для структурированных артефактов, графа зависимостей, фаз методологии, evidence и quality gates**. У ForgePlan уже есть существенная часть нужного фундамента: MCP-сервер, `/forge` skill, `/smith` master orchestrator, guardian-агенты, state machine с фазами `routing → shaping → coding → evidence → pr`, а также наблюдаемость через activity logs и `activity-stats`. citeturn33search0turn32search2turn34search0turn25search0turn2search0turn21search6

Ключевая рекомендация после исследования такая: **не выносить `.forgeplan/` в отдельный submodule на первом этапе**. Гораздо устойчивее держать `.forgeplan/` рядом с кодом в основном продуктном репозитории, а отдельно вынести только **harness**: сам оркестратор `forgeplansform`, общие профили агентов, промпты, policy packs и UI. Причина в том, что ForgePlan уже проектирует артефакты в Markdown под `.forgeplan/{kind}s/`, при этом производные индексы и конфиг локальны и могут быть подняты заново через `init -y`, `scan-import` или `import`; а вот submodule добавляет второй history, фиксированный pointer на commit, обязательный lifecycle `submodule init/update` и дополнительную операционную хрупкость. citeturn24search1turn31search3turn32search3turn36search4turn36search2turn36search3

Самое важное архитектурное замечание: **не завязывайте автоматизацию на Forgejo Project board API, пока не проверите именно ваш `/api/swagger`**. В документации Forgejo Projects описаны как kanban-доски для issues, но автоматизация бордов через API не так прозрачно документирована, как automation по issues, PR, Actions и webhooks. При этом Forgejo прямо дает Swagger/OpenAPI на экземпляре, а совместимость API зависит от major-версии Forgejo и совместимого Gitea API. Поэтому безопасный путь — строить свой board/view в Plansform как производное представление из issues, labels, assignees, session phase ForgePlan и статусов CI, а не как primary-state внутри Project board Forgejo. citeturn6search0turn3view0turn1search5

## Что именно вы описали

По вашему описанию это не просто “много агентов”, а **иерархический multi-agent delivery pipeline**, где один слой делает routing и архитектуру, другой — decomposition и review, третий — implementation, а еще один — валидацию, guardian-checks и возврат в fail-loop. Такая модель очень хорошо совпадает с тем, как ForgePlan уже мыслит рабочий процесс: глубина (`Tactical` / `Standard` / `Deep` / `Critical`) влияет на строгость validation gate, необходимость ADI-рассуждений и “review ceremony”, а текущая сессия уже имеет явные фазы `idle`, `routing`, `shaping`, `coding`, `evidence`, `pr`. Иными словами, ваш L0/L1/L2/L3 — это не что-то инородное, а практическое расширение уже существующей state machine ForgePlan. citeturn33search3turn34search0turn32search2

Также важно, что ForgePlan в текущей документации уже говорит не только про одиночный `/forge`, но и про **полный harness** с `/smith` master orchestrator, `/forge-cycle`, `/audit`, `/sprint`, `/methodology-check`, guardian-профилями, FPF ADI reasoning и Hindsight memory. Это означает, что концептуально вы не идете “в сторону от ForgePlan”, а скорее делаете следующий продуктовый слой поверх того, что в ForgePlan уже заложено как methodology runtime и agent harness. Поэтому наиболее рационально думать о вашем будущем продукте не как о замене ForgePlan, а как о **control-plane и UI/ops-надстройке над ForgePlan + Forgejo**. citeturn33search0turn32search2

С точки зрения Forgejo ваша идея тоже естественна. Forgejo уже дает issues с labels, milestones, assignees и фильтрацией; kanban-style Projects; автоматически связанные ссылки между issues и PR; “actionable references” вида `closes #123`; issue search с query syntax; webhooks; Actions с триггерами по issue/PR events и ручным `workflow_dispatch` через API. То есть базовый substrate для “issue-driven orchestration” уже есть из коробки. citeturn6search1turn21search5turn22view0turn13search3turn28view0turn28view3

## Что уже дают ForgePlan и Forgejo для вашей схемы

ForgePlan уже умеет заводить рабочее пространство `.forgeplan/` с директориями для `adrs`, `prds`, `rfcs`, `epics`, `specs`, `evidence`, `problems`, `solutions`, `notes`, `refresh`, `memory`, а также поднимать локальный LanceDB-индекс и `config.yaml`. При этом документация прямо говорит, что Markdown под `.forgeplan/{adrs,prds,...}` трекается в Git, а `.forgeplan/lance/` и `config.yaml` не должны коммититься и восстанавливаются локально. Это критически важно для вашей архитектуры: артефакты уже спроектированы как **Git-tracked projections**, а не как opaque database-only state. citeturn24search1turn32search4

Связность артефактов в ForgePlan — не декоративная, а операционная. `forgeplan link` создает типизированные направленные relation между артефактами; эти relation питают health checks, weakest-link scoring, Mermaid dependency graph, blind-spot detection и, что особенно важно для вас, **topological sort for sprint planning**. Это означает, что dependency ordering для вашего backlog и для автоматического scheduler’а уже концептуально существует внутри самого ForgePlan, а не должно изобретаться с нуля в отдельной базе Plansform. citeturn35search0

Для интеграции с агентами ForgePlan дает два слоя. Первый — skill layer: `forgeplan setup-skill` ставит `/forge`, который внутри Claude Code запускает полный цикл `route → shape → validate → ADI → code → evidence → activate`. Второй — MCP layer: в install guide явно показан запуск `forgeplan serve` как MCP server для AI agents, а в docs для `serve` сказано, что сервер работает только по stdio и intentionally не поднимает HTTP/WebSocket/SSE транспорт. Для вас это означает очень конкретную архитектурную развилку: Plansform должен либо **спавнить локальные/worker-side процессы `forgeplan serve`**, либо работать через CLI/MCP host abstraction, но не строить свою интеграцию с ForgePlan как с обычным сетевым HTTP-сервисом. citeturn32search1turn24search2turn17search0

Еще один уже готовый кирпич — session state machine. `forgeplan_session` возвращает текущую фазу, active artifact, routed depth и историю переходов; в документации прямо сказано, что типовой цикл — это `forgeplan_session → forgeplan_guard(target_phase) → phase work`, причем phase auto-advances по мере движения артефактов. Именно это лучше всего использовать как канонический внутренний lifecycle для вашей доски: не изобретать отдельные статусы “architecture/review/implementation/evidence/pr”, а проецировать в UI уже существующие phase semantics ForgePlan. citeturn34search0turn33search1

Для динамического выбора “силы агента” у ForgePlan уже есть полезный primitive: `forgeplan_calibrate` рекомендует глубину `Tactical / Standard / Deep / Critical`, а depth влияет на validator strictness, ADI requirement и review ceremony. Это почти готовый вход для вашего policy engine выбора моделей: условно, `Critical` и `Deep` направляйте в L0/L1 с дорогими reasoning-моделями, а `Tactical`/часть `Standard` — в L2/L3 с более дешевыми моделями или кодогенераторами. citeturn33search3

С точки зрения наблюдаемости ForgePlan тоже уже очень близок к тому, что вы хотите видеть на живой панели. `forgeplan activity-stats` агрегирует логи по инструментам, показывает count вызовов, count ошибок, p50, p95 и total duration; docs прямо позиционируют команду как быстрый ответ на вопрос “куда ушло время сессии?” и как стартовую точку расследования медленного workflow. Это не полноценный distributed tracing, но это отличная база для real-time operations view внутри Plansform. citeturn25search0

Наконец, ForgePlan умеет **детерминированно засеивать CI и новые рабочие пространства** через `forgeplan_export`/`forgeplan_import`. Документация `forgeplan_import` отдельно называет среди use-cases “seeding CI pipelines with a reference workspace” и “reproduce a deterministic artifact set before running integration tests against the MCP server”. Это очень сильный аргумент против раннего вынесения артефактов в отдельный submodule: ту же воспроизводимость вы уже можете получить через export/import pipeline без раздвоения Git-истории проекта. citeturn32search3

Со стороны Forgejo у вас есть все публичные integration points для issue-driven control plane. API по умолчанию включен, поддерживает token/bearer auth, pagination и Swagger/OpenAPI на instance; issue search поддерживает query syntax с `is:open`, `assignee:*`, `author:*`, `sort:updated:desc`, `modified:>YYYY-MM-DD`; linked references позволяют связывать issues и PR, а `closes #123` закрывает issue после merge; webhooks могут быть repository-, organization- или system-wide и отправляют JSON payload на ваши URL; Actions умеют триггериться по `issues`, `pull_request` и `workflow_dispatch`, а `workflow_dispatch` можно дергать через API endpoint `POST /repos/{owner}/{repo}/actions/workflows/{workflowname}/dispatches`. citeturn3view2turn22view0turn21search5turn13search3turn28view0turn28view3

## Рекомендуемая целевая архитектура Forge Plansform

Оптимальная целевая архитектура для вашей идеи выглядит так:

```text
Forgejo Issues / PR / Actions / Webhooks
                │
                ▼
      Forge Plansform Control Plane
   ┌────────────┼────────────┐
   │            │            │
   ▼            ▼            ▼
Scheduler   Realtime UI   Telemetry store
   │
   ▼
Agent Pools L0 / L1 / L2 / L3
   │
   ├── Git worktrees / CI runners
   └── ForgePlan MCP workers
             │
             ▼
      .forgeplan artifact graph
      PRD / ADR / RFC / Epic / Evidence
```

Самая важная мысль здесь такая: **source of truth должен быть разделен по слоям, а не смешан**. У задач и статусов выполнения source of truth — Forgejo issues, labels, assignees, PRs и CI runs. У инженерных артефактов и связей между ними source of truth — `.forgeplan/` плюс ForgePlan graph/model state. У real-time orchestration source of truth — уже сам Plansform, который хранит derived state: active claims, lease timeouts, worker heartbeat, throughput, fail-loop statistics и UI projections. Такой split позволит вам не превращать Forgejo ни в scheduler, ни в workflow engine, а ForgePlan — ни в issue tracker, ни в dashboard backend. citeturn24search1turn35search0turn3view2turn13search3

Для ingestion я бы рекомендовал гибридную схему. События из Forgejo лучше получать через webhooks и Actions events, потому что так у вас будет push-модель для изменений issues/PR/labels/CI. Но чтение артефактов и их графа лучше делать через локальный MCP/CLI слой ForgePlan, потому что это канонический интерфейс самой системы, и он уже знает про links, phases, evidence, depth и projection model. Практически это означает: Plansform слушает Forgejo webhooks, обновляет свой event log, а когда нужно реально планировать/валидировать работу — ходит в forgeplan worker process за `session`, `graph`, `order`, `get`, `list`, `calibrate`, `reason`, `decay` и смежными примитивами. citeturn13search3turn17search0turn34search0turn35search0turn33search3turn33search5

Состояние доски я бы строил не из Forgejo Project columns как primary-state, а как **derived board** в Plansform. Например, `Backlog` — open issue без активного lease/claim; `Ready` — open issue, у которого dependency graph не блокирует старт; `Shaping` — по `forgeplan_session.phase=shaping`; `Coding` — по `phase=coding`; `Evidence` — по `phase=evidence`; `Review/PR` — по `phase=pr`; `Fail` — когда CI/job/guard/validation возвращает отказ или когда evidence decay/drift/blocking condition требует возврата в очередь. Это даст вам ровно ту гибкость, которую вы описали: fail-loop будет не ручной колонкой в внешней системе, а формальным следствием состояния методологии и результатов проверок. citeturn34search0turn33search5turn25search0turn28view0turn28view2

## Как разложить систему по агентным уровням

Я бы рекомендовал прямо зафиксировать четыре слоя.

**L0 — routing и архитектурное решение.** Здесь живут самые дорогие reasoning-модели. Их задача — прочитать epic/issue, поднять контекст из артефактов, определить depth, выбрать pipeline и порождать/обновлять PRD, RFC, ADR, decomposed specs и acceptance criteria. Для этого у вас уже есть хорошие нативные примитивы ForgePlan: `route`, `calibrate`, FPF/ADI reasoning и `/smith` как master orchestrator в полном harness bundle. citeturn32search2turn33search0turn33search3turn26search2

**L1 — shaping и decomposition.** Здесь модель может быть слабее, но ей нужны хорошие структурные инструменты. Ее задача — разрезать L0-решение на выполнимые work items, связывать issue с нужными артефактами, поддерживать typed relations и dependency order, назначать owners/skills/classes и готовить handoff на implementation. Это тот слой, который должен особенно активно жить на `forgeplan link`, `graph`, `order` и project-specific policies Plansform. citeturn35search0turn25search1

**L2 — implementation.** Это ваш “много дешевых кодящих агентов”. Они должны работать либо в изолированных git worktree, либо в sandbox/runner на CI, чтобы не ломать общий workspace. Здесь надо минимизировать глобальный reasoning и максимизировать determinism: агент берет claim, тянет прикрепленные артефакты и acceptance criteria, пишет код, тесты, обновляет evidence, открывает PR. Forgejo Actions здесь очень полезен как execution substrate: есть триггеры на issues/PR и ручной `workflow_dispatch`, а branch protection дает merge control через approvals. citeturn28view0turn28view2turn28view3turn1search7

**L3 — guardian, review и evidence enforcement.** Это слой, который должен искать проблемы, а не “помогать закрыть задачу любой ценой”. Здесь должны жить policy agents, reviewers, validators, auditors, evidence-checkers и fail-loop resolvers. В ForgePlan эта философия уже присутствует: validation gate, adversarial review, weakest-link reliability, decay awareness и guardian/канонические профили агентов уже являются частью методологии и full harness bundle. citeturn32search4turn33search5turn33search0

Практически это хорошо маппится на ваши наблюдения про real-time панель: в UI надо показывать не просто “агент работает”, а **какой слой сейчас держит item, по какой причине, с каким lease, с каким quality level и на каком evidence state**. Тогда борд становится не просто kanban, а live process map всего delivery pipeline. ForgePlan session history и activity-stats уже дают часть этого telemetry слоя. citeturn34search0turn25search0

## Как лучше организовать репозитории и версионирование

Здесь у вас три реалистичных варианта.

Первый вариант — **основной рекомендованный**: код и `.forgeplan/` живут в одном продуктном репозитории, а `forgeplansform` и общий `forgegpt-harness` живут отдельно. Это лучший баланс между атомарностью изменений и повторным использованием. В одном PR вы меняете код, PRD, ADR, evidence links и acceptance notes; review видит всю инженерную историю рядом; fresh clone поднимается через `forgeplan init -y` и `scan-import`; CI или локальная машина могут восстановить deterministic state через export/import. Это полностью соответствует тому, как ForgePlan сам описывает workspace model. citeturn24search1turn32search3turn31search3

Второй вариант — **submodule только для shared harness**, а не для артефактов проекта. Например, в монорепо есть `tools/forgegpt-harness` как submodule с профилями агентов, policy packs, prompts, reusable workflows и UI client contracts. Это хороший use-case для submodule, потому что у harness действительно есть собственный lifecycle и собственная история. Git определяет submodule как embedded repository с собственной историей, а superproject хранит pointer на конкретный commit submodule. Это нормально для “shared platform layer”, но обычно избыточно для артефактов конкретного продукта. citeturn36search4turn36search2

Третий вариант — **`.forgeplan/` как submodule**. Его можно сделать, но я бы шел туда только если у вас есть жесткая организационная причина: отдельные права доступа, отдельные compliance-потоки, юридическое разделение артефактов и кода или необходимость зеркалировать/архивировать артефакты отдельным процессом. Техническая цена здесь заметная: superproject привязывается к конкретному SHA submodule; разработчики и агенты должны помнить про `git submodule update --init` и синхронизацию; Git даже имеет отдельные diagnostics для кейсов, когда submodules не инициализированы или расходятся; в `.gitmodules` отдельно описывается update-политика. Для людей это терпимо, но для swarm of agents это дополнительный источник failed runs и nondeterministic setup. citeturn36search2turn36search3turn36search7turn36search14

Поэтому мой вывод здесь однозначный: **артефакты проекта держите вместе с проектом; общую агентную платформу держите отдельно**. Если позже окажется, что нужно выносить часть дерева в отдельный репозиторий, GitHub прямо документирует, как split-ить subfolder в новый repository без потери истории для нового clone. То есть эту оптимизацию можно сделать позже, когда у вас уже будет доказанный operating model. citeturn36search11

## Риски, ограничения и тонкие места

Первый архитектурный риск — **непрозрачность board automation в Forgejo**. Forgejo Projects документированы как kanban board для issues, но публичная документация по automation вокруг issues/PR/actions/webhooks существенно богаче и надежнее, чем narrative around project board APIs. Плюс API surface у Forgejo versioned и завязан на major-compatibility / Gitea compatibility. Поэтому, если вы попытаетесь сделать Projects в Forgejo primary orchestration store, вы рискуете рано упереться в version-specific или undocumented ограничения. Надежнее использовать Forgejo issues + labels + milestones + PR links как canonical task store, а board в Plansform — как derived visual layer. citeturn6search0turn3view2turn1search5turn6search1

Второй риск — **локальность ForgePlan runtime**. `forgeplan serve` намеренно работает только по stdio и не открывает HTTP/WebSocket/SSE. Это означает, что ваш оркестратор обязан думать категориями worker process lifecycle, workspace mounts, isolation и tool host integration. То есть Plansform — это не просто “backend, который дергает API”, а скорее supervisor над локальными или runner-side ForgePlan workers. Если это учесть с самого начала, архитектура будет чистой; если проигнорировать — вы получите болезненный рефакторинг позже. citeturn17search0turn32search1

Третий риск — **безопасность CI и PR automation**. В Forgejo Actions workflow на `pull_request` из fork не получает secrets и write-токенов; `pull_request_target`, наоборот, работает в контексте base branch и может иметь write permission. Это очень полезно для label/comment automation, но опасно, если не понимать модель исполнения. Для вашей системы это значит: issue-driven scheduling, queueing и assignment лучше триггерить либо из `issues` events, либо через `workflow_dispatch`, а не строить critical write automation на непрерывном потоке внешних PR. citeturn21search7turn28view2turn28view3

Четвертый риск — **операционные баги на стыке MCP и агентного рантайма**. В мае 2026 у ForgePlan был критический закрытый issue о том, что MCP `forgeplan_update` в версии `0.32.1` не разворачивал `@/path/to/file.md`, а записывал literal path string в body, что приводило к silent data loss. Даже если у вас уже стоит фикс, safety pattern остается правильным: агент должен читать содержимое файла хост-инструментом и передавать в MCP уже literal body string, а не симулировать CLI-синтаксис `@file`. Для swarm-архитектуры это важная инженерная дисциплина, потому что вы будете писать артефакты массово и без ручного контроля. citeturn32search0

Пятый риск — **version skew внутри workspace**. ForgePlan сам предупреждает, что schema tied to binary, рекомендует `export` перед upgrade, `migrate` после upgrade, `health` после migrate и не советует смешивать разные версии бинаря на одном workspace. Если у вас будет несколько runner pools, локальные агенты и CI-агенты, это нужно формализовать как platform rule: pin version, smoke-check `forgeplan health`, миграции делать централизованно. citeturn31search3

## Практический план внедрения

Сначала я бы построил **минимальный working architecture**, а не “полный автономный swarm”. На первом шаге оставьте `.forgeplan/` внутри продуктного репозитория, заведите строгие labels в Forgejo для типа работы и класса агента, включите webhooks и Actions, зафиксируйте protected branches и начните собирать projection layer в Plansform: issues, labels, PRs, CI runs, active artifact, phase, depth, graph edges, telemetry. Уже на этом этапе вы получите ту самую живую картину scope/tasks/artifacts, которую вы увидели у другого человека. Forgejo и ForgePlan поддерживают для этого почти все необходимые primitives уже сейчас. citeturn13search3turn28view0turn1search7turn24search1turn34search0turn25search0

Следующий шаг — включить **один orchestration loop, а не четыре сразу**. Я бы начал с L0 и L2: L0 делает route/calibrate/shaping, L2 берет только clearly-ready implementation tasks. Failures, evidence и review пока оставьте более консервативными, с большим количеством hard gates и меньшей автономией. Это позволит доказать, что ваш scheduler правда умеет читать dependency graph, не брать заблокированные items и не плодить хаос в репозитории. Для dependency order и methodology state у вас уже есть нативная опора в ForgePlan relations и phase machine. citeturn35search0turn34search0turn33search3

После этого имеет смысл добавить **реальный fail-loop**. Причины для перевода в Fail должны быть формальными: CI failed, `guard` не пустил переход, `validate`/review нашли blocking issues, evidence decay опустил доверие, task lease expired, subtask blocked by graph dependency. На этом слое Plansform становится по-настоящему полезен, потому что начинает не просто показывать карточки, а управлять возвратом задач в поток на основе наблюдаемых причин. Для UX это важнее, чем “еще один агент”. citeturn33search5turn25search0turn34search0

И только потом я бы выносил в отдельный репозиторий **shared harness** — ваш будущий ForgeGPT/ForgePlansform platform layer. Туда должны уйти canonical agent profiles, prompt packs, policies, reusable workflows, telemetry contracts и UI/frontend. А вот артефакты конкретного продукта лучше оставить рядом с кодом, потому что именно там они наиболее reviewable, наиболее атомарны и наименее ломки для CI, локальных агентов и разработчиков. Это даст вам и reuse, и операционную стойкость одновременно. citeturn32search2turn33search0turn24search1turn32search3

Если свернуть все в одну фразу, то оптимальная формула для вас выглядит так: **Forgejo — это task and execution plane; ForgePlan — methodology and artifact plane; Forge Plansform — orchestration and visibility plane**. Делать именно так, на мой взгляд, гораздо сильнее, чем пытаться превратить любую одну из этих систем в “универсальный центр всего”. citeturn2search0turn13search3turn24search1turn34search0
