01 · An operational layer for decisions

Concept 01 · a point-of-sale analogy

The waiter takes the order; the terminal tracks prices and discounts

Picture a restaurant’s point-of-sale terminal handling prices, tax, discounts, and loyalty balances while the waiter takes an order. The division is between making a substantive choice and recording it consistently.

Forgeplan is comparable to that terminal, but its adaptations are not identical to every upstream methodology. BMAD informs product planning, OpenSpec informs deltas, Quint Code informs evidence-oriented assurance, and FPF informs reasoning. The product has its own templates, validators, FGR heuristics, and R_eff engine. None of these integrations replaces inspection of the underlying evidence.

Before · remembered by the team
Things a shared process must specify
  • Which PRD sections the local template requires
  • Which delta verbs the implementation supports
  • Where ADRs live and how their metadata is stored
  • How evidence fields differ from trust-assessment rubrics
  • How to compare serious alternatives using ADI
  • Which graph edges represent dependencies
Explicit conventions, not a memory contest
After · supported by tools
What Forgeplan provides
  • forgeplan new prd "Feature title" · a local template, not a verbatim upstream BMAD checklist
  • forgeplan validate · kind- and depth-dependent structural checks
  • .forgeplan/ · Markdown sources and derived index data
  • forgeplan score · R_eff; forgeplan fgr · a separate FGR heuristic
  • forgeplan reason · an LLM prompt requesting 3+ approaches, not a parser-enforced count
  • forgeplan graph · Mermaid graph text for inspection
Adaptations with explicit implementation boundaries

Workspace initialization creates .forgeplan/. The following commands illustrate creating an ADR; this is not a captured transcript.

Authored terminal example · creating an ADR $ forgeplan init # Inspect initialization output before continuing. $ forgeplan new adr "Vault architecture: Express + SQLite + Ollama + Anthropic" # Use the actual returned ID and file path. # Fill context, decision, alternatives, and consequences. # Record evidence requirements and review conditions. # Select depth explicitly for the real task. # A review condition does not install an event monitor. Next: forgeplan reason ADR-001

Complete the template actually returned by the tool. The checked ADR template separates Context, Decision, Alternatives Considered, Consequences, Evidence Requirements, and Valid Until, with additional depth-specific material. Three alternatives are a local prompt convention, not a universal FPF threshold. A generated template is not a completed reasoning record.

The MCP server exposes tools to a connected client. The client’s instructions, tool access, and agent behavior determine whether it retrieves the relevant PRD and ADR. For “add logging to the auth service,” ask it to inspect those records and verify the references. Providing access is not a guarantee of automatic retrieval or of compliance with every previous decision.

Distinguish framework concepts from product calculations

Upstream FPF uses ordinal F (rigor of expression), G (ClaimScope), and claim-specific R. Forgeplan instead computes Formality, Granularity, and Reliability on 0–1 scales: overall FGR is cube_root(F × G × R). Quint Code’s reference has textual FGR guidance and a separate formality/reliability calculator; these are not one shared formula.

02 · Artifact kinds and the dependency graph

Concept 02 · artifact types

Six highlighted kinds, with explicit relationships

Imagine requirements in Jira, design discussions in Confluence, ADRs in docs/, and evidence in PR comments or benchmark files. If their relationships exist only in the author’s memory, a later reader may not know why gRPC was chosen over REST.

Forgeplan stores records in a file-based workspace. Six kinds are highlighted here; the table selects ten kinds, not the entire core taxonomy or every MCP creation enum.

PRD
prefix · prd-
What? What to build, and for whom
Product requirements. Upstream BMAD places PRD work in Planning, not a “Delivery” phase. Write functional requirements as “[Actor] can [capability]” rather than embedding implementation choices.
RFC
prefix · rfc-
How? Possible ways to implement it
A proposal with alternatives: “We are considering REST versus gRPC; here are the options.” It opens a technical discussion rather than declaring the final choice.
ADR
prefix · adr-
Why? Why this choice
An accepted architectural decision linked to proposals and evidence. Active files are editable through authorized updates. Use an explicit replacement when the decision changes; activation is not technical immutability.
Spec
prefix · spec-
Contract? How the system behaves
API contracts and data models. The target delta parser supports ADDED / MODIFIED / REMOVED. Upstream OpenSpec also supports RENAMED; that does not establish target support. See the specification cycle.
Epic
prefix · epic-
Group? What several PRDs share
Groups related work around a larger goal. An Epic can organize multiple PRDs; it is not a separate mandatory Critical pipeline inferred from the label.
Evidence
prefix · evid-
Observed? What supports or challenges the choice
Tests, measurements, benchmarks, or audits with scope and provenance. The scorer reads verdict and CL declarations and an evidence type. R_eff aggregates eligible contributions; it does not read a 0–9 F/G/R triplet as a universal trust formula.

03 · Depth calibration and quality checks

Concept 03 · a screening analogy

Match the review effort to the task, not one pipeline for everything

A cosmetic change and a database migration need different scrutiny. The router proposes a depth based on task signals; project policy and actual risk still need review.

Think of different screening procedures for different situations. This analogy motivates proportionate review; it is not a description of airport rules or a quality guarantee.

● Tactical
Minimal artifact pipeline
pipeline: none
Cosmetic work or a small rename may fit. This does not waive project checks. Core also has a lightweight Note mode.
● Standard
PRD + RFC
PRD → RFC
A bounded feature can fit Standard. Evidence supports completion, but is not another node in this router’s pipeline list.
● Deep
Spec + RFC + ADR
PRD → Spec → RFC → ADR
Security, public-API, or irreversibility signals can require Deep. Inspect the highest matching signal.
● Critical
Parsed as a Deep alias
Critical → Deep in the core mode parser
This is not a separate built-in Epic/Adversarial pipeline. Core modes are Note, Tactical, Standard, and Deep.

Inspect the recommendation and its rationale. These are authored examples, not captured classifications:

Illustrative routing · commands, not a verified transcript $ forgeplan route 'Add streaming endpoint GET /query/stream for Vault' Illustrative depth: deep Deep pipeline: PRD → Spec → RFC → ADR # Inspect public-API, dependency, and budget implications. # No latency or classification confidence measured here. $ forgeplan route 'Rename button color from blue to indigo' Illustrative depth: tactical Tactical pipeline: (none) # Confirm there is no behavior change or wider impact.

The keyword rules take the maximum matching signal: security maps to Deep, cross-team to Standard. CLI help describes level 0 as the default, while the handler can auto-select configured LLM routing and escalate. Confidence is heuristic, not measured correctness.

Three review concerns · not three universal CLI gates $ forgeplan validate PRD-018
01 PRD structure Check the local kind/depth rules. The local template’s thirteen substantive H2 sections are not an upstream BMAD thirteen-section requirement. review
02 Delta consistency Check base references, supported verbs, and dependency structure where applicable. A PRD validation does not demonstrate all delta behavior. review
03 Reasoning Compare serious alternatives, rejection reasons, and evidence. ADI is Abduction–Deduction–Induction; the product prompt requests 3+ approaches, not an enforced universal threshold. review

These rows organize manual review; they are not a successful validation result. The selected CLI validate path reports a named legacy-store limitation on migrated workspaces. Captured help proves syntax, not that every handler works on every layout.

Activation and replacement have different roles

forgeplan activate adr-001 checks content length, stubs, evidence links, MUST findings, and readiness; callers also handle provenance. It does not lock the file. Create a replacement before forgeplan supersede adr-001 --by adr-002. Expiry detection can list an active record as overdue without rewriting its stored status. Supersede links an existing replacement; it does not create that replacement. forgeplan renew adr-001 --reason "Rechecked applicability" --until 2026-12-01 uses the stored-status transition guard. Help calls it stale → active, but being listed overdue does not make an active → active renewal legal; the guard also permits draft → active. forgeplan reopen adr-001 --reason "Context changed" accepts active or stale, creates a new draft with lineage, and deprecates the old record. Neither command is a captured full-profile MCP tool.

Worked illustration · Vault · a streaming endpoint

An authored example of linking intent, contracts, decisions, and evidence. No benchmark or current product run is reported here. Complete the routed artifacts, implementation, and checks before claiming completion.

01 · route

forgeplan route 'Add streaming endpoint GET /query/stream'

The example chooses Deep: PRD → Spec → RFC → ADR. Inspect the real routing response and public-API signals. No half-second response time or automatic agreement is promised.

02 · new prd

forgeplan new prd "Streaming endpoint for Vault queries"

Complete the generated local PRD template, then create the Spec, RFC, and ADR required by the chosen route. The new command accepts kind and title; it does not infer this example’s deep depth or parent Epic from the title. Set actual metadata and links explicitly through supported tools.

03 · reason

forgeplan reason PRD-018 · ADI

Compare SSE, WebSockets, and HTTP/2 push with testable consequences. Three alternatives illustrate the local anti-anchoring heuristic. A configured LLM provider is required for reason; missing configuration is an error, not an offline blank-slot output.

04 · validate

forgeplan validate PRD-018 · inspect actual findings

Review template completeness, applicable contracts, and the reasoning separately. A structural check cannot demonstrate implementation behavior or guarantee full OpenSpec/FPF conformance. Preserve a layout refusal rather than inventing a PASS.

05 · evidence

forgeplan new evidence "SSE vs WS benchmark" + link

Design a first-token p50 comparison between SSE and WebSockets—for example, at 50 RPS with a 2 KB payload. These are scenario parameters, not observed results. Record revision, method, verdict, congruence_level, evidence_type, and limits. Link with forgeplan link EVID-001 ADR-001 --relation informs, then inspect forgeplan score ADR-001. Do not assume every mutation reconciles every ancestor cache.

06 · activate

forgeplan activate ADR-001 · an explicit transition

If the applicable gates pass, the persisted status is active, not activated (a derived display category). Active bodies remain editable. Evidence scoring keeps its ordinary value until expiry, then contributes 0.1; it does not gradually decay to 0.6. A missing valid_until means no expiry in that scorer. Reassessment needs new observations, not just a later date.
