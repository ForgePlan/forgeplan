DECISION LOG · PRACTICE

How to introduce decision logging into your team

A decision log is not «one more document for the team». It is a set of concrete rules: when to write a record and when not to; how to set it up to give an AI agent (Claude Code, Cursor, Codex) access to context, tell it what to read, or explicitly load records of rejected options; what a day looks like for an engineer whose process includes the log - without overload and without bureaucracy.

When to write a record, and when not to

The most common mistake is trying to record every decision. It is tiring and it kills the habit fast. A good empirical rule: write a record if the answer is «yes» to at least two of the four questions below.

QUESTION 01

Does this decision affect code in 6+ months?

A library choice, a data schema, an exchange protocol - yes. Fixing a typo in a log line - no.

QUESTION 02

Is the context the decision was taken in not obvious from the code?

If the code will not answer «why this way» a year from now - you need a record. If the code itself says «because» - you do not.

QUESTION 03

Was there a discussion with two or more viable options?

A ten-message argument in chat - definitely yes. The decision to write a switch instead of an if - no.

QUESTION 04

Is rolling this decision back quickly and painlessly impossible?

Changing an environment variable - reversible. Changing the database - not. The more expensive the rollback, the more important the record.

If fewer than two answers are «yes» - skip it. A record written «just in case» is worse than no record: it takes up space, it costs writing time, and over time it becomes noise in which the important records get lost.

Task depth scale - how many records, and which ones

Not every task needs the same set of documents. An empirical scale of four levels has settled in - it correlates well with the risk and the reversibility of a task. Each level has its own minimum set of records. This is our series' working scale, not a description of any tool's internal router.

Level
What to write
Example tasks
01 · TACTICAL 1 file, reversible in an hour
Nothing. Just the code plus a commit message.
A typo in a log line, renaming a variable, fixing a rounding error.
02 · STANDARD 1-3 days, there is a choice
A product document plus a draft architectural decision.
A new feature in an existing module, choosing a library for one task.
03 · DEEP 1-2 weeks, irreversible
A product document plus a specification plus a decision plus measured evidence.
A new service, a move to another database, a change to a public API schema.
04 · CRITICAL cross-team, strategy
A group of documents (5-10 records), including a separate architecture overview.
Migrating from one authentication model to another, splitting a new product out of the monolith.

Start with two questions: «is it easy to roll back?» and «are other teams affected?». A small local change with «yes/no» answers is tactical. A larger reversible task with a choice of options is standard. A hard-to-reverse change is deep; cross-team strategy is critical on our scale. Use the table, not just the two answers. A detailed calculator is in one of the later lessons of the series.

A typical day for an engineer with the log in the process

To stay out of abstraction - a real day. From the life of a six-person team building a B2B product. Without tying it to one specific tool: any way of storing records works - a folder in the repo, your own CLI, an off-the-shelf product.

  • 09:15 · MORNING · GETTING INTO CONTEXT
    I open the project's decision directory. I skim the active records and the ones whose revisit condition is approaching. That gives a picture of «what is in flight» and a signal «this one is due for discussion».
  • 09:30 · STARTING THE TASK
    I pick up the ticket «optimize the file upload processing». Other teams are not affected and the change is reversible, but there are implementation choices and several days of work - standard according to the table. I create a product document stub: markdown from a template, or a record in the chosen tool.
  • 10:00 · THREE OPTIONS · TESTABLE CONSEQUENCES
    I fill in the main sections. I write out three implementation options with testable consequences (if we pick option A, X should be observed; if B - Y; if C - Z). An hour goes into running three prototypes, and the metrics are recorded as evidence. I would do this work even without the log - just without writing it down.
  • 14:00 · IMPLEMENTATION
    I give the AI agent access to the records and instructions to «read the project's active decisions before starting a task». I check that the relevant record was read and yesterday's rejection was considered. The instruction alone does not guarantee correct application.
  • 17:30 · RECORDING THE RESULT
    The implementation is done and the measurement showed the numbers we needed. I create a short evidence record (one page: what was measured, on which data, what the result was). I link it to the decision. I move the decision to the «active» status - it is now marked as in force rather than a draft. Editing the file itself is still technically possible: the rule «a new version explicitly replaces the old one» is one we keep, not one the tool enforces.
  • 18:00 · END OF DAY
    I open a pull request. The description links to the related records. The reviewer reads them before the code review and arrives with the right context instead of «let us try to remember what we wanted here».

This example allocates about an hour to filling in the record and activating the decision. The record preserves the reasons for future discussions and can provide context for an agent if read. A person or explicitly configured external automation checks the revisit condition.

How an AI agent reads your context at session start

This matters for anyone who codes with an AI assistant. A new session with Claude Code or Cursor may lack the reasons for choosing library X, so the agent may propose Y. Give it access to the records and instructions to read the relevant files, or explicitly load them into the session. A folder of markdown files and an instruction may suit this task, but they guarantee neither reading the records nor drawing correct conclusions from them.

Three ways to connect it, from simple to advanced.

Way 1 · Plain text files in the repository

The records live in a dedicated project directory as ordinary markdown files. Any AI agent with file access can read them. Name the relevant directory in the project instructions (such as CLAUDE.md, .cursorrules or an equivalent): 

# CLAUDE.md or .cursorrules
Before starting any task, read the files in the docs/decisions/
directory whose status is active. These are the project's active
architectural decisions.
Do not propose options that are explicitly recorded as rejected.

This way can be sufficient for a suitable task: you need no plugin and no special integration, the agent reads ordinary markdown files. But remember: a line in the system instruction gives the agent knowledge of the directory, not a guarantee that it will open those files itself - and still less a guarantee that the conclusions it draws from them are correct.

Way 2 · Through your agent's own tooling

Modern agents have their own mechanisms for pulling in external context - Cursor Rules for Cursor, slash commands and connectable tools in Claude Code, custom GPTs at OpenAI. Each of them can fetch decision records in its own way: wholesale, on request, or by semantic search. If the tool has its own data-connection mechanism - consider it: for some tasks it is more convenient than reading whole files every time. There is no universal rule here - the choice depends on the task and on how your agent works.

Way 3 · Gates in the continuous integration pipeline

The strictest option: a pull request does not merge if it touches files that have no active decision. This is not «bureaucracy» - it is protection against accidentally bypassing constraints that were already agreed on. It is implemented as an ordinary CI step (GitHub Actions, GitLab CI, Buildkite - whatever you use) that compares the diff against the decision directory and blocks the merge when it finds a mismatch.

Five ways an agent works with the records

With access to the records and the necessary tools, an agent can be asked to perform these tasks. Its results need to be checked.

01 · READ CONTEXT

«Which active decisions relate to module X?»

Ask the agent to read the relevant architectural decisions and briefly list the current constraints and rejected options. Check the references and how those constraints are reflected in the work that follows.

02 · CREATE RECORDS

«Create a decision record from the discussion we are having right now»

The agent gathers context from the conversation, writes out the three options considered, proposes a revisit condition. A human checks the «rejected alternatives» - the real reasons are often internal.

03 · CHECK CONFORMANCE

«Does this code conform to active decision X?»

The agent reads the decision, reads the code, and says «conforms» / «violates it in part X». Useful before a commit or a code review.

04 · LINK EVIDENCE

«Create an evidence record from the test result and link it to decision X»

The agent takes the benchmark output or the load test result, formats it as structured evidence, links it to the decision, and updates the reliability assessment.

05 · INITIATE A REVIEW

«Find the decisions whose revisit trigger is approaching»

The agent checks the metrics (if any are connected), compares them with the revisit conditions of the records, and proposes a list of «these three decisions are due for another look».

What to show a new team member on day one

If the team already has a decision log, a new person should get through four steps on their first day to get up to speed. That takes about an hour in total.

  1. Open the decision directory and look at the structure. This shows which record types live in the project.
  2. Skim the active records - sort by date, read the 10-15 most recent ones. Do not study them; just get a sense of «what this team actually decides about».
  3. Open the relationship graph (if you have a visualisation) or simply look at which decisions reference each other. This shows how the project «map» is laid out.
  4. Try creating one test record (for example a note about a day-one observation). This takes away the fear of «what if I break something».

After those four steps the person knows: where decisions live, how to read them, how to create new ones, and how they relate to each other. Everything after that is learned organically - on real tasks.

Anti-patterns: what not to do

Six typical mistakes I have seen in teams that started keeping a decision log. Each one lowers trust in the process and often leads to abandoning the practice after a few months.

DO NOT DO THIS
  • A record for every commit. If the repository collected 200 decisions in a month - that is noise in which the real ones get lost. The four rules from the first section of this lesson are the filter.
  • A record written after the fact «for the record». If the decision was already made and was not discussed while being recorded - it is not a decision record but a report of something that happened. Reports are useful too, but that is a different genre.
  • Copying the template without context. The six fields of every record must be filled in specifically for that task. «Context: a typical situation» is not context.
  • One person writes all the records. If the writing is delegated to a «team secretary» - the records will be written formally, without knowledge of the internal reasons. Everyone who owns a task writes their own records.
  • A record without a revisit condition. The sixth section is the most important one. Without it a record becomes a monument that nobody looks at a year later.
  • Activation without evidence. If a decision has no linked evidence at all - it is not a decision, it is an intention. Activate only after at least one measurement, or an explicit argument.

What it integrates with, and what it does not replace

So it is clear where a decision log fits, and what should stay with separate tools.

Integrates well with

  • git - the records live next to the code, in the same repository. The edit history is visible through git log.
  • AI agents (Claude Code, Cursor, Codex and others) - through direct file reading or through dedicated protocols.
  • CI/CD (GitHub Actions, GitLab CI, Buildkite) - gates before merging, checking a pull request against the active decisions.
  • Slack / Telegram - notifications about approaching revisit conditions through a small script.
  • Monitoring systems (Grafana, Datadog, Prometheus) - metrics from monitoring dashboards as a revisit trigger.

Does not replace

  • Jira / Linear / Trello - task and deadline management. A decision log does not know who is doing what right now, nor when the deadline is.
  • Notion / Confluence - shared documents, design systems, meeting notes. Not for retelling meetings.
  • Slack / Discord - communication. Decisions are recorded after a discussion in chat, not instead of it.
