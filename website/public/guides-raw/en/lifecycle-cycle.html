The artifact lifecycle · theory

Lifecycle · from draft to terminal

An artifact is not a static document that gets written once and forgotten. It evolves: a draft becomes a validated plan, an active decision is replaced a year later by a better one, a benchmark goes stale and asks for a review. Without lifecycle management you get zombie documents, outdated specs that nobody trusts but nobody deletes. Lifecycle gives every artifact an explicit status and explicit transition rules - so you always know: is it current? validated? replaced? does it still deserve trust?

01 · Five states · what each one means

Concept 01 · the analogy of a passport with a visa

Every artifact is always in one of five states

A passport by itself is a draft: the document exists, but without a visa you cannot cross the border. An active visa resembles active; an expired visa suggests a review. But an artifact's date does not write status: stale: that is a separate explicit change. Replacing a visa resembles supersede; revoking one without a replacement resembles deprecate.

The system records this explicitly - every artifact has a status: field in its frontmatter, strictly one of five values. No "we don't remember", no "I think we closed it".

The diagram is not exhaustive: the generic guard used by renew allows stored draft → active and stale → active, but not active → active. reopen accepts active or stale, creates a new draft and deprecates the old record. Detecting an expired valid_until is none of these writes.

Terminal is literally terminal

There is no way out of superseded and deprecated. This is not "put it away for now, we will bring it back" - it is a point in history. If a decision has to come back (for example: we picked JWT → moved to sessions → now we need JWT again) a new artifact ADR-003 is created that supersedes ADR-002. The old ADR-001 stays superseded - that preserves the real timeline of decisions.

02 · Five commands and a separate date signal

Concept 02 · a decision tree of transitions

Not "how do I rename it" - but "which transition reflects reality"

Every transition is a semantic statement, not just a changed line in the frontmatter. The choice is not "what name suits me best" but "what actually happened to the decision".

decision tree · which transition to apply
activate The artifact is ready, validated, and the team can build on it draft → active "green light" - the plan is approved and work starts

reopen An active or stale artifact needs a fresh assessment active/stale → deprecated + new draft The old one is deprecated, a new draft is created with lineage

Validation gates per artifact kind

PRD, RFC, ADR, Epic and Spec have to pass a check before activation - dozens of rules per artifact kind (MUST sections, no implementation leakage, information density, measurability, traceability): a deep PRD has more than thirty of them, while Spec, ADR, RFC and Epic have ten or so. Note and Problem can be activated without a validation gate - they are quick captures, and formal rules here would only get in the way of recording a signal.

03 · Stale · the most dangerous state

Concept 03 · the forgotten state

Stale does not mean "wrong". Stale means "nobody checked that it still holds"

Most teams ignore stale - and that is the most dangerous mistake. When the valid_until date of an artifact passes, the artifact lands in the list of overdue ones. This does not mean "it broke" - it is a signal that the context may have changed while the decision stayed frozen on old data.

Overdue status is derived from an optional date: forgeplan stale finds records whose valid_until is in the past. It does not rewrite status:: active stays active rather than automatically becoming stale. Without a date there is no such expiry; there is no universal artifact or evidence TTL here. renew uses the generic guard: stored draft → active and stale → active are allowed, active → active is not. An overdue active record first needs a considered choice: an explicit separate stale write before renew, or reopen for a fresh assessment. Reopen accepts active and stale. Extending the decision's date does not remeasure or update linked evidence.

⚡ illustrative scenario · not a measurement history

Suppose a team chose LanceDB six months ago, considering its Rust SDK suitable for their work. They set valid_until: 2026-04-15 for the ADR review. In this fictional scenario the date has passed. The choice might still fit, or it might need replacing. The overdue signal suggests a review but does not change the stored active status. The SDK assessment is a scenario assumption, not a measured product ranking.

A linked benchmark has its own valid_until, if specified. Being six months old does not by itself make it expired in the scorer. Applicability to a new version or load needs separate assessment; an absent date neither proves freshness nor starts an otherwise nonexistent timer.

The link to scoring

An artifact's review date and each evidence item's date are separate inputs. An eligible item expired by its own date contributes 0.1 before verdict, CL and evidence-type arithmetic. An unexpired refutes item contributes 0, so its expiry can raise its contribution from 0 to 0.1 rather than lower it. Final recursive R_eff is the minimum over eligible own evidence and dependency contributions with their penalties; it may be below 0.1. The flat helper omits type modifiers and dependencies. Without valid_until an item has no expiry in this scorer.

M 12 · detect

valid_until expired · the artifact is flagged as overdue

In the illustrative scenario the ADR review date passed. forgeplan stale finds it but preserves status: active. This does not establish an R_eff drop: the evidence items' own dates have not passed. This is not an observed health response.

M 12 · renew

Illustrative outcome: explicit stale → renew until 2027-06-30

Renew directly from active would be refused. After review, an operator separately and explicitly changes the frontmatter to status: stale, then renew ADR-001 --reason "Re-evaluated" --until 2027-06-30 uses the allowed stale → active path (the generic guard also allows draft → active). The command appends a reason and changes the ADR status/date, not evidence. A separate new measurement on a newer LanceDB version reaffirms the choice in this fictional example; its results and own date must be recorded as new evidence, linked to the decision and rescored. No real measurement is claimed here.
