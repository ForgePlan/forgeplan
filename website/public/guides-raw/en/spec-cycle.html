01 · Spec versus PRD - the difference is in how you check it

Concept 01 · the analogy of a recipe and a taste test

A PRD says "what to build". A spec says "how the system has to behave"

The difference looks small and the consequences are huge. A PRD answers the question "what to build". A Spec answers the question "how the system has to behave".

The analogy is a recipe versus a taste test. A recipe can sound delicious and be impossible to execute; the final taste of a dish is checked only by eating it. A PRD is a recipe. A spec is the taste test.

PRD · intent
"Add tags to notes"
Sounds good at the product level. It is clear what the user wants. But: you cannot write a test for it, you cannot run it, and "matches / does not match" cannot be told apart.
not testable · level: product
Spec · behaviour
"POST /notes/:id/tags with an array of 1-10 ASCII strings → 200 + the tag list; duplicates are idempotent; an empty array → 400"
Testable behaviour. You can write a test, run it, and tell "matches" from "does not match". A contract between the expectation and the implementation.
testable · level: system behaviour
notes-tagging-spec.md · minimal skeleton active
Behaviour
  • POST /notes/:id/tags with a valid array → 200 + the tag list
  • POST with a duplicate existing tag → 200, idempotent
  • POST with an empty array → 400 {"error": "empty_tags"}
Invariants
  • A tag: 1-32 ASCII characters, normalisation - lowercase
  • At most 10 tags per note
Triggers · review zone
  • Changing the tag limit → review search-spec (filtering)
  • Changing the normalisation → review migration-spec
Out-of-scope
  • Tag hierarchy (covered by a future tag-hierarchy-spec)
  • Tag colors and icons
⚡ mandatory section
Out-of-scope is what makes specs composable

A PRD often skips this section, a spec never does. One spec owns one boundary of behaviour, everything else belongs to the neighbouring specs. Instead of one monolith you get a set of small independent files, each checked and changed on its own. The skeleton above is this lesson's teaching minimum; the Forgeplan spec template keeps its own sections (Summary, Scope, API Contracts, Data Models, Relationships, Validation Rules, Events / Side Effects, Versioning, Related), and there the boundary of responsibility is spelled out in Scope.

02 · Delta-spec and the dependency DAG

Concept 02 · the analogy of a git diff for requirements

A spec is not rewritten - it is changed through a delta

Say you already have notes-spec.md. Now you add tags. The bad path - rewrite the whole spec as v2 and commit it over the old one. Three months later nobody can tell what actually changed. The good path - write a delta-spec: an explicit diff with three sections.

+ ADDED
What appeared
New requirements that did not exist before. For example - POST /notes/:id/tags with an array of 1-10 strings, duplicates idempotent.
~ MODIFIED
What changed
Existing requirements marked BEFORE / AFTER. For example - GET /notes got the optional parameter ?tag=<name> for filtering.
− REMOVED
What was removed
Requirements that stop being in force. This feature has none - but if the old endpoint /tag-search existed, it would land here with its reason.
delta-notes-tagging.md · example # Delta for Notes - add tagging ## ADDED Requirements ### Requirement: Notes can be tagged POST /notes/:id/tags accepts an array of 1-10 strings (1-32 ASCII each). Duplicates are idempotent. Returns 200 + the full tag list. ## MODIFIED Requirements ### Requirement: Notes listing BEFORE: GET /notes returns all notes of the user. AFTER: GET /notes accepts an optional ?tag=<name> for filtering. Without ?tag - the behaviour is unchanged. ## REMOVED Requirements (empty - nothing is removed in this feature)

The team records the cascade explicitly in the Triggers section or a separate dependency file. This static teaching chart was not computed from a project and installs no monitoring. 85%, 80%, 60% and 25% are illustrative review-effort estimates, not measurements, probabilities or a promise to detect every consequence. The chart suggests neighbouring specs to inspect.

Delta is the contract between the past and the future

Without a delta every edit to a spec erases the history. With one you can open git log .forgeplan/specs/ six months later and walk through every ADDED / MODIFIED / REMOVED Requirement in reverse order - like git blame for requirements. The ADDED / MODIFIED / REMOVED section format is the one the Forgeplan delta parser reads (crates/forgeplan-core/src/artifact/delta.rs). This is not a formality, it is insurance against "why did a ?tag parameter appear in our GET /notes".

03 · R_eff - the coordinates of quality + Evidence Decay

Concept 03 · the analogy of a roadworthiness inspection

"Roadworthy" is not an average, it is the ability to spot a dangerous system

The analogy is a car's roadworthiness inspection. The inspector does not give one overall grade of "good car". He checks several independent systems: brakes, suspension, engine, electrics, body. The overall verdict "roadworthy / not roadworthy" is not an average, it is the ability to answer: "is there at least one system that makes the journey dangerous". A hypothetical brake score of 2 out of 9 illustrates why an average can hide a risk. A repeat inspection after six months is part of this teaching analogy, not a universal evidence deadline in Forgeplan.

R_eff uses a similar minimum principle, not inspection rules. Eligible evidence depends on verdict, CL, type and its own optional expiry date; the recursive result also includes dependencies. This is a product scale, not a probability of truth.

  • Verdict · the base contribution of unexpired evidence: supports = 1.0 / weakens = 0.5 / refutes = 0.0. On expiry the 0.1 override comes first, including for refutes.
  • CL · Congruence Level · where it came from. CL3 your own measurement in this same project (penalty 0.0) · CL2 a PoC in a related module or a test in a sibling project (penalty 0.1) · CL1 external documentation, someone else's blog, a talk (penalty 0.4) · CL0 a Stack Overflow answer from a different context, an opposing domain (penalty 0.9).
  • Score · for unexpired evidence only: the flat helper uses max(0, verdict − CL_penalty); the recursive engine uses max(0, verdict − CL_penalty − type_modifier) (measurement/test = 0, benchmark = 0.1, audit = 0.2). An expired eligible item returns 0.1 before verdict/CL/type, without these subtractions. Without valid_until this scorer applies no expiry; there is no universal TTL.
  • R_eff · the recursive minimum over eligible own evidence and dependency contributions. based_on/informs subtract 0.1 from a dependency contribution, floored at 0; refines/depends_on subtract 0. Terminal evidence is excluded, draft remains eligible; an empty ordinary population scores 0. The flat helper omits types and dependencies, so report fields can differ. Even with an expired item's 0.1 contribution, the result may be lower.

Evidence valid_until is optional: without it this scorer has no expiry and no default deadline. In this illustrative timeline E1 has its own 2026-10-01 date; its contribution stays 1.0 until expiry, then becomes 0.1 before verdict/CL/type, not a gradual decline along the coloured gradient. For refutes this can raise the contribution from 0 to 0.1. The final evidence/dependency minimum can be below 0.1; this diagram neither changes status nor shows final R_eff. The Spec's review date is separate. A 2023 Redis 6.x benchmark does not establish applicability to Redis 7.4; hypothetical 50 RPS does not establish results at 500 RPS. These illustrate contextual limits, not measurements. refresh_trigger: notes_count > 100_000 is an illustrative recommendation for a human or external monitor, not a built-in trigger. A date change is not a new measurement.
R_eff is not a verdict · it is a sensor

In the teaching population R_eff = 0.1 points to E3's weak contribution, not proof of a wrong decision. You can obtain a real CL3 measurement and reassess E3's applicability. Adding strong evidence alone cannot raise the minimum while E3 remains eligible: excluding it needs a separately justified applicability review. You can accept risk explicitly. "Review in 30 days or after 100k notes" is an illustrative team rule, not a product timer.

01 · Spec

You write notes-tagging-spec.md with four sections

Behaviour (3 behavioural contracts), Invariants (ASCII 1-32, max 10 tags), Triggers (links to search and migration), Out-of-scope (hierarchy, colors). A spec is checkable - every behaviour can be turned into a test.

02 · Delta

You write delta-notes-tagging.md on top of notes-spec

ADDED: the new endpoint /notes/:id/tags. MODIFIED: GET /notes with the optional ?tag. REMOVED: empty. The DAG shows: search-spec and migration-spec need a review. api-spec adds a new endpoint.

03 · R_eff

You score the decision "junction table vs JSON"

Use the table's synthetic E1/E2/E3 with the same complete assumptions: only these three eligible unexpired nonterminal items, explicit measurement type for each, no lower source_tier and no dependencies. E1 is an illustrative own measurement (CL3, supports, 1.0), E2 a fictional SQLite docs recommendation (CL1, supports, 0.6), E3 a fictional mailing-list report (CL1, weakens, 0.1). Recursive R_eff = min(1.0, 0.6, 0.1) = 0.1 matches the flat result here; average ≈ 0.57. This is not an executed benchmark: explicit benchmark type would reduce E1's recursive contribution to 0.9. "at risk" is a teaching assessment.

04 · Decay

Separate Spec review and evidence dates

In the illustrative Spec, frontmatter valid_until: 2026-10-01 is its review date, not every evidence item's date. E1's own optional scoring parameter valid_until: 2026-10-01 belongs in that evidence record's own frontmatter, from which it becomes record.valid_until; matching dates are chosen for this example. refresh_trigger: notes_count > 100_000 is a human note, not a built-in monitor. A real new measurement at 100k would require its own report and rescoring, not just a date change. Returning to a MODIFIED delta after six months is an illustrative team schedule, not a universal TTL.
