Agent interaction cycle · theory

Hint Contract · 5 markers

When a CLI command or an MCP tool returns a result - what should the agent do next? Without an explicit marker it re-reads CLAUDE.md, guesses, sometimes hallucinates and loops. Every guess costs tokens and risks an error. The Hint Contract is a local design for hint formatting. It reduces ambiguity where implemented, but does not guarantee that an agent will avoid errors.

01 · Why this contract is needed at all

Concept 01 · the analogy of traffic lights

Without an explicit next-action the agent pays a "guessing tax"

Imagine a road without traffic lights or signs. At every intersection the driver guesses: who goes first? Is the turn allowed? Do I have to stop? Every guess costs seconds of delay and the risk of a collision. Traffic lights remove the uncertainty: the colour is the action.

Forgeplan is a methodology engine. Every command or MCP call is one step of a long process (Shape → Validate → Code → Evidence → Activate). When nothing tells the agent what to do after the answer, it:

The tax · before the contract
What an agent does without an explicit next-action
  • Re-reads CLAUDE.md to reopen the methodology
  • Guesses the next step and sometimes hallucinates a command
  • Loops on the same phase
  • Substitutes a placeholder like EVID-NNN into a real command
  • Sees three equally weighted options - paradox of choice
tokens · risk of error · loss of context continuity
The solution · the 5-rule contract
What an agent does with an explicit marker
  • Reads Next: and checks authorization and prerequisites before executing the command
  • On Wait: schedules a retry with a condition
  • On Done. moves to the next task instead of looping
  • On Fix: checks whether the action addresses the error and is authorized
  • On Or: uses the fallback only if the primary is blocked
explicit next step · less ambiguity · not protection against hallucinations
Not "one more rule" · an interface contract

The Hint Contract is an intended local format contract for CLI text, CLI JSON, MCP success and MCP error. Individual output sites implement it; it is not a universal engine wrapper. For example, forgeplan score --all --json returns a response without _next_action. Clients must account for the specific response shape. A marker helps identify a suggested next step, but does not establish that the step is sufficient, authorized or correct.

02 · The five rules of the contract

Concept 02 · five intended format rules

The rules describe the intended contract, not a guarantee for every response

These local rules help hint authors make the next step clearer. Their application is response-specific; current universal coverage has not been established.

01
PRESENCE
Goal: a next-action or an explicit terminal. Exceptions exist: score --all --json has no _next_action.
02
ACTIONABILITY
Goal: a complete command with real IDs, not a fragment or placeholder. Prerequisites still need checking.
03
DETERMINISM
Goal: the same state yields the same hint at a particular output site.
04
CONDITIONALITY
Goal: an actionable hint or an honest terminal Done., not an "all done" promise.
05
CONSISTENCY
Goal: the same meaning in text, JSON and MCP; inspect each response's actual shape separately.
Where to read the hint, by surface

Where hints are implemented: CLI text · the last lines of stdout (Next:, Fix:, Wait:, Done.); CLI JSON / MCP · the _next_action field. list --json and tree --json retain a bare array for jq compatibility; the hint goes to stderr. forgeplan score --all --json has no _next_action; a missing field alone is not a bug.

03 · The five markers · the next-action language

Concept 03 · 5 markers with a fixed semantics

How to read markers within the local contract

In the intended contract, Next: denotes the primary action, Or: a fallback, and Error: with Fix: the error and proposed remediation. Done. is intended as a separate terminal signal, not proof that every check has been performed.

5 hint markers · v0.25.0+
Next:
Primary action - the recommended next step. A complete command with real IDs.
check prerequisites
Or:
An alternative, when the primary is blocked (for example, the claim is held by another agent).
fallback only
Wait:
Async / TTL state. The condition after which the request should be retried.
retry after condition
Done.
A terminal signal for this step under the contract, not proof that every check passed.
move on
Fix:
Proposed remediation paired with Error:. Check that it addresses the cause and is authorized.
check remediation

Drift prevention

The integration test crates/forgeplan-cli/tests/hint_contract.rs checks selected cases; scripts/audit-hints.sh collects a coverage metric. EVID-086 records a historical 70/70 command run, not current acceptance of all 120 command paths or every MCP response. Those checks were not run here. Their existence does not turn local rules into a universal guarantee of a marker in every response.

Three illustrative work-order patterns

These are authored illustrations, not captured responses or an executed scenario. forgeplan_…(...) is schematic MCP notation, not ready-to-send JSON; forgeplan … lines use CLI syntax. IDs are illustrative: use the IDs actually returned in your workspace. A marker does not replace authorization or prerequisite checks.

Pattern A
Shape → Validate → Evidence → Score → Activate

A validation PASS does not mean activation readiness. First fix the content, obtain truthful evidence and link it to the decision; then inspect the score and all applicable conditions: length, no stubs, evidence links, MUST checks and provenance.

forgeplan_route("add OAuth login") → Next: forgeplan new prd "OAuth login support" forgeplan_new(kind: "prd", title: "OAuth login support") → Next: forgeplan validate PRD-042 forgeplan_validate("PRD-042") → Next: obtain, record and link evidence (pattern B), then forgeplan score PRD-042 → Fix: correct the reported content errors, then rerun forgeplan validate PRD-042 forgeplan score PRD-042 → inspect evidence verdict, congruence, expiry and eligibility, dependency contributions and every activation condition forgeplan_activate("PRD-042") (only when all applicable conditions are met) → Done. (only if activation actually succeeds; not executed here)
Pattern B
Recovery after an error

Repeating validate and score without changing evidence cannot fix "No evidence linked". First obtain verifiable data, truthfully record it with its source, verdict and congruence_level, and link it to the decision. Support is not assured: the result may refute the decision and require reconsideration.

forgeplan_activate("PRD-042") → Error: No evidence linked → Fix: obtain truthful data and create an evidence record: forgeplan new evidence "OAuth login verification" → fill the created record with actual data; use its real returned ID → for this illustration, suppose the returned ID is EVID-017: forgeplan link EVID-017 PRD-042 --relation informs forgeplan validate PRD-042 forgeplan score PRD-042 → resolve remaining issues; inspect every condition in pattern A → retry activate only when all applicable conditions are met; no success is claimed here
Pattern C
Multi-agent dispatch with a claim conflict

Another worker's live claim is a signal not to take the same work: choose another assigned task, or wait for ordinary handoff, release by the holder or TTL expiry and recheck the claim. It is advisory, not a file-access lock. --force is only for explicitly authorized recovery after confirming the holder is no longer working, not an ordinary response to a live conflict.

forgeplan dispatch --agents 3 → Next: forgeplan claim PRD-054 --agent worker-1 --ttl-minutes 30 → Or: forgeplan list --status draft forgeplan claim PRD-054 --agent worker-1 --ttl-minutes 30 → Error: Already held by worker-2 → Wait: ordinary handoff/release or TTL expiry; then recheck the claim → Or: move to another assigned task, leaving worker-2's live claim intact

Quick reference

This is a reference for the local contract, not a universal guarantee. If a marker is absent, inspect the specific response and its documentation: forgeplan score --all --json is a known valid exception. Do not invent the next step or treat a marker as authorization to act.

FORGEPLAN HINT CONTRACT v0.25.0+
Next:<command> · check prerequisites and authorization
Or:<command> · fallback if primary blocks
Wait:<condition> · retry after condition
