FPF · First Principles Framework

FPF is not "just another methodology". It is an operating system for thought: a layer that turns intelligence - human or machine - into structured reasoning that works in collaborative settings. Trust Calculus and ADI, which I covered separately, are two FPF techniques. This page selects six concepts, not the whole framework, and three of the plugin's four modes: /fpf decompose, /fpf evaluate, /fpf reason. The fourth is /fpf lookup.

01 · What FPF is · six selected concepts

Concept 01 · an operating system for thought

Six concepts for this overview, not the full contents of FPF

FPF provides concepts for building methodologies, while tools (CLI, MCP, files) apply their own adaptations. In current upstream FPF, F is ordinal expression rigour, G is ClaimScope, and R is claim-specific warrant. ADI is Abduction → Deduction → Induction. Upstream requires a serious rival to the selected candidate, or justification for its absence, not a universal minimum of three.

These six selected concepts help you see connections between Trust Calculus, ADI, depth routing and decomposition. Three or more approaches are a local anti-anchoring habit and a product prompt request, not a parser guarantee.

01 · structure
Bounded Context
A part of the system with explicit boundaries and its own vocabulary. Inside, one set of rules and terms applies; outside, another. It stops you from mixing up "authorization" in the frontend sense with "authorization" in the backend sense. FPF section: A.1.1.
used in → /fpf decompose
02 · quality
Trust Calculus
A way to discuss a claim's warrant. The companion 3D lesson uses local 0–9 ratings and a min rule. That is a teaching rubric, not the upstream formula: F is ordinal expression rigour, G is ClaimScope, and R is claim-specific warrant. Current FPF has no universal min(F, G, R).
FPF B.3 · deep dive → trust-calculus.html (3D)
03 · axes
F-G-R
In current upstream FPF, Formality is expression rigour, G is ClaimScope (scope of applicability), and Reliability is claim-specific warrant. Granularity ("concreteness") is a local adaptation of G in the lesson and product, not the upstream definition. Your own measurement also needs assessment for applicability and quality.
FPF C.2 · local adaptation → trust-calculus 3D scene
04 · cycle
ADI Cycle
Abduction → Deduction → Induction: propose explanations → derive checkable consequences → check against facts. FPF B.5.2 requires a serious rival to the selected candidate, or an explanation of why there is none. At least three hypotheses is a separate local exercise and product prompt request, not a universal FPF rule.
FPF B.5 · local exercise → decision-cycle.html
05 · trap
Category Error
Confusing a role with a function, a method with the work, a process with a result. "Tech lead" is a role; "ran the review" is work. The same person can play different roles in different contexts. FPF section: A.7 (strict distinction).
checked in → /fpf decompose
06 · assembly
Gamma Algebra
The rules by which parts compose into a whole while keeping their properties. If every bounded context works correctly, that does not mean the whole system works - you need composition rules. FPF section: B.1 (universal algebra of aggregation, Γ).
used in architecture discussions
Not a methodology · a framework

FPF provides a vocabulary and reasoning rules on which working methodologies can be built. This overview connects Trust Calculus and ADI to six selected concepts without calling them the complete FPF kernel. Teaching number rubrics and workflow rules must be distinguished from upstream definitions.

02 · Three selected plugin modes

Concept 02 · three of the plugin's four modes

Modes help choose a perspective on the task

This page selects three plugin /fpf modes, not an upstream FPF taxonomy: decompose to understand a system's structure, evaluate to compare options, reason to explore causes and approaches. These perspectives can complement each other. Choosing a mode shapes the agent's task, but does not by itself guarantee the quality of the answer.

/fpf decompose, /fpf evaluate and /fpf reason are host-session commands of marketplace plugin fpf 1.7.1, not CLI subcommands. The fourth mode is /fpf lookup. Its 0–3 Formality/Granularity/Reliability rubric is local, not an upstream scale. The Rust forgeplan fpf group works with the knowledge base, dashboard, sections and rules.

/fpf decompose
Break it into parts
When you have a complicated system and need to understand its structure: who owns what, which subsystems exist, where the boundaries run.
Requested in this example: • table of contexts • diagram with boundaries • category-error check
when - starting a new feature, analysing an existing system, planning
/fpf evaluate
Compare the options
When you have to choose between alternatives with a count of the evidence. React vs Vue vs Svelte. SQLite vs PostgreSQL vs LanceDB.
Requested in this example: • strengths / weaknesses • F-G-R ratings using the plugin's local rubric • decision matrix • recommendation
when - choosing a library, a vendor, an architectural approach
/fpf reason
Reason about the cause
When you need to understand why something happens, or how to approach a problem. "Why did our response time degrade". "Why did conversion drop".
Requested in this example: • 3+ hypotheses as a local exercise (Abduction) • checkable consequences (Deduction) • check against facts (Induction) • scored hypotheses
when - debugging, incident analysis, justifying architecture
Illustrative agent session with a plugin · not a verified shell transcript > /fpf decompose our authentication system → Table: Context · Responsibility · Roles · Interfaces → Mermaid diagram with boundaries → Check: is "token generation" a role or a function? > /fpf evaluate React vs Vue vs Svelte for our SPA → Strengths / weaknesses for every option → F-G-R ratings using the plugin's local rubric → Matrix + recommendation > /fpf reason why our API response times degraded → Abduction: 3+ hypotheses in this example (load / index / N+1 / GC pauses) → Deduction: what should be observed for each → Induction: check against metrics → Conclusion + remaining uncertainties

03 · Knowledge base and how it links to the other moves

Concept 03 · a searchable base of first principles

FPF ships as a searchable knowledge base and enriches the ADI analysis

The full FPF specification can be indexed as a searchable base. That means you can look up specific FPF sections and enrich the ADI analysis with them. For example, section B.3 describes the Trust & Assurance Calculus (F-G-R together with Congruence), while B.5 is the canonical reasoning cycle, with the abductive loop B.5.2 inside it. If in a complex ADI run you want to use notions such as "bounded rationality" or the "exploration-exploitation trade-off", the --fpf flag pulls the relevant context out of the base.

Conceptual flow · working with the FPF base # 1. Load the FPF specification into the index → sections indexed · the count depends on the revision of the loaded specification # 2. Find a specific section by keyword → search "bounded context" → A.1.1 (definition) · A.14 (composition) · A.7 (strict distinction) # 3. Open the full text of the section you need → section B.5 - the canonical reasoning cycle # 4. Run the ADI analysis enriched from the FPF base (the --fpf flag) → sections B.3 (Trust Calculus) + B.5 (ADI) pulled in → hypotheses proposed with "bounded rationality" in mind
When to use --fpf, and when not to

Without --fpf the ADI run works on general grounds. With --fpf the model sees the concrete definitions and techniques from the specification, which often gives a deeper analysis. But it costs extra LLM calls. Use --fpf for Deep+ decisions, where the cost of a mistake pays for the overhead. For Standard - without the flag is enough. On workspaces migrated to the new storage layout, the path with --fpf may report that the knowledge base is unavailable: that is the expected answer, not a breakage.

The three selected plugin modes can form a chain with resulting artefacts. /fpf decompose helps you take a new system apart - the result becomes the basis of a requirements document. /fpf evaluate gives you a comparison of options - the output becomes the rationale for an architectural decision. /fpf reason runs the ADI analysis, which lands in the "options considered" section of the accepted decision.
