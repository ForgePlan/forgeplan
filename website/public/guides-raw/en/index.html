Interactive breakdowns of the methodology

A catalog of twenty self-contained pages that explain the ForgePlan methodology through analogies, visualisations and worked examples. Each one opens with a double click, reads as one person's sitting, and runs from concept to cli command. This file is a separate entry point into the catalog. Below are three ways to find the breakdown you need: by question, by the core route, or by topic.

The core route · ten breakdowns

Ten breakdowns that form the core route: each one builds on the previous ones. You can jump around, but if this is your first time, top to bottom leaves the fewest gaps. This is a selection, not the whole catalog: the other ten breakdowns are gathered in the "By topic" section below.

01
foundation · one decision theory
ADI · DDR · Trust Calculus
How an investigator works: three hypotheses, checkable consequences, evidence. The DDR is the rationale with the conditions for revisiting. The Trust Calculus is an F/G-R reading of evidence strength under the WLNK rule.
→
02
companion to 01 · interactive 3D chart
Trust Calculus in 3D F/G/R
A 3D scene with seven pieces of evidence on a /search latency scenario. The F+G+R=12 threshold plane, hover cards, hypothesis selection by WLNK. You can spin the scene with the mouse - a teaching artefact for a projector.
→
03
one feature theory
BMAD · local PRD mockup · Adversarial Review
Upstream BMAD phases: Analysis (optional) → Planning → Solutioning → Implementation. The 13-section PRD mockup and 3 highlighted sections (Non-Goals, Risks, Open Questions) are a local teaching exercise, not upstream requirements. Fresh-eyes review is the local third quality gate.
→
04
one specification theory
Spec · Delta · R_eff
Spec versus PRD: verifiable behaviour, not intent. The ADDED/MODIFIED/REMOVED delta format as a git diff for requirements. R_eff = min(scores) with Evidence Decay - why the average deceives and the minimum does not.
→
05
the tool itself meta
Forgeplan as the operational layer
A POS for methodologies: CLI + MCP + .forgeplan/ connect FPF, BMAD, OpenSpec, QuintCode with a dependency DAG. The lesson selects a historical subset of 10 types, not all 17 current ArtifactKind variants; 6 are highlighted for examples. Four depth levels and three quality gates in one validate.
→
06
companion to 05 · interactive 3D graph
DAG Explorer · artifacts in 3D
A Plotly 3D scatter with artifact nodes and edge lines. Knowledge Vault MVP is an authored teaching dataset, not a measured real project: 24 nodes, 23 logical edges (22 relations + a trigger), and 29 rendered segments because 6 evidence links are drawn twice. Type filters show healthy chains, blindspots, orphans and branching.
→
07
companion to 05 · interactive calculator
Depth Calibrator · routing in real time
Three sliders (complexity / blast radius / reversibility) plus three hard gates (public API / security / cross-team) give a real-time depth tier and pipeline. Presets for typical scenarios (cosmetic / team feature / public API / auth rewrite). Move the sliders and watch the marker move and the artifact list change.
→
08
after activate theory
Lifecycle · from draft to terminal
Five stored states. Superseded/deprecated have no outgoing transitions. Reopen from active/stale creates a new draft with lineage and a based_on edge, then deprecates the old artifact. Renew uses the generic draft/stale → active guard, not terminal states. Active remains editable; expiry detection does not rewrite status.
→
09
agent ↔ tool language theory
Hint Contract · 5 markers
How the agent stopped hallucinating next steps. Five markers (Next: / Or: / Wait: / Done. / Fix:) plus five contract rules (Presence / Actionability / Determinism / Conditionality / Consistency). A reference card.
→
10
parallel work theory
Multi-agent · dispatch · claim · release
A teaching workflow for 2–5 agents in one repo. Dispatch considers claims and declared-file overlap heuristics; it does not guarantee freedom from conflicts. A claim with a TTL is an advisory intent marker, not an access lock. WIP=1 and a separate reviewer are local workflow rules, not runtime limits.
→
