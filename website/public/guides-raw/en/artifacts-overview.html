ARTIFACTS · OVERVIEW

Managing team artifacts

Six months after a release, decisions have to be reconstructed from records or memory. An agreement about where decisions must be recorded helps. Here an artifact is a structured record with an owner and a review process. This is a proposed team practice, not a universal standard for every document.

What counts as an artifact?

In everyday usage, an artifact can be any work file. In the decision-journal practice described here, it means something more specific: a record with a required structure that captures one decision, one requirement, or one item of evidence.

Three properties distinguish this kind of artifact from an ordinary document.

First, required fields defined by an agreed template. The decision format proposed here requires a review condition. Requirements and evidence may need different fields. Agreeing on a structure helps expose omissions before a record is approved.

Second, version history. Keep the artifact alongside the code in version control. Its history should show who reconsidered what and when. This is a chronology, not just a file labelled “latest version.”

Third, substantial changes are recorded as a review. This is a team rule, not technical immutability after activation. A typo can be corrected with a recorded change; a changed decision is better captured separately, with a date, rationale, and link to the old decision. A wiki can also preserve history.

A useful analogy is a series of dated observations: add new information with an author and date rather than presenting it as earlier knowledge. This illustrates record keeping; it is not a claim about medical-record rules.

One file, one responsibility

A possible antipattern is “let’s put every decision this quarter in one big document,” or “we have a master specification; everything is there.” The appeal is understandable: fewer files and less switching.

Imagine that after four to six months the master document has reached 80 pages and finding a decision takes an hour. These are illustrative values, not a team measurement. Without explicit statuses and review conditions, current and obsolete decisions become hard to distinguish. The document risks becoming “the archive we never open.”

“One file, one decision” makes targeted review easier. When the context for one choice changes, open its record. Related decisions still need checking: file boundaries do not remove dependencies. An explicit status—active, replaced, or requiring review—helps readers navigate without reading the archive.

In practice, the database choice gets a file. The API format gets another. A performance requirement gets its own record. Evidence that the requirement was met gets another record, with an explicit link to the requirement.

For example, a team might accumulate 40–80 artifacts in a year. That is a hypothetical scale, not a norm or statistic. What matters is that each record answers one question and can be found by title, keyword, or relation.

A working rhythm for artifacts

Structure makes more sense alongside the work it supports. The following is a suggested cycle, from first draft to the point when a record no longer reflects the current context.

  1. Create a draft
    Start from a template and record the context and provisional rationale. A draft is not a commitment: it is space to think before recording a final choice.
  2. Fill the required fields
    For a decision: context, alternatives, evidence, the choice, reasons for rejecting alternatives, and a review condition. Three alternatives are a useful local anti-anchoring heuristic, not a universal FPF threshold. The record type determines its fields and readiness criteria.
  3. Review the record
    Ask a teammate to read it: “If I work with this a year from now, will I understand what was decided and why?” If not, revise the record.
  4. Activate
    The record moves from draft to active. It represents an accepted choice, not a technically locked file. Under the proposed team convention, substantial changes get a separate review linked to the earlier record.
  5. Monitor the review condition
    Record a date or event and who will check it. Date-based detection can list an overdue record without changing its stored status. A person or separately configured monitor must track an event or metric; writing a condition does not install a monitor.
  6. Reconsider or extend
    If the decision remains appropriate, extend its review date with a reason. If the context has invalidated it, open a new draft with the updated context and repeat the cycle. Keep the old record as history.

What makes an artifact maintainable?

Documentation can become obsolete when nobody returns to it after creation. Structure alone is not enough: it needs an owner and an actual review process. The following three properties support review, but do not make records update themselves.

A named person, not an anonymous “team secretary.” Anonymous corporate phrasing—“it was decided,” “the team agreed”—hides useful context. Name the person responsible for the choice. A year later, readers know whom to ask if the record is incomplete.

An observable review condition and an owner. Instead of “review someday,” specify a date six months away, a threefold increase in load, or a library release. Use an actual date for a deadline and an observation method for an event. Configure reminders or an external monitor separately. A sentence in the record does not initiate review.

Linked evidence, not a passing mention. “We checked; it was fine” is not inspectable evidence. Link to a concrete measurement. An illustrative entry might say “230 ms at peak load, data from April 12, stored in this file.” When the context changes, readers can inspect whether the conditions of that measurement still apply.

Antipatterns

Five illustrative failures. These scenarios show risks, not measured frequencies or a measured timetable for documentation decay.

  • ARCHIVE DUMP
    A team creates records but never reviews them. Imagine 60 “active” records a year later, half describing a world that no longer exists. Nobody touches them “in case something breaks.”
  • SILENT EDIT
    Someone silently rewrites an active record “to bring it up to date.” There is no dated explanation. Three months later, nobody knows when the decision changed or what it replaced.
  • EMPTY TEMPLATE
    The fields exist but say nothing: “context: working on project X,” “options: considered several,” “review: as needed.” This creates the appearance of documentation without recording a usable decision.
  • MEGADOCUMENT
    Every decision for the quarter lives in one file. A change to one choice rewrites the shared document. The history becomes difficult to interpret. In this hypothetical example, finding a decision takes 20 minutes.
  • NO EVIDENCE
    A decision is chosen, recorded, and activated, but has no linked evidence. “We decided” without inspectable supporting data records a choice but gives readers no way to reassess it when the facts change.
