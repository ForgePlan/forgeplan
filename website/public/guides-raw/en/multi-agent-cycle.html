Multi-agent work · coordination

Multi-agent · dispatch · claim · release

When five PRDs, three ADR reviews, and two evidence investigations need attention, independent work can be split across agents. Planning, claiming work, and releasing it help coordinate that split. Forgeplan’s dispatch, claim, and release are one implementation. They neither launch the agents nor guarantee conflict-free edits.

CLI notes refer to the inspected 0.39.0+constellation.s1.1 source snapshot, not the public 0.38.0 release. Captured help supplies syntax, not evidence that a proposed wave ran. Names are coordination identities, not access permissions.

01 · Where sequential work becomes a bottleneck

Concept 01 · a surgical-team analogy

A surgeon, anesthetist, assistant, and nurse have distinct responsibilities

Picture a surgical team: the surgeon operates, the anesthetist monitors vital signs, the assistant helps with instruments, and the nurse manages the sterile field. This is an analogy for explicit responsibilities, not a claim that software agents provide clinical safeguards.

In repository work, separate writing and critical review can help expose assumptions. A fresh review session has not authored the draft, but that does not eliminate bias. It still needs the relevant context and inspectable evidence.

Solo · sequential
One agent handles five activities in turn
  • Draft PRD-001
  • Draft PRD-002
  • Review PRD-001 in the same context; inspect anchoring risk
  • Collect evidence
  • Inspect the score and activation requirements
Illustrative schedule · no measured duration
Multi · independent work in parallel
Three agents and a separate coordinator
  • worker-1 drafts PRD-001
  • worker-2 drafts PRD-002 in a separate bucket
  • reviewer critically reviews a completed draft in a fresh session
  • Each worker follows the team’s WIP=1 convention
  • The coordinator assembles evidence and checks readiness
Illustrative roles · no speedup or bias-free guarantee
Parallel work needs coordination

Agents can collide on files or act on stale assumptions. Planning, claims, and releases make intentions visible; they do not replace explicit file ownership, isolated worktrees, integration review, or serialized access to shared build and runtime resources.

02 · Three coordination primitives

Concept 02 · dispatch / claim / release

Each primitive handles one part of the handoff

Treat them as three phases of a coordination cycle: a planner proposes buckets, a worker records intent with an expiry, and the same holder releases the marker when handing work back.

01 · planner
forgeplan dispatch --agents N
Suggests buckets and a serial queue for N agents. Declared-file overlap and graph heuristics help identify conflicts; they do not prove safe execution. The core supports 1–64 agents. The help phrase “parallel-safe” describes intent, not a conflict-free guarantee.
When: before a parallel work wave
02 · worker
forgeplan claim <id> --agent <name> --ttl-minutes 30
Records advisory intent for an artifact. TTL defaults to 30 minutes and accepts 1–1440. Another live holder is refused; the same holder can renew. Expired files remain on disk but are omitted from ordinary claim reads. File edits are not locked.
When: before starting the assigned work
03 · worker
forgeplan release <id> --agent <name>
Releases a marker held by the matching identity. If work continues near expiry, renew using claim with the same holder. Do not release another worker’s live marker; force is an explicit recovery capability, not the normal workflow.
When: work is complete or explicitly handed back

03 · WIP=1 as a team convention and independent review

Concept 03 · rules and failure modes

Agree on one work item per worker; give reviewers fresh sessions

WIP=1 means limiting a worker to one current work item. This is a suggested team convention, not an enforced one-claim-per-agent product limit. Claims are keyed by artifact: one agent can hold markers for several artifacts.

Illustrative claims table

$ forgeplan claims Authored HTML · not live or auto-updating
Artifact Agent Task TTL left
PRD-054 worker-1 draft OAuth login PRD 25m
PRD-055 worker-2 draft email digest PRD 12m
PRD-056 worker-3 draft search v2 PRD 28m
ADR-007 reviewer adversarial review (clean session) 15m

If PRD-056 has a live claim held by worker-3, a claim from worker-2 is refused. That protects the advisory marker, not file access: either process could still edit a file outside this protocol. Read actual hints rather than assuming every refusal has a particular Or/Wait response.

Use a separate review session by team agreement

After worker-1 hands PRD-054 back and releases its claim, reviewer can claim it in a fresh session. Supply the draft, requirements, and evidence, but not a demand to defend the author. This is the review convention proposed here, not an enforced claim rule or a guarantee of unbiased BMAD review.

One illustrative wave · 3 workers + a reviewer

OAuth, email digest, and search v2 provide three example work streams. A coordinator proposes assignments, workers draft PRDs, and a reviewer checks completed drafts. The allocation and TTL values are authored examples, not current project observations.

01 · dispatch

forgeplan dispatch --agents 3 --json

In this illustration, worker-1 has OAuth (4 artifacts), worker-2 digest (3), and worker-3 search (3). Review file ownership, dependencies, shared resources, and serial work before starting. A dispatch result does not prove that the buckets are conflict-free.

02 · claim ×3

Each worker records intent in its own session

For example: forgeplan claim PRD-054 --agent worker-1 --ttl-minutes 30. worker-2 uses PRD-055 and worker-3 PRD-056 with their own identities. Inspect forgeplan claims. WIP=1 is the team’s agreement, not a product-enforced agent limit.

03 · work

Draft, collect evidence, and validate within assigned boundaries

To renew, the same holder repeats forgeplan claim PRD-054 --agent worker-1 --ttl-minutes 30; there is no --extend flag. If done sooner, release with forgeplan release PRD-054 --agent worker-1, then take the next assigned artifact.

04 · adversarial

A completed draft is handed to the reviewer

After the author releases the marker, reviewer claims the record in a fresh session and checks specific assertions. Report substantiated findings and return revisions to the author. There is no promised number of findings or “real defects.” Release the review claim before the author reacquires it.

05 · release

Finish the assignment and release its marker

The current holder releases when its assigned work ends, whether that assignment was drafting, review, or implementation. Release is not activation. The coordinator checks actual readiness and integration results before starting another wave or closing the work.
