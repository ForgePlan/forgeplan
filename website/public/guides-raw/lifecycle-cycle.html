Цикл жизни артефакта · теория

Lifecycle · от draft до terminal

Артефакт - не статичный документ, который пишется один раз и забывается. Он эволюционирует: draft становится validated planом, активное решение через год заменяется лучшим, бенчмарк устаревает и требует пересмотра. Без управления жизненным циклом - зомби-документы, устаревшие спеки, которым никто не доверяет, но никто не удаляет. Lifecycle даёт каждому артефакту явный статус и явные правила перехода - так что вы всегда знаете: это current? validated? replaced? нужно ли ему ещё доверять?

01 · Пять состояний · что означает каждое

Концепция 01 · аналогия паспорта с визой

Каждый артефакт всегда находится в одном из пяти состояний

Паспорт сам по себе - это draft: документ есть, но без визы пересечь границу нельзя. Активная виза напоминает active, просроченная — необходимость пересмотра. Но у артефакта дата сама не записывает status: stale: это отдельное явное изменение. Замена визы напоминает supersede, отмена без замены — deprecate.

Система журналирования фиксирует это явно - у каждого артефакта в frontmatter поле status: строго одно из пяти значений. Никаких «не помним», никаких «вроде закрыли».

● draft
Work in progress
→ active (activate; нужны все применимые проверки)
● active
Validated, in use
→ superseded
→ deprecated
→ stale (явная запись, не детект)
● stale
Записан status: stale
→ active (renew)
→ deprecated + новый draft (reopen)
● superseded
Заменён новым
terminal · no exit
● deprecated
Больше не релевантен
terminal · no exit
State machine · выбранные переходы записанного статуса, не детект срока
транзишн, требующий действия транзишн в терминальное состояние явная запись stale, не авто-переход

Схема не исчерпывающая: общий guard для renew допускает записанные draft → active и stale → active, но не active → active. reopen принимает active или stale, создаёт новый draft и переводит старый в deprecated. Обнаружение истёкшего valid_until не является ни одной из этих записей.

Terminal - буквально terminal

Из superseded и deprecated нет выхода. Это не «временно убрали, потом вернём» - это точка истории. Если решение нужно вернуть (например, выбирали JWT → переходили на sessions → опять нужен JWT) - создаётся новый артефакт ADR-003, который supersede'ит ADR-002. Старый ADR-001 остаётся superseded - это сохраняет реальный timeline решений.

02 · Пять команд и отдельный сигнал по дате

Концепция 02 · decision tree переходов

Не «как переименовать» - а «какой transition отражает реальность»

Каждый переход - это семантическое утверждение, а не просто смена строки в frontmatter. Выбор не «как мне удобнее назвать», а «что на самом деле произошло с решением».

decision tree · какой transition применять
activate Артефакт готов, validated, можно строить от него draft → active «зелёный свет» - план одобрен и пошёл в работу
supersede Появился лучший вариант, который заменяет старый active → superseded PRD-001 (basic JWT) → PRD-002 (OAuth2 federation)
deprecate Артефакт больше не релевантен совсем active → deprecated Фича отменена, модуль удалён, контекст изменился
renew Пересмотр обосновал продление; записан draft или stale, не active draft/stale → active Учебный ADR про LanceDB: выбор подтверждён; evidence обновляется отдельно
reopen Active- или stale-артефакт нужно переосмыслить заново active/stale → deprecated + new draft Старый deprecated, новый draft создаётся с lineage
stale (детект) Необязательный valid_until истёк — запись найдена как просроченная status не меняется Это сигнал для ревью, не запись active → stale и не таймер по умолчанию
Независимые учебные примеры · не протокол запуска // Проверить готовность; PASS сам по себе не доказывает все условия активации review PRD-001 // Иллюстративный исход: Review PASSED; проверить остальные применимые условия // Активировать: draft → active activate PRD-001 → Activated PRD-001 (draft → active) // Заменить: active → superseded, PRD-002 становится преемником supersede PRD-001 --by PRD-002 → Superseded PRD-001 → PRD-002 // Устаревить: больше не релевантен deprecate PRD-001 --reason "No longer needed" → Deprecated PRD-001: No longer needed // Отдельный пример с записанным stale (draft тоже допустим); active отклоняется renew PRD-001 --reason "Re-validated" --until 2026-12-31 → Renewed PRD-001 (stale → active) // Другой пример с active/stale, не продолжение supersede/deprecate выше reopen PRD-001 --reason "Needs major revision" → Reopened PRD-001 → deprecated Link: PRD-NNN --based_on--> PRD-001
Validation gates по типу артефакта

PRD, RFC, ADR, Epic, Spec требуют проверки перед активацией - десятки правил на тип артефакта (MUST-секции, отсутствие implementation leakage, information density, measurability, traceability): у глубокого PRD их больше тридцати, у Spec, ADR, RFC и Epic - от десятка. Note и Problem могут активироваться без validation gate - они быстрые captures, и формальные правила здесь только мешали бы фиксировать сигнал.

03 · Stale · самое опасное состояние

Концепция 03 · забытое состояние

Stale не значит «неверно». Stale значит «никто не проверил, что всё ещё верно»

Большинство команд игнорируют stale - и это самая опасная ошибка. Когда дата valid_until у артефакта истекает, артефакт попадает в список просроченных. Это не «он сломался» - это сигнал, что контекст мог измениться, а решение зафиксировано на старых данных.

Просроченность вычисляется по необязательной дате: forgeplan stale находит записи, у которых valid_until уже в прошлом. Поле status: не переписывается: active остаётся active, а не автоматически становится stale. Без даты такого срока нет; универсального TTL для артефактов или evidence здесь нет. renew использует общий guard: записанные draft → active и stale → active допустимы, active → active — нет. Для просроченной active-записи сначала нужен осмысленный выбор: отдельная явная запись stale перед renew либо reopen для нового разбора. Reopen принимает active и stale. Продление даты решения не перезамеряет и не обновляет связанные evidence.

⚡ учебный сценарий · не история измерений

Допустим, полгода назад команда выбрала LanceDB, считая Rust SDK подходящим для своих задач. Для ревью ADR задали valid_until: 2026-04-15. В этом вымышленном сценарии дата уже прошла. Выбор может оставаться подходящим, а может потребовать замены. Сигнал просроченности предлагает пересмотр, но не меняет записанный active. Оценка SDK здесь — условие примера, не измеренный рейтинг продуктов.

У связанного бенчмарка своя дата valid_until, если она задана. Шесть месяцев возраста сами по себе не делают его просроченным в scorer. Применимость к новой версии и нагрузке нужно оценить отдельно; отсутствие даты не доказывает актуальность, но и не включает несуществующий таймер.

01 · сейчас
active · до даты ревью
Дата решения ещё впереди. Evidence оцениваются по собственным полям и датам.
02 · истечение
active · обнаружен просроченным
valid_until решения прошёл; forgeplan stale находит запись. Status остаётся active. Даты и оценки evidence от этого не меняются.
03 · выбор
renew или reopen
Рекомендуется пересмотр. Renew допускает записанные draft/stale → active, но не active → active. Для active сначала явно записывают stale либо выбирают reopen (active/stale → новый draft + deprecated старого).
04 · итог
Продление или новый draft
Renew меняет статус/дату цели и добавляет причину. Reopen создаёт новый draft с lineage и закрывает старый. Новый замер evidence — отдельная работа.
Независимые учебные команды · не результаты запуска // Найти просроченные по дате записи, не переписывая status forgeplan stale // Только если записан draft/stale и продление обосновано; не для active renew ADR-001 --reason "Re-evaluated, still best option" --until 2027-06-30 // Альтернатива для active/stale: новый разбор, не автоматический результат renew reopen ADR-001 --reason "New alternatives available, fresh evaluation"
Связь со scoring

Дата ревью артефакта и дата каждого evidence — разные входы. Если пригодный элемент evidence просрочен по собственной дате, его вклад равен 0.1 до расчёта verdict, CL и модификатора типа. Для непросроченного refutes вклад 0, поэтому его истечение может повысить вклад с 0 до 0.1, а не понизить. Итоговый рекурсивный R_eff — минимум по пригодным собственным evidence и вкладам зависимостей с их штрафами; он может быть ниже 0.1. Плоский helper не учитывает типы и зависимости. Без valid_until у элемента нет истечения в этом scorer.

Полный цикл на одном артефакте · ADR-001

Учебный сценарий выбора Vault DB за 18 месяцев, не исторический отчёт. Все числа, исходы проверок, замеры и сравнения API ниже иллюстративны; это один путь, не все состояния.

М 0 · draft

ADR-001 создан · статус draft

Frontmatter: status: draft, depth: deep, valid_until не установлен. 3 гипотезы из ADI (FAISS / LanceDB / pgvector), evidence пока пустое.

М 0.5 · active

Учебный исход: проверки пройдены → активация

Условно прошли 3 quality gates; это не полный список условий активации, остальные применимые условия также считаем выполненными. Ровно один пригодный непросроченный собственный evidence: supports, явный CL2, benchmark — max(0, 1 − 0.1 − 0.1) = 0.8. Ровно одна пригодная based_on-зависимость с таким же единственным evidence и без своих зависимостей даёт 0.8 − 0.1 = 0.7. Других вкладов нет; оба evidence не terminal, source_tier не задан. Рекурсивный R_eff = min(0.8, 0.7) = 0.7; плоский helper только собственного evidence дал бы 0.9. status: active, дата ревью ADR valid_until: 2026-12-01; evidence имеют отдельные даты после неё. Активный Markdown можно править.

М 12 · детект

valid_until истёк · артефакт помечен просроченным

В учебном сценарии дата ревью ADR прошла. forgeplan stale находит его, но status: active сохраняется. Из этого нельзя вывести падение R_eff: собственные даты evidence ещё не прошли. Это не наблюдавшийся вывод health.

М 12 · renew

Учебный исход: явный stale → renew до 2027-06-30

Renew прямо из active был бы отклонён. После пересмотра оператор отдельно и явно меняет frontmatter на status: stale, затем renew ADR-001 --reason "Re-evaluated" --until 2027-06-30 использует допустимый stale → active (общий guard допускает также draft → active). Команда добавляет причину и меняет статус/дату ADR, не evidence. Отдельный новый замер на новой версии LanceDB в этом вымышленном примере подтверждает выбор; его результаты и собственную дату нужно записать как новое evidence, связать с решением и пересчитать оценку. Реального замера здесь не заявлено.

М 18 · supersede

Появился лучший вариант → ADR-002 заменяет ADR-001

В учебном сценарии команда сочла API sqlite-vec более подходящим — это не измеренный факт о продуктах. Предположим, ADR-002 создан и активирован после всех применимых проверок. Затем ADR-001 явно superseded с заменой на ADR-002; история сохранена. Успех этих операций здесь иллюстративен.
