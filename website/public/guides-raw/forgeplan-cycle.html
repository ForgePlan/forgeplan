Forgeplan как operational layer

Forgeplan — CLI и MCP-сервер рядом с репозиторием. Он автоматизирует часть работы с артефактами; обоснование решений и проверка результатов остаются за людьми и агентами.

Примеры интерфейсов относятся к проверенному снимку исходников 0.39.0+constellation.s1.1, не публичному релизу 0.38.0. Captured help задаёт синтаксис; ревью исходников и сохранённые наблюдения — оговорки о поведении. Новый результат выполнения здесь не заявлен.

01 · Forgeplan как operational layer

Концепция 01 · аналогия POS-терминала

Официант выбирает блюдо. Терминал помнит цены, НДС, дисконты, бонусы

Когда в ресторане официант принимает заказ, он не держит в голове прайс, состав блюд, НДС, дисконтные карты и бонусы. Он нажимает кнопки в POS-терминале, а терминал помнит всё. Роль официанта - выбрать блюдо. Роль терминала - правильно оформить.

Forgeplan похож на такой терминал, но его адаптации не тождественны upstream-методикам. BMAD влияет на продуктовое планирование, OpenSpec — на изменения спецификаций, Quint Code — на работу с evidence, FPF — на рассуждение. В продукте свои шаблоны, проверки, эвристики FGR и движок R_eff. Интеграция не заменяет проверку самих доказательств.

Адаптации с явными границами реализации

Инициализация создаёт .forgeplan/. Команды ниже иллюстрируют создание ADR; это не captured стенограмма.

Авторский пример терминала · создание ADR $ forgeplan init # Прочитайте фактический результат инициализации. $ forgeplan new adr "Vault architecture: Express + SQLite + Ollama + Anthropic" # Используйте ID и путь из фактического ответа. # Заполните контекст, решение, альтернативы и последствия. # Укажите требования к evidence и условия пересмотра. # Выберите глубину для реальной задачи явно. # Текст условия пересмотра не устанавливает монитор событий. Next: forgeplan reason ADR-001

Заполните шаблон, который действительно вернул инструмент. Проверенный ADR-шаблон разделяет Context, Decision, Alternatives Considered, Consequences, Evidence Requirements и Valid Until; есть дополнительные секции по глубине. Три альтернативы — местная договорённость промпта, не универсальный порог FPF. Сгенерированный шаблон ещё не является завершённым рассуждением.

MCP-сервер предоставляет инструменты подключённому клиенту. Получит ли агент нужные PRD и ADR, зависит от инструкций клиента, доступа к инструментам и поведения агента. Для «добавь логирование в auth-сервис» попросите прочитать записи и проверить ссылки. Сам доступ не гарантирует автоматическое чтение или соблюдение всех прежних решений.

Различайте рамку и расчёты продукта

Upstream FPF различает порядковую F (строгость выражения), G (ClaimScope) и R конкретного утверждения. Forgeplan отдельно считает Formality, Granularity и Reliability на шкалах 0–1: итог FGR — cube_root(F × G × R). В reference Quint Code есть текстовая рубрика FGR и отдельный калькулятор формальности/надёжности; это не одна общая формула.

02 · Типология артефактов и DAG зависимостей

Концепция 02 · типология артефактов

Шесть выделенных типов с явными связями

Представим требования в Jira, обсуждение дизайна в Confluence, ADR в docs/, evidence в PR-комментариях и файлах бенчмарков. Если связи остаются только в памяти автора, позднему читателю трудно восстановить, почему выбрали gRPC вместо REST.

Forgeplan хранит записи в файловом workspace. Здесь выделены шесть типов; таблица выбирает десять, а не перечисляет все типы ядра или enum создания MCP.

PRD
prefix · prd-
Что? Что строим и для кого
Продуктовые требования. В upstream BMAD работа с PRD относится к Planning, не к фазе «Delivery». Формулируйте FR как «[Actor] can [capability]», без выбора технологии вместо требования.
RFC
prefix · rfc-
Как? Как это можно сделать
Предложение изменения с альтернативами. «Рассматриваем переход с REST на gRPC, вот три варианта». Открытое обсуждение, не финальное решение.
ADR
prefix · adr-
Почему? Почему именно так
Принятое архитектурное решение со ссылками на предложения и evidence. Активные файлы можно менять разрешёнными update. При смене решения оформляйте явную замену; активация не делает файл технически неизменяемым.
Spec
prefix · spec-
Контракт? Как ведёт себя система
API-контракты и модели данных. Парсер delta в выбранном продукте поддерживает ADDED / MODIFIED / REMOVED. В upstream OpenSpec есть также RENAMED; это не доказывает поддержку в продукте. Подробнее — цикл спецификации.
Epic
prefix · epic-
Связка? Что общего у группы PRD
Объединяет несколько PRD вокруг крупной цели. Epic помогает организовать группу работ, но не следует из отдельного обязательного конвейера Critical.
Evidence
prefix · evid-
Работает? Какие данные подтверждают
Тест, замер, бенчмарк или аудит с объёмом и происхождением. Scorer читает verdict, CL и тип evidence. R_eff агрегирует допустимые вклады, а не тройку F/G/R на шкале 0–9 как универсальную формулу доверия.

Метаданные и типизированные связи делают отношения проверяемыми. Ниже схема, не дословный сгенерированный файл и не полное описание типизированных рёбер:

Схема frontmatter · условные ID, не captured файл --- id: adr-001 type: adr title: "Vault architecture: Express + SQLite + Ollama" depth: deep status: active related_artifacts: - prd-001 # откуда требование - rfc-001 # откуда обсуждение - evidence-001 # бенч p99 latency valid_until: 2026-12-01 ---

Через полгода - одна команда вместо археологии

forgeplan graph выдаёт текст Mermaid; отобразите его совместимым просмотрщиком. В captured help нет флага --format mermaid. Граф помогает проследить путь от требования до evidence, если связи поддерживаются. Ссылки становятся проверяемыми, но их утверждения от этого не становятся доказанными.

03 · Depth calibration и quality gates

Концепция 03 · аналогия досмотра в аэропорту

Соотносите глубину проверки с задачей, не выбирайте один конвейер для всего

Косметическая правка и миграция базы требуют разного внимания. Маршрутизатор предлагает глубину по сигналам задачи; политику проекта и реальный риск всё равно нужно оценить.

Полезна аналогия разных процедур досмотра для разных ситуаций. Она объясняет соразмерность проверки, но не описывает правила аэропортов и не обещает качество результата.

● Tactical
Минимальный конвейер
конвейер: none
Косметика или небольшое переименование могут подходить. Это не отменяет проверки проекта. В ядре есть и облегчённый режим Note.
● Standard
PRD + RFC
PRD → RFC
Ограниченная функция может соответствовать Standard. Evidence подтверждает завершение, но не является отдельным узлом списка маршрутизатора.
● Deep
+ SPEC + ADR
PRD → Spec → RFC → ADR
Сигналы безопасности, публичного API или необратимости могут требовать Deep. Проверяется наивысший совпавший сигнал.
● Critical
Парсится как алиас Deep
Critical → Deep в парсере режима ядра
Это не отдельный встроенный конвейер Epic/Adversarial. Режимы ядра: Note, Tactical, Standard, Deep.

Проверьте рекомендацию и её основания. Ниже авторские примеры, не captured классификации:

Иллюстративный выбор глубины · не проверенная стенограмма $ forgeplan route 'Add streaming endpoint GET /query/stream for Vault' Условная глубина: deep Конвейер Deep: PRD → Spec → RFC → ADR # Проверьте публичный API, зависимости и влияние на бюджет. # Задержка и уверенность классификации здесь не измерялись. $ forgeplan route 'Rename button color from blue to indigo' Условная глубина: tactical Конвейер Tactical: (none) # Убедитесь, что нет изменения поведения или более широкого влияния.

Правила ключевых слов берут максимум совпавших сигналов: security — Deep, cross-team — Standard. Help называет уровень 0 значением по умолчанию, но обработчик может выбрать настроенный LLM и повысить глубину. Confidence — эвристика, не измеренная вероятность.

Три вопроса ревью · не три универсальных гейта CLI $ forgeplan validate PRD-018
01 Структура PRD Проверьте местные правила типа и глубины. Тринадцать содержательных H2 местного шаблона не являются требованием upstream BMAD к тринадцати секциям. ревью
02 Согласованность delta Проверьте базовые ссылки, поддерживаемые операции и зависимости там, где они применимы. Проверка PRD не доказывает всё поведение delta. ревью
03 Рассуждение Сравните серьёзные альтернативы, причины отказа и evidence. ADI — Abduction–Deduction–Induction; промпт запрашивает 3+ подхода, но это не обеспеченный универсальный порог. ревью

Строки систематизируют ручное ревью, не сообщают об успешной проверке. Выбранный CLI validate явно отказывает с ограничением legacy-store на migrated workspace. Captured help подтверждает синтаксис, не поддержку каждого обработчика на любой раскладке.

У активации и замены разные роли

forgeplan activate adr-001 проверяет длину, заглушки, связи evidence, MUST и готовность; вызывающие интерфейсы отдельно обрабатывают происхождение. Файл не блокируется. Создайте замену до forgeplan supersede adr-001 --by adr-002. Обнаружение срока может показать активную запись просроченной без смены сохранённого статуса. Supersede связывает существующую замену, а не создаёт её. forgeplan renew adr-001 --reason "Rechecked applicability" --until 2026-12-01 использует переход по сохранённому статусу. Help описывает stale → active, но попадание в список просроченных не разрешает active → active; тот же guard допускает draft → active. forgeplan reopen adr-001 --reason "Context changed" принимает active или stale, создаёт новый draft с происхождением и переводит старую запись в deprecated. В captured полном MCP этих двух команд нет.

Пример · Vault · streaming endpoint

Авторский пример связей намерения, контрактов, решения и evidence. Это не отчёт о бенчмарке или текущем прогоне продукта. До заявления о завершении выполните артефакты выбранного маршрута, реализацию и проверки.

01 · route

forgeplan route 'Add streaming endpoint GET /query/stream'

В примере выбран Deep: PRD → Spec → RFC → ADR. Прочитайте фактическую рекомендацию и сигналы публичного API. Ответ за полсекунды или автоматическое согласие не обещаются.

02 · new prd

forgeplan new prd "Streaming endpoint for Vault queries"

Заполните сгенерированный местный PRD-шаблон, затем создайте Spec, RFC и ADR выбранного маршрута. New принимает тип и название; глубина deep и родительский Epic не выводятся автоматически из названия примера. Задайте реальные метаданные и связи явно поддерживаемыми инструментами.

03 · reason

forgeplan reason PRD-018 · ADI

Сравните SSE, WebSockets и HTTP/2 push с проверяемыми следствиями. Три варианта показывают местную эвристику против привязки к первой идее. Reason требует настроенного LLM-провайдера; без него будет ошибка, а не офлайн-заготовка.

04 · validate

forgeplan validate PRD-018 · прочитать реальные замечания

Проверьте полноту шаблона, применимые контракты и рассуждение отдельно. Структурная проверка не доказывает поведение реализации или полное соответствие OpenSpec/FPF. Сохраните отказ раскладки, не выдумывая PASS.

05 · evidence

forgeplan new evidence "SSE vs WS benchmark" + link

Спланируйте сравнение p50 первого токена для SSE и WebSockets: например, при 50 RPS и payload 2 KB. Это параметры сценария, не результаты замера. Укажите ревизию, методику, verdict, congruence_level, evidence_type и ограничения. Свяжите forgeplan link EVID-001 ADR-001 --relation informs, затем прочитайте forgeplan score ADR-001. Не считайте, что любая мутация согласует кэш всех предков.

06 · activate

forgeplan activate ADR-001 · явный переход

При выполнении применимых условий сохраняется active, не activated (это производная категория отображения). Активный body остаётся редактируемым. Оценка evidence сохраняется до истечения срока, затем вклад равен 0.1, а не плавно падает до 0.6. Без valid_until в этом scorer нет истечения. Пересмотр требует новых наблюдений, не просто новой даты.
