Issue #287 Phase C - вычисление extract_score (0.0-1.0) для Domain Model. Читает секцию `## Composition` DM, чтобы получить ожидаемые количества glossary / use_cases / invariants / scenarios / hypotheses; подсчитывает фактические значения по рабочему пространству; возвращает взвешенный extract_score. Канонические поля (DDL/SDL/pseudo-code) по умолчанию 0/false до выхода marketplace#79 Phase E.

Один вызов отвечает на вопрос «сколько из этой доменной модели фактически извлечено в артефакты». Это коэффициент покрытия, а не мера корректности - рабочее пространство может получить 1.0 и при этом быть неправильным, а может легитимно получить 0.4, пока модель ещё открывается.

**Категория**: Quality & Validation

## Входные параметры

| Имя | Тип | Обязательный | Описание |
|---|---|---|---|
| `domain_model_id` | `string` | да | Артефакт `DM-` для измерения. Должен разрешаться в артефакт вида `domain_model`. |
| `workspace` | `string` | нет | Разрешить рабочее пространство из этой директории вместо стартового CWD MCP-сервера. Абсолютный путь или с тильдой. Полезно, когда агент работает в git worktree отдельно от сервера. |

_Источник схемы: `crates/forgeplan-mcp/src/server.rs::CoverageBusinessParams` (общие DTO находятся в `crates/forgeplan-mcp/src/types.rs`)_

Стоит знать о двух режимах отказа, потому что оба возвращаются как MCP-ошибки с подсказкой по исправлению, а не как пустые данные:

- id разрешается в другой вид - ответ сообщает, какой вид найден, и говорит передать `DM-` id.
- id не существует - ответ является ошибкой «артефакт не найден».

## Откуда берётся `expected`

Знаменатель самодекларируется самой доменной моделью. Секция `## Composition` парсится на отдельные токены в форме id по префиксу:

| Ожидаемое количество | Префикс, подсчитываемый в `## Composition` |
|---|---|
| `glossary.expected` | `GLOS-` |
| `use_cases.expected` | `UC-` |
| `invariants.expected` | `INV-` |
| не используется в оценке | `SCEN-` и `HYP-` |

- Подсчёт дедуплицируется, поэтому id, указанный дважды, считается один раз.
- Плейсхолдеры шаблона пропускаются: буквальный `GLOS-XXX` никогда не считается, поэтому никогда не редактированная доменная модель не выглядит так, будто у неё есть по одному из каждого.
- Доменная модель без секции `## Composition` даёт нулевые ожидаемые количества, и отчёт всё равно возвращается как валидный конверт с `rate = 0.0` для каждого термина.
- Фактические значения подсчитываются по всему рабочему пространству по виду (`glossary`, `use_case`, `invariant`, `hypothesis`), поэтому артефакты, которые композиция не упоминает, всё равно увеличивают `count`.

## Как вычисляется `extract_score`

`extract_score` - это взвешенная сумма пяти ограниченных соотношений, каждый компонент ограничен 1.0:

| Компонент | Вес | Используемое соотношение |
|---|---|---|
| `glossary` | 0.15 | `count / expected` |
| `use_cases` | 0.25 | `count / expected` |
| `invariants` | 0.25 | `count / expected` |
| `scenarios` | 0.20 | `coverage_rate` - use cases с хотя бы одним связанным сценарием, от всех use cases |
| `hypotheses` | 0.15 | `(verified + strong_inferred + 0.5 * inferred) / total` |

Детали, которые меняют то, что означает оценка, скажем, 0.62:

- Соотношение с `expected = 0` равно `0.0`, никогда не `NaN`, поэтому пустая композиция не вносит вклада, а не отравляет JSON.
- Компонент сценариев использует *коэффициент покрытия*, а не среднее количество сценариев на use case. `per_use_case_avg` сообщается как информация; целевое значение шаблона DM - минимум два сценария на use case - не входит в оценку.
- Компонент гипотез - это среднее по популяции, и он равен `0.0`, когда рабочее пространство не содержит гипотез - не `1.0`.
- Только пять положительных отношений покрытия (`informs`, `based_on`, `refines`, `demonstrates`, `covers`) учитываются в покрытии сценариями.

## Возвращает

```json
{
  "glossary": { "count": 12, "expected": 14, "rate": 0.857 },
  "use_cases": { "count": 9, "expected": 12, "rate": 0.75 },
  "invariants": { "count": 7, "expected": 9, "rate": 0.778 },
  "scenarios": { "per_use_case_avg": 1.44, "coverage_rate": 0.667 },
  "hypotheses": {
    "by_state": {
      "parked": 1,
      "inferred": 4,
      "strong_inferred": 2,
      "verified": 3,
      "refuted": 1
    },
    "total": 11
  },
  "canonical": {
    "ddl_compile": false,
    "sdl_parse": false,
    "pseudo_code_coherence": 0.0,
    "reproducibility": 0.0
  },
  "extract_score": 0.71,
  "_next_action": "Next: extract_score = 0.71. Improve coverage by adding artifacts referenced in DM-001's Composition section."
}
```

Примечания к полям:

- `canonical` - это блок-плейсхолдер в v1. Все четыре поля возвращают свои значения по умолчанию (`false`, `false`, `0.0`, `0.0`) до тех пор, пока плагин marketplace brownfield (#79, Phase E) не заполнит проверки компиляции DDL, парсинга SDL, когерентности псевдокода и воспроизводимости. Не читайте их как результаты.
- Ключи `hypotheses.by_state` - это пять состояний жизненного цикла в их полевом написании (`parked`, `inferred`, `strong_inferred`, `verified`, `refuted`); каждое значение парсится из секции `## Lifecycle State` гипотезы, где каноническая форма - kebab-case (`strong-inferred`). Тело, состояние которого не удаётся распарсить, считается `parked`.
- `glossary`, `use_cases` и `invariants` имеют одинаковую тройную форму: `count`, `expected`, `rate`.
- `_next_action` всегда указывает оценку и называет секцию композиции как место для добавления артефактов.

## Пример вызова

Оценить доменную модель в рабочем пространстве по умолчанию:

```json
{ "domain_model_id": "DM-001" }
```

Оценить доменную модель в worktree, а не в стартовом CWD сервера:

```json
{ "domain_model_id": "DM-002", "workspace": "~/work/forgeplan-feature-branch" }
```

## Когда агент вызывает это

- **После `forgeplan_discover_complete`** - превратить завершённую сессию открытия в одно число для отчёта.
- **Перед объявлением доменной модели извлечённой** - оценка - это честный ответ на вопрос «чего-то не хватает».
- **При очистке корзин сирот** - перезапустить после связывания сценариев или триангуляции гипотез, чтобы увидеть движение оценки.
- **В дашборде или CI-тренде** - одно и то же рабочее пространство даёт детерминированную оценку, поэтому дельты значимы.

## Типичная последовательность

1. `forgeplan_orphans` - четыре корзины говорят вам, *какие* артефакты отсутствуют; этот инструмент говорит, *сколько*.
2. `forgeplan_coverage_business` с `DM-` id - записать базовую оценку.
3. Добавить артефакты, которые ожидает композиция, затем связать сценарии.
4. Перезапустить и сравнить - `extract_score` должен сдвинуться, а `rate` по компонентам скажет, какой компонент сдвинулся.
5. Оставить `scenarios.coverage_rate` и `hypotheses.by_state` в отчёте: они выявляют пробелы, которые одна оценка скрывает.

## Примечания по безопасности

- Только чтение: доменная модель, список записей и отношения читаются как снимок под блокировкой рабочего пространства, которая освобождается до запуска чистого построителя отчёта. Ничего не записывается.
- Нет вызова LLM и нет сетевого доступа.
- `expected` самодекларируется. Композиция, перечисляющая один термин, удовлетворяется одним термином, поэтому малый знаменатель может дёшево дать высокую оценку - всегда читайте коэффициенты компонентов, а не только `extract_score`.
- Оценка ничего не говорит о том, *корректны* ли извлечённые артефакты, или осмысленны ли термины и инварианты. Соедините её с [`forgeplan_contradictions`](/ru/docs/mcp/forgeplan_contradictions/) и [`forgeplan_orphans`](/ru/docs/mcp/forgeplan_orphans/) перед тем, как объявить доменную модель готовой.
- `forgeplan coverage` - это другой инструмент: он сообщает о покрытии решений на модуль кода. Нет CLI-эквивалента для этой оценки бизнес-покрытия.
