Просит настроенную LLM разбить PRD на предложения RFC с заголовками, описаниями, областью FR, зависимостями и оценкой глубины. Промпт ориентируется на 3–7 предложений; обработчик не проверяет тип PRD, результат его валидации, число предложений или граф зависимостей. Проверьте текст перед созданием артефактов через `forgeplan_new`, `forgeplan_update` и `forgeplan_link`.

**Категория**: Рассуждения и ИИ

## Когда агент вызывает это

- После того как Standard/Deep PRD проходит валидацию и приходит время планировать реализацию.
- Планирование спринта: пользователь спрашивает: «как нам разделить PRD-042 на следующие 3 спринта?».
- После того как `forgeplan_reason` определяет направление - decompose преобразует его в готовые к поставке RFC.

## Входные параметры

| Имя | Тип JSON | Обязательно | Описание и ограничения |
|---|---|---|---|
| `id` | `string` | да | ID артефакта PRD для разбиения на задачи RFC. |
| `workspace` | `string \| null` | нет | Необязательный явный каталог рабочего пространства для этого вызова. Сервер ищет `.forgeplan/` по этому пути, а не в каталоге запуска. Используйте для агента в отдельном git worktree. PRD-078 / ADR-015. Принимает абсолютный путь или путь с `~`. По умолчанию в схеме: `null`. |

Обязательное поле означает, что ключ должен присутствовать. Значение `null` допустимо только тогда, когда оно перечислено в типе JSON. Значения по умолчанию в схеме не обязательно совпадают с теми, которые использует обработчик и описывает текст.

_Источник схемы: MCP `tools/list`, Forgeplan 0.38.0, `inputSchema`._

## Возвращает

Успешный ответ — JSON в текстовом содержимом MCP с полями `prd_id`, `prd_title`, `tasks`, `provider`, `model`, `resolved_workspace`, `resolved_via` и `_next_action`. **`tasks` — строка Markdown**, а не массив RFC или разобранный DAG. Провайдер получает запрос на нумерованный список; результат не проверяется по схеме задач.

Условный фрагмент ответа (трассировка и подсказка опущены):

```json
{
  "prd_id": "PRD-042",
  "prd_title": "Login flow",
  "tasks": "1. **Token issuer service**\n   Description: Issue tokens.\n   Scope: FR-001.\n   Dependencies: None.\n   Estimated depth: Standard.",
  "provider": "ollama",
  "model": "configured-model"
}
```

Инструмент не создаёт RFC и связи и не сохраняет предложения в PRD. Он разрешает рабочее пространство через путь с возможностью записи и вызывает LLM; сбой провайдера возвращает `isError` с текстом и подсказкой по настройке/входу. Отсутствующий ID также возвращает ошибку MCP.

## Пример вызова

Аргументы этого инструмента, а не оболочка JSON-RPC. Замените условные ID, идентификаторы сессий и пути значениями из своего рабочего пространства. Соответствие схеме не отменяет проверки рабочего пространства, жизненного цикла и согласия на выполнение.

```json
{
  "id": "PRD-001"
}
```

## Типичная последовательность

Рекомендуемый процесс: валидировать PRD → при необходимости выполнить ADI → декомпозировать → проверить предложения → создать каждый RFC → заполнить тело → связать новый RFC с PRD отношением `refines` через реальные аргументы `from`/`to` инструмента `forgeplan_link` → планировать реализацию. Это отдельные действия агента, а не автоматические эффекты декомпозиции.
