Обнаружение «дрейфующих решений» - архитектурных решений (ADR / RFC), чьи заявленные затронутые файлы были изменены с момента записи решения. Дрейф - это сильный сигнал того, что реализация отклонилась от задокументированного обоснования, и решение может потребовать обновления, замещения или нового ADR.

**Категория**: Качество

## Когда агент вызывает его

-   **Ежеквартальный аудит** - поиск ADR, которые больше не соответствуют коду.
-   **Перед тем как объявить ADR авторитетным** - убедитесь, что затронутые файлы не были переписаны.
-   **Перед рефакторингом** - проверьте, регулируются ли ваши целевые файлы дрейфующим ADR, и сначала обновите его.
-   **Подготовка к релизу** - убедитесь, что ни одно архитектурное решение не ушло в просрочку незаметно.

Детектор читает пути/маски из Markdown-разделов тела `Affected Files`, `Affected Scope` или `affected_files`, а не массива фронтматтера. Для **активных ADR/RFC** запускает `git log --since <created_at> -- <pattern>` в корне проекта пространства, затем читает дату последнего коммита. Он не использует mtime файловой системы, `modified_at` LanceDB, незакоммиченные изменения или смысловое сравнение. В ответе может быть сама маска, а не развёрнутый путь файла.

## Входные параметры

_Объявленных входных полей нет. Вызывайте инструмент с пустым объектом `{}`._

_Источник схемы: MCP `tools/list`, Forgeplan 0.38.0, `inputSchema`._

## Возвращает

Успешный ответ — JSON в MCP `content[0].text`: `total` (проверено решений), `stale` (число с дрейфом), `reports`, `_next_action`. В отчётах есть и изменённые, и чистые проверенные решения. Запись содержит `artifact_id`, `artifact_title`, `created_at`, `affected_files` (строки), `changed_files` (объекты `path`, `last_modified`), `is_stale`. Здесь `is_stale` означает найденные git-изменения, а не просрочку или сохранённый статус.

Условный фрагмент ответа (`_next_action` опущен):

```json
{
  "total": 1,
  "stale": 1,
  "reports": [
    {
      "artifact_id": "ADR-004",
      "artifact_title": "Storage design",
      "created_at": "2026-02-15T00:00:00Z",
      "affected_files": ["src/storage.rs"],
      "changed_files": [{"path": "src/storage.rs", "last_modified": "2026-04-07 10:00:00 +0000"}],
      "is_stale": true
    }
  ]
}
```

Это только отчёт. Ошибки пространства возвращаются текстом. Ошибки ядра подавляются до пустого отчёта; неудачные git-команды дают пустой список изменений, поэтому пустой/чистый отчёт не доказывает отсутствия дрейфа. Записи без раздела затронутых путей не проверяются.

## Типичная последовательность

1.  `forgeplan_drift` - перечислить дрейфующие решения.
2.  `forgeplan_get` каждый ADR - прочитать исходное обоснование.
3. Изучите, действительно ли закоммиченное изменение нарушает обоснование. Продление `valid_until` не сбрасывает `created_at` и потому не убирает этот сигнал истории git.
4. При необходимости создайте замену и заместите старое решение по правилам жизненного цикла. Повторите отчёт и изучите число проверенных решений и решений с дрейфом, не предполагая, что любое исправление удаляет строку.
