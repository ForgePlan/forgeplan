Возвращает список артефактов, которые информируют / основаны на гипотезе (каскад) - только для информации, автоматически не обновляются. Отклоняет недопустимые переходы со структурированной ошибкой, перечисляющей разрешённые следующие состояния."

Специализированный инструмент жизненного цикла `kind: hypothesis` обновляет
`hypothesis_state:` вместе с соответствующим статусом артефакта.
[`forgeplan_activate`](/ru/docs/mcp/forgeplan_activate/) намеренно отклоняет этот kind и перенаправляет
сюда, потому что обычная активация переключила бы `status`, не затрагивая `hypothesis_state`, и оставила бы
два поля в противоречии.

Вызов с изменением состояния переписывает артефакт в трёх связанных местах; повтор того же состояния ничего не записывает:

1. `hypothesis_state:` во frontmatter перезаписывается целевым состоянием.
2. `status` выводится из этого целевого состояния в той же записи, поэтому пара никогда не может разойтись:
   `verified` становится `active`, `refuted` становится `deprecated`, а `parked` / `inferred` /
   `strong-inferred` все остаются `draft`.
3. Одна строка аудита добавляется в секцию тела `## Lifecycle State` - создаётся на месте, если
   устаревший артефакт предшествует ей.

Мутация проходит через вспомогательный механизм проекции file-first (сначала markdown, затем строка хранилища),
и весь обработчик выполняется под блокировкой записи рабочего пространства, поэтому два агента, продвигающие одну и ту же
гипотезу, не могут потерять строку аудита.

**Категория**: Прочее

## Когда агент вызывает это

- **Прибыло доказательство.** Проход извлечения brownfield припарковал утверждение, затем появилось подтверждающее доказательство:
  шаг вперёд, `parked` → `inferred` → `strong-inferred` → `verified`.
- **Появилось контр-доказательство.** `any` → `refuted` в любой момент; это также переключает `status` на
  `deprecated`, и список каскада в ответе называет нижестоящие артефакты для пересмотра.
- **Сигнал был недостаточным.** `any` → `parked` - это обратимая приостановка, а `parked` → `inferred`
  позже возобновляет работу.
- **Активация.** Продвижение в `verified` - единственный путь, который делает гипотезу `active`.
  Вызов [`forgeplan_activate`](/ru/docs/mcp/forgeplan_activate/) вместо этого возвращает ошибку, говорящую
  использовать этот инструмент с `new_state=verified` (активировать) или `new_state=refuted` (отменить).
- **После вызова.** Изучите `cascade` и решите, каким затронутым артефактам нужен [`forgeplan_score`](/ru/docs/mcp/forgeplan_score/). `_next_action` рекомендателен: буквальная подсказка называет саму гипотезу, а не каждый элемент каскада.

## Конечный автомат верификации

Прямая цепочка строго пошаговая. `parked`, `inferred` и `strong-inferred` - это рабочие состояния; `verified` и `refuted` - терминальные состояния, которые поглощают прямые переходы.

| Состояние | Значение | Допустимые следующие состояния |
|---|---|---|
| `parked` | На паузе - ничего ещё не собрано или работа намеренно приостановлена. Обратимо. | `inferred`, `parked`, `refuted` |
| `inferred` | Утверждение сформулировано с некоторым сигналом, подтверждающих доказательств пока нет. Значение по умолчанию в шаблоне. | `parked`, `inferred`, `strong-inferred`, `refuted` |
| `strong-inferred` | Одно или несколько независимых доказательств согласуются, но планка для `verified` не достигнута. | `parked`, `strong-inferred`, `verified`, `refuted` |
| `verified` | Терминальное. Нижестоящие артефакты могут считать утверждение несущим. | `parked`, `verified`, `refuted` |
| `refuted` | Терминальное. Контр-доказательство опровергло утверждение. | `parked`, `refuted` |

Правила, стоящие за этой таблицей:

- **Вперёд, на один шаг.** `parked` → `inferred`, `inferred` → `strong-inferred`, `strong-inferred` → `verified`. Пропуск шага (`parked` → `verified`) отклоняется.
- **Без понижения.** `verified` → `inferred` и `verified` → `strong-inferred` отклоняются - верифицированное утверждение не откатывается, вместо этого создаётся новая гипотеза.
- **Два универсальных стока.** `any` → `refuted` (контр-доказательство может появиться в любой момент) и `any` → `parked` (приостановить работу) всегда разрешены.
- **Из того же в то же** допустимо в конечном автомате, но короткозамкнуто этим инструментом - см. [Идемпотентное повторное применение](#идемпотентное-повторное-применение).

## Входные параметры

| Имя | Тип JSON | Обязательно | Описание и ограничения |
|---|---|---|---|
| `evidence_refs` | `array<string>` | нет | ID артефактов-доказательств, обычно `EVID-NNN`, обосновывающих переход. Список может быть пустым, например для паузы parked, но обоснование обязательно. По умолчанию в схеме: `[]`. |
| `hypothesis_id` | `string` | да | ID или slug гипотезы (`HYP-001`, `hyp-some-claim`). Должен разрешаться в артефакт с `kind == "hypothesis"`. |
| `new_state` | `string` | да | Целевое состояние в kebab-case: `parked`, `inferred`, `strong-inferred`, `verified` или `refuted`. |
| `rationale` | `string` | да | Однострочное обоснование для аудита в `## Lifecycle State`. Сохраняется в теле дословно, очищается при выводе подсказок. |
| `workspace` | `string \| null` | нет | Необязательный явный каталог рабочего пространства для этого вызова. Сервер ищет `.forgeplan/` по этому пути, а не в каталоге запуска. Используйте для агента в отдельном git worktree. PRD-078 / ADR-015. Принимает абсолютный путь или путь с `~`. По умолчанию в схеме: `null`. |

Обязательное поле означает, что ключ должен присутствовать. Значение `null` допустимо только тогда, когда оно перечислено в типе JSON. Значения по умолчанию в схеме не обязательно совпадают с теми, которые использует обработчик и описывает текст.

_Источник схемы: MCP `tools/list`, Forgeplan 0.38.0, `inputSchema`._

## Что делает

1. Захватывает блокировку записи пространства, разбирает `new_state`, разрешает ID/slug гипотезы и требует `kind: hypothesis`.
2. Читает `hypothesis_state` из frontmatter. Отсутствующее, null, нестроковое или нераспознаваемое значение становится `parked`. Единственный шаг вперёд отсюда — `inferred`, а не прямой переход в `verified`.
3. Проверяет матрицу переходов. Повтор того же состояния возвращает `unchanged: true` и пустой каскад до проверки rationale/refs; он не добавляет строку аудита и не исправляет несогласованный статус хранилища.
4. Для реального изменения запрещает управляющие символы и Unicode-разделители строк и абзацев в `rationale`. Каждая ссылка должна быть ASCII-токеном ID с первой буквой. `rationale` — обязательная строка, хотя пустая строка допустима; только отсутствующий `evidence_refs` получает `[]`. Сокращённый путь no-op не отменяет обязательные ключи схемы.
5. Для перехода в `verified` требует хотя бы одну ссылку и проверяет разрешение и существование каждого артефакта. **Ограничение 0.38.0:** проверяется существование, а не `kind: evidence`, вердикт, конгруэнтность или положительная оценка. Связи доказательств сами не создаются.
6. Обновляет frontmatter/статус и добавляет строку аудита через хелпер проекции. Возвращает источники входящих `informs` / `based_on` в `cascade`; зависимые артефакты не продвигаются и не пересчитываются автоматически. Сбой перечисления не фатален и может дать пустой каскад.

## Возвращает

При изменении состояния успешный ответ содержит `id`, `old_state`, `new_state`, переданные `evidence_refs` и `rationale`, `cascade`, `_next_action`. Этот обработчик не добавляет трассировку пространства. Каскад — источники входящих рёбер `informs` / `based_on`, а не число выполненных последующих действий.

Например, переход `parked` → `inferred` может добавить:

```text
- 2026-09-16: parked → inferred (refs: none; rationale: initial signal from the refund policy grep)
```

Пустые ссылки отображаются как `none`, пустая причина — как `(no rationale provided)`. У no-op другая структура ответа, описанная ниже; переданные причина и ссылки в неё не включаются.

## Идемпотентное повторное применение

Продвижение в состояние, в котором гипотеза уже находится, ничего не записывает и сообщает об этом:

```json
{
  "_next_action": "Done. - `HYP-001` already in `inferred`.",
  "cascade": [],
  "id": "HYP-001",
  "new_state": "inferred",
  "old_state": "inferred",
  "unchanged": true
}
```

Обратите внимание на пустой каскад в этом конверте: путь без операций возвращается до запуска перечисления каскада,
поэтому пустой список здесь означает «ничего не произошло», а не «от этого ничего не зависит».

## Отклонённые вызовы

Отказы по переходу, типу и вводу дают текст ошибки MCP, часто с рекомендательной строкой `_next_action`. У ошибок хранилища и проекции может быть другой текст; универсального структурированного объекта ошибки нет.

| Отклонение | Текст ошибки |
|---|---|
| Неизвестное состояние | `unknown hypothesis state:` за которым следует переданное вами значение |
| Неизвестный артефакт | `Artifact 'HYP-999' not found.` |
| Неверный тип | `` artifact `PRD-001` is kind=`prd`, expected `hypothesis` `` |
| Недопустимый переход | `` illegal hypothesis transition for `HYP-001`: `inferred` → `verified` `` |
| Многострочный rationale | `rationale contains control characters or Unicode line separators` |
| Некорректный идентификатор доказательства | `` evidence_ref `not an id` is not a valid artifact id `` |
| Нет доказательств для `verified` | `Cannot promote to verified with no evidence_refs` |
| Отсутствующее доказательство для `verified` | `` evidence_ref `EVID-999` does not exist in workspace `` |

Ошибка недопустимого перехода содержит в подсказке разрешённый набор, например из `inferred`:

```text
Allowed next states from `inferred`: parked, inferred, strong-inferred, refuted.
```

## Замечания по безопасности

- **Это мутация тела.** Операция не является read-only и не помечена как идемпотентная в MCP-аннотациях — успешное продвижение изменяет артефакт на диске.
- **`status` следует за `hypothesis_state`.** Не боритесь с этим через [`forgeplan_update`](/ru/docs/mcp/forgeplan_update/); правило валидации `hypothesis-state-status-consistent` (серьёзность `should`) отмечает гипотезу, у которой эти два поля расходятся.
- **`refuted` отменяет.** Продвижение в `refuted` выводит `status: deprecated`, что сообщает остальной части рабочего пространства о том, что утверждение мертво.
- **Каскад — это совет.** Инструмент никогда не повышает автоматически нижестоящие артефакты по дизайну — агент сам решает, что пересчитывать.

## Пример вызова

Аргументы этого инструмента, а не оболочка JSON-RPC. Замените условные ID, идентификаторы сессий и пути значениями из своего рабочего пространства. Соответствие схеме не отменяет проверки рабочего пространства, жизненного цикла и согласия на выполнение.

```json
{
  "hypothesis_id": "HYP-001",
  "new_state": "parked",
  "rationale": "Awaiting an independent source."
}
```

## Типичная последовательность

1. Прочитать `forgeplan_hypothesis_status` и гипотезу.
2. Зафиксировать подтверждённые пошаговые переходы: `parked` → `inferred` → `strong-inferred`.
3. Для `verified` передать существующие ссылки, например `evidence_refs: ["EVID-001"]`, и правдивую причину. Создать и связать доказательства отдельно, если это нужно процессу.
4. Изучить `cascade`, затем явно пересчитать или проверить затронутые артефакты. Не выполнять `_next_action` как команду shell.

## Связанные команды

- [`forgeplan graph --brownfield-only`](/ru/docs/cli/graph/) - отображает узлы гипотез, окрашенные в соответствии с их текущим состоянием.
