Сторона чтения конечного автомата состояний гипотез, поддерживаемого
[`forgeplan_hypothesis_promote`](/ru/docs/mcp/forgeplan_hypothesis_promote/). Один вызов отвечает на вопрос «сколько из этой brownfield-модели действительно верифицировано?», подсчитывая каждый артефакт `kind: hypothesis` по его состоянию жизненного цикла и извлекая аудит-строки повышения за последние 30 дней из тел артефактов, чтобы вы могли видеть, как недавно что-то изменилось.

Это чистый отчёт: ни один артефакт не создаётся, не изменяется и не активируется.

**Категория**: Прочее

## Когда агент вызывает это

- **Brownfield-триаж.** Перед предложением новой работы узнайте, сколько утверждений находятся в состоянии `parked` (ожидают интервью с доменом), а не `verified` (безопасны для использования).
- **После promote.** Подтвердите, что состояние установлено и аудит-строка находится в теле, особенно когда пакет повышений выполнялся несколькими агентами.
- **Проверка триангуляции.** Большая корзина `inferred` + `strong-inferred` с маленькой корзиной `verified` - сигнал собрать независимые доказательства, а не писать сценарии.
- **Контекст покрытия.** [`forgeplan_coverage_business`](/ru/docs/mcp/forgeplan_coverage_business/) оценивает доменную модель; этот отчёт объясняет, *почему* её термин гипотез низкий.

## Входные параметры

| Имя | Тип JSON | Обязательно | Описание и ограничения |
|---|---|---|---|
| `id` | `string \| null` | нет | Необязательный ID HYP- для отчёта об одной гипотезе. Без фильтра возвращается распределение по рабочему пространству. По умолчанию в схеме: `null`. |
| `workspace` | `string \| null` | нет | Необязательный явный каталог рабочего пространства для этого вызова. Сервер ищет `.forgeplan/` по этому пути, а не в каталоге запуска. Используйте для агента в отдельном git worktree. PRD-078 / ADR-015. Принимает абсолютный путь или путь с `~`. По умолчанию в схеме: `null`. |

Обязательное поле означает, что ключ должен присутствовать. Значение `null` допустимо только тогда, когда оно перечислено в типе JSON. Значения по умолчанию в схеме не обязательно совпадают с теми, которые использует обработчик и описывает текст.

_Источник схемы: MCP `tools/list`, Forgeplan 0.38.0, `inputSchema`._

## Что делает

1. Разрешает рабочее пространство через worktree-aware путь чтения, который не захватывает гейт записи.
2. Захватывает блокировку рабочего пространства только на время чтения снимка, затем освобождает её перед построением отчёта - список записей уже согласован со снимком, и удержание эксклюзивной блокировки через CPU-проход излишне сериализовало бы другие инструменты.
3. Оставляет только артефакты, чей kind - `hypothesis` (регистронезависимо); записи других видов пропускаются молча, поэтому передача всего рабочего пространства безвредна.
4. Читает `hypothesis_state:` из frontmatter каждого оставленного артефакта. Отсутствующее, null, нестроковое или непарсируемое значение считается `parked`; тело без парсируемого frontmatter также считается `parked`.
5. Сканирует секцию `## Lifecycle State` каждого тела на предмет аудит-строк и оставляет те, что датированы последними 30 днями.
6. Возвращает отчёт с подсказкой `_next_action`.

## Возвращает

Успешный ответ — JSON в MCP `content[0].text`. Значения условные (предполагается, что даты примера попадают в окно):

```json
{
  "_next_action": "Next: promote a hypothesis — `forgeplan_hypothesis_promote` (1 tracked).",
  "by_state": {
    "inferred": 0,
    "parked": 0,
    "refuted": 0,
    "strong_inferred": 0,
    "verified": 1
  },
  "recent_transitions": [
    {
      "date": "2026-09-16",
      "id": "HYP-001",
      "new_state": "inferred",
      "old_state": "parked"
    },
    {
      "date": "2026-09-16",
      "id": "HYP-001",
      "new_state": "strong-inferred",
      "old_state": "inferred"
    },
    {
      "date": "2026-09-16",
      "id": "HYP-001",
      "new_state": "verified",
      "old_state": "strong-inferred"
    }
  ],
  "total": 1
}
```

| Поле | Значение |
|---|---|
| `total` | Подсчитанные гипотезы после опционального фильтра `id`. |
| `by_state` | Счётчик по состояниям для пяти состояний. Всегда все пять ключей, включая нули. |
| `recent_transitions` | Аудит-записи в порядке обхода записей/строк тела, без общей сортировки по датам. Даты раньше текущей даты UTC минус 30 дней пропускаются; будущие даты не отбрасываются. |

## Примечания

- **Именование ключей смешанное, намеренно.** Счётчики `by_state` в snake_case (`strong_inferred`), в то время как значения состояний в `old_state` / `new_state` и в frontmatter в kebab-case (`strong-inferred`). Счётчики уплощены, чтобы JSON-потребители могли обращаться к ним как к полям.
- **Распределение доверяет frontmatter.** Подсчёты читают `hypothesis_state:`, а не аудит-строки - поэтому вручную отредактированное тело с устаревшими строками не исказит `by_state`. Список переходов - противоположность: он извлекается из тела и поэтому является best-effort.
- **Извлечение переходов строгое.** Распознаётся только каноническая форма строки, записываемая [`forgeplan_hypothesis_promote`](/ru/docs/mcp/forgeplan_hypothesis_promote/). Строки, использующие `to` вместо стрелки или не имеющие ведущего тире, пропускаются молча.
- **30-дневное окно вычисляется от текущей UTC-даты**, а не от какой-либо временной метки артефакта.
- **Фильтр, не совпавший ни с чем, не является ошибкой.** Запрос id, которого не существует, возвращает `total: 0` со всеми счётчиками на нуле, и подсказка тогда читается как `Done. - no hypothesis artifacts in workspace.`, даже когда рабочее пространство полно гипотез. Трактуйте эту подсказку как «ничего не совпало с этим фильтром» и проверяйте `total` перед выводом, что рабочее пространство пусто.
- **Чтение - не перечисление.** Возвращаются только подсчёты и недавние переходы; вызывайте [`forgeplan_get`](/ru/docs/mcp/forgeplan_get/) на id, когда вам нужно само утверждение.
- **Ошибка — не пустой отчёт.** Сбои пространства, блокировки или чтения записей возвращают текстовую ошибку инструмента MCP (`isError: true`). Успешный фильтр без совпадений возвращает описанный выше отчёт с нулевыми счётчиками.

## Пример вызова

Аргументы этого инструмента, а не оболочка JSON-RPC. Замените условные ID, идентификаторы сессий и пути значениями из своего рабочего пространства. Соответствие схеме не отменяет проверки рабочего пространства, жизненного цикла и согласия на выполнение.

```json
{}
```

## Типичная последовательность

```text
forgeplan_hypothesis_status                       ← распределение + недавнее движение
forgeplan_list kind=hypothesis                    ← идентификаторы за подсчётами
forgeplan_get HYP-001                             ← само утверждение
forgeplan_hypothesis_promote (…, new_state=…)     ← возвращённый `_next_action`
```

## Связанные команды

- [`forgeplan graph --brownfield-only`](/ru/docs/cli/graph/) - те же состояния, отрисованные как подграф.
- [`forgeplan anomalies`](/ru/docs/cli/anomalies/) - находки по артефактам, включая `untriangulated_hypothesis`, где этот отчёт агрегированный.
