title: forgeplan_activate
description: "Активирует артефакт (черновик → активный). Требует прохождения всех правил валидации MUST."
---

Переводит артефакт в `active`, обычно из `draft`. Для PRD, Epic, Spec, RFC и ADR обычный путь проверяет методологические гейты и результаты валидации MUST. `force: true` явно обходит эти проверки и гейт происхождения доказательств, но не подтверждает их прохождение. Облегчённые типы, например Note, Problem и Evidence, пропускают полный гейт методологии и валидации; для гипотез нужен [`forgeplan_hypothesis_promote`](/ru/docs/mcp/forgeplan_hypothesis_promote/).

**Категория**: Жизненный цикл

## Когда агент вызывает это

- После заполнения заглушки PRD + `validate` PASS + прикреплённое доказательство + R_eff > 0 - «готово к отправке».
- В конце чеклиста спринта: все FR проверены, все тесты зелёные, PR объединён - время переключить рубильник.
- Когда пользователь говорит «пометь PRD-042 как активный сейчас», и агент проверил гейты.

## Входные параметры

| Имя | Тип JSON | Обязательно | Описание и ограничения |
|---|---|---|---|
| `force` | `boolean` | нет | Принудительная активация даже при ошибках MUST в валидации. По умолчанию в схеме: `false`. |
| `id` | `string` | да | ID артефакта для активации. |
| `workspace` | `string \| null` | нет | Необязательный явный каталог рабочего пространства для этого вызова. Сервер ищет `.forgeplan/` по этому пути, а не в каталоге запуска. Используйте для агента в отдельном git worktree. PRD-078 / ADR-015. Принимает абсолютный путь или путь с `~`. По умолчанию в схеме: `null`. |

Обязательное поле означает, что ключ должен присутствовать. Значение `null` допустимо только тогда, когда оно перечислено в типе JSON. Значения по умолчанию в схеме не обязательно совпадают с теми, которые использует обработчик и описывает текст.

_Источник схемы: MCP `tools/list`, Forgeplan 0.38.0, `inputSchema`._

## Возвращает

Успешный ответ содержит `artifact_id`, `forced`, `must_errors` (массив строк с замечаниями), `message`, `resolved_workspace`, `resolved_via` и `_next_action`. Полей `ok`, `from`, `to`, `activated_at` нет.

`forced` означает, что были обойдены замечания MUST, а не повторяет входной флаг. В 0.38.0 поле может остаться `false`, если `force: true` обошёл только методологические проверки или проверку происхождения. Предупреждение о происхождении в режиме warn попадает в `message`.

Отказ — это ошибка MCP с текстом, а не JSON-объект `validation_failed` / `must_findings`. Ошибка валидации перечисляет замечания MUST в тексте; у методологических проверок и проверки происхождения свои сообщения. Нельзя считать, что все отказы имеют одну структуру.

## Проверки и побочные эффекты

- Артефакт должен существовать, а переход в `active` должен быть разрешён (`draft` или `stale` → `active`). `force` не обходит автомат жизненного цикла и отказ для гипотез.
- При `force: false` (по умолчанию) типам с полным жизненным циклом нужны заполненное тело без маркеров заглушки длиной не менее 100 байт UTF-8 после trim, прохождение гейта связанного доказательства и отсутствие замечаний MUST. Эти проверки не запускают код или тесты и не являются отдельным гейтом положительного R_eff.
- Настроенный режим проверки происхождения может пропустить, предупредить или заблокировать активацию. `force: true` обходит и его; это согласованное исключение, а не автоматическая реакция на подсказку.
- Обработчик удерживает блокировку записи пространства и синхронизирует проекцию перед изменением. После активации он пытается пересчитать оценку, перерисовать проекцию и продвинуть рекомендательную фазу в `done`.
- Последние шаги выполняются best-effort: их сбои могут попасть только в журнал. Успешный ответ не удостоверяет обновление всех кешированных оценок, маркеров фаз и Markdown-проекций.

## Пример вызова

Аргументы этого инструмента, а не оболочка JSON-RPC. Замените условные ID, идентификаторы сессий и пути значениями из своего рабочего пространства. Соответствие схеме не отменяет проверки рабочего пространства, жизненного цикла и согласия на выполнение.

```json
{
  "id": "PRD-001"
}
```

## Типичная последовательность

Полный цикл: `forgeplan_new` → `forgeplan_update` → `forgeplan_validate` PASS → код → `forgeplan_new evidence` → `forgeplan_link` → `forgeplan_score` > 0 → `forgeplan_activate`. Никогда не активируйте PRD без кода и доказательств - это становится ложным обещанием.
