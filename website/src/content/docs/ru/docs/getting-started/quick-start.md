Это пошаговый пример. Более подробная версия с восстановлением после ошибок -
[первый артефакт](/ru/docs/guides/first-artifact/). ID и вывод ниже
иллюстративны, это не записанный runtime transcript; используйте ID,
который вернула ваша команда.

:::tip[Быстрый способ]
В Claude Code установите встроенный навык `/forge` командой `forgeplan setup-skill` и запустите `/forge "описание вашей задачи"`. Другим клиентам нужен собственный поддерживаемый способ установки навыков: эта команда пишет только в путь Claude Code.
См. [рабочий процесс Forgeplan](/ru/docs/marketplace/forgeplan-workflow/).
:::

К концу этой страницы вы получите:

1. Инициализированное рабочее пространство Forgeplan
2. Роутированный и валидированный PRD
3. Зафиксированное ADI-обоснование
4. Доказательство, связанное с PRD
5. Оценку `R_eff > 0`
6. Артефакт в состоянии `active`

## 0. Установка

Если Forgeplan ещё не установлен, см. [установку](/ru/docs/getting-started/installation/).

Убедитесь, что он работает:

```bash
forgeplan --version
```

:::caution[Подготовьте нужные возможности]
Build feature `semantic-search`, файлы модели и векторы workspace -
разные условия. FPF и плагины агентов - дополнительные зависимости
workflow, не обязательные для обычного keyword-поиска.
См. [установку](/ru/docs/getting-started/installation/).
:::

## 1. Инициализация рабочего пространства

```bash
cd /path/to/your/project
forgeplan init -y
```

В новом проекте создаёт каталоги артефактов и `config.yaml`; `-y` пропускает
запросы. Если `.forgeplan/` уже есть, в том числе у родителя, `init -y`
завершается без исправлений. После клонирования используйте `reindex` для
производного индекса. Если config отсутствует и нужны defaults, осознанно
выполните `init -y --force`, затем верните свои настройки из копии.

Этот CLI lifecycle пример не означает, что каждая команда поддерживает
мигрированный workspace локальной `0.39.0+constellation.s1.1`. Для такого
layout см. [руководство Constellation](/ru/docs/guides/constellation/).

```bash
forgeplan health
# -> 0 артефактов, 0 слепых пятен. Рабочее пространство готово.
```

## 2. Роутинг вашей задачи

Прежде чем что-либо писать, позвольте Forgeplan выбрать правильную глубину:

```bash
forgeplan route "add user authentication"
```

```
Глубина: Standard
Конвейер: PRD → RFC
Уверенность: 90%
Далее: forgeplan new prd "Аутентификация пользователя"
```

`Standard` означает PRD для «что» и RFC для «как». См. [роутинг и глубину](/ru/docs/methodology/routing/).

## 3. Shape - создание PRD

```bash
forgeplan new prd "User Authentication"
# -> Создано: PRD-001 в .forgeplan/prds/PRD-001-user-authentication.md
```

Подготовьте полное тело в `prd-body.md` вне `.forgeplan/` и примените его
командой `forgeplan update PRD-001 --body @prd-body.md`. Заполните MUST-разделы:

- **Проблема** - почему это существует?
- **Цели** - как выглядит успех? (критерии SMART)
- **Не-цели** - что явно выходит за рамки?
- **Целевые пользователи** - кто получает выгоду?
- **Функциональные требования (FR)** - `[Актер] может [возможность]`
- **Related Artifacts** - родительские решения либо явное указание, что их нет

Сохраняйте английские заголовки шаблона: валидатор не считает их русский
перевод автоматически равнозначным.

:::caution[Не оставляйте заглушки]
Заполните недостающие разделы до активации. Не удаляйте черновик только
из-за того, что валидация сообщает о неполном содержании.
:::

## 4. Валидация

```bash
forgeplan validate PRD-001
```

Проверенное покрытие совместимости и оставшиеся ограничения описаны в
[справочнике Constellation](/ru/docs/reference/constellation/). При вызове
`forgeplan_validate` через full MCP передавайте явный `workspace`.
Регистрация сама по себе не доказывает проверку всех lifecycle-инструментов.

Иллюстративный вывод валидатора для поддерживаемого workspace:
```
PRD-001: ПРОЙДЕНО ✓ (0 ошибок MUST, 2 предупреждения SHOULD)
```

MUST-находки не ограничиваются отсутствующими разделами. Исправьте каждое
указанное правило и повторите проверку. Технологии вроде JWT относятся к
дизайну, а не требованиям: implementation-leakage имеет уровень SHOULD для
Standard и MUST для Deep.

## 5. Обоснование (ADI)

Для глубины Standard рекомендуется ADI. Для Deep и Critical это обязательно:

```bash
forgeplan reason PRD-001 --save
```

Настроенной LLM предлагается создать гипотезы, предсказания и сравнение
с опорой на evidence; роутер выбирает глубину, не содержание ADI.
Сверьте вывод с реальными данными. `--save` создаёт связанную Note; без него CLI только
печатает анализ.

Либо запросите FPF-контекст (оба примера создадут две saved Notes).
На migrated Constellation workspace этот CLI-путь пока продолжает работу
без FPF-контекста retired table:

```bash
forgeplan reason PRD-001 --fpf --save
```

Полный цикл: [ADI-обоснование](/ru/docs/methodology/adi/).

## 6. Сборка

Напишите код для вашей фичи. Критическое правило: **напишите тест для каждой `pub fn` перед переходом к следующей функции**. Тесты становятся Доказательством на шаге 7.

Когда фича готова:

```bash
cargo test       # или ваш эквивалент
cargo fmt
cargo check
```

Все должно быть зелёным, прежде чем вы активируете.

## 7. Доказательство - создание Доказательства

```bash
forgeplan new evidence "Auth tests - 12 pass, JWT validate 0.3ms"
# -> Создано: EVID-001
```

Подготовьте `evidence-body.md` вне `.forgeplan/` с реальными результатами и
блоком **структурированных полей**. Пример CL3 требует совпадения контекста тестов:

```markdown
## Structured Fields

verdict: supports
congruence_level: 3
evidence_type: test
```

При отсутствующем/нераспознанном verdict или отсутствующем/некорректном
источнике CL парсер использует CL0 (штраф 0.9). Указывайте и `evidence_type`:
у него отдельная роль в оценке. Не копируйте учебные числа тестов и тайминги
как измерения. Для code-claiming evidence нужны реальные Git provenance
по правилам вашего гейта.

Примените полное тело доказательства и свяжите его с PRD:

```bash
forgeplan update EVID-001 --body @evidence-body.md
forgeplan link EVID-001 PRD-001 --relation informs
```

## 8. Проверка оценки

```bash
forgeplan score PRD-001
```

```
PRD-001: R_eff = 1.00 - Adequate
  EVID-001: supports, CL3, test -> score 1.0
```

Если R_eff равен 0.0, посмотрите детализацию: причиной могут быть отсутствие
текущих доказательств, refutes, штраф CL или зависимости. Отсутствие
структурированных claims обычно даёт 0.1, не обязательно ноль.
См. [доказательства и R_eff](/ru/docs/methodology/evidence/).

## 9. Активация

```bash
forgeplan review PRD-001
# -> Проверка ПРОЙДЕНА - готово к активации

forgeplan activate PRD-001
# -> draft → active
```

Гейт валидации запускается ещё раз при активации. Если он завершается неудачей, переход отклоняется.

## 10. Проверка состояния

```bash
forgeplan health
```

```
Артефакты: 3 (1 active, 2 draft: EVID-001 и сохранённая ADI Note)
Слепые пятна: 0
Сироты (артефакты без связей): 0
Покрытие доказательствами: 100%
```

Теперь у вас есть полностью отслеживаемое решение с измеримым уровнем доверия. Вы в будущем (или ваш коллега) сможете открыть PRD-001 через шесть месяцев и увидеть: проблему, цели, ADI-гипотезы, выбранный подход и доказательства, которые его обосновывают.

## Полный цикл (шпаргалка)

```
Роутинг → Shape → Validate → Обоснование → Сборка → Доказательство → Activate
  1        2        3         4       5       6         7

1. forgeplan route "задача"
2. forgeplan new prd "Заголовок"     # заполнить обязательные (MUST) разделы
3. forgeplan validate PRD-XXX
4. forgeplan reason PRD-XXX      # ADI, обязательно для Deep+
5. код + тест
6. forgeplan new evidence "..." + link + score
7. forgeplan review + activate
```

:::tip[Работа не завершена, пока]
PRD заполнено + валидировано + ADI зафиксировано (Standard+) + доказательство создано + R_eff > 0 + активировано.
Всё, что меньше, - это открытая вкладка, а не завершённая задача.
:::
