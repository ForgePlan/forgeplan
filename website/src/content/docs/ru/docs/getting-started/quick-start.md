description: "Создайте первое решение, проверьте его и свяжите с доказательствами."

Это руководство показывает цикл CLI для решения, подтверждённого реализованной
работой. Оно не обещает фиксированного времени: требования, код и реальные
проверки занимают столько, сколько нужно задаче. Разбор ошибок — в
[Руководстве по первому артефакту](/ru/docs/guides/first-artifact/).

:::tip[Быстрый способ]
В Claude Code `forgeplan setup-skill` устанавливает встроенные инструкции
`/forge`, но не MCP и не полную обвязку маркетплейса. Для `/smith`,
`/forge-cycle` и специалистов следуйте
[инструкции установки](/ru/docs/getting-started/installation/#полный-harness-комплект-claude-code).
:::

К концу этой страницы вы получите:

1. Инициализированное рабочее пространство Forgeplan
2. Роутированный и валидированный PRD
3. Зафиксированное ADI-обоснование
4. Доказательство, связанное с PRD
5. Оценку `R_eff > 0`
6. Артефакт в состоянии `active`

## 0. Установка

Если вы ещё не установили Forgeplan, см. [Установка](/docs/getting-started/installation/).

Убедитесь, что он работает:

```bash
forgeplan --version
```

:::caution[Выберите нужные предпосылки]
Базовые операции с артефактами не требуют модели или LLM. На шаге 5 команда
`reason` требует провайдера LLM в `.forgeplan/config.yaml`; `--save` сохраняет
результат. Контекст FPF опционален для CLI и требует импорта корпуса.
Семантическому поиску отдельно нужны веса модели и векторы артефактов.
Плагины агентов маркетплейса для этого руководства по CLI не обязательны.
:::

## 1. Инициализация рабочего пространства

```bash
cd /path/to/your/project
forgeplan init -y
```

Это создаёт `.forgeplan/` с пустыми директориями `prds/`, `rfcs/`, `adrs/`, `evidence/` и файлом `config.yaml`. Флаг `-y` пропускает интерактивные запросы (требуется для ИИ-агентов).

```bash
forgeplan health
# -> 0 артефактов, 0 слепых пятен. Рабочее пространство готово.
```

## 2. Роутинг вашей задачи

До создания артефакта запросите рекомендацию глубины. Здесь явно выбран
поиск по ключевым словам, чтобы не вызывать LLM без намерения:

```bash
forgeplan route "add user authentication" --level 0
```

Читайте фактическую глубину, сработавшие условия и конвейер, а не ожидайте
фиксированную уверенность или `Standard`. Задаче безопасности может
потребоваться более глубокий конвейер. Создайте рекомендованные артефакты
и явно задайте глубину: маршрутизация не меняет глубину нового PRD по
умолчанию. Здесь показан PRD, а не замена обязательной работы над RFC,
ADR или SPEC. См. [Роутинг и глубина](/ru/docs/methodology/routing/).

## 3. Shape - создание PRD

```bash
forgeplan new prd "User Authentication"
# Используйте ID и путь, которые напечатает команда.
```

Ниже `PRD-001`, `EVID-001` и `NOTE-001` — примеры идентификаторов;
подставляйте ID из своего workspace.

Прочитайте созданный шаблон и подготовьте его тело в редакторе вне
`.forgeplan/`, сохраняя заголовки шаблона. Заполните разделы, обязательные
для выбранной глубины, в том числе:

- **Executive Summary** — видение, проблема и целевые пользователи
- **Success Criteria** — измеримые цели и способ измерения
- **Product Scope** — что входит и не входит в задачу
- **User Journeys** — действия пользователя и ответы системы
- **Functional Requirements** — `[Actor] can [capability]` со связью с journeys
- **Non-Functional Requirements** — метрики, условия и измерение

Сохраните тело без YAML frontmatter в `/tmp/auth-prd-body.md` и
синхронизируйте его через CLI:

```bash
forgeplan update PRD-001 --body @/tmp/auth-prd-body.md
```

Если маршрутизатор выбрал deep, используйте
`forgeplan update PRD-001 --depth deep`. Не редактируйте канонические
артефакты `.forgeplan/` напрямую: `update` синхронизирует файл и индекс.

:::caution[Не оставляйте заглушки]
Заглушка PRD без Проблемы/Целей копит технический долг. Заполните её сейчас или `forgeplan delete PRD-001`. Наполовину заполненные PRD загрязняют `forgeplan health`.
:::

## 4. Валидация

```bash
forgeplan validate PRD-001
```

Продолжайте, когда команда не сообщает ошибок MUST. Число предупреждений
SHOULD зависит от содержимого. Исправьте указанные разделы или нарушения
правил и повторите проверку. Требования описывают ЧТО, а не техническое
решение; валидатор ищет утечки реализации, но PASS не доказывает
корректность проекта или кода.

## 5. Обоснование (ADI)

ADI генерирует альтернативы и предсказания для независимой оценки.
Публичная обвязка требует ADI для Standard+; он не заменяет тесты.
Сначала настройте провайдера LLM и аутентификацию. HTTP-провайдеры используют
настроенную переменную окружения с API-ключом; локальные CLI-провайдеры по
подписке требуют существующего входа и явного выбора для личной разработки,
а не общего окружения или CI.

```bash
forgeplan reason PRD-001 --save
```

Это команда `reason`, а не маршрутизатор задач. Без `--save` CLI печатает
анализ; с ним создаёт связанную Note. Проверьте гипотезы и их утверждения,
не выдавая ответ LLM за наблюдаемые доказательства.

Хотите, чтобы контекст базы знаний FPF был внедрён в промпт?

```bash
forgeplan reason PRD-001 --fpf --save
```

См. [ADI-обоснование](/docs/methodology/adi/) для полного цикла.

## 6. Сборка

Реализуйте согласованную функцию и проверьте критерии приёмки. До кода
выберите методологию: BMAD — новый продукт; SPARC — одна фича в существующей
активной системе; TDD с принудительными ограничениями требует активных PRD
и SPEC со сценариями. Артефакт планирования можно активировать до реализации;
такая активация не доказывает, что функция уже поставлена.

Когда фича готова:

```bash
cargo test       # или ваш эквивалент
cargo fmt
cargo check
```

Все должно быть зелёным, прежде чем вы активируете.

## 7. Доказательство - создание Доказательства

```bash
forgeplan new evidence "Authentication acceptance test results"
# Используйте полученный ID; не заявляйте результат теста в заголовке до измерения.
```

В шаблоне доказательства уже есть раздел **Structured Fields**.
Подготовьте полное тело вне `.forgeplan/`, замените заполнители измерений
и результатов реальными командами, результатами, окружением и ограничениями.
Поля должны соответствовать наблюдениям. Для подтверждающего теста в том же
контексте блок выглядит так:

```markdown
## Structured Fields

verdict: supports
congruence_level: 3
evidence_type: test
```

В 0.38.0 отсутствующий или нераспознанный вердикт и отсутствие объявления
конгруэнтности дают CL0: базовая подтверждающая оценка 1.0 становится 0.1.
Не выбирайте CL3 ради балла: объясните, почему контекст теста соответствует
утверждению. Для доказательств о коде укажите `base_sha`, `result_sha` и
`changed_paths` вместе, чтобы проверить происхождение по реальному git-delta.
См. [Доказательство и R_eff](/ru/docs/methodology/evidence/).

Сохраните полное тело в `/tmp/auth-evidence-body.md` и синхронизируйте:

```bash
forgeplan update EVID-001 --body @/tmp/auth-evidence-body.md
```

Свяжите доказательство с PRD:

```bash
forgeplan link EVID-001 PRD-001 --relation informs
```

## 8. Проверка оценки

```bash
forgeplan score PRD-001
```

Используйте фактическую оценку команды, а не число, которое нужно скопировать
в доказательство. R_eff берёт самое слабое текущее связанное доказательство;
черновики учитываются, superseded/deprecated — нет. Текущий вердикт `refutes`
может обнулить результат. При низкой оценке проверьте связи, поля,
конгруэнтность и свежесть. Положительный балл сам по себе не доказывает корректность.

## 9. Активация

```bash
forgeplan review PRD-001
# -> Проверка ПРОЙДЕНА - готово к активации

forgeplan activate PRD-001
# -> draft → active
```

Активация повторяет валидацию и может отклонить переход. Исправьте указанные
проблемы; не обходите команды жизненного цикла через `update --status active`.
В обвязке агентов независимый ревьюер/guardian выдаёт вердикт, а главный
оркестратор активирует артефакт. Автор не удостоверяет свою работу сам.

## 10. Проверка состояния

```bash
forgeplan health
```

Читайте фактические числа и замечания. В примере создаются PRD, EvidencePack
и, с `reason --save`, Note с ADI. Другие рекомендованные артефакты увеличивают
число. Не ожидайте workspace с одним артефактом или фиксированного вердикта
health. Разберите слепые пятна, артефакты без связей и устаревшие доказательства.

Теперь у вас есть полностью отслеживаемое решение с измеримым уровнем доверия. Вы в будущем (или ваш коллега) сможете открыть PRD-001 через шесть месяцев и увидеть: проблему, цели, ADI-гипотезы, выбранный подход и доказательства, которые его обосновывают.

## Полный цикл (шпаргалка)

```
Роутинг → Shape → Validate → Обоснование → Сборка → Доказательство → Activate
  1        2        3         4       5       6         7

1. forgeplan route "задача"
2. forgeplan new prd "Заголовок"     # заполнить обязательные (MUST) разделы
3. forgeplan validate PRD-XXX
4. forgeplan reason PRD-XXX --save  # нужна LLM; сохранить ADI
5. код + тест
6. forgeplan new evidence "..." + link + score
7. forgeplan review + activate
```

:::tip[Работа не завершена, пока]
Для завершённой функции: требования заполнены и валидированы, ADI сохранён
для Standard+ в обвязке, реализация независимо проверена, доказательства
связаны, R_eff разобран и нужные артефакты активированы. Активный план и
поставленная функция — разные этапы.
:::
