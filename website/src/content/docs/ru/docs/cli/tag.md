Прикрепите один или несколько тегов к артефакту. Теги работают как основной сквозной механизм обнаружения - они позволяют группировать артефакты по теме, слою, источнику или флагу статуса **без** создания отношения родитель/потомок.

Теги дополняют, а не заменяют граф артефактов. Используйте связи ([`forgeplan link`](/ru/docs/cli/link/)) для выражения цепочки решений. Используйте теги для разделения рабочего пространства по ортогональным осям, таким как «всё, что связано с аутентификацией», «всё, помеченное тегом `legacy`», или «все артефакты с `source=quint-code`».

## Использование

```text
forgeplan tag <ID> <TAGS>...
```

## Аргументы

```text
  <ID>       Artifact ID (e.g. PRD-001)
  <TAGS>...  Tags to add (e.g. source=code layer=auth legacy)
```

## Опции

```text
  -h, --help     Print help
  -V, --version  Print version
```

## Что делает команда

1. Загружает запись по точному ID и синхронизирует имеющиеся правки проекции.
2. Канонизирует новые теги: обрезает края, приводит к нижнему регистру, заменяет пробелы на `-`, оставляет буквы, цифры и `-`, `_`, `=`, `.`, удаляет пустые результаты и дубликаты.
3. Объединяет список `tags`, обновляет индекс и формирует Markdown-проекцию.

Берите точный ID из `list`: этот обработчик не преобразует отображаемый ID в запись, чей ключ — slug. Вывод текстовый: оценка числа добавленных тегов и текущий список, не JSON. Отсутствующая запись — ошибка.

## Примеры

Теги из одного слова:

```bash
forgeplan tag PRD-001 security auth
```

Теги ключ-значение (полезны для структурированных фильтров):

```bash
forgeplan tag PRD-018 source=openspec layer=storage
```

Несколько стилей одновременно:

```bash
forgeplan tag EVID-012 benchmark performance source=dogfood
```

## Канонизация тегов (v0.18)

Начиная с исправления PROB-026 в v0.18.0, теги канонизируются при записи:

- Приводятся к нижнему регистру: `Security` → `security`.
- Обрезаются от окружающих пробелов.
- Удаляются дубликаты: `forgeplan tag PRD-001 auth auth Auth` добавляет `auth` один раз.
- Внутренние пробелы становятся дефисами; кроме букв, цифр, `-`, `_`, `=`, `.` символы удаляются. Например, `"Auth Layer!"` становится `auth-layer`.

Старые или вручную изменённые проекции могут содержать теги с разным регистром. `reindex` извлекает теги из проекции при создании отсутствующей записи; для существующей записи он инкрементально синхронизирует изменения тела, но не столбец тегов. Он не исправляет метаданные тегов существующих записей и не нормализует все теги на месте. Исправляйте их через `untag` / `tag`: удалите точное сохранённое значение, затем добавьте нужное написание.

## Обнаруживаемость: где используются теги

Теги используются в нескольких последующих командах:

| Команда                                                 | Как используются теги                               |
|---------------------------------------------------------|-----------------------------------------------------|
| [`forgeplan tag <ID> <TAGS>...`](/ru/docs/cli/tag/)        | Добавляет теги артефакту                              |
| [`forgeplan untag <ID> <TAGS>...`](/ru/docs/cli/untag/)    | Убирает теги у артефакта                              |
| [`forgeplan list --tag <t>`](/ru/docs/cli/list/)           | Выводит список артефактов, соответствующих тегу       |
| [`forgeplan health`](/ru/docs/cli/health/)                 | Показывает нетегированные активные артефакты        |

Последовательный словарь тегов делает полезными `list --tag` и счётчик нетегированных артефактов в `health`. Разрастание тегов превращает и то и другое в шум.

## Соглашения по тегированию (рекомендуемые)

CLI не навязывает таксономию, но следующие шаблоны хорошо работают:

- **Теги тем** (простые слова): `auth`, `security`, `performance`, `docs`.
- **Теги источников** (`key=value`): `source=quint-code`, `source=bmad`, `source=dogfood` - отслеживают, откуда пришло решение или доказательство.
- **Теги слоёв**: `layer=cli`, `layer=core`, `layer=mcp`.
- **Флаги статуса**: `legacy`, `experimental`, `blocked`, `wip`.

Выберите небольшой, продуманный словарь и придерживайтесь его. Распространение тегов затрудняет обнаружение.

## Метки источника и поля доказательства

Теги `source_tier=t1`, `source_tier=t2`, `source_tier=t3` подходят для поиска и классификации. В 0.38.0 парсер доказательств читает `source_tier` и `congruence_level` из **тела**, не из `record.tags`. Добавление или удаление такого тега само по себе не задаёт CL для оценки.

Для оценки укажите проверенные поля в теле, например:

```markdown
## Structured Fields

verdict: supports
evidence_type: measurement
source_tier: t2
congruence_level: 2
```

Это иллюстративный фрагмент, а не подтверждение измерения. Поле тела `source_tier` задаёт T1 → CL3, T2 → CL2, T3 → CL1 со штрафами 0.0, 0.1, 0.4. Если заданы и уровень источника, и явный CL, используется `min(tier_cl, explicit_cl)`. Сама метка не подтверждает происхождение и достоверность доказательства.

Примеры меток для поиска:

```bash
forgeplan tag PRD-050 source_tier=T3 source=vendor-api
forgeplan tag PRD-051 source_tier=T2 source=team-alpha
forgeplan tag EVID-060 source_tier=T1 source=dogfood
```

Теги сохранятся в нижнем регистре. Меняйте поля тела через предусмотренный процесс изменения артефактов и пересчитывайте `score` после существенных правок доказательств. Правила репозитория могут требовать только CLI/MCP, даже если библиотека умеет синхронизировать проекции: возможность не означает разрешение прямого редактирования.

## Примечания

- Теги хранятся в индексе и выводятся списком YAML в проекции. Меняйте теги существующей записи через `tag` / `untag`; `reindex` не исправляет ручные изменения тегов в её frontmatter.
- Для удаления тегов используйте [`forgeplan untag`](/ru/docs/cli/untag/).
- Позиционный аргумент `<TAGS>...` принимает сколько угодно тегов - передавайте их за один вызов.
