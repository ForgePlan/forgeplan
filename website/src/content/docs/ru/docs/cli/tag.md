title: forgeplan tag
description: "Добавить теги к артефакту"
---

Прикрепите один или несколько тегов к артефакту. Теги являются основным сквозным механизмом обнаружения - они позволяют группировать артефакты по теме, слою, источнику или флагу статуса **без** создания отношения родитель/потомок.

Теги дополняют, а не заменяют граф артефактов. Используйте связи ([`forgeplan link`](/docs/cli/link/)) для выражения цепочки решений. Используйте теги для разделения рабочего пространства по ортогональным осям, таким как «всё, что связано с аутентификацией», «всё, помеченное тегом `legacy`», или «все артефакты с `source=quint-code`».

## Использование

```text
forgeplan tag <ID> <TAGS>...
```

## Аргументы

```text
  <ID>       ID артефакта (например, PRD-001)
  <TAGS>...  Теги для добавления (например, source=code layer=auth legacy)
```

## Опции

```text
  -h, --help     Вывести справку
  -V, --version  Вывести версию
```

## Что делает команда

1. Загружает frontmatter артефакта.
2. Канонизирует каждый тег (приводит к нижнему регистру, удаляет пробелы по краям, удаляет дубликаты - см. исправление PROB-026 в v0.18).
3. Объединяет новые теги с существующим списком `tags:`.
4. Перезаписывает канонический frontmatter и обновляет обслуживающий индекс. На Constellation запрашивает reconciliation, не открывая legacy-таблицы.

## Примеры

Теги из одного слова:

```bash
forgeplan tag PRD-001 security auth
```

Теги ключ-значение (полезны для структурированных фильтров):

```bash
forgeplan tag PRD-018 source=openspec layer=storage
```

Несколько стилей одновременно:

```bash
forgeplan tag EVID-012 benchmark performance source=dogfood
```

## Канонизация тегов (v0.18)

Начиная с исправления PROB-026 в v0.18.0, теги канонизируются при записи:

- Приводятся к нижнему регистру: `Security` → `security`.
- Обрезаются от окружающих пробелов.
- Удаляются дубликаты: `forgeplan tag PRD-001 auth auth Auth` добавляет `auth` один раз.
- Сохраняются `=` и `-` для форм ключ-значение и форм с дефисами.

Если старые теги имеют разный регистр, изучите канонический Markdown и исправьте метки командами `tag`/`untag`. `index` обслуживает Constellation; перестроение индекса само по себе не гарантирует перезапись каждого тега в исходнике.

## Обнаруживаемость: где используются теги

Теги используются в нескольких последующих командах:

| Команда                                                 | Как используются теги                               |
|---------------------------------------------------------|-----------------------------------------------------|
| [`forgeplan list --tag <t>`](/ru/docs/cli/list/) | Фильтрует артефакты выбранного workspace |
| [`forgeplan get`](/ru/docs/cli/get/) | Показывает канонические теги артефакта |

В выбранной сборке `search` не имеет параметра `--tag`, `discover` управляет сессиями исследования, а не просмотром тегов, и `health` не выделяет артефакты без тегов в отдельный класс проблем.

## Соглашения по тегированию (рекомендуемые)

CLI не навязывает таксономию, но следующие шаблоны хорошо работают:

- **Теги тем** (простые слова): `auth`, `security`, `performance`, `docs`.
- **Теги источников** (`key=value`): `source=quint-code`, `source=bmad`, `source=dogfood` - отслеживают, откуда пришло решение или доказательство.
- **Теги слоёв**: `layer=cli`, `layer=core`, `layer=mcp`.
- **Флаги статуса**: `legacy`, `experimental`, `blocked`, `wip`.

Выберите небольшой, продуманный словарь и придерживайтесь его. Распространение тегов затрудняет обнаружение.

## Сопоставление уровней источников и CL (v0.17.0, PRD-035)

Метки вроде `source_tier=T1` описывают происхождение. **Текущий парсер доказательств не читает список `tags:` для скоринга.** Он читает отдельные поля тела, включая `source_tier: t1` и `congruence_level: 3`.

| Поле тела | Выведенный CL | Штраф CL в продукте |
|---|---|---|
| `source_tier: t1` | CL3 | 0.0 |
| `source_tier: t2` | CL2 | 0.1 |
| `source_tier: t3` | CL1 | 0.4 |

### Приоритет безопасности (`min(tier_cl, explicit_cl)`)

Если тело EvidencePack содержит распознаваемый `verdict` и одновременно поля `source_tier: ...` и `congruence_level: ...`, скоринг выбирает меньший CL:

```
final_cl = min(tier_cl, explicit_cl)
```

Например, поля тела `verdict: supports`, `source_tier: t1` и `congruence_level: 0` дают CL0, несмотря на соответствие T1 → CL3.
Это консервативное правило относится к полям скоринга, **а не к изменению тегов**.
Без распознаваемого verdict или объявления CL скоринг использует CL0.
Это правила ForgePlan, а не универсальная формула текущего upstream FPF.

### Вариант использования: внедрение в существующую систему (brownfield onboarding)

При исследовании теги уровней могут обозначать происхождение для последующей проверки. Следующие команды сами по себе не задают отдельные поля скоринга EvidencePack:

```bash
# Документы внешнего поставщика - низкий уровень доверия
forgeplan tag PRD-050 source_tier=T3 source=vendor-api

# Внутренний PoC от соседней команды - умеренный уровень доверия
forgeplan tag PRD-051 source_tier=T2 source=team-alpha

# Наш собственный производственный бенчмарк - наивысший уровень доверия
forgeplan tag EVID-060 source_tier=T1 source=dogfood
```

См. [Методология доказательств - Приоритет SourceTier](/docs/methodology/evidence/#gotchas-and-migration-notes) для получения информации о том, как это взаимодействует с оценкой R_eff после обновления.

## Примечания

- Теги хранятся во frontmatter как список YAML. Предпочитайте `tag`/`untag` прямым правкам; для обслуживания Constellation используйте `index`, не `scan-import`.
- Для удаления тегов используйте [`forgeplan untag`](/docs/cli/untag/).
- Позиционный аргумент `<TAGS>...` является вариативным - передавайте столько тегов, сколько хотите, за один вызов.
