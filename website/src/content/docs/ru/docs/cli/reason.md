---

`forgeplan reason` просит настроенный LLM проанализировать существующий артефакт по циклу **ADI** FPF: **абдукция** (предложить альтернативы) → **дедукция** (оценить последствия) → **индукция** (рекомендовать подход). Стандартный промпт просит не менее трёх различных гипотез и обоснованную уверенность. Методология Deep/Critical требует такого разбора до кода, но CLI не проверяет число гипотез, не валидирует артефакт перед вызовом и не блокирует последующие команды. Сгенерированная рекомендация не является эмпирической проверкой.

## Forgeplan 0.38.0

Требуется `llm` в `.forgeplan/config.yaml`. HTTP-провайдеры читают ключ из переменной, названной в `llm.api_key_env`. Локальные профили `claude-code`, `codex-cli`, `devin-cli`, `gemini-cli`, `cursor-agent` используют существующий вход в официальный CLI без ключа API Forgeplan. Это явный выбор для личной локальной разработки, не для production, общего сервера или CI. Каждый вызов расходует тариф соответствующего поставщика и подчиняется его условиям. Анализ LLM не заменяет измерения или проверку кода. CLI печатает строку прогресса даже с `--json`; сочетание с `--save` добавляет сообщения о сохранении. Не считайте весь stdout одним чистым JSON-документом.

Ollama — исключение с локальным HTTP без ключа; веса модели векторов не нужны ни самому ADI, ни его поиску по словам в базе знаний. Провайдер и модель выбираются через конфигурацию `llm` и поддерживаемые переменные окружения, не через флаг `reason --model`.

## Когда использовать

- Сразу после `forgeplan new prd` + `forgeplan validate` PASS, до начала работы с кодом.
- Глубина **Deep** или **Critical** - ADI не подлежит обсуждению.
- Глубина **Standard**, и пространство решений имеет реальные компромиссы (уровень кэширования, алгоритм ограничения скорости, поток аутентификации).

## Когда НЕ использовать

- Глубина **Tactical** - исправление ошибки за один час не требует трёх гипотез.
- Разделы MUST ещё не заполнены - ADI на заглушке создаёт галлюцинаторный контекст.
- Артефакт попадает в чистый EvidencePack, Note или RefreshReport (нет решения для рассуждений).

## Использование

```text
forgeplan reason [OPTIONS] <ID>
```

## Аргументы

```text
  <ID>
          Artifact ID to analyze
```

## Опции

```text
      --json
          Output structured JSON instead of markdown

      --save
          Save ADI analysis as a Note artifact linked to the source

      --fpf
          Inject relevant FPF patterns into the ADI prompt

  -h, --help
          Print help (see a summary with '-h')

  -V, --version
          Print version
```

## Примеры

### Пример 1: Стандартный ADI для PRD

```bash
forgeplan reason PRD-001
```

Читает полное сохранённое тело и добавляет метаданные, ID/типы/заголовки исходящих связей, обнаруженный ограниченный контекст при наличии и описание архитектуры. Просит LLM предложить альтернативы и последствия, но не загружает полные тела всех связанных артефактов и не выполняет проверки доказательств. Описание архитектуры берётся из `.forgeplan/prompts/architecture.md` относительно текущего каталога, иначе используется стандартное описание самого Forgeplan; задайте реальную архитектуру проекта, чтобы не передавать неверный контекст.

### Пример 2: ADI с контекстом базы знаний FPF

```bash
forgeplan reason PRD-001 --fpf
```

`--fpf` ищет значимые слова из заголовка артефакта, выбирает до трёх уникальных разделов базы знаний и включает до 300 символов каждого. Команда не гарантирует выбор B.3 или B.5, не использует семантический поиск и не проверяет инварианты FPF. Если база пуста или поиск завершается ошибкой, рассуждение продолжается без этого контекста.

### Пример 3: Сохранение анализа как Note

```bash
forgeplan reason PRD-001 --save
```

Создаёт Note уровня Tactical со статусом draft и связь Note → источник типа `informs`. Для структурированного ответа Note содержит JSON `AdiRecord` и читаемую сводку; при резервном markdown-ответе сохраняется исходный анализ. Без `--save` Note и связь не создаются. Ни один режим не активирует источник и не превращает анализ в EvidencePack.

### Пример 4: Машиночитаемый вывод для агентов

```bash
forgeplan reason PRD-001 --json
```

JSON содержит `artifact_id`, `artifact_kind`, `depth`, `r_eff_score`, `_next_action` и либо `adi_output` (структурированный результат), либо `adi_analysis` (резервный markdown).

## Интерпретация вывода

Без `--json` CLI печатает ответ модели как есть: это может быть JSON или Markdown. Структурированный `adi_output` содержит:

- `hypotheses`: объекты с `id`, `description`, `assumptions` и строкой `confidence`.
- `deductions`: объекты с `hypothesis_id`, `consequence`, `risks` и строкой `feasibility`.
- `evidence_needed`: объекты с `for_hypothesis`, `test` и строкой `effort`.
- Строки `recommendation` и `confidence`.

Уверенность — свободный текст вроде “High — justification”, а не проверенный процент. В этом DTO нет поля вердикта `supported`/`weakened` для каждой гипотезы. Для отсутствующих полей парсер подставляет значения по умолчанию; успешно разобранный ответ может содержать ноль гипотез. При ошибке разбора `--json` возвращает `adi_analysis` вместо `adi_output`.

Красные флаги:

- Альтернатив нет или они повторяют один подход — уточните артефакт, промпт или провайдер/модель; повторный ответ не является независимым доказательством.
- Рекомендация зависит от непроверенных предположений — соберите целевые доказательства до реализации.
- Уверенность не обоснована — оценивайте объяснение, а не произвольный процентный порог.

## Как это вписывается в рабочий процесс

Эта команда входит в [полный жизненный цикл артефакта](/ru/docs/guides/first-artifact/) - см. руководство для сквозного процесса. `reason` запускается после `validate` PASS и до написания кода; для глубины Critical используйте команду в паре с `/audit` и человеческим ревью перед реализацией.
