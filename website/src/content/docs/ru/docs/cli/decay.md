---
title: forgeplan decay
description: "Показать текущее влияние уже просроченных доказательств на R_eff."
---

`forgeplan decay` показывает решения с уже просроченными связанными EvidencePack,
которые участвуют в оценке. Сравниваются R_eff при свежих доказательствах и текущий
R_eff. Сохранённый вердикт evidence не меняется, но в расчёте просроченный пакет получает 0.1 до обработки вердикта, включая `refutes`. Выведенные из использования пакеты исключены.

Используйте отчёт для **Refresh sprint**: проверьте доказательства заново,
запишите наблюдения в `RefreshReport` и только затем продлевайте срок.

## Когда использовать

-   Начало месяца: «какие решения потребуют повторной верификации в этом спринте?»
- Прежде чем полагаться на решение - снизили ли просроченные доказательства его R_eff?
- После проверки дат `valid_until` - какие решения уже затронуты?
-   Начало сессии вместе с `forgeplan health` для полного обзора «что требует внимания».

## Когда НЕ использовать

-   Когда у вас вообще нет доказательств (R_eff уже 0) - нечему приходить в упадок.
-   Как одноразовый гейт качества - используйте `stale` для жёсткого обнаружения истечения срока действия.

## Использование

```text
forgeplan decay
```

## Опции

```text
  -h, --help     Вывести справку
  -V, --version  Вывести версию
```

## Примеры

### Текущее влияние просрочки

```bash
forgeplan decay
```

Иллюстрация, не записанный вывод команды:

```text
Evidence Decay Report — 1 artifact(s) affected:

  PRD-003 "Authentication"
    R_eff: 0.90 → 0.10 (drop: 0.80)
    ⚠ EVID-012 expired 2026-10-01 (22 days ago, score=0.9)
```

### Включение в план спринта

Совместите со `stale` и `health`:

```bash
forgeplan decay          # текущая потеря оценки из-за просрочки
forgeplan stale          # что уже истекло
forgeplan health         # общий обзор слепых пятен
```

Эти три команды представляют полную картину «бэклога обновления».

## Интерпретация вывода

- **expired DATE (N days ago)** - истёкшая дата действия доказательства.
- **R_eff X → Y** - оценка при свежих пакетах и текущая оценка.
- **drop** - разница между ними, не прогноз будущего падения.
- Команда не обнаруживает будущие «обрывы»; приоритет повторной проверки определяет команда проекта.

## Как это вписывается в рабочий процесс

```
monthly review → decay → plan refresh sprint → renew evidence → score
```

И `decay`, и `stale` работают с уже истёкшими датами. Для профилактического планирования проверяйте будущие `valid_until` отдельно.
