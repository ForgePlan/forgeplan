---
title: forgeplan drift
description: "Найти Git-изменения затронутых файлов активных ADR/RFC после создания артефакта."
---

`forgeplan drift` проверяет активные ADR/RFC с разделом `Affected Files`.
Git-история сравнивается с `created_at` артефакта, не `decided_at` или `activated_at`.
Изменение пути - повод для ревью, не доказательство нарушения решения.
Статус жизненного цикла команда не меняет.

Дрифт отличается от устаревания доказательств. Устаревание связано со временем (истекает `valid_until`);
дрифт - с изменением кода (перемещением файлов). И то, и другое может сделать решение ненадёжным,
и дрифт часто является тем, о чём забывают.

## Когда использовать

- Ежемесячный обзор - какие пути ADR/RFC изменились после создания артефакта?
- После крупного рефакторинга - посмотрите, какие решения необходимо повторно валидировать с учётом новой формы кода.
- Перед ссылкой на ADR в ревью PR - соответствует ли оно всё ещё реальности?
- Подготовка к релизу - обновите дрифтанувшие решения перед выпуском релиза.

## Когда НЕ использовать

- На артефактах без раздела `Affected Files` - сначала используйте `coverage --backfill`.
- На свежем рабочем пространстве - дрифту нужна история Git для вычислений.

## Использование

```text
forgeplan drift [OPTIONS]
```

## Опции

```text
      --json     Вывод в формате JSON для машинной обработки
  -h, --help     Вывести справку
  -V, --version  Вывести версию
```

## Примеры

### Найти дрифтанувшие решения

```bash
forgeplan drift
```

Иллюстрация, не записанный вывод:

```text
  ⚠ ADR-002 "Storage design" — STALE
    Created: 2026-03-15T00:00:00
    Changed: crates/forgeplan-core/src/db/schema.rs (2026-10-01 10:00:00 +0000)

  ✓ ADR-005 "Lifecycle design" — up to date
  2 decisions checked, 1 stale
```

### Машиночитаемый формат для CI

```bash
forgeplan drift --json | jq '.reports[] | select(.is_stale) | .id'
```

Передайте этот список в напоминание Slack или генератор задач бэклога.

### Устранить дрифт

Для каждого дрифтанувшего ADR у вас есть три действия:

1. **Повторная проверка**: прочитайте диффы и запишите результат; `renew` подходит только при допустимом переходе жизненного цикла.
2.  **Замещение**: напишите новый ADR, документирующий новую реальность, `supersede --by ADR-NEW`.
3.  **Отмена**: решение больше не применимо, пометьте его как окончательное.

## Интерпретация вывода

| Поле / подпись | Значение |
|---|---|
| `is_stale: true` / `STALE` | Найден более поздний Git-коммит затронутого пути |
| `is_stale: false` / `up to date` | Проба не нашла более позднего коммита |
| `changed_files` | Шаблоны путей и время последнего коммита |

Вердиктов сильного/слабого дрейфа нет. Отсутствующая история или ошибка Git-пробы
могут оставить список пустым: это не доказательство соответствия архитектуре.

## Как это вписывается в рабочий процесс

```
scan → coverage → drift → remediate (renew | supersede | deprecate)
```

`drift` - это одна из опор моста между кодовой базой и артефактами. `coverage` спрашивает: "есть ли у модулей ADR?", а `drift` спрашивает: "соответствуют ли эти ADR всё ещё коду?"
