`forgeplan drift` проверяет активные ADR и RFC с разделом `Affected Files`. Для каждого пути или шаблона Git ищет коммиты начиная с сохранённого `created_at`, а не с даты активации или принятия решения. Любое совпадение помечает отчёт как stale; команда не определяет, противоречит ли изменение решению.

Это отличается от просрочки доказательств (`valid_until`). Проверяется история коммитов, а не незакоммиченные правки. Ошибки запуска Git трактуются как отсутствие изменений, поэтому чистый отчёт сам по себе не доказывает актуальность решения.

## Когда использовать

- Ежемесячный архитектурный обзор — какие ADR требуют пересмотра после изменений кода?
- После крупного рефакторинга - посмотрите, какие решения необходимо повторно валидировать с учётом новой формы кода.
- Перед ссылкой на ADR в ревью PR - соответствует ли оно всё ещё реальности?
- Подготовка к релизу - обновите дрифтанувшие решения перед выпуском релиза.

## Когда НЕ использовать

- На артефактах без раздела `Affected Files` - сначала используйте `coverage --backfill`.
- На свежем рабочем пространстве - дрифту нужна история Git для вычислений.

## Использование

```text
forgeplan drift [OPTIONS]
```

## Опции

```text
      --json     Output as JSON for machine consumption
  -h, --help     Print help
  -V, --version  Print version
```

## Примеры

### Найти дрифтанувшие решения

```bash
forgeplan drift
```

Текстовый вывод помечает каждый проверенный артефакт как `STALE` или `up to date`. Для stale печатает `Created:` и строки `Changed: путь (дата последнего коммита)`. Итог содержит число проверенных и stale-решений. Количество коммитов и степень изменений не оцениваются.

### Машиночитаемый формат для CI

```bash
forgeplan drift --json | jq '.reports[] | select(.is_stale) | .id'
```

Передайте этот список в напоминание Slack или генератор задач бэклога.

### Устранить дрифт

Для каждого дрифтанувшего ADR у вас есть три действия:

1. **Повторная проверка**: прочитайте диффы и зафиксируйте, сохраняет ли решение силу. Продление меняет срок и статус, но не дату создания, поэтому этот сигнал дрифта не исчезнет.
2. **Замещение**: создайте новый ADR, затем выполните `forgeplan supersede ADR-OLD --by ADR-NEW`. Старый артефакт должен быть active, а замена — существовать.
3. **Отмена**: если решение больше не применимо, используйте `forgeplan deprecate ADR-OLD --reason "No longer applicable"`.

## Интерпретация вывода

JSON содержит `reports`, `_next_action`, `hints`. Поля отчёта: `id`, `title`, `is_stale`, `created_at`, `changed_files` (объекты с `path` и `last_modified`). Возвращаются и stale, и неизменённые отчёты. Находки сами по себе не дают ненулевой код завершения; задайте свою политику для `.reports[].is_stale`.

## Как это вписывается в рабочий процесс

```
scan → coverage → drift → remediate (renew | supersede | deprecate)
```

`drift` - это одна из опор моста между кодовой базой и артефактами. `coverage` спрашивает: "есть ли у модулей ADR?", а `drift` спрашивает: "соответствуют ли эти ADR всё ещё коду?"
