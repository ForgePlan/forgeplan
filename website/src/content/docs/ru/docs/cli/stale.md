`forgeplan stale` перечисляет записи с истёкшим `valid_until`. Он не переписывает
их статус и кэшированный R_eff. Артефакт с истёкшей датой может сохранять
`status: active`: обнаружение истечения и переход жизненного цикла — разные операции.

Скоринг доказательств применяет собственное правило истечения при расчёте оценок.
Этот список не моделирует постепенное затухание.

`stale` перечисляет уже истёкшие даты. После изучения сохранённого статуса и доказательств выберите подходящий переход; отдельный `decay` показывает влияние истёкших доказательств на оценки, а не прогноз дат.

## Когда использовать

- В начале сессии, сразу после `forgeplan health` - устраните просроченную задолженность перед новой работой.
- Импорт в "коричневом поле" (Brownfield import) - посмотрите, какие импортированные артефакты уже просрочены.
- Перед тем как полагаться на ADR - это решение всё ещё действительно?
- CI pipeline (с `--json`) - предупреждайте, если просроченные артефакты упоминаются в новом коде.

## Когда НЕ использовать

- В качестве гейта качества при `activate` - используйте `validate` и `review` вместо этого.
- Чтобы применить фиксированный TTL для Note — эта команда не устанавливает автоматическое истечение через 90 дней и не скрывает Note по такому правилу.

## Использование

```text
forgeplan stale [OPTIONS]
```

## Опции

```text
      --json     Вывод в формате JSON для машинной обработки
  -h, --help     Вывести справку
  -V, --version  Вывести версию
```

## Примеры

### Найти все просроченные артефакты

```bash
forgeplan stale
```

Текстовый отчёт печатает `ID`, `Title`, `Expired` и `Days ago`.
Колонки с прежним и текущим R_eff в нём нет. Влияние на оценки изучайте
командой `score`; истечение решения не означает автоматическое истечение всех пакетов.

### Машиночитаемый формат

```bash
forgeplan stale --json | jq '.stale[] | select(.days_expired > 30)'
```

Фильтрует артефакты, просроченные более чем на 30 дней - кандидаты на обновление с высоким приоритетом.

### Сортировка в начале сессии

```bash
forgeplan health && forgeplan stale
# изучите сохранённый статус и причину истечения, прежде чем выбирать переход
forgeplan get ADR-002 --json
# пример для сохранённого статуса stale, после обоснованного ревью:
forgeplan renew ADR-002 --reason "проверены подтверждающие доказательства" --until 2027-04-23
forgeplan reopen PRD-007 --reason "replace with new approach"
```

## Интерпретация вывода

| Столбец            | Значение                                             |
|--------------------|------------------------------------------------------|
| ID / заголовок     | идентификатор артефакта                              |
| истёк X дн. назад  | дней после `valid_until`                             |
| Дней назад         | прошедшие дни от разобранной даты; список сам по себе не меняет R_eff |

Выбирайте действие по ревью и сохранённому статусу:

1. **`renew`** - для решения в сохранённом статусе `stale` после обоснованного ревью. Запись, у которой истёк срок, но сохранён статус `active`, не допускает продления `active → active`.
2. **`reopen`** - контекст изменился; создайте новый черновик и отмените старый (связи сохраняются).
3. **`deprecate`** - решение больше не применимо; пометьте его как окончательное с указанием причины.

## Как это вписывается в рабочий процесс

```
session start → health → stale → renew | reopen | deprecate → start new work
```

`Stale` - это ограничитель "не начинайте новую работу, пока накапливается долг". Протокол Unified Workflow рассматривает устранение просроченных артефактов как обязательное перед началом выполнения задач P0.
