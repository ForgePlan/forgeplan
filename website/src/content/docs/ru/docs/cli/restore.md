`forgeplan restore` требует существующей записи отмены в `.forgeplan/trash/`: по одному ID нельзя восстановить прошлую операцию. Команда находит самую свежую подходящую неиспользованную запись и применяет сохранённое состояние. Поддерживаются типы delete (создать строку заново и попытаться вернуть проекцию Markdown), supersede (вернуть сохранённые status/title в хранилище и убрать связь старый → замена), deprecate (вернуть сохранённые status/title в хранилище). Сохранённые связи добавляются заново, если другой артефакт ещё существует.

**Условие наличия записи в 0.38.0:** CLI `forgeplan delete` создаёт запись до удаления. CLI `forgeplan supersede` и `forgeplan deprecate` записи **не** создают; соответствующие MCP-инструменты создают. Restore может использовать эти записи MCP, но поддержка типа операции не означает возможность отменить изменение статуса через CLI. Убедитесь, что запись относится именно к нужной операции, а не является более старой записью для того же ID.

Для записи delete любая существующая запись с тем же ID блокирует восстановление. Supersede не освобождает ID. Для supersede/deprecate строка обычно остаётся: restore возвращает сохранённые status/title, а для supersede удаляет связь старый → замена; другой kind блокирует восстановление. Прежде чем вручную разрешать конфликт, сохраните и сравните обе версии. Не удаляйте и не заменяйте живую работу лишь ради успешного restore.

CLI запускает асинхронную очистку записей и парных тел старше 30 дней по возможности. Это отложенная очистка, не гарантированное удаление ровно в срок; сам поиск записи не фильтрует возраст. Trash — краткосрочное восстановление, не резервная копия.

Это точечный вариант [`forgeplan undo-last`](/ru/docs/cli/undo-last/) - `undo-last` откатывает самую свежую деструктивную операцию независимо от артефакта, а `restore` нацеливается на один конкретный артефакт по ID. Аналог [`forgeplan_restore`](/ru/docs/mcp/forgeplan_restore/) на MCP-стороне.

## Когда использовать

- Поняли, что вчерашний `forgeplan delete PRD-042` был ошибкой - восстанавливайте по точному ID.
- Существующая запись supersede/deprecate, например созданная соответствующим MCP-инструментом, относится к операции, которую нужно отменить.
- Нужно точное восстановление без риска откатить случайно ещё какую-то операцию, произошедшую позже.

## Когда НЕ использовать

- Не помните ID - [`forgeplan undo-last`](/ru/docs/cli/undo-last/) сам пройдёт по логу деструктивных операций от свежих к старым.
- Запись delete конфликтует с живым ID — изучите и сохраните обе версии до выбора способа восстановления.
- Подходящей записи нет, в том числе после CLI supersede/deprecate, которые её не создавали, — сохраните текущее состояние и изучите исходные проекции, историю системы контроля версий или резервную копию до выбора способа восстановления. `reindex` может импортировать возвращённую проекцию, если её строки нет, но не обновляет существующие status/title/depth/tags и не удаляет прежние связи между оставшимися записями. Не удаляйте индекс и не используйте `scan-import` для ремонта метаданных.

## Использование

```text
forgeplan restore [OPTIONS] <ID>
```

## Аргументы

```text
  <ID>  Artifact ID to recover from the most recent non-consumed receipt
```

## Опции

```text
      --json     Output as JSON for machine consumption
  -h, --help     Print help
  -V, --version  Print version
```

## Примеры

### Пример 1: Восстановление удалённого PRD

```bash
forgeplan restore PRD-042
```

Находит самую свежую неиспользованную запись для `PRD-042`, проигрывает оригинальную операцию в обратную сторону и печатает, сколько связей восстановлено. Если какие-то связи указывали на артефакты, которых больше нет, они попадают в `relations_skipped` - будете знать, что чинить руками.

### Пример 2: Проверка после восстановления

```bash
forgeplan restore PRD-042
forgeplan get PRD-042 --json
```

Проверьте сохранённые тело, статус и связи через `get --json`, **а затем отдельно откройте реальную проекцию Markdown в `.forgeplan/`**, чтобы сравнить frontmatter, тело и связи. `get` читает хранилище и не доказывает согласованность Markdown с индексом. Восстанавливайте пропущенные связи только после проверки их прежнего направления/типа и необходимости второго артефакта.

### Пример 3: Машинно-читаемый вывод

```bash
forgeplan restore PRD-042 --json | jq '.relations_skipped'
```

Возвращает JSON и извлекает ID других концов связей, пропущенных из-за отсутствия артефактов. Это не полные тройки связей. Перед повторным связыванием прочитайте запись восстановления, чтобы узнать направление и тип.

JSON успеха содержит `ok`, `restored`, `op_reversed`, `relations_restored`, `relations_skipped`, `projection_restored`, `warnings`, `_next_action`. При отсутствии записи JSON содержит `ok: false`, `error`, `_next_action`, код завершения — 1. Другие ошибки restore — обычные ошибки CLI и не обязательно имеют этот JSON-формат. Успех может сопровождаться предупреждениями или `projection_restored: false`; проверяйте оба поля, не предполагая возврат файла. Это не полный побайтовый откат исторической проекции и метаданных.

**Известное расхождение проекции ([#296 ARCH-5](https://github.com/ForgePlan/forgeplan/issues/296#issuecomment-6374114519)):** для записей supersede/deprecate релизный обработчик ставит `projection_restored: true`, потому что файл не перемещался; после возврата состояния хранилища он не перегенерирует проекцию. В хранилище статус может быть `active`, а в Markdown оставаться `deprecated` или `superseded`. Поэтому даже `ok: true` и `projection_restored: true` не доказывают согласованность двух представлений. Сохраните и изучите оба; одного `get` и обычного `reindex` недостаточно для полного исправления этого расхождения.

## Место в рабочем процессе

До восстановления определите нужную запись отмены и сравните её с текущим артефактом. Лог активности помогает установить последовательность событий, но не является записью отмены. После `restore <ID>` проверьте и хранилище (`get --json`), и настоящий файл проекции, включая статус и связи. Перед ручным исправлением изучите предупреждения и пропущенные артефакты; успешные флаги ответа не устраняют известное расхождение проекции.
