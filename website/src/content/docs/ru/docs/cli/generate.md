Создаёт Markdown-черновик через LLM по описанию. Обязательный блок `llm:` в `.forgeplan/config.yaml` задаёт провайдера/модель по умолчанию; переменные окружения могут их переопределить. HTTP-провайдеры — `openai`, `claude` (Anthropic), `gemini`, `ollama`, `custom`; явно выбранные subscription-CLI используют локальную сессию входа. Автоопределения провайдера нет. Промпт просит структуру по типу артефакта, но ответ сохраняется без валидации и сверки с кодом.

## Когда использовать

- Вы знаете, что хотите, и предпочли бы просмотреть черновик LLM, чем набирать шаблонный текст самостоятельно.
- **Прототип артефакта для обсуждения**: сгенерируйте одноразовый PRD, чтобы изучить полусформированную идею с командой, прежде чем приступать к созданию настоящего.
- **Исследование существующей системы (brown-field)**: опишите существующую подсистему и попросите модель реконструировать PRD / Spec / RFC для документации.
- У вас есть четкая однострочная задача («добавить ограничение скорости для /api/v1/») и вы хотите, чтобы все разделы были заполнены согласованно.
- Быстрая итерация на этапе Shape, когда вы хотите быстро попробовать 2-3 варианта формулировки.

## Когда НЕ использовать

- Выбранный провайдер недоступен — настройте API-ключ или локальный вход либо используйте [`forgeplan new`](/ru/docs/cli/new/) без LLM.
- Решение тактическое и не требует артефакта вообще - просто закоммитьте.
- Вы хотите полностью контролировать формулировки вручную - используйте [`forgeplan new`](/ru/docs/cli/new/) и заполняйте разделы самостоятельно.
- Вы фиксируете решение из разговора - используйте [`forgeplan capture`](/ru/docs/cli/capture/).
- Содержимое уже существует в сохраненной памяти - используйте [`forgeplan promote`](/ru/docs/cli/promote/).

## Использование

```text
forgeplan generate <KIND> <DESCRIPTION>
```

## Аргументы

```text
  <KIND>         Artifact kind: prd, epic, spec, rfc, adr, problem, solution, evidence
  <DESCRIPTION>  Description of what to generate
```

## Опции

```text
  -h, --help     Print help
  -V, --version  Print version
```

У `generate` нет флагов провайдера/модели и JSON-вывода. Отсутствующие обязательные учётные данные вызывают ошибку конфигурации; keyless-провайдерам API-ключ не нужен. При сбое генерации шаблон вместо ответа не создаётся. Описание отправляется настроенному провайдеру; исходники подсистемы команда не читает.

После значений YAML применяются `FORGEPLAN_LLM_PROVIDER`,
`FORGEPLAN_LLM_MODEL`, `FORGEPLAN_LLM_BASE_URL`,
`FORGEPLAN_LLM_MAX_TOKENS`, `FORGEPLAN_LLM_API_KEY_ENV`.
Последняя меняет **имя** переменной ключа, не значение ключа.
Лимит токенов переопределяется только при разборе значения как беззнакового
32-битного целого. Эти переменные не заменяют обязательный блок `llm:`,
даже для keyless-провайдера. Если неожиданны провайдер, endpoint, модель
или поиск ключа, проверьте унаследованные переопределения.

## Примеры

### Пример 1: Сгенерировать PRD из однострочной задачи

```bash
forgeplan generate prd "add rate limiting to /api/v1/ endpoints"
```

Создаёт `draft` с `depth: standard`. Заголовок метаданных — первая строка описания, до 80 символов; назначенный ID и реальный путь проекции выводятся как `ID:` и `Created:`. Используйте их, не угадывая имя файла. Проверьте текст модели, затем выполните `forgeplan validate <returned-id>`.

### Пример 2: Реконструировать RFC для существующей подсистемы

```bash
forgeplan generate rfc "current embedding pipeline: tract CPU inference, BGE-M3, 1024 dimensions, shared machine-wide cache"
```

Подходит для черновика по переданному описанию, не для аудита фактической системы. Промпт просит незакрытые чекбоксы действий; выполненность фаз автоматически не устанавливается. Сверьте каждое утверждение об архитектуре с исходниками.

### Пример 3: Составить черновик ProblemCard для нового сигнала

```bash
forgeplan generate problem "users report search returns stale results after renaming artifacts"
```

Промпт Problem запрашивает Signal / Context / Impact / Anti-Goodhart Indicators. Реальные разделы зависят от ответа модели. Проверьте текст перед облегчённой активацией: утверждение модели не является доказательством.

## Как это вписывается в рабочий процесс

```
route  →  generate  →  (review + edit)  →  validate  →  reason  →  code  →  evidence  →  review  →  activate
```

`generate` заменяет ручное написание первого черновика, не валидацию и ревью. Команда не задаёт состояние рассуждений, не создаёт связи с доказательствами и не активирует результат. Дальнейшие требования к reasoning/evidence определяются методологией и проверками отдельных команд, а не автоматическим поведением генерации.
