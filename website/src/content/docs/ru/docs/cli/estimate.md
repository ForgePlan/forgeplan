`forgeplan estimate` извлекает элементы FR и Phase и оценивает все пять грейдов.
Сложность Фибоначчи 1/2/3/5/8/13 соответствует базовым часам Senior
3/5/8/13/21/34, после чего применяются настроенные множители.
Это модель планирования по правилам, а не измеренный прогноз поставки.

## Когда использовать

- Планирование спринта: оценивайте каждый кандидат PRD/RFC, чтобы он соответствовал пропускной способности (≈40–50% от номинальной).
- Проверка пропускной способности перед началом Epic - это 2 недели или 2 месяца?
- Делегирование коллеге по команде - `--grade middle`, чтобы увидеть, как задача выглядит для него.
- Планирование агентов — `--grade ai` выделяет AI в заголовке; часы зависят от типа задачи и накладных расходов на ревью человеком.

## Когда НЕ использовать

- Для Note или ProblemCard - у них нет структуры FR/Phase для оценки.
- В качестве контракта - оценки предназначены для планирования, а не для обещаний. Откалибруйте с помощью `calibrate-estimate` постфактум.

## Использование

```text
forgeplan estimate [OPTIONS] <ID>
```

## Аргументы

```text
  <ID>  Artifact ID to estimate
```

## Опции

```text
      --grade <GRADE>            Override grade for all items (junior|middle|senior|principal|ai)
      --my-grade                 Use grade profile from config (domain-aware)
      --llm-score                Use LLM-based complexity scoring instead of rule-based heuristics
      --complexity <COMPLEXITY>  Manual complexity overrides: FR-001=5,FR-002=3 (Fibonacci: 1,2,3,5,8,13)
      --json                     Output as JSON for machine consumption
  -h, --help                     Print help
  -V, --version                  Print version
```

## Примеры

### Оценка PRD для вашего собственного профиля грейда

```bash
forgeplan estimate PRD-001 --my-grade
```

Текстовый отчёт содержит таблицу всех грейдов (`ID`, `Description`, `Cmpl`,
`Jun`, `Mid`, `Senior`, `PS`, `AI`), суммы, эквиваленты восьмичасовых дней,
confidence и подсказки. `--grade` / `--my-grade` выбирают грейд в заголовке,
но не убирают остальные столбцы и не меняют суммы JSON.

Условный расчёт: pure-coding элемент сложности 3 имеет 8 базовых часов Senior.
По умолчанию Senior — 8h, Middle — 12h, AI —
`8 × 0.10 × 1.30 = 1.04h`.

### Сравнение человеческого и AI-помощного пути

```bash
forgeplan estimate PRD-001 --grade senior
forgeplan estimate PRD-001 --grade ai
```

AI использует множители 0.10 / 0.25 / 0.30 / 0.50 / 1.00 для чистого кода,
кода с инфраструктурой, проектирования с кодом, чистой инфраструктуры
и координации. Ревью по умолчанию добавляет 30% только к AI-часам.
Эти значения настраиваются.

### Ручное переопределение сложности

```bash
forgeplan estimate PRD-001 --complexity FR-001=8,FR-002=2
```

Используйте, когда эвристика неверно оценивает сложность (например, «простое» FR скрывает миграцию).

### Оценка с помощью LLM

```bash
forgeplan estimate PRD-001 --llm-score
```

Требует настроенной LLM. При сбое оценки используется эвристика;
ручные переопределения `--complexity` применяются последними.
Рассчитанные оценки не сохраняются обратно в артефакт.

## Интерпретация вывода

| Значение | Смысл |
|---|---|
| Часы элемента | Базовые часы × множитель грейда человека либо множитель типа AI-задачи × `(1 + review_overhead)` |
| Totals | Сумма часов элементов для каждого грейда |
| Score | Число Фибоначчи × базовые часы Senior, суммируется по элементам |
| Confidence | Оценка структурных признаков с причинами, не вероятность поставки |
| Safety margin | В конфигурации по умолчанию 0.50, но калькулятор релиза его не применяет |

`--json` возвращает `result`, `_next_action` и внешние workflow-`hints`.
В `result` входят `artifact_id`, `artifact_title`, `items`, `totals`,
`total_score`, `confidence`, `confidence_reasons` и необязательные
подсказки оценки `hints`. Элемент содержит `id`, `description`, `complexity`
(строка enum, например `"Medium"`, не `3`), `task_type` (например
`"pure_coding"`), `hours` с ключами
`junior`/`middle`/`senior`/`principal`/`ai` и `score`.
Отсутствие элементов — успешный пустой результат, не ошибка.

Красный флаг: общая сумма более 40 часов - рассмотрите возможность разделения PRD или увеличения глубины.

## Как это вписывается в рабочий процесс

```
route → new → validate → estimate → sprint commit → code → calibrate-estimate
```

Внесите общую сумму в пропускную способность вашего спринта (senior разработчик, планирующий с 50% загрузкой, имеет около 20 «часов оценки» в неделю). После завершения спринта `calibrate-estimate` покажет, насколько точной была оценка.
