`forgeplan fpf ingest` загружает отдельно установленные файлы разделов **First Principles Framework** в таблицу `fpf_spec` рабочего пространства в `.forgeplan/lance/`. На каждый непустой Markdown-файл в непосредственном подкаталоге разделов создаётся строка, кроме `_index.md`; файлы в корне и более глубоких каталогах не сканируются. Число разделов зависит от установленного корпуса.

Запускайте после инициализации пространства, когда нужны `fpf search`, `fpf section` или `fpf list`. `fpf rules`, `fpf check` и `fpf dashboard` работают с артефактами и конфигурацией, поэтому загрузка базы знаний им не нужна.

## Когда использовать

- **Сразу после `forgeplan init -y`** - для заполнения базы знаний перед началом любой работы по рассуждению.
- **В свежем клоне** — производная база LanceDB игнорируется Git и заполняется локально.
- **После обновления отдельно установленного корпуса FPF** — обновление бинарника само по себе не поставляет новые файлы разделов.
- **Когда `fpf status` сообщает, что база знаний просрочена или пуста.**

## Когда НЕ использовать

- Вам не нужно запускать его перед каждой сессией рассуждения; база знаний сохраняется между вызовами.
- Не запускайте его параллельно с `forgeplan reason --fpf` - сначала дождитесь завершения загрузки.
- Это не замена `forgeplan reindex`: команда сканирует проекции **артефактов** пространства, не базу знаний FPF. Она импортирует новые записи, синхронизирует различающиеся тела, добавляет недостающие связи и убирает сирот, но не полностью обновляет метаданные существующих записей и не удаляет прежние связи между оставшимися записями.

## Использование

```text
forgeplan fpf ingest [OPTIONS]
```

## Опции

```text
      --path <PATH>  Path to FPF sections directory
  -h, --help         Print help
  -V, --version      Print version
```

**Спецификация FPF не вшита в бинарник**, она поставляется как скилл Claude Code и ставится отдельно. Без неё индексировать нечего, а `fpf search` продолжит отвечать «нет совпадений», что читается как пустой корпус, а не как отсутствующий.

По умолчанию `fpf ingest` ищет разделы в каталоге скиллов, начиная с актуального имени:

```text
~/.claude/skills/fpf-knowledge/sections
~/.claude/skills/fpf/sections
~/.claude/skills/fpf-simple/sections     # historical name, still accepted
```

Скилл `fpf` ставится из [маркетплейса](https://github.com/ForgePlan/marketplace). Передайте `--path`, чтобы взять разделы откуда угодно ещё: из чекаута спецификации, из исправленного корпуса или прямо из клона маркетплейса:

```bash
forgeplan fpf ingest --path <marketplace>/plugins/fpf/skills/fpf-knowledge/sections
```

## Примеры

```bash
# First-time setup - uses the installed skill
forgeplan init -y
forgeplan fpf ingest

# Re-ingest after upgrade
forgeplan fpf ingest
forgeplan fpf status

# Ingest from an external FPF sections directory
forgeplan fpf ingest --path ./fpf-sections/
```

## Что происходит

1. Forgeplan находит разделы FPF: установленный скилл или то, на что указывает `--path`.
2. Из файлов извлекаются ID, имена родительских разделов, заголовки, тела, число строк и исходные пути.
3. До кодирования и вставки прежние строки FPF удаляются. Это замена базы знаний, не добавление; индекс артефактов не очищается.
4. Сборки с `semantic-search` кодируют заголовок и тело через BGE-M3 (1024 измерения; около 2.1 GB при первой загрузке). Сборка без этой функции вставляет строки только для поиска по словам. При включённой функции ошибка модели или кодирования прерывает загрузку: резервного перехода на поиск по словам у этой команды нет.
5. Строки вставляются с меткой `created_at`. Отдельной записи статуса загрузки нет.

Не запускайте загрузку параллельно с чтением. Ошибка после очистки таблицы может оставить базу знаний пустой; исправьте проблему источника или модели и повторите загрузку. Провайдер LLM и API-ключ не нужны. Кеш весов исключает повторное скачивание, но не вычисление векторов на CPU.

## Как это вписывается

Загрузка подготавливает команды чтения базы знаний:

```text
forgeplan fpf ingest
  ├── fpf search
  ├── fpf section B.3
  └── fpf list
```

Она также делает доступным необязательный контекст для `forgeplan reason <ID> --fpf`. Если совпадений нет, `reason --fpf` сообщает об этом и продолжает без контекста базы знаний: загрузка не является жёстким условием рассуждения. `fpf status` сравнивает число исходных файлов и строк таблицы, а не хеши содержимого, поэтому одинаковое количество не доказывает неизменность корпуса.
