Инкрементально синхронизирует LanceDB с изменениями Markdown после `git pull`, `git merge` или `git rebase`. Вместо полной перестройки индекса `git-sync` выбирает пути, изменившиеся между git-ссылкой и `HEAD`, затем читает эти пути с диска.

## Использование

```text
forgeplan git-sync [OPTIONS]
```

## Опции

```text
      --since <SINCE>  Git ref to diff against (default: ORIG_HEAD from last pull/merge)
  -h, --help           Print help
  -V, --version        Print version
```

## Как это работает

1. Выполняет `git diff --name-status <SINCE> HEAD -- .forgeplan/` и оставляет пути `.md`.
2. Читает текущие файлы для добавленных/изменённых путей и разбирает frontmatter.
3. Создаёт новые записи из frontmatter. Существующие обновляются только при различии тел после trim; тогда же синхронизируется status, если он задан. Изменения только метаданных пропускаются; этот путь не обновляет полностью title, depth, tags и оценки.
4. Для удалённых файлов извлекает ID из имени и удаляет соответствующий артефакт из индекса вместе со связями.
5. Для обработанных файлов добавляет отсутствующие связи frontmatter, но не удаляет прежние. Записывает изменения с источником `git_sync` и хешем текущего коммита.

`ORIG_HEAD` используется по умолчанию, потому что `git pull`/`git merge`/`git rebase` устанавливают его на предыдущий кончик текущей ветки, предоставляя `git-sync` точное «окно» того, что пришло с этим pull.

## Когда это использовать

-   **После `git pull`** - коллеги объединили новые PRD/RFC в `dev`, вы только что выполнили pull, и хотите, чтобы они появились в вашем локальном LanceDB. `git-sync` выполняется за долю времени полной переиндексации.
-   **После `git merge feature/xyz`** - то же самое для локальных слияний.
-   **После `git checkout`** между ветками с расходящимся состоянием артефактов - передайте `--since <other-branch>` для синхронизации изменений.

## Рабочий процесс удалённой команды

```bash
# Morning routine with an active team
git checkout dev
git pull origin dev          # pulls 3 new PRDs from teammates
forgeplan git-sync           # incrementally sync paths changed by the pull
forgeplan log                 # see what arrived
forgeplan health             # check for new blind spots
```

Сравнение со сканированием проекций всего пространства:

```bash
forgeplan reindex            # scans workspace projections; see limits below
```

Для небольших рабочих пространств разница незначительна; для рабочих пространств с сотнями артефактов `git-sync` значительно быстрее.

## `git-sync` vs `reindex` vs `watch`

| Команда     | Использовать, когда                                    | Стоимость         |
|-------------|--------------------------------------------------------|-------------------|
| `git-sync`  | После git pull/merge, если известна ссылка для сравнения | O(изменённые файлы) |
| `reindex`   | Новые проекции пространства, изменения тела, очистка сирот | O(все артефакты) |
| `watch`     | Интерактивная правка тела с объединением событий | наблюдатель на переднем плане |

**Эмпирическое правило:** после перемещения `HEAD` команда `git-sync` может обработать изменившиеся пути. Для ручной правки тела используйте `reindex` или запущенный `watch`. `reindex` сканирует проекции, импортирует новые записи из их frontmatter, обновляет различающиеся тела существующих записей, добавляет отсутствующие связи frontmatter и удаляет осиротевшие записи и связи. Это **не** полный сброс: существующие title, depth, status и tags из frontmatter не обновляются, а удалённые связи между оставшимися записями не убираются. Там, где это поддерживается, используйте явные команды метаданных, тегов и связей, например `update --depth`, а не рассчитывайте исправить любое расхождение ещё одной переиндексацией.

## Пример

```bash
# Default - since last pull/merge
forgeplan git-sync

# Explicit diff base (e.g. against main)
forgeplan git-sync --since origin/main

# Check what a PR branch brought in
git checkout feat/prd-050-discover
forgeplan git-sync --since dev
```

## Ограничения

- Команда не требует чистого рабочего дерева. Список путей берётся из зафиксированных ссылок, но содержимое читается из рабочего дерева: незафиксированные изменения выбранных путей могут попасть в индекс, а изменения остальных путей будут пропущены.
-   Если `ORIG_HEAD` устарел (не было недавних pull/merge), передайте `--since` явно.
- Для внеполосной правки тела нужны `reindex` или `watch`; для изменений только метаданных — соответствующая явная команда, а не обещание полного обновления метаданных.
- Статусы rename/copy пропускаются. `reindex` может обнаружить пути проекций и убрать сирот, но сохраняет описанные выше ограничения для метаданных существующих записей и связей. Не удаляйте производный индекс ради восстановления.
- Отдельные ошибки чтения, разбора и отсутствующий ID печатаются как `SKIP` и учитываются в итогах, но код завершения может остаться 0. Изучите сводку, прежде чем считать синхронизацию полной.
