`forgeplan phase` показывает рекомендательный этап артефакта: Shape, Validate, Adi, Code, Test, Audit, Evidence или Done. Состояние хранится в `.forgeplan/state/<id>.yaml`. JSON содержит сохранённую историю переходов, текст — только последние три записи. Обычно команда читает состояние, но обработка повреждённого YAML может переименовать файл, как описано ниже.

Фаза **рекомендательная** - это подсказка для людей и агентов, а не блокировка. Никакая другая команда Forgeplan не откажет в работе из-за «неправильной» фазы. Если у артефакта ещё нет файла состояния (создан до появления отслеживания фаз или с `phase.enabled: false` в конфиге), команда напечатает `current_phase: unknown` с пустой историей - это норма, не ошибка.

Это CLI-вариант [`forgeplan_phase`](/ru/docs/mcp/forgeplan_phase/) на MCP-стороне.

## Когда использовать

- Возвращаетесь к артефакту, который уже в работе - «на чём я остановился?».
- Перед работой — сопоставить записанный этап с реально выполненной работой. Метка не доказывает запуск валидации, тестов или расчёта оценки.
- Ревью старого артефакта - прочитать историю переходов и понять путь, который он прошёл.
- Аудит или отладка - у каждого перехода есть timestamp и опциональная причина, можно реконструировать решения.

## Когда НЕ использовать

- Как жёсткий гейт для блокировки работы - фаза рекомендательная. Для структурной блокировки используйте [`forgeplan validate`](/ru/docs/cli/validate/).
- Для lifecycle-переходов (`draft` → `active` → `superseded`) - это отдельная state-машина; см. [`forgeplan activate`](/ru/docs/cli/activate/), [`forgeplan supersede`](/ru/docs/cli/supersede/), [`forgeplan deprecate`](/ru/docs/cli/deprecate/).
- На Note или тривиальных тактических фиксах - отслеживание фаз не ожидается для одноразовой работы.

## Использование

```text
forgeplan phase [OPTIONS] <ID>
```

## Аргументы

```text
  <ID>  Artifact ID whose phase state to read
```

## Опции

```text
      --json     Output as JSON for machine consumption
  -h, --help     Print help
  -V, --version  Print version
```

## Примеры

### Пример 1: Инспекция in-flight PRD

```bash
forgeplan phase PRD-057
```

Печатает текущую фазу, тип workflow и последние три перехода в text-режиме (полная
история - в `--json`). Иллюстративный вывод для трёх записанных переходов:

```text
PRD-057 phase: code (workflow: greenfield)
  last advanced: 2026-04-26 09:30:00 UTC
  history (showing last 3 of 3):
    2026-04-25 14:00 - -> shape
    2026-04-25 15:20 shape -> validate
    2026-04-26 09:30 validate -> code -- ready for implementation
  suggested next: test (override: `forgeplan phase-advance PRD-057 --to <phase>`)

Next: forgeplan phase-advance PRD-057 --to test
```

### Пример 2: Полная история как JSON

```bash
forgeplan phase PRD-057 --json | jq '.history'
```

Возвращает все переходы, оставшиеся в файле состояния. При записи история ограничена 1024 элементами: сохраняются первая запись и наиболее свежие переходы. Это не бесконечный журнал аудита; для более длительного анализа отдельно сохраняйте доступную историю.

### Пример 3: Артефакт без файла состояния

```bash
forgeplan phase PRD-001
```

Если у артефакта нет файла состояния (создан до появления отслеживания фаз или с выключенным `phase.enabled`), вывод покажет `current_phase: unknown` и пустую историю. Это намеренно, не ошибка. Начать отслеживание можно через [`forgeplan phase-advance`](/ru/docs/cli/phase-advance/).

JSON существующего состояния содержит `artifact_id`, `workflow_type`, `current_phase`, `advanced_at`, `schema_version`, `history` (`from`, `to`, `at`, `reason`), `_next_action`. При отсутствии файла возвращаются `current_phase: "unknown"`, `workflow_type: "greenfield"`, пустая `history`, `message` и `_next_action`, без времени и версии схемы. Несуществующий артефакт тоже может вернуть это рекомендательное состояние unknown: команда не проверяет существование.

## Unknown, ошибки и карантин

Отсутствие файла состояния возвращает рекомендательный ответ unknown. Симлинк вместо файла, размер больше 1 МиБ или разобранное состояние с `schema_version` больше 1 тоже дают unknown, но без карантинного переименования повреждённого YAML.

Ошибка десериализации YAML обрабатывается иначе: читатель пишет предупреждение и пытается переименовать `<id>.yaml` в `<id>.yaml.corrupt.<UTC-unix-seconds>`. Он возвращает unknown и при успехе, и при ошибке переименования, отдельно записывая ошибку в лог. Поэтому эта команда просмотра не является безусловно операцией только чтения, а unknown не доказывает сохранность карантинной копии. До инициализации или продвижения нового состояния изучите реальный каталог состояния.

Неверные ID артефактов, отсутствие нужного пространства/хранилища и другие переданные наверх ошибки чтения/ввода-вывода могут завершить команду ошибкой. Рекомендательный характер не означает, что любая ошибка превращается в unknown.


## Место в рабочем процессе

Отслеживание фаз — слой наблюдаемости над методологическим процессом (Shape → Validate → Code → Evidence → Activate). Чтение через `phase`, запись через [`forgeplan phase-advance`](/ru/docs/cli/phase-advance/). Ручная метка не выполняет названный этап, не проверяет его завершение и не заменяет отдельные проверки жизненного цикла при `activate`.
