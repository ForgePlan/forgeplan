Forgeplan сочетает лексический поиск с необязательными semantic-векторами.
Разделы v0.18 ниже описывают исторический BM25 engine; числа benchmark -
исторические наблюдения, не замеры локальной сборки Constellation.

Для мигрированных workspace локальной `0.39.0+constellation.s1.1` (не
опубликованной 0.38.0) см. [руководство Constellation](/ru/docs/guides/constellation/)
и [справочник](/ru/docs/reference/constellation/). Обычный `search` по
умолчанию возвращает до 20 результатов, отдельный `constellation search` - до 10.

## Для кого это

- Вы написали артефакт несколько месяцев назад и помните только "что-то про аутентификацию".
- Вы работаете в двуязычной команде (английский + русский) и хотите, чтобы оба запроса находили один и тот же PRD.
- Вы создаете ИИ-агента на базе MCP-сервера Forgeplan и нуждаетесь в детерминированном, быстром извлечении данных.

## Производственный движок BM25 (v0.18.0)

До v0.18 Forgeplan поставлялся с 140-строчной реализацией BM25, написанной вручную. Она работала, но ее было трудно настраивать, у нее не было встроенного стеммера, и она оценивала записи по одной - O(N²) на практике, как только рабочее пространство разрасталось до сотни артефактов. Версия v0.18.0 заменяет этот прототип производственным крейтом [`bm25` v2.3.2](https://crates.io/crates/bm25), который приносит четыре конкретных преимущества:

-   **Корректное взвешивание терминов.** Производственный TF-IDF / BM25 с нормализацией по длине вместо нашего наивного подсчета подстрок.
-   **Пакетный поиск O(N).** Один вызов `search_scores()` ранжирует весь корпус за один проход. Рабочее пространство со 193 артефактами возвращает результат за **0.23с**, что значительно быстрее многосекундных задержек, из-за которых `search` казался медленным.
-   **Встроенный стек токенизатора.** Сегментация Unicode, удаление стоп-слов и (что крайне важно) подключаемые стеммеры - это то, что обеспечивает русскую морфологию в следующем разделе.
-   **Удаление шаблонного "шума".** `strip_indexing_noise()` запускается перед токенизацией и удаляет YAML-фронтматтер, строки `{placeholder}`, строки `|table|` и HTML-комментарии из индексируемого текста. Это исправляет PROB-030: в v0.17 `forgeplan search "auth"` находил каждый PRD, у которого в фронтматтере было `author:`, заполняя результаты ложными срабатываниями. v0.18 индексирует только реальное содержимое тела документа.

Эти четыре изменения внесены в v0.18.0 и покрыты регрессионными тестами в `crates/forgeplan-core/src/search/` - см. запись в CHANGELOG.

## Как это работает

В smart-режиме лексическое ранжирование и необязательные semantic-оценки
объединяются до расширения графа. Принудительные keyword и semantic
используют другие пути.

1. **Лексический (BM25 + подстроки)** — BM25 учитывает частоты терминов,
   обратную частоту документов и длину; отдельный substring-канал даёт
   частичные совпадения. Измеренный процент покрытия запросов не заявляется.
2. **Фильтры и усилители** — kind/status ограничивают кандидатов.
   R_eff, active status и центральность графа повышают оценки совпадений.
3.  **Расширение графа** - результаты опционально обогащаются соседними артефактами через типизированные ссылки (`informs`, `refines`, `supersedes`), так что попадание в PRD также выводит его RFC и доказательство.

Сверху может быть наложен опциональный семантический этап, основанный на эмбеддингах BGE-M3 - см. раздел [Семантический поиск](#семантический-поиск-флаг-функции) ниже.

### Токенизация и стемминг

Перед индексацией тело документа очищается. Запрос использует тот же
токенизатор, но не проходит через удаление шаблонного шума документа:

```
document body → strip_indexing_noise() → prepend title
document text or query
  → whichlang detect             // per document/query; detection can be wrong
  → lowercase + unicode split
  → stop-word filter
  → Snowball stem (when the detected language has a supported stemmer)
  → BM25 term vector
```

Если обе стороны выбрали русский стеммер, формы существительного вроде
`"аутентификация"` и `"аутентификации"` могут иметь общий stem и совпадать.

### Удаление шаблонного "шума"

PRD и RFC, созданные из шаблонов Forgeplan, содержат много структурного шаблонного текста, который раньше загрязнял индекс:

-   YAML-фронтматтер (`id:`, `author:`, `status:` …)
-   Строки-заполнители, такие как `{problem statement}`, оставшиеся в заготовках артефактов
-   Таблицы Markdown (`| FR | Description | Status |`)
-   HTML-комментарии из подсказок шаблонов

До v0.18 запрос `auth` совпадал со словом `author:` в каждом блоке фронтматтера. `strip_indexing_noise()` удаляет эти разделы до того, как они достигнут токенизатора, поэтому лексические оценки отражают только реальное содержимое. Это отслеживается как PROB-030.

### Пакетный поиск O(N)

Реализация v0.17 вызывала `.score()` для каждой записи, что приводило к поведению O(N²) в рабочих пространствах с сотнями артефактов. v0.18 использует `search_scores()` из крейта `bm25`, который ранжирует весь корпус за один проход:

-   Рабочее пространство со 193 артефактами: **0.23с** от начала до конца
- Этот датированный результат не гарантирует задержку на другой машине или корпусе.

## Многоязычная морфология

v0.18.0 включила `LanguageMode::Detect`. В закреплённом токенизаторе
`bm25` 2.3.2 есть 17 fixed-language variants, но auto-detection сопоставляет
со стеммерами только часть: арабский, немецкий, английский, французский,
итальянский, голландский, португальский, русский, испанский, шведский и
турецкий. Для неподдерживаемых результатов detection стеммер не применяется.
Это не перевод между языками.

Иллюстрация выдачи для русского существительного, не runtime transcript:

```
$ forgeplan search "аутентификация"
PRD-019 Auth middleware    (matches "аутентификации" via stem "аутентификац")
EVID-023 Auth benchmark    (matches "аутентификацию")
```

Словоформы существительного могут иметь общий stem при совпадающем
определении языка. Detection, статистика корпуса и другие каналы ранжирования
влияют на выдачу и score; одинаковые оценки не гарантируются.

## Русская морфология на практике

Создайте PRD на русском языке:

```bash
forgeplan new prd "Система аутентификации"
```

Попробуйте склонения существительного и связанный глагол отдельно:

```bash
forgeplan search "аутентификация"     # именительный падеж
forgeplan search "аутентификации"     # родительный / дательный падеж
forgeplan search "аутентификацией"    # творительный падеж
forgeplan search "аутентифицировать"  # глагольная форма
```

Стемминг не является поиском синонимов или словообразовательных связей.
Не предполагается, что `аутентифицировать` имеет stem существительного
или что все английские производные сводятся к одному stem. Короткие и
смешанные запросы могут получить неверный язык. Сравнивайте фактическую
выдачу, не требуйте одинаковых оценок.

## Использование CLI

Все примеры предполагают, что вы находитесь внутри рабочего пространства Forgeplan.

### 1. Простой запрос

```bash
forgeplan search "bm25 russian morphology"
```

По умолчанию выводит до 20 результатов с типом, ID, заголовком и оценкой.

### 2. Фильтрация по типу

```bash
forgeplan search "auth" --type prd
forgeplan search "auth" --type rfc
forgeplan search "auth" --type evidence
```

Возвращаются только артефакты запрошенного типа. Полезно, когда вам нужен RFC, объясняющий, как создается PRD.

### 3. Фильтрация по статусу

```bash
forgeplan search "tags canonicalization" --status active
forgeplan search "deprecated semantics"   --status deprecated
```

Объедините с `--type` для точного выбора:

```bash
forgeplan search "scoring" --type prd --status active
```

### 4. Ограничение результатов

```bash
forgeplan search "LanceDB" --limit 5
```

По умолчанию 20. Для запроса одного результата задайте `--limit 1`.

### 5. Переиндексация после ручных изменений

После осознанной правки канонического Markdown опубликуйте производный
индекс командой, соответствующей его layout:

```bash
forgeplan index  # Constellation; для legacy layout используйте forgeplan reindex
```

`reindex` читает канонический Markdown артефактов. На layout Constellation
он выполняет reconcile, а не создаёт legacy-таблицы. Свежий canonical read
и сохранённое поколение индекса - разные состояния.

## Использование MCP

Сервер MCP предоставляет тот же движок в виде инструмента под названием `forgeplan_search`. Агенты могут вызывать его через stdio. Пример вызова JSON:

```json
{
  "name": "forgeplan_search",
  "arguments": {
    "query": "semantic scoring intelligence",
    "kind": "prd",
    "status": "active",
    "limit": 5
  }
}
```

MCP payload использует `results`, `total`, `coverage`, а не `hits` или
`took_ms`. Поля описаны в [`forgeplan_search`](/ru/docs/mcp/forgeplan_search/).
Этот пустой payload - иллюстрация формы, не runtime transcript:

```json
{
  "results": [],
  "total": 0,
  "coverage": {
    "semantic": false,
    "lexical": true,
    "graph": false
  }
}
```

MCP использует `kind`, CLI - `--type`. MCP также принимает `workspace` и
`no_expand`; default limit - 20. `coverage` сообщает состояние каналов,
а не доказывает вклад каждого из них в ранжирование этого ответа. В текущем
full-MCP smart path `coverage.graph` задаётся как `!no_expand`, даже если
загрузка графа не удалась и граф не был передан ранжировщику. Поэтому true
не подтверждает вклад графа или полноту ответа; false для semantic
по-прежнему указывает на неполный отрицательный результат без semantic retrieval.

## Семантический поиск (флаг функции)

Для semantic-поиска нужны бинарник с `semantic-search`, снапшот BGE-M3
в кэше и подходящие векторы в индексе workspace. Текущий engine - tract,
не прежний fastembed; поддерживается только `bge-m3`. Веса модели занимают
около 2.1 GB отдельно от бинарника.

```bash
cargo install forgeplan --features semantic-search
forgeplan setup
forgeplan embed
forgeplan search "how do I prove a decision is sound" --semantic
```

Корень кэша - заданный `FORGEPLAN_MODEL_CACHE`, иначе `~/.forgeplan/models`
(платформенный/старый fallback лишь без home). `HF_HOME` не переопределяет
tract. Запросы и обслуживание не скачивают веса. Для фоновых эмбеддингов
также нужен явный `embedding:` config; одного `--auto-index` или прежнего
ручного `embed` недостаточно.

На мигрированном workspace принудительный `--semantic` не гарантирует
keyword fallback. Проверяйте доступность и coverage. Для лексического
поиска без semantic prerequisites явно используйте `--keyword`.

## Устранение неполадок

**Оценка всегда 0 или нет результатов.**
Сначала проверьте запрос, фильтры, source content и выбранный режим. Если
сохранённое поколение устарело, используйте `index` для Constellation или
`reindex` для legacy layout. Пустая выдача сама по себе не устанавливает причину.

**Запрос на русском языке ничего не находит, но тот же английский термин работает.**
Проверьте ограничения detection и различие существительных/глаголов выше.
Морфология не является переводом; переиндексация не даёт всем родственным
словам общий stem.

**Слишком много нерелевантных результатов из полей фронтматтера.**
Проверьте выбранную версию и поля источника. Наличие noise stripping не
доказывает, что любой нерелевантный результат вызван старым бинарником.

**Поиск медленный в большом рабочем пространстве.**
Историческая запись v0.18 сообщает 0.23с на 193 артефактах, не гарантирует
задержку менее секунды. В отчёте о производительности укажите режим, версию,
размер корпуса и фактически наблюдавшуюся задержку.

**Я удалил файл, но он все еще отображается в результатах.**
Различайте source и сохранённое поколение. Выполните reconcile через `index`
для Constellation либо `reindex` для legacy layout; свежесть canonical read
и сохранённого индекса — разные контракты.
