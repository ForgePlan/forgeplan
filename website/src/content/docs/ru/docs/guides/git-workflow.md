Эти соглашения о ветках и ревью описывают разработку самого Forgeplan.
Другие проекты могут выбрать свои ветки; CLI не навязывает эту стратегию.

## Стратегия ветвления

```
main                    ← продакшн (тегированные релизы)
  │
dev                     ← интеграционная ветка
  ├── feat/prd-018-dag  ← ветка новой функциональности
  ├── fix/search-bug    ← ветка исправления ошибок
  └── docs/rfc-002      ← ветка только для документации
```

## Правила ветвления

| Ветка | Создаётся из | Вливается в | Стратегия |
|--------|-------------|-------------|----------|
| `feat/*`, `fix/*` | **dev** | **dev** | Коммит слияния через PR |
| `release/v0.x.0` | **dev** | **main** + **dev** | Коммит слияния |
| `hotfix/*` | **main** | **main** + **dev** | Cherry-pick |

## Формат коммитов

```
<type>(<scope>): <description>

[тело - что и почему]

Refs: RFC-001, FR-001..004
```

### Типы

| Тип | Когда |
|------|------|
| `feat` | Новая функциональность |
| `fix` | Исправление ошибки |
| `docs` | Документация / артефакты |
| `refactor` | Без изменения поведения |
| `test` | Только тесты |
| `chore` | Сборка, зависимости, CI |

## Конвейер PR

```
Code → Audit → Fix → Test → Fmt → Lint → Verify → PR
```

**Не создавайте PR сразу после написания кода.** Помимо нужных тестов проверьте
затронутые пользовательские сценарии через реальный CLI/MCP-клиент.
Форматирование и успешная компиляция сами по себе не доказывают сквозное поведение.

## Перед каждым коммитом

```bash
cargo fmt           # форматирование
cargo fmt -- --check  # проверка: 0 различий
cargo check         # компиляция: 0 предупреждений
cargo test          # все проходят
```

## Синхронизация индекса артефактов с Git

Коммитьте markdown артефактов, конфигурацию и связи, но не производную базу
`.forgeplan/lance/`. У каждого клона свой индекс. После свежего клонирования
восстановите его из markdown командой `forgeplan reindex`.

В инициализированном Git-репозитории можно установить необязательные хуки
синхронизации без загрузки модели:

```bash
forgeplan setup --skip-model --skip-alias
```

Setup устанавливает или обновляет собственные хуки `post-merge` и
`post-checkout` по пути, который определяет Git (включая `core.hooksPath`).
Чужие хуки оставляет без изменений и сообщает об этом. `--skip-hooks`
отключает установку.

- `post-merge` вызывает `forgeplan git-sync`, используя предыдущий ref `ORIG_HEAD`.
- `post-checkout` при смене ветки передаёт предыдущий HEAD через `--since`.
- Хуки **не** запускают `embed`, скрывают вывод и ошибки синхронизации и не
  прерывают Git-операцию. Успешный pull не доказывает, что индекс обновлён.

Для восстановления с видимым выводом после pull/merge:

```bash
forgeplan git-sync
forgeplan health
```

Для другой Git-операции задайте известный ref до изменения, например
`forgeplan git-sync --since HEAD@{1}`, если эта запись reflog соответствует
предыдущему checkout. Без `--since` команде нужен `ORIG_HEAD`.

Git sync обрабатывает добавленные файлы артефактов, изменения тел и удаления.
В 0.38 он пропускает rename/copy и может пропускать правки только метаданных
или связей, если тело не изменилось. Для восстановления файлового индекса
используйте `reindex`, но не полагайтесь ни на один из этих путей для изменения
только метаданных существующей записи; используйте `update` или команду
жизненного цикла. `scan-import` импортирует новые документы, а не чинит индекс.

После синхронизации изменённых тел отдельно выполните `forgeplan embed`, если
нужен семантический поиск. Команда обрабатывает отсутствующие/изменённые тела
и может загрузить модель BGE-M3 объёмом ~2.1 ГБ, если её нет в кэше.

## Синхронизация релизных веток

После слияния `release/v* → main` откройте sync-PR из выпущенного состояния
`main` обратно в `dev` (например `chore/sync-main-to-dev-after-v0.38.0`).
Не отправляйте изменения напрямую в защищённые ветки и не продолжайте push
в feature-ветку, PR которой уже слит.
