## Стратегия ветвления

```
main                    ← продакшн (тегированные релизы)
  │
dev                     ← интеграционная ветка
  ├── feat/prd-018-dag  ← ветка новой функциональности
  ├── fix/search-bug    ← ветка исправления ошибок
  └── docs/rfc-002      ← ветка только для документации
```

## Правила ветвления

| Ветка | Создаётся из | Вливается в | Стратегия |
|--------|-------------|-------------|----------|
| `feat/*`, `fix/*` | **dev** | **dev** | Коммит слияния через PR |
| `release/v0.x.0` | **dev** | **main**, затем отдельный sync PR main → dev | Коммит слияния для релиза |
| `hotfix/*` | **main** | **main**, затем backport PR в **dev** | Cherry-pick или merge для backport |

## Формат коммитов

```
<type>(<scope>): <description>

[тело - что и почему]

Refs: RFC-001, FR-001..004
```

До присвоения номера при слиянии используйте стабильный slug в `Refs:`;
ID вроде `RFC-001` используйте только после присвоения номера.

### Типы

| Тип | Когда |
|------|------|
| `feat` | Новая функциональность |
| `fix` | Исправление ошибки |
| `docs` | Документация / артефакты |
| `refactor` | Без изменения поведения |
| `test` | Только тесты |
| `chore` | Сборка, зависимости, CI |

## Конвейер PR

```
Code → Audit → Fix → Test → Fmt → Lint → Verify → PR
```

**Не создавайте PR сразу после написания кода.** Записывайте фактически
выполненные проверки, включая реальный E2E каждой затронутой поверхности.
Прошедшие unit-тесты не доказывают работу всех сценариев.

## Перед каждым коммитом

```bash
cargo fmt           # форматирование
cargo fmt -- --check  # проверка: 0 различий
cargo check         # компиляция: 0 предупреждений
cargo test          # все проходят
```

Это проверки участников Rust-репозитория, не обязательные команды каждого
проекта с Forgeplan. При параллельной работе проверки после завершения правок
выполняет один build-owner; остальные агенты не запускают конкурирующие Cargo-процессы.
