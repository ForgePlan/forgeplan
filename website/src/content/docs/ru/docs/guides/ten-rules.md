---
title: 10 правил для структурированных решений
description: Практические правила из методологии Forgeplan
---

## 1. Сначала роутинг, потом разработка
`forgeplan route "your task"` предлагает глубину и конвейер артефактов. Уровень 0 использует ключевые слова; `--level 1` требует настроенного LLM. Команда не выбирает и не устанавливает агентов маркетплейса.

## 2. Каждое требование: «[Действующее лицо] может [возможность]»
Никаких технических названий в PRD. Описывайте ЧТО, а не КАК. «Пользователь может войти» вместо «React-компонент отображает форму входа».

## 3. Конвейер = руководство, а не бюрократия
Тактическая задача может обойтись без артефактов, но не без проверки. Для Standard обычно используют PRD → RFC; добавляйте остальные типы по потребности задачи, а не ради полного списка.

## 4. Дочерний артефакт ссылается на родительский
PRD → Epic, RFC → PRD, ADR → RFC. Всегда прослеживается вверх.

## 5. Замещайте, не удаляйте
Используйте `forgeplan supersede OLD-ID --by NEW-ID`, а не правку фронтматтера или `update --status superseded`. Если замены нет — `deprecate --reason`. История и причины остаются явными.

## 6. R_eff = min(evidence)
Доверие определяется слабым звеном, а не средним. CLI `score` рекурсивно берёт минимум собственных текущих доказательств и допустимых оценок зависимостей после штрафов за тип связи. Оценка доказательства учитывает verdict, CL и тип; истёкший допустимый пакет вместо этого получает 0.1 до вычитания штрафов. Терминальные пакеты `superseded`/`deprecated` исключаются, черновики учитываются, отсутствие допустимых собственных доказательств даёт собственную оценку 0.

## 7. Доказательства имеют срок действия
Истёкший допустимый EvidencePack оценивается в 0.1; это не фиксированная оценка любого просроченного решения. Изучите `forgeplan stale`, `forgeplan decay`, `forgeplan score ID` и перепроверьте утверждение до продления срока.

## 8. Сначала Shape, потом Code
Создайте артефакт, замените шаблонный текст, валидируйте и независимо проверьте передачу результата до кода. Используйте `forgeplan update ID --body @body.md`, чтобы markdown и производный индекс оставались согласованными. Никаких PRD-заглушек.

## 9. Тестируйте каждую `pub fn`
Тесты и ревью должны проверять требования, а не просто соглашаться с созданным кодом. В публичных конвейерах BMAD/SPARC/TDD автор и проверяющий работают в разных контекстах. TDD проверяет и фиксирует RED-тесты до GREEN; автор кода не может незаметно переписать этот эталон.

## 10. Работа не завершена, пока не активирована
Заполните и валидируйте артефакт, запишите реальные доказательства с `verdict`, `congruence_level`, `evidence_type`, свяжите их, изучите R_eff, проведите ревью и явно активируйте. Ревью плана может зафиксировать его до кода; доказательства реализации должны следовать за реальной реализацией. Активация не запускает тесты и не доказывает выпуск функции.
