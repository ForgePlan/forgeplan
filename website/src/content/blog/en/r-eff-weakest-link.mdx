> **Scoring clarification, 2026-10-23.** This is a product-specific heuristic, not a probability of truth or a universal FPF law. In target revision `c852f40c`, the recursive report uses `max(0, verdict_base − CL_penalty − type_modifier)` per unexpired pack, then the weakest eligible evidence/dependency contribution. Superseded/deprecated evidence is excluded, draft evidence still counts. Flat captured scores omit type/dependency modifiers and can differ. The worked example below assumes unexpired packs at the article's publication date, no dependency cap, and the recursive engine; the cover's 0–10 bars are only a schematic illustration.

### The claim

ForgePlan scores every decision artifact with a single number, **R_eff** (effective rigor). The formula is deliberately uncomfortable:

```
R_eff = min(evidence_scores)
```

Not the mean. Not the median. The minimum.

If a PRD has three EvidencePacks scored `0.9`, `0.6`, `0.1`, then R_eff = `0.1`. The PRD is as trustworthy as its weakest evidence, and pretending otherwise is statistical laundering.

This post unpacks why the minimum, what the individual evidence scores actually compute, and how to read a real R_eff number when you're staring at one in `forgeplan score`.

### Why minimum, not average

The minimum is Forgeplan's chosen bottleneck rule, not a consequence of Boole's inequality. A probability model can require different aggregation: two necessary independent conditions with success probabilities 0.9 give 0.81 jointly, not min(0.9, 0.9). [Current FPF B.3](https://fpf.tools/B.3) requires an applicable model rather than a universal minimum.

Average and median have an obvious failure mode: a single rigorous measurement can statistically mask a sloppy one. Imagine a PRD claiming "this scales to 10K QPS." You have three EvidencePacks:

- A staging benchmark at 10K QPS - score `0.9`
- A code review by two senior engineers - score `0.6`
- A note saying "tested locally on Mac mini, looked fine" - score `0.1`

The mean is about 0.53 and the median 0.6. The minimum exposes the weakest recorded support, but a weak anecdote neither causes nor predicts a production failure at 4K QPS. Whether that load works needs a suitable test.

R_eff = 0.1 forces the conversation onto the weakest evidence. Either upgrade that evidence (run the real benchmark) or admit the PRD is not yet trustworthy. The minimum is mean-spirited on purpose.

### What goes into a single evidence score

An EvidencePack's score is computed from three structured fields plus a TTL.

A minimal illustrative structured block (not a verbatim full template):

```markdown
## Structured Fields

verdict: supports            # supports / weakens / refutes
congruence_level: 3          # CL3 (best) … CL0 (worst, opposed)
evidence_type: measurement   # measurement / test / benchmark / audit
```

Absent/unrecognized `verdict` or absent congruence declaration forces CL0 in the current parser; a missing type defaults to measurement. That does not force every malformed pack to exactly 0.1: verdict, type and expiry also matter. PROB-034 was a different historical defect: multiline comments shadowed the real CL and the old fallback inflated it to CL3. v0.17.2 fixed comment skipping.

#### Verdict bases (1.0 / 0.5 / 0.0)

The verdict tells the scorer which direction the evidence pulls:

- `supports` - the evidence is consistent with the parent decision; full positive contribution.
- `weakens` — base 0.5, reduced by CL and type penalties; this is a nonnegative score, not a signed negative contribution.
- `refutes` — base 0.0, so an unexpired pack scores exactly zero. The expiry branch returns 0.1 before verdict handling, including for a refuting pack.

For unexpired eligible evidence, `supports` starts at 1.0, `weakens` at 0.5 and `refutes` at 0.0 before applicable penalties. Expiry and eligibility are separate branches; inspect them before interpreting the final score.

#### Congruence Level (CL3-CL0)

CL captures the contextual fidelity of the evidence - does it actually measure the thing the parent decision claims, in the conditions the parent decision applies?

| CL | Penalty | Meaning |
|----|---------|---------|
| CL3 | `0.0` | Same context as the decision. Best - production data, real users, the actual workload. |
| CL2 | `0.1` | Adjacent context. Staging environment, similar workload, comparable scale. |
| CL1 | `0.4` | Different context, related domain. Lab benchmark; different language but similar pattern. |
| CL0 | `0.9` | Very poor or unrelated fit. Lack of useful support is not itself evidence that the claim is false. |

A supports/measurement pack at CL0 scores 0.1 while unexpired. A one-machine test can be highly congruent for a one-machine claim; a production label alone cannot establish congruence. Record the claim and tested conditions before choosing CL.

#### Evidence type and score surfaces

The recursive engine subtracts 0 for measurement/test, 0.1 for benchmark and 0.2 for audit. Flat captured scores and some evidence breakdown fields omit this modifier. Therefore those displays can disagree with the recursive report; do not treat every displayed number as the same calculation. The old `compare` mention was a proposal, not a supported command contract.

#### TTL and decay

`valid_until` is optional. With no date the scorer does not expire the pack. With a date, the normal score holds until expiry, then returns 0.1 before verdict/CL/type arithmetic. This is a discrete product rule, not gradual physical decay or proof that every old observation is useless.

### A worked example

Suppose PRD-XYZ ("Adopt LanceDB as the derived index") has three EvidencePacks:

**EVID-A** - staging benchmark, 343-artifact workspace, p95 query latency 80ms.

```
verdict: supports
congruence_level: 3
evidence_type: benchmark
valid_until: 2026-08-01
```

Recursive score while unexpired: `1 − 0 − 0.1 = 0.9` (supports, CL3, benchmark).

**EVID-B** - adversarial code review by two engineers, identified one edge case (concurrent write contention).

```
verdict: weakens
congruence_level: 2
evidence_type: audit
valid_until: 2026-06-01
```

Recursive score while unexpired: `0.5 − 0.1 − 0.2 = 0.2` (weakens, CL2, audit). The original 0.55 was not produced by this formula.

**EVID-C** - note from a developer saying "I ran it on my MacBook, felt fast."

```
verdict: supports
congruence_level: 0
evidence_type: measurement
valid_until: 2026-12-01
```

Computed score: `0.10` (CL0 penalty kills it; "supports" verdict can't rescue CL0).

```
R_eff(PRD-XYZ) = min(0.9, 0.2, 0.10) = 0.10
```

Under these assumptions, R_eff is 0.10; the mean would be 0.40 and median 0.20. At a later date, expiry changes the inputs, so this is not expected output for a run today.

Improve weak evidence or justify a scope/lineage change with new evidence. Do not remove a relevant warning just to raise a score; retain counterevidence and the reason for any supersession or deprecation.

### How to read a real R_eff number

Reading guidance, not release policy:

- A low score identifies a recorded bottleneck; inspect its claim, context, freshness and provenance.
- A high score does not prove safety, correctness, readiness or that every requirement was tested.
- Neither number replaces applicable activation gates or the team's release criteria.

No population study is supplied for the original claim that most artifacts pass through particular score bands. No threshold here is a calibrated probability of surviving a postmortem.

### The phrase to remember

> **Trust = weakest link. R_eff = min(evidence_scores), never average.**

If you take only the formula away from this piece, that's the one that matters. The rest is unpacking.

ForgePlan operationalises it. The same idea applies if you build your own decision tooling: the aggregator you pick determines the conversation your team has during reviews. `min` forces honesty. `average` forecloses it. Pick deliberately.
