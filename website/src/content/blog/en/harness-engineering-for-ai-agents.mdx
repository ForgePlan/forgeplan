> **Historical scope, clarified 23 October 2026.** v0.30.0, test/workspace/plugin counts, binary size, stars and roadmap gaps below are dated author reports, not current acceptance evidence. MEMORY.md and Hindsight are separately configured host integrations. The session-amnesia analogy assumes no restored context. Claims are advisory intent markers, not filesystem locks. Creating a Note supplies no default 90-day TTL; expiry reporting requires an explicit `valid_until` and does not delete the record. The current repository's `CLAUDE.md` requires ADI for Standard+ work; document validation not enforcing the full workflow does not waive that obligation.

If your AI agent ships a feature with the wrong logic and a green test suite, the failure isn't in the prompt. It's in the harness around the prompt: the rules the agent reads on startup, the state it persists between turns, the tools it can call, the checks it has to pass, and the environment those checks run in.

That framing isn't mine. It comes from a small site called **walkinglabs** that has been writing the most precise material I've seen on what they call *harness engineering*:

> "If it's not the model weights, it's the harness." - *walkinglabs, Lecture 02*

[OpenAI's essay is dated 11 February 2026](https://openai.com/index/harness-engineering/), and [Anthropic's "Effective harnesses for long-running agents" is dated 26 November 2025](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents). Both show ways to improve the environment around a model; neither proves that the harness universally dominates model choice.

I'm going to walk through the five harness subsystems and show how I've implemented them in **ForgePlan** - an open-source Rust CLI + MCP server I've been dogfooding for six months. The code is at [github.com/ForgePlan/forgeplan](https://github.com/ForgePlan/forgeplan) if you want to read along.

## The five harness subsystems

walkinglabs *Lecture 02* lays out the model:

```
Rules (AGENTS.md / CLAUDE.md) ──┐
State (PROGRESS.md / git)      ──┤
                                  ↓
                          AI agent → Tools (shell / files / tests)
                                  ↑                ↓
                       Checks (test/lint/build) ← Env (deps/services)
```

The killer line from the same lecture: **"of the five subsystems, feedback usually has the lowest input and highest return."** Most teams ship vague tools and stop. The high-leverage move is rebuilding feedback.

### 1. Rules - the contract the agent reads on startup

The unfashionable opinion: a single well-structured `CLAUDE.md` (or `AGENTS.md`) can outperform a model upgrade. ForgePlan's project root has a CLAUDE.md with eleven explicit red lines and a *hint protocol* (PRD-071) that defines the next-action contract for every CLI and MCP response.

The intended hint contract uses these markers (separate examples, not one captured response):

```
Next: forgeplan validate PRD-074
```

```
Or: forgeplan reason PRD-074

Wait: claim TTL expires in 12m

Done.

Fix: forgeplan link evid-bench-p95 PRD-074 --relation informs
```

The agent can follow a marker, but a hint does not enforce ordering or prevent bypass. EVID-086's historical 70/70 command audit is not current proof that every CLI/MCP path emits exactly one correct next action.

walkinglabs *Lecture 03* phrases the underlying principle: **"Information that's not in the repo doesn't exist for the agent."** If the contract isn't in the repo, the agent doesn't follow it.

### 2. State - continuity between sessions

walkinglabs *Lecture 05* is short and unforgiving:

> "Treat the agent as a brilliant engineer with amnesia."

Every session starts from zero context. Three layers handle this in ForgePlan:

- `MEMORY.md` auto-loaded at session start (lightweight always-relevant facts)
- Per-project Hindsight memory bank (lazy semantic recall for the long tail)
- The `.forgeplan/` markdown corpus that *is* the repo's system of record

A fresh agent runs:

```bash
forgeplan health
forgeplan list --type prd
```

…and reads structured artifacts to reconstruct state. *Lecture 03*: **"Documentation that diverges from code is more dangerous than no documentation."** ADR-003 makes Markdown authoritative and LanceDB derived. Constellation rebuilds with `forgeplan index`; legacy workspaces use `forgeplan reindex`. `scan-import` imports external Markdown. The PROB-048 migration and `pub(crate)` boundary restrict direct mutating store calls across crates, not every possible file/index inconsistency.

### 3. Tools - typed, not free-form

ForgePlan ships 76 CLI commands and 73 MCP tools. The MCP server uses [rmcp](https://github.com/modelcontextprotocol/rust-sdk) (the official Model Context Protocol Rust SDK) so Claude Code, Cursor, or Aider can drive the methodology natively:

```jsonc
// MCP tool call
{
  "tool": "forgeplan_score",
  "arguments": { "id": "PRD-074" }
}

// Illustrative response, not a captured or complete current schema
{
  "id": "PRD-074",
  "r_eff": 0.10,
  "weakest_evidence": "EVID-091",
  "_next_action": "forgeplan link evid-bench-p95 PRD-074 --relation informs"
}
```

`_next_action`, when present, carries workflow guidance structurally. It is not an enforcement boundary and can be absent or semantically wrong; check the actual response rather than assuming universal coverage.

### 4. Checks - externalised judgement

walkinglabs *Lecture 09*:

> "Students can't grade their own exams."

The project's evidence-before-activation rule is a workflow obligation. Ordinary activation checks body length, evidence links, stubs and MUST findings, with separate caller-level provenance checks. It does not enforce an R_eff>0 threshold or prove the code works. Scoring supports the review:

**Weakest-link, never average:**
The snippet illustrates only the minimum of a **non-empty** list of already scored, eligible evidence. It is not production code: an empty iterator below yields infinity, whereas ordinary no-evidence production scoring returns zero; recursive production scoring also handles expiry, types, terminal status and dependencies.


```rust
pub fn r_eff(scores: &[f64]) -> f64 {
    scores.iter().cloned().fold(f64::INFINITY, f64::min)
}
```

If three pieces of evidence score 0.9, 0.6, 0.1 - your decision's `R_eff` is 0.1, not 0.53. Average lets a strong evidence statistically launder a weak one. Minimum forces the conversation onto the worst-supported claim.

**Congruence-level penalty:**

| CL | Meaning | Penalty |
|---|---|---|
| CL3 | Same context (e.g. benchmark on your production-shape data) | 0.0 |
| CL2 | Similar context | 0.1 |
| CL1 | Different context, transferred | 0.4 |
| CL0 | Opposed context | 0.9 |

A blog post that says "library X is fast" doesn't get to count the same as a benchmark you ran in your own workload, even if both produce numbers.

**PROB-034** records an A/B on one workspace using v0.17.1 and v0.17.2, not different clones under one binary. Multi-line HTML comment examples shadowed the real `congruence_level`, causing explicit CL0 to fall back to CL3: 1.00 before the fix, 0.10 after it. The fix skipped comment bodies. Current missing-verdict/CL fail-closed behavior is separate later work; `evidence_type` has a fallback.

A harness has to be able to catch itself cheating, or it has no business grading anyone else.

### 5. Env - reproducible by construction

BGE-M3 inference (1024d) can run locally with a compatible build, configuration and complete model cache. That does not mean installation is air-gapped: dependencies and model weights may need downloading. The article's ~41 MB binary is a historical report, not the size of the weights. The Cargo package is `forgeplan`, not `forgeplan-cli`.

For an existing Constellation clone, a conceptual maintenance sequence is:

```bash
git clone <repo>
cd <cloned-repo>
forgeplan index         # publish from canonical Markdown
forgeplan health        # inspect the actual verdict, not an expected PASS
```

Git preserves the committed source records, not the whole agent environment. Dependencies, configuration, host memory connections and model caches must be prepared separately. Use `reindex` for the legacy layout; `scan-import` is for importing foreign documents.

## What ForgePlan harness doesn't do yet

I'm naming the gaps because *Lecture 12* has a relevant principle: **"'we'll clean it up later' equals 'never.'"** Public gap lists are how I keep myself honest.

- **H1 - per-session task trace.** Process observability is solid (`forgeplan graph`, `forgeplan blindspots`, `forgeplan blocked`). Runtime observability is missing. No OpenTelemetry-style trace of "this agent, in this session, ran these tools, hit this gate." Reconstructing weird multi-agent runs from git history is not a sustainable answer.
- **H2 - Sprint Contract artifact.** In this dated roadmap sketch, the spectrum was Note (light, optionally given a review date) → PRD (heavy, MUST sections, ADI required for Standard+ work by repository policy). A Note's expiry is not assigned automatically. No dedicated one-week scope-bound primitive with explicit acceptance criteria and a deadline. *Lecture 11* makes a strong case for this. Drafted, not implemented.
- **H9 - WIP=1 hard limit.** `forgeplan claim/release` is a soft TTL lock. Nothing prevents one agent from holding three claims at once. *Lecture 07*: **"Don't bite off more than you can chew' applies particularly well to AI agents."**

## Try it
Use an isolated new project for the example below. `new` creates a template, not complete requirements: fill the body and fix validation findings before reasoning. `reason` needs a configured provider; `score` is not evidence generation and returns no support until real evidence is linked. Use the actual identifier printed by `new`.


```bash
brew install ForgePlan/tap/forgeplan
forgeplan init -y
forgeplan new prd "Migrate auth from Auth0 to Clerk"
forgeplan validate prd-migrate-auth-from-auth0-to-clerk
forgeplan reason prd-migrate-auth-from-auth0-to-clerk
forgeplan score prd-migrate-auth-from-auth0-to-clerk
```
