> **Уточнение скоринга, 2026-10-23.** Это эвристика продукта, не вероятность истинности и не универсальный закон FPF. В целевой ревизии `c852f40c` рекурсивный отчёт использует `max(0, verdict_base − CL_penalty − type_modifier)` для непросроченного пака, затем слабейший учитываемый вклад evidence/зависимости. Superseded/deprecated evidence исключаются, draft учитывается. Плоские оценки captured-записей не включают модификаторы типа/зависимостей и могут отличаться. Пример ниже предполагает непросроченные на дату публикации паки, отсутствие ограничения от зависимостей и рекурсивный скорер; столбцы 0–10 на обложке — лишь схема.

### Тезис

ForgePlan оценивает каждый артефакт решения единственным числом - **R_eff** (effective rigor, «реальная строгость»). Формула намеренно неудобная:

```
R_eff = min(evidence_scores)
```

Не среднее арифметическое. Не медиана. Минимум.

Если у PRD три EvidencePack с оценками `0.9`, `0.6`, `0.1`, то R_eff = `0.1`. PRD настолько же надёжен, насколько надёжно его слабейшее доказательство. Притворяться иначе - значит отмывать статистику.

Этот пост разбирает: почему минимум, что именно вычисляет оценка отдельного evidence, и как читать реальное число R_eff в выводе `forgeplan score`.

### Почему минимум, а не среднее

Минимум — выбранное Forgeplan правило узкого места, не следствие неравенства Буля. Вероятностная модель может требовать другой агрегации: два необходимых независимых условия с вероятностями успеха 0.9 дают совместно 0.81, не min(0.9, 0.9). [Текущий FPF B.3](https://fpf.tools/B.3) требует применимой модели вместо универсального минимума.

У среднего и медианы есть очевидный изъян: одно строгое измерение способно статистически замаскировать небрежное. Представьте PRD с утверждением «масштабируется до 10K QPS». Три EvidencePack:

- Benchmark на staging при 10K QPS - оценка `0.9`
- Code review двух senior-инженеров - оценка `0.6`
- Заметка «запустил локально на Mac mini, работало нормально» - оценка `0.1`

Среднее — около 0.53, медиана — 0.6. Минимум показывает слабейшую записанную поддержку, но слабый анекдот не вызывает и не предсказывает отказ production при 4K QPS. Работу на такой нагрузке нужно проверять подходящим тестом.

R_eff = 0.1 переносит разговор на слабейшее доказательство. Либо его нужно улучшить (запустить реальный benchmark), либо признать, что PRD пока нельзя доверять. Минимум - принципиально жёсткий инструмент.

### Из чего складывается оценка одного evidence

Оценка EvidencePack вычисляется из трёх структурных полей плюс TTL.

Минимальный иллюстративный структурный блок, не дословный полный шаблон:

```markdown
## Structured Fields

verdict: supports            # supports / weakens / refutes
congruence_level: 3          # CL3 (лучший) ... CL0 (худший, противоположный)
evidence_type: measurement   # measurement / test / benchmark / audit
```

Отсутствующий/неизвестный `verdict` или отсутствие декларации congruence принудительно задаёт CL0 в текущем парсере; без типа выбирается measurement. Не всякий некорректный пак получает ровно 0.1: влияют также verdict, тип и срок. PROB-034 был другим историческим дефектом: многострочные комментарии затеняли реальный CL, а старый fallback завышал его до CL3. В v0.17.2 исправлен пропуск комментариев.

#### Базы verdict (1.0 / 0.5 / 0.0)

Verdict указывает скореру, в каком направлении тянет данное доказательство:

- `supports` - доказательство согласуется с родительским решением; полный положительный вклад.
- `weakens` — база 0.5, уменьшаемая штрафами CL и типа; это неотрицательный балл, не отрицательный вклад со знаком.
- `refutes` — база 0.0, поэтому непросроченный пак получает ровно ноль. Ветка срока возвращает 0.1 до обработки verdict, в том числе у опровергающего пака.

Для непросроченного учитываемого evidence `supports` начинается с 1.0, `weakens` с 0.5, `refutes` с 0.0 до применимых штрафов. Срок и учитываемость — отдельные ветки; проверьте их до интерпретации итогового числа.

#### Congruence Level (CL3-CL0)

CL отражает контекстуальное соответствие доказательства: измеряет ли оно именно то, о чём говорит родительское решение, в тех условиях, к которым оно применяется?

| CL | Штраф | Смысл |
|----|-------|-------|
| CL3 | `0.0` | Тот же контекст, что и решение. Лучший вариант - production-данные, реальные пользователи, реальная нагрузка. |
| CL2 | `0.1` | Смежный контекст. Staging-среда, похожая нагрузка, сопоставимый масштаб. |
| CL1 | `0.4` | Другой контекст, родственная область. Lab-benchmark; другой язык, но схожий паттерн. |
| CL0 | `0.9` | Очень слабое или отсутствующее соответствие. Недостаток полезной поддержки сам по себе не доказывает ложность утверждения. |

Непросроченный supports/measurement с CL0 получает 0.1. Тест на одной машине может точно соответствовать утверждению про одну машину; ярлык production сам по себе congruence не доказывает. До выбора CL запишите утверждение и условия проверки.

#### Тип evidence и разные поверхности скоринга

Рекурсивный скорер вычитает 0 для measurement/test, 0.1 для benchmark и 0.2 для audit. Плоские captured-оценки и часть полей разбивки evidence этот модификатор не используют. Поэтому их числа могут отличаться от рекурсивного отчёта; не считайте все отображаемые баллы одним расчётом. Старое упоминание `compare` — предложение, не поддержанный контракт команды.

#### TTL и устаревание

`valid_until` необязателен. Без даты скорер не считает пак просроченным. При наличии даты обычная оценка сохраняется до срока, затем возвращается 0.1 до арифметики verdict/CL/типа. Это дискретное правило продукта, не постепенный физический распад и не доказательство бесполезности любого старого наблюдения.

### Разбор на конкретном примере

Допустим, у PRD-XYZ («Использовать LanceDB как derived index») три EvidencePack:

**EVID-A** - benchmark на staging, рабочее пространство из 343 артефактов, p95-задержка запроса 80ms.

```
verdict: supports
congruence_level: 3
evidence_type: benchmark
valid_until: 2026-08-01
```

Рекурсивная оценка до истечения срока: `1 − 0 − 0.1 = 0.9` (supports, CL3, benchmark).

**EVID-B** - adversarial code review двух инженеров, выявлен один краевой случай (конкуренция при параллельной записи).

```
verdict: weakens
congruence_level: 2
evidence_type: audit
valid_until: 2026-06-01
```

Рекурсивная оценка до истечения срока: `0.5 − 0.1 − 0.2 = 0.2` (weakens, CL2, audit). Исходные 0.55 из этой формулы не получаются.

**EVID-C** - заметка разработчика «запустил на MacBook, казалось быстро».

```
verdict: supports
congruence_level: 0
evidence_type: measurement
valid_until: 2026-12-01
```

Вычисленная оценка: `0.10` (штраф CL0 убивает оценку; verdict `supports` не в состоянии спасти CL0).

```
R_eff(PRD-XYZ) = min(0.9, 0.2, 0.10) = 0.10
```

При этих допущениях R_eff равен 0.10; среднее было бы 0.40, медиана — 0.20. Позже истечение сроков меняет входы, поэтому это не ожидаемый вывод прогона сегодня.

Улучшайте слабые доказательства или обосновывайте изменение области/истории замены новыми данными. Нельзя удалять относящееся к делу предупреждение ради высокого балла; сохраняйте опровергающие данные и причину supersession/deprecation.

### Как читать реальное число R_eff

Рекомендации по чтению, не политика выпуска:

- Низкий балл указывает на записанное узкое место: проверьте утверждение, контекст, свежесть и происхождение.
- Высокий балл не доказывает безопасность, корректность, готовность или проверку всех требований.
- Ни одно число не заменяет применимые гейты активации и критерии выпуска команды.

Для исходного заявления о прохождении большинства артефактов через определённые диапазоны нет исследования популяции. Ни один порог здесь не является калиброванной вероятностью пережить постмортем.

### Формула, которую стоит запомнить

> **Доверие = слабое звено. R_eff = min(evidence_scores), никогда не среднее.**

Если из этого текста уносить только одно - пусть это будет данная формула. Всё остальное - её расшифровка.

ForgePlan операционализирует её в коде. Та же идея работает, если вы строите собственный инструментарий для принятия решений: агрегатор, который вы выбираете, определяет разговор, который ваша команда ведёт на ревью. `min` принуждает к честности. `average` закрывает её. Выбирайте осознанно.
