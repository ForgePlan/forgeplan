Если AI-агент выкатил фичу с неправильной логикой, а тесты прошли, проблема не в промпте. Она в harness вокруг него: правилах, которые агент читает при старте, состоянии, которое сохраняет между сессиями, доступных инструментах, обязательных проверках и среде, в которой эти проверки выполняются.

Этот взгляд я позаимствовал у небольшого сайта **walkinglabs**, который публикует, на мой взгляд, самые точные материалы по тому, что они называют *harness engineering*:

> "Если дело не в весах модели - дело в harness." - *walkinglabs, Lecture 02*

OpenAI ("Harness engineering: leveraging Codex in an agent-first world", 2025) и Anthropic ("Effective harnesses for long-running agents", 2026) подходят к той же идее с разных сторон: модель остаётся фиксированной, а разброс результатов определяется тем, что её окружает.

Я реализовал эти пять подсистем harness в **ForgePlan**, CLI на Rust и MCP-сервере с открытым кодом, которым сам пользуюсь уже шесть месяцев. Код на [github.com/ForgePlan/forgeplan](https://github.com/ForgePlan/forgeplan), если хотите читать параллельно.

## Пять подсистем harness

walkinglabs *Lecture 02* описывает модель так:

```
Rules (AGENTS.md / CLAUDE.md) ──┐
State (PROGRESS.md / git)      ──┤
                                  ↓
                          AI agent → Tools (shell / files / tests)
                                  ↑                ↓
                       Checks (test/lint/build) ← Env (deps/services)
```

Мне запомнилась фраза из той же лекции: **"из пяти подсистем у обратной связи обычно наименьший вклад и наибольшая отдача."** Большинство команд делают инструменты без чёткого назначения и на этом останавливаются. Перестройка обратной связи даёт больше отдачи.

### 1. Rules - контракт, который агент читает при запуске

Непопулярное мнение: один хорошо структурированный `CLAUDE.md` (или `AGENTS.md`) может давать лучший результат, чем обновление модели. В корне проекта ForgePlan лежит CLAUDE.md с одиннадцатью явными красными линиями и *hint protocol* (PRD-071), который определяет контракт следующего действия для каждого ответа CLI и MCP.

Каждый ответ содержит ровно одну финальную подсказку:

```
Next: forgeplan validate PRD-074
```

```
Or: forgeplan reason PRD-074

Wait: claim TTL expires in 12m

Done.

Fix: forgeplan link evid-bench-p95 PRD-074 --relation informs
```

Агент читает маркер и выполняет следующий шаг. Сценарий "агент импровизирует вокруг конвейера" исключён, потому что harness сам диктует следующий шаг. Регрессионные тесты проверяют, что каждый путь выполнения команды выдаёт ровно одну финальную подсказку.

walkinglabs *Lecture 03* формулирует основной принцип: **"Информация, которой нет в репозитории, для агента не существует."** Если контракт не в репозитории - агент его не соблюдает.

### 2. State - непрерывность между сессиями

walkinglabs *Lecture 05* - короткая и беспощадная:

> "Относитесь к агенту как к блестящему инженеру с амнезией."

Каждая сессия начинается с нулевого контекста. В ForgePlan с этим справляются три слоя:

- `MEMORY.md` - загружается автоматически при старте сессии (лёгкие, всегда актуальные факты)
- Банк памяти Hindsight на уровне проекта (семантический поиск по запросу для редко нужных фактов)
- Корпус markdown в `.forgeplan/` - это и есть система учёта проекта

Свежий агент запускает:

```bash
forgeplan health
forgeplan list prd
```

Агент восстанавливает состояние проекта из структурированных артефактов без записки для передачи дел. И снова *Lecture 03*: **"Документация, расходящаяся с кодом, опаснее её отсутствия."** ForgePlan отвечает на это ADR-003: markdown - источник истины, индекс LanceDB - производный. Одна команда `forgeplan scan-import` пересобирает индекс из markdown. Компилятор закрепляет инвариант после устранения PROB-048: 32 нарушения, четыре раунда аудита, 56 находок. В итоге доступ ограничили через `pub(crate)`, и прямые записи в LanceDB из кода команд больше не компилируются.

### 3. Tools - типизированные, не произвольные

ForgePlan поставляется с 76 CLI-командами и 73 MCP-инструментами. MCP-сервер использует [rmcp](https://github.com/modelcontextprotocol/rust-sdk) (официальный Rust SDK Model Context Protocol), так что Claude Code, Cursor или Aider могут нативно управлять методологией:

```jsonc
// MCP tool call
{
  "tool": "forgeplan_score",
  "arguments": { "id": "PRD-074" }
}

// Response (truncated)
{
  "id": "PRD-074",
  "r_eff": 0.10,
  "weakest_evidence": "EVID-091",
  "_next_action": "forgeplan link evid-bench-p95 PRD-074 --relation informs"
}
```

Поле `_next_action` следует тому же контракту подсказок, что и строка `Next:` в CLI. Агент читает его и выполняет следующий шаг. Интерфейс инструментов структурирован, агент не придумывает порядок операций сам.

### 4. Checks - вынесенная наружу оценка

walkinglabs *Lecture 09*:

> "Студенты не могут сами проверять свои контрольные работы."

На этом строится методология. Красная линия #7 ForgePlan говорит: артефакт нельзя активировать без кода и доказательств; `R_eff` должен быть больше нуля. Это обеспечивают два технических решения.

**Минимум вместо среднего:**

```rust
pub fn r_eff(scores: &[f64]) -> f64 {
    scores.iter().cloned().fold(f64::INFINITY, f64::min)
}
```

Если три доказательства получают оценки 0.9, 0.6, 0.1, `R_eff` решения равен 0.1, а не 0.53. Среднее позволяет сильному доказательству статистически "отмыть" слабое. Минимум заставляет разбирать утверждение, которое подкреплено хуже всего.

**Штраф за уровень конгруэнтности:**

| CL | Значение | Штраф |
|---|---|---|
| CL3 | Тот же контекст (например, benchmark на ваших production-данных) | 0.0 |
| CL2 | Похожий контекст | 0.1 |
| CL1 | Другой контекст, перенесённое | 0.4 |
| CL0 | Противоположный контекст | 0.9 |

Пост в блоге, который говорит "библиотека X быстрая", не может считаться наравне с benchmark'ом на вашей реальной нагрузке - даже если оба приводят числа.

Баг **PROB-034** научил меня, почему это важно. Через шесть недель эксплуатации одно и то же рабочее пространство возвращало `R_eff = 1.00` в одном клоне и `R_eff = 0.10` в другом. HTML-комментарии внутри шаблона EvidencePack (`<!-- TODO: fill verdict -->`) парсились как реальные данные структурированных полей. Инструмент подсчёта доверия лгал о собственной надёжности, и ложь зависела от того, какая версия шаблона последней использовалась в файле. Hotfix v0.17.2: парсер теперь отклоняет любой EvidencePack, в котором нет конкретных (не закомментированных) строк `verdict:`, `congruence_level:` и `evidence_type:`.

Harness должен уметь поймать себя на жульничестве - иначе ему нечего проверять у других.

### 5. Env - воспроизводимость по конструкции

Семантический поиск BGE-M3 (1024d) работает полностью локально - без API-ключа, без исходящего трафика. Единственный бинарник ~41 МБ после strip (`brew install ForgePlan/tap/forgeplan` или `cargo install forgeplan-cli`). Каждый артефакт - markdown-файл, который агент может читать, писать и проверять через тот же парсер, что использует человек.

Свежий клон разворачивается командами:

```bash
git clone <repo>
forgeplan init -y
forgeplan scan-import   # пересборка индекса LanceDB из markdown
forgeplan health        # Verdict: Healthy / NeedsAttention / Unhealthy
```

Для воспроизведения среды агента достаточно git.

## Что harness ForgePlan пока не делает

В *Lecture 12* есть уместный здесь принцип: **"'почистим потом' равно 'никогда'."** Публичный список пробелов помогает мне не забывать о них.

- **H1 - трассировка задач на уровне сессии.** С наблюдаемостью процессов всё хорошо (`forgeplan graph`, `forgeplan blindspots`, `forgeplan blocked`). Наблюдаемости во время выполнения нет. Нет трассировки в стиле OpenTelemetry: "этот агент, в этой сессии, вызвал эти инструменты, попал в этот гейт." Постоянно восстанавливать странные прогоны нескольких агентов по истории git не получится.
- **H2 - артефакт Sprint Contract.** Сейчас есть Note (лёгкий, TTL 90 дней) и PRD (тяжёлый, обязательные разделы, требуется ADI). Между ними не хватает отдельного формата для задачи на одну неделю с ограниченным объёмом, явными критериями приёмки и дедлайном. *Lecture 11* убедительно объясняет, зачем он нужен. Набросок есть, реализации нет.
- **H9 - жёсткий лимит WIP=1.** `forgeplan claim/release` - мягкая TTL-блокировка. Ничто не мешает одному агенту удерживать три claim одновременно. *Lecture 07*: **"'Не откусывай больше, чем можешь прожевать' - особенно применимо к AI-агентам."**

```bash
brew install ForgePlan/tap/forgeplan
forgeplan init -y
forgeplan new prd "Migrate auth from Auth0 to Clerk"
forgeplan validate prd-migrate-auth-from-auth0-to-clerk
forgeplan reason prd-migrate-auth-from-auth0-to-clerk
forgeplan score prd-migrate-auth-from-auth0-to-clerk
```
