MEMORY.md и Hindsight - отдельно настроенные интеграции хоста. Амнезия предполагает отсутствие восстановленного контекста. Захваты - рекомендательные метки намерения, не запрет доступа к файлам. Создание Note не задаёт TTL в 90 дней по умолчанию; обнаружение истечения требует явного `valid_until` и не удаляет запись. Текущий `CLAUDE.md` репозитория требует ADI для Standard+; неполная проверка рабочего процесса валидатором документа не отменяет этой обязанности.

Если AI-агент выкатил фичу с неправильной логикой и зелёным тест-сьютом, проблема не в prompt. Проблема в harness вокруг prompt: правилах, которые агент читает при старте, состоянии, которое он сохраняет между сессиями, инструментах, которые доступны, проверках, которые он должен пройти, и среде, в которой эти проверки выполняются.

Этот фрейм - не моя идея. Он пришёл с небольшого сайта **walkinglabs**, который публикует, на мой взгляд, самые точные материалы по тому, что они называют *harness engineering*:

> "Если дело не в весах модели - дело в harness." - *walkinglabs, Lecture 02*

[Статья OpenAI датирована 11 февраля 2026](https://openai.com/index/harness-engineering/), а [«Effective harnesses for long-running agents» Anthropic - 26 ноября 2025](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents). Обе показывают способы улучшить среду вокруг модели, но не доказывают универсальное превосходство обвязки над выбором модели.

Я разберу пять подсистем harness и покажу, как реализовал их в **ForgePlan** - open-source Rust CLI + MCP server, который я использую сам уже шесть месяцев. Код на [github.com/ForgePlan/forgeplan](https://github.com/ForgePlan/forgeplan), если хотите читать параллельно.

## Пять подсистем harness

walkinglabs *Lecture 02* описывает модель так:

```
Rules (AGENTS.md / CLAUDE.md) ──┐
State (PROGRESS.md / git)      ──┤
                                  ↓
                          AI agent → Tools (shell / files / tests)
                                  ↑                ↓
                       Checks (test/lint/build) ← Env (deps/services)
```

Ключевая фраза из той же лекции: **"из пяти подсистем у обратной связи обычно наименьший вклад и наибольшая отдача."** Большинство команд делают размытые инструменты и на этом останавливаются. Рычаг с высокой отдачей - перестроить обратную связь.

### 1. Rules - контракт, который агент читает при запуске

Непопулярное мнение: один хорошо структурированный `CLAUDE.md` (или `AGENTS.md`) может давать лучший результат, чем обновление модели. В корне проекта ForgePlan лежит CLAUDE.md с одиннадцатью явными красными линиями и *hint protocol* (PRD-071), который определяет контракт следующего действия для каждого ответа CLI и MCP.

Контракт подсказок использует следующие маркеры (отдельные примеры, не один записанный ответ):

```
Next: forgeplan validate PRD-074
```

```
Or: forgeplan reason PRD-074

Wait: claim TTL expires in 12m

Done.

Fix: forgeplan link evid-bench-p95 PRD-074 --relation informs
```

Агент может следовать маркеру, но подсказка не принуждает к порядку и не исключает обход. Исторический аудит EVID-086 на 70/70 команд не доказывает, что каждый текущий путь CLI/MCP выдаёт ровно одно правильное следующее действие.

walkinglabs *Lecture 03* формулирует основной принцип: **"Информация, которой нет в репозитории, для агента не существует."** Если контракт не в репозитории - агент его не соблюдает.

### 2. State - непрерывность между сессиями

walkinglabs *Lecture 05* - короткая и беспощадная:

> "Относитесь к агенту как к блестящему инженеру с амнезией."

Каждая сессия начинается с нулевого контекста. В ForgePlan с этим справляются три слоя:

- `MEMORY.md` - загружается автоматически при старте сессии (лёгкие, всегда актуальные факты)
- Банк памяти Hindsight на уровне проекта (отложенный семантический поиск по долгому хвосту)
- Корпус markdown в `.forgeplan/`, который и является системой учёта проекта

Свежий агент запускает:

```bash
forgeplan health
forgeplan list --type prd
```

...и читает структурированные артефакты для восстановления состояния. *Lecture 03*: **"Документация, расходящаяся с кодом, опаснее её отсутствия."** ADR-003 делает Markdown авторитетным источником, LanceDB - производным индексом. Constellation пересобирается через `forgeplan index`, legacy-хранилище - через `forgeplan reindex`. `scan-import` импортирует внешний Markdown. Миграция PROB-048 и граница `pub(crate)` ограничивают прямые мутирующие вызовы между крейтами, но не любую возможную рассинхронизацию файла и индекса.

### 3. Tools - типизированные, не произвольные

ForgePlan поставляется с 76 CLI-командами и 73 MCP-инструментами. MCP-сервер использует [rmcp](https://github.com/modelcontextprotocol/rust-sdk) (официальный Rust SDK Model Context Protocol), так что Claude Code, Cursor или Aider могут нативно управлять методологией:

```jsonc
// MCP tool call
{
  "tool": "forgeplan_score",
  "arguments": { "id": "PRD-074" }
}

// Учебный ответ, не записанная и не полная текущая схема
{
  "id": "PRD-074",
  "r_eff": 0.10,
  "weakest_evidence": "EVID-091",
  "_next_action": "forgeplan link evid-bench-p95 PRD-074 --relation informs"
}
```

`_next_action`, когда присутствует, передаёт следующую рекомендацию структурно. Это не граница принуждения; поле может отсутствовать или быть смыслово неверным. Нужно читать реальный ответ, а не предполагать универсальное покрытие.

### 4. Checks - вынесенная наружу оценка

walkinglabs *Lecture 09*:

> "Студенты не могут сами проверять свои контрольные работы."

Правило о доказательствах до активации - обязанность рабочего процесса. Обычная активация проверяет длину тела, связи с доказательствами, заглушки и MUST-замечания, с отдельными проверками происхождения у вызывающей стороны. Она не обеспечивает порог R_eff>0 и не доказывает, что код работает. Оценка помогает ревью:

**Минимум вместо среднего:**
Фрагмент показывает только минимум **непустого** списка уже оценённых допустимых доказательств. Это не production-код: пустой итератор ниже даёт бесконечность, тогда как обычный production-подсчёт без доказательств даёт ноль; рекурсивный подсчёт также учитывает срок, тип, терминальные статусы и зависимости.


```rust
pub fn r_eff(scores: &[f64]) -> f64 {
    scores.iter().cloned().fold(f64::INFINITY, f64::min)
}
```

Если три единицы доказательств дают 0.9, 0.6, 0.1 - `R_eff` решения равен 0.1, а не 0.53. Среднее позволяет сильному доказательству статистически "отмыть" слабое. Минимум переводит разговор на худшее подкреплённое утверждение.

**Штраф за уровень конгруэнтности:**

| CL | Значение | Штраф |
|---|---|---|
| CL3 | Тот же контекст (например, benchmark на ваших production-данных) | 0.0 |
| CL2 | Похожий контекст | 0.1 |
| CL1 | Другой контекст, перенесённое | 0.4 |
| CL0 | Противоположный контекст | 0.9 |

Пост в блоге, который говорит "библиотека X быстрая", не может считаться наравне с benchmark'ом на вашей реальной нагрузке - даже если оба приводят числа.

**PROB-034** фиксирует A/B на одном workspace с v0.17.1 и v0.17.2, не разные клоны под одним бинарником. Примеры в многострочных HTML-комментариях перекрывали реальный `congruence_level`, и явный CL0 заменялся CL3 по умолчанию: 1.00 до исправления, 0.10 после. Исправление пропускало комментарии. Текущее закрытие отсутствующих verdict/CL в низкий балл - отдельная последующая работа; у `evidence_type` есть значение по умолчанию.

Harness должен уметь поймать себя на жульничестве - иначе ему нечего проверять у других.

### 5. Env - воспроизводимость по конструкции

Инференс BGE-M3 (1024d) может работать локально при совместимой сборке, конфигурации и полном кэше модели. Это не означает изолированную от сети установку: зависимости и веса могут требовать скачивания. Бинарник ~41 МБ - историческое сообщение, не размер весов. Cargo-пакет называется `forgeplan`, не `forgeplan-cli`.

Для существующего Constellation-клона концептуальная последовательность обслуживания:

```bash
git clone <repo>
cd <cloned-repo>
forgeplan index         # публикация из канонического Markdown
forgeplan health        # читать фактический verdict, не ожидать PASS
```

Git сохраняет закоммиченные исходные записи, не всю среду агента. Зависимости, конфигурацию, подключения памяти хоста и кэш модели готовят отдельно. Для legacy-формата используется `reindex`; `scan-import` нужен для импорта внешних документов.

## Что harness ForgePlan пока не делает

Называю пробелы, потому что *Lecture 12* формулирует уместный принцип: **"'почистим потом' равно 'никогда'."** Публичный список пробелов - способ держать себя в честности.

- **H1 - трассировка задач на уровне сессии.** Наблюдаемость процессов твёрдая (`forgeplan graph`, `forgeplan blindspots`, `forgeplan blocked`). Наблюдаемость в реальном времени отсутствует. Нет трассировки в стиле OpenTelemetry: "этот агент, в этой сессии, вызвал эти инструменты, попал в этот гейт." Восстанавливать странные multi-agent прогоны из git-истории - не масштабируемый ответ.
- **H2 - артефакт Sprint Contract.** В этом датированном эскизе дорожной карты спектр был таким: Note (лёгкий, с необязательной датой пересмотра) → PRD (тяжёлый, обязательные разделы, ADI требуется для Standard+ по правилам репозитория). Срок Note не назначается автоматически. Нет специального примитива на одну неделю с явными критериями приёмки и дедлайном. *Lecture 11* убедительно аргументирует в пользу этого. Набросок есть - реализации нет.
- **H9 - жёсткий лимит WIP=1.** `forgeplan claim/release` - мягкая TTL-блокировка. Ничто не мешает одному агенту удерживать три claim одновременно. *Lecture 07*: **"'Не откусывай больше, чем можешь прожевать' - особенно применимо к AI-агентам."**

## Попробуйте
Пример ниже - для изолированного нового проекта. `new` создаёт шаблон, не готовые требования: заполните тело и исправьте замечания валидации до рассуждения. `reason` требует настроенного провайдера; `score` не создаёт доказательства и не даст поддержки, пока не связаны реальные подтверждения. Используйте фактический идентификатор из вывода `new`.


```bash
brew install ForgePlan/tap/forgeplan
forgeplan init -y
forgeplan new prd "Migrate auth from Auth0 to Clerk"
forgeplan validate prd-migrate-auth-from-auth0-to-clerk
forgeplan reason prd-migrate-auth-from-auth0-to-clerk
forgeplan score prd-migrate-auth-from-auth0-to-clerk
```
